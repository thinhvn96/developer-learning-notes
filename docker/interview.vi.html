Docker: câu hỏi và trả lời phỏng vấn

Trang chủ · Docker · 11 câu hỏi · Lộ trình Docker · Lộ trình tổng · English

Các câu hỏi Docker cho buổi phỏng vấn Senior backend, có góc nhìn riêng cho Java (image, memory của JVM, hardening).

Hãy thử trả lời thành tiếng trước, rồi mới mở đáp án. Các link chỉ số trên dẫn tới nguồn chứng minh cho nhận định đó.

1.Container khác máy ảo (virtual machine) ở điểm nào?

Trả lời ngắn: container là các process được cô lập và dùng chung kernel của host; còn mỗi VM chạy nguyên một guest OS.

Container là một process được cô lập, chạy một thành phần của ứng dụng trong môi trường riêng mà không ảnh hưởng tới host hay các container khác. Nó "nhẹ hơn máy ảo vì nhiều container dùng chung một kernel thay vì mỗi cái cần nguyên một hệ điều hành", và mang đi chạy được trên máy dev, data center lẫn cloud.[1] Điểm đánh đổi (trade-off) bạn nên chủ động nêu ra: dùng chung kernel nghĩa là mức cô lập yếu hơn ranh giới của hypervisor, và container cần một kernel tương thích (trade-off này ai cũng biết, nhưng không được viết rõ trong các trang tài liệu tôi đã đọc).

Câu hỏi nối tiếp thường gặp: Có chạy được Linux container trên Windows không? (Trả lời từ kinh nghiệm của bạn; thông thường bên dưới có một Linux VM. Các nguồn đã đọc ở đây không đề cập.)

Học bài: Container, image và layer

2.Image khác container thế nào? Layer là gì?

Trả lời ngắn: image là một gói bất biến; container là một instance đang chạy; layer là các thay đổi trên file system tạo nên image.

"Container image là một gói chuẩn hóa chứa tất cả file, binary, library và cấu hình cần để chạy một container." Image là bất biến: đã tạo thì không sửa được, chỉ có thể mở rộng bằng cách tạo image mới hoặc thêm thay đổi lên trên. "Container image được tạo thành từ các layer. Mỗi layer là một tập thay đổi trên file system: thêm, xóa hoặc sửa file."[3] Dữ liệu ghi trong một container đang chạy không làm thay đổi image; đó là lý do bạn dùng volume cho dữ liệu cần lưu lâu dài.

Câu hỏi nối tiếp thường gặp: Vậy dữ liệu của database nên nằm ở đâu? (Trong một volume; Compose mô hình hóa điều này một cách tường minh.[2])

Học bài: Container, image và layer

3.Làm sao để Docker build nhanh?

Trả lời ngắn: sắp xếp các lệnh trong Dockerfile để các layer ít thay đổi nằm trước, và dùng .dockerignore.

Mỗi lệnh trở thành một layer, và "nếu một layer thay đổi, mọi layer đứng sau nó cũng bị ảnh hưởng."[5] Vì vậy hãy copy file mô tả dependency và cài dependency trước khi copy source; khi đó sửa source chỉ làm mất hiệu lực các layer từ COPY src/ trở đi. .dockerignore giữ các file không liên quan nằm ngoài build context và các layer.[4] (Cách sắp xếp này là hệ quả trực tiếp của quy tắc invalidation cache.)

Câu hỏi nối tiếp thường gặp: Làm sao ép build sạch từ đầu? (Best practices của Docker nhắc tới việc kết hợp --pull và --no-cache.[4])

Học bài: Layer cache

4.Multi-stage build là gì và dùng nó cho ứng dụng Java thế nào?

Trả lời ngắn: compile trong một stage có JDK, rồi chỉ copy artifact sang một stage runtime nhỏ hơn.

Multi-stage build "tách bạch rõ ràng hơn giữa quá trình build image và đầu ra cuối cùng." Đặt tên stage bằng AS, copy bằng COPY --from=build, dừng ở một stage bằng docker build --target.[6][4] Trong ví dụ tôi đo, image single-stage dùng JDK nặng 475 MB, còn image multi-stage dựa trên JRE là 318 MB. Nói thêm: USER non-root, CMD dạng exec form, base image được pin phiên bản.

Câu hỏi nối tiếp thường gặp: Debug một stage trung gian bị lỗi thế nào? (--target.)

Học bài: Image multi-stage cho Java

5.Container Java của bạn bị OOM-kill. Bạn điều tra và xử lý thế nào?

Trả lời ngắn: so sánh giới hạn memory của container với heap cộng non-heap; chủ động đặt kích thước heap.

Flag --memory là "lượng memory tối đa container được dùng"; vượt quá nó, cơ chế xử lý out-of-memory của kernel bắt đầu kill process.[7] Trên Linux, JVM mặc định phát hiện giới hạn của container và tính kích thước heap dựa trên đó; MaxRAMPercentage mặc định là 25 phần trăm (và 50 phần trăm cho heap nhỏ thông qua MinRAMPercentage).[8] Khi tôi chạy thử, giới hạn 256 MB cho max heap 121 MB; với MaxRAMPercentage=75 thì là 185 MB. Heap không phải toàn bộ footprint: metaspace, thread stack, direct buffer và code cache cũng cộng thêm vào, nên cho heap 100 phần trăm là tự rước OOM kill. Các bước: kiểm tra giới hạn, bật log -Xlog:os+container=trace, đặt MaxRAMPercentage khoảng 60 đến 75, đo mức dùng thực tế, và tăng giới hạn nếu cần.

Câu hỏi nối tiếp thường gặp: Giới hạn --cpus ảnh hưởng gì tới JVM? (JVM thấy số CPU đã bị giới hạn; khi tôi chạy với --cpus=1 thì nó báo 1 processor.[7])

Học bài: Giới hạn memory và CPU

6.Bạn áp dụng những cách hardening Dockerfile nào?

Trả lời ngắn: pin theo digest, user non-root, CMD dạng exec form, base image tối giản và tin cậy, mỗi container một nhiệm vụ.

Theo best practices của Docker: dùng base image tối giản và tin cậy; pin base image theo digest vì tag có thể thay đổi, không đảm bảo lần build nào cũng ra cùng một image; nếu service chạy được mà không cần đặc quyền thì dùng USER; tránh sudo; dùng exec form cho CMD/ENTRYPOINT để signal được xử lý đúng khi chạy với vai trò PID 1; tách rời các ứng dụng, mỗi container một nhiệm vụ; dùng .dockerignore.[4]

Câu hỏi nối tiếp thường gặp: Vì sao exec form quan trọng với việc tắt ứng dụng Java? (Với shell form, shell là PID 1; tài liệu khuyên dùng exec form để xử lý signal, nhờ đó JVM nhận được SIGTERM và chạy các shutdown hook. Hãy kiểm chứng bằng thực nghiệm như bài tập gợi ý.)

Học bài: Image được pin, non-root, xử lý signal đúng

7.Giải thích Docker Compose. Làm sao để ứng dụng đợi database sẵn sàng?

Trả lời ngắn: một file YAML khai báo service, network và volume; dùng health check kết hợp depends_on: condition: service_healthy.

File Compose cấu hình các service của một ứng dụng, và chỉ một lệnh CLI là tạo và start tất cả. Một service là cùng một image và cấu hình được chạy một hoặc nhiều lần; các service nói chuyện với nhau qua network và lưu dữ liệu lâu dài trong volume.[2] Container đã start chưa chắc đã sẵn sàng, nên hãy định nghĩa healthcheck cho database và cho ứng dụng depends_on nó với service_healthy. Ví dụ của tôi làm đúng như vậy với pg_isready, và client chỉ được start khi database đã healthy.

Câu hỏi nối tiếp thường gặp: Compose hay Kubernetes? (Compose cho dev local và các trường hợp đơn giản trên một host; Kubernetes khi cần lập lịch trên cluster, tự phục hồi và rollout.)

Học bài: Compose

8.CMD khác ENTRYPOINT thế nào? docker run image args thay thế cái gì?

Trả lời ngắn: ENTRYPOINT là chương trình thực thi, CMD là các tham số mặc định của nó; tham số truyền vào docker run chỉ thay thế CMD.

Chỉ CMD cuối cùng có hiệu lực; CMD cung cấp giá trị mặc định cho ENTRYPOINT hoặc tự chạy một mình; khi ENTRYPOINT và CMD đều ở exec form thì CMD được nối vào làm tham số; ENTRYPOINT ở shell form sẽ bỏ qua CMD và chạy qua /bin/sh -c. Nên ưu tiên exec form (không có shell, xử lý signal đúng).[9][4] Demo của tôi: docker run lesson-entry in ra "hello world", docker run lesson-entry Docker in ra "hello Docker", và --entrypoint printenv thay thế luôn chương trình thực thi.

Câu hỏi nối tiếp thường gặp: ENV khác ARG thế nào? (ARG chỉ tồn tại lúc build; ENV được giữ lại trong image và container; tôi đã xác nhận BUILD_ID không có giá trị lúc runtime.)

Học bài: CMD và ENTRYPOINT

9.Làm sao lưu giữ dữ liệu của container? Volume khác bind mount thế nào?

Trả lời ngắn: volume cho dữ liệu lâu dài do Docker quản lý; bind mount để chia sẻ file của host, chủ yếu khi dev.

Nội dung của volume "tồn tại bên ngoài vòng đời của một container cụ thể"; không có volume thì writable layer bị hủy cùng container. Volume do Docker quản lý; bind mount gắn một đường dẫn trên host và "gắn chặt với host"; thêm readonly để bảo vệ file của host.[10][11] Kết quả tôi chạy: dữ liệu không nằm trong volume thì mất khi tạo container mới; named volume giữ được dữ liệu; bind mount read-only từ chối thao tác ghi.

Câu hỏi nối tiếp thường gặp: File của database nên nằm ở đâu? (Trong một named volume, như ví dụ Compose.)

Học bài: Volume và bind mount

10.Vì sao các container gọi nhau được bằng tên trên network này mà không được trên network khác? -p làm gì?

Trả lời ngắn: user-defined bridge có sẵn DNS theo tên container; default bridge thì không; -p publish một port của container ra host.

User-defined bridge cung cấp phân giải DNS tự động và cô lập tốt hơn; các container trên default bridge không gọi nhau bằng tên được. Không có -p thì các port không truy cập được từ bên ngoài host, và mặc định cũng không truy cập được từ container trên network khác.[12][13] Kết quả tôi chạy: ping theo tên thất bại trên default bridge và thành công trên user-defined bridge, và một container trên user-defined network không phân giải được tên của container nằm trên default bridge.

Câu hỏi nối tiếp thường gặp: Ứng dụng trong Compose kết nối tới database bằng cách nào? (Bằng tên service trên network của Compose.)

Học bài: Network

11.Bạn sẽ dùng restart policy nào, và nó không làm được gì?

Trả lời ngắn: unless-stopped hoặc on-failure cho service; restart policy phản ứng khi process thoát, chứ không xử lý process bị treo nhưng vẫn đang chạy.

no (mặc định), on-failure[:max] (thoát với mã khác 0), always, unless-stopped (giữ nguyên trạng thái dừng nếu bạn đã chủ động stop, kể cả sau khi daemon khởi động lại).[14] Kết quả tôi chạy: on-failure:3 trên một container liên tục crash ghi nhận 3 lần restart, sau đó nằm yên ở trạng thái exited; policy no ghi nhận 0 lần.

Câu hỏi nối tiếp thường gặp: Cái gì xử lý một container đang chạy nhưng không healthy? (Health check trong Docker; liveness probe trong Kubernetes.)
