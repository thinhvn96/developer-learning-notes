Docker questions for a Senior backend interview, with Java-specific angles (images, JVM memory, hardening).

Try answering out loud first, then open the answer. Superscript links go to the source that backs the claim.

1.What is the difference between a container and a virtual machine?

Short answer: containers are isolated processes that share the host kernel; VMs each run a full guest OS.

A container is an isolated process running an application component in its own environment without affecting the host or other containers. It is "more lightweight than virtual machines since multiple containers share the same kernel rather than each requiring a full operating system", and portable across dev machines, data centers and clouds.[1] The trade-off you should volunteer: sharing a kernel means weaker isolation than a hypervisor boundary and that containers need a compatible kernel (that trade-off is well known but not spelled out in the pages I read).

Likely follow-up: Can you run a Linux container on Windows? (Answer from your own experience; it typically uses a Linux VM underneath. Not covered by the sources read here.)

Learn it: Containers, images and layers

2.What is the difference between an image and a container? What is a layer?

Short answer: an image is an immutable package; a container is a running instance; layers are the file-system changes that make up an image.

"A container image is a standardized package that includes all of the files, binaries, libraries, and configurations to run a container." Images are immutable: once created they cannot be modified, only extended by adding a new image or changes on top. "Container images are composed of layers. Each layer represents a set of file system changes that add, remove, or modify files."[3] Data written in a running container does not change the image; that is why you use volumes for persistent data.

Likely follow-up: Where should a database's data live then? (In a volume; Compose models this explicitly.[2])

Learn it: Containers, images and layers

3.How do you make Docker builds fast?

Short answer: order Dockerfile instructions so stable layers come first and use a .dockerignore.

Each instruction becomes a layer, and "if a layer changes, all other layers that come after it are also affected."[5] So copy the dependency descriptor and install dependencies before copying source; then a source edit only invalidates layers from COPY src/ onward. A .dockerignore keeps irrelevant files out of the build context and layers.[4] (The ordering recipe is a consequence of the invalidation rule.)

Likely follow-up: How do you force a clean build? (Docker's best practices mention combining --pull and --no-cache.[4])

Learn it: Layer cache

4.What are multi-stage builds and how do you use them for a Java app?

Short answer: compile in a JDK stage, copy only the artifact into a smaller runtime stage.

Multi-stage builds "give a cleaner separation between the building of your image and the final output." Name stages with AS, copy with COPY --from=build, stop at a stage with docker build --target.[6][4] In my measured example a JDK single-stage image was 475 MB and the JRE-based multi-stage image 318 MB. Add: non-root USER, exec-form CMD, pinned base image.

Likely follow-up: How do you debug a failing intermediate stage? (--target.)

Learn it: Multi-stage Java image

5.Your Java container gets OOM-killed. How do you investigate and fix it?

Short answer: compare the container memory limit with heap plus non-heap; size the heap deliberately.

The --memory flag is "the maximum amount of memory the container can use"; past it, the kernel's out-of-memory handling starts killing processes.[7] The JVM detects container limits on Linux by default and sizes the heap from them; MaxRAMPercentage defaults to 25 percent (and 50 percent for small heaps via MinRAMPercentage).[8] In my run a 256 MB limit produced a 121 MB max heap; with MaxRAMPercentage=75 it was 185 MB. The heap is not the whole footprint: metaspace, thread stacks, direct buffers and the code cache add to it, so 100 percent heap invites an OOM kill. Steps: check limit, log -Xlog:os+container=trace, set MaxRAMPercentage around 60 to 75, measure real usage, and raise the limit if needed.

Likely follow-up: What do --cpus limits do to the JVM? (The JVM sees the limited CPU count; in my run --cpus=1 reported 1 processor.[7])

Learn it: Memory and CPU limits

6.What Dockerfile hardening practices do you apply?

Short answer: pinned digests, non-root user, exec-form CMD, minimal trusted base, one concern per container.

From Docker's best practices: use trusted minimal base images; pin base images by digest because mutable tags do not guarantee the same image every build; if a service can run without privileges use USER; avoid sudo; use exec form for CMD/ENTRYPOINT so signals are handled properly as PID 1; decouple applications, one concern per container; use .dockerignore.[4]

Likely follow-up: Why does exec form matter for Java shutdown? (With shell form a shell is PID 1; the doc advises exec form for signal handling, so the JVM gets SIGTERM and runs shutdown hooks. Verify by experiment, as the exercise suggests.)

Learn it: Pinned, non-root, signal-safe images

7.Explain Docker Compose. How do you make an app wait for its database?

Short answer: a YAML file declaring services, networks and volumes; use a health check with depends_on: condition: service_healthy.

A Compose file configures an application's services, and one CLI command creates and starts them. A service is the same image and configuration run one or more times; services talk over networks and store persistent data in volumes.[2] A started container is not necessarily ready, so define a healthcheck on the database and make the app depends_on it with service_healthy. My example did this with pg_isready and it started the client only once the database was healthy.

Likely follow-up: Compose or Kubernetes? (Compose for local dev and simple single-host use; Kubernetes for cluster scheduling, self-healing and rollouts.)

Learn it: Compose

8.What is the difference between CMD and ENTRYPOINT? What does docker run image args replace?

Short answer: ENTRYPOINT is the executable, CMD its default arguments; arguments on docker run replace CMD only.

Only the last CMD counts; CMD provides defaults for an ENTRYPOINT or runs alone; with exec-form ENTRYPOINT and exec-form CMD the CMD is appended as arguments; a shell-form ENTRYPOINT ignores CMD and runs via /bin/sh -c. Exec form is preferred (no shell, proper signal handling).[9][4] My demo: docker run lesson-entry printed "hello world", docker run lesson-entry Docker printed "hello Docker", and --entrypoint printenv replaced the executable.

Likely follow-up: ENV versus ARG? (ARG is build-time only; ENV persists in the image and container; I confirmed BUILD_ID was unset at runtime.)

Learn it: CMD and ENTRYPOINT

9.How do you persist container data? Volume versus bind mount?

Short answer: volumes for Docker-managed persistent data; bind mounts to share host files, mainly in development.

A volume's contents "exist outside the lifecycle of a given container"; without one, the writable layer is destroyed with the container. Volumes are managed by Docker; bind mounts attach a host path and "are strongly tied to the host"; add readonly to protect host files.[10][11] My run: data without a volume was gone in a new container; the named volume kept it; a read-only bind mount rejected writes.

Likely follow-up: Where should a database's files live? (A named volume, as in the Compose example.)

Learn it: Volumes and bind mounts

10.Why can containers reach each other by name on one network but not another? What does -p do?

Short answer: user-defined bridges give automatic DNS by container name; the default bridge does not; -p publishes a container port on the host.

User-defined bridges provide automatic DNS resolution and better isolation; default-bridge containers cannot refer to each other by name. Without -p ports are not reachable from outside the host or, by default, from containers on other networks.[12][13] My run: ping by name failed on the default bridge and worked on a user-defined one, and a container on the user-defined network could not resolve one on the default bridge.

Likely follow-up: How does a Compose app reach its database? (By service name on the Compose network.)

Learn it: Networks

11.Which restart policy would you use, and what does it not do?

Short answer: unless-stopped or on-failure for services; restart policies react to exits, not to a hung-but-running process.

no (default), on-failure[:max] (non-zero exit), always, unless-stopped (stays stopped if you stopped it, even after a daemon restart).[14] My run: on-failure:3 on a crashing container recorded 3 restarts, then stayed exited; policy no recorded 0.

Likely follow-up: What handles an unhealthy but running container? (Health checks in Docker; liveness probes in Kubernetes.)

Learn it: Restart policies
