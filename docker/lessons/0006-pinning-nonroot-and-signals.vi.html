Image được pin phiên bản, chạy non-root và xử lý signal đúng

Docker · Bài 0006 · bước 12/12 · Senior · ~10 phút · Trang chủ · Lộ trình Docker · Lộ trình tổng · English

Thành quả hôm nay: review một Dockerfile theo bốn quy tắc hardening có trong tài liệu: pin base image, user non-root, CMD dạng exec form, mỗi container một nhiệm vụ.

Bốn quy tắc từ best practices chính thức

  • Pin base image. Tag có thể thay đổi, nên "không có gì đảm bảo mỗi lần build bạn nhận được cùng một image." Hãy pin theo digest, ví dụ alpine:3.21@sha256:....[1]
  • Chạy với user non-root. "Nếu một service chạy được mà không cần đặc quyền, hãy dùng USER để chuyển sang một user không phải root."[1]
  • Dùng exec form cho CMD và ENTRYPOINT để process xử lý signal đúng khi là PID 1.[1]
  • Mỗi container một nhiệm vụ; tách rời các ứng dụng để dễ mở rộng và module hóa.[1]

Trong ví dụ

Dockerfile multi-stage tạo một system user và chuyển sang user đó; khi chạy, kết quả hiện uid=10001(app). CMD của nó ở dạng exec form (một mảng JSON), nên java là PID 1 và nhận trực tiếp SIGTERM từ docker stop. Với shell form, shell sẽ là PID 1 (tài liệu khuyên dùng exec form để xử lý signal; việc kiểm chứng signal có tới nơi hay không để dành cho bài tập).

Cũng từ trang đó: dùng .dockerignore; dùng base image tối giản và tin cậy (Docker Official Images).[1]

Câu nói khi phỏng vấn: "Tôi pin base image theo digest, bỏ quyền root, dùng entrypoint dạng exec form để shutdown hook chạy khi nhận SIGTERM, và giữ mỗi container một process."

Luyện truy hồi

Trả lời theo trí nhớ. Mỗi câu chỉ một lần chọn.

1. Vì sao pin base image theo digest?

Tag có thể thay đổi nên không đảm bảo mỗi lần build đều ra cùng một image.[1]

2. Dòng nào trong Dockerfile bỏ đặc quyền?

USER chuyển sang một user non-root.[1]

3. Vì sao CMD nên dùng exec form?

Exec form đảm bảo signal được xử lý đúng khi process là PID 1.[1]

4. Một container chạy cả app, database và cron. Sửa thế nào?

Docker khuyến nghị mỗi container một nhiệm vụ.[1]
