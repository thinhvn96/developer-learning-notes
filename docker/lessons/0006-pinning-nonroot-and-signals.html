Pinned, non-root and signal-safe images

Docker · Lesson 0006 · step 12 of 12 · Senior · ~10 minutes · Home · Docker ladder · Roadmap · Tiếng Việt

Today's win: review a Dockerfile against four documented hardening rules: pinned base, non-root user, exec-form CMD, one concern per container.

Four rules from the official best practices

  • Pin base images. Tags are mutable, so "you're not guaranteed to get the same for every build." Pin by digest, for example alpine:3.21@sha256:....[1]
  • Run as non-root. "If a service can run without privileges, use USER to change to a non-root user."[1]
  • Use exec form for CMD and ENTRYPOINT so the process handles signals properly as PID 1.[1]
  • One concern per container; decouple applications for scalability and modularity.[1]

In the example

The multi-stage Dockerfile creates a system user and switches to it; the run showed uid=10001(app). Its CMD is in exec form (a JSON array), so java is PID 1 and receives SIGTERM from docker stop directly. In shell form, a shell would be PID 1 (the docs advise exec form for signal handling; verifying signal delivery is left as an exercise).

Also from the same page: use a .dockerignore; use trusted, minimal base images (Docker Official Images).[1]

Interview line: "I pin base images by digest, drop root, use exec-form entrypoints so shutdown hooks run on SIGTERM, and keep one process per container."

2. Which Dockerfile line drops privileges?

4. A container runs app plus database plus cron. Fix?

Docker recommends one concern per container.[1]
