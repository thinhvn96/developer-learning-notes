CMD, ENTRYPOINT and exec vs shell form

Docker · Lesson 0009 · step 5 of 12 · Core · ~10 minutes · Home · Docker ladder · Roadmap

Today's win: predict what a container runs from ENTRYPOINT plus CMD, and what changes when you pass arguments to docker run.

The rules

  • "There can only be one CMD instruction ... only the last one takes effect."
  • CMD provides defaults for an ENTRYPOINT, or executes on its own; "CMD will be overridden when running the container with alternative arguments".
  • Use ENTRYPOINT when the container acts as an executable.[1]
ScenarioResult[1]
no ENTRYPOINT, CMD setCMD runs
ENTRYPOINT exec form + CMD exec formENTRYPOINT runs; CMD is appended as arguments
ENTRYPOINT in shell formCMD is ignored; runs via /bin/sh -c

Exec vs shell form

Exec form (["executable","arg"]) is JSON, does not invoke a shell and does no variable substitution; shell form always uses a shell.[1] Docker's best practices recommend exec form for CMD/ENTRYPOINT so signals are handled properly as PID 1 (see the hardening lesson).[2]

./05-cmd-entrypoint-arg-env.sh
docker run lesson-entry                      -> hello world      # ENTRYPOINT + CMD
docker run lesson-entry Docker               -> hello Docker     # args replace CMD
docker run --entrypoint printenv lesson-entry APP_MODE -> prod

For Java: ENTRYPOINT ["java","-jar","app.jar"] with CMD for default args, and JAVA_TOOL_OPTIONS in the environment for JVM flags (design suggestion; test it).

Retrieval practice

Answer from memory. One attempt each.

1. ENTRYPOINT exec form plus CMD exec form. What runs?

ENTRYPOINT runs and CMD is appended as arguments.[1]

2. Two CMD lines in one Dockerfile. Which counts?

Only the last CMD takes effect.[1]

3. Arguments after the image name replace what?

CMD is overridden by alternative arguments.[1]

4. Why prefer exec form?

Exec form ensures proper signal handling as PID 1.[2]
