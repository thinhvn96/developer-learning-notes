Compose: an app and a database

Docker · Lesson 0004 · step 9 of 12 · Core · ~10 minutes · Home · Docker ladder · Roadmap

Today's win: describe Compose's service, network and volume model, and start an app with a database that waits for it to be healthy.

The model

"With Docker Compose you use a YAML configuration file, known as the Compose file, to configure your application's services, and then you create and start all the services from your configuration with the Compose CLI." A service is "running the same container image, and configuration, one or more times". Services communicate through networks and keep persistent data in volumes.[1]

A working example

File: compose.yaml. It starts postgres:18 with a health check, then runs a client that connects to the host name db (the service name on the default network) and prints the server version.

cd docker/examples/compose-postgres
docker compose up --abort-on-container-exit
docker compose down -v      # -v also removes the volume

Running it here printed a psql result table with PostgreSQL 18.6 in the server log. depends_on with condition: service_healthy makes the client wait for the health check; without it, the client may start before the database accepts connections.

Interview angle: Compose is for local development and simple single-host setups. The same idea (services, networking, config, storage) is what Kubernetes expresses with Deployments, Services and PersistentVolumes; see the Kubernetes ladder.

Retrieval practice

Answer from memory. One attempt each.

1. What is a Compose service?

A service is the same image and configuration run one or more times.[1]

2. How do services reach each other?

Services communicate through networks.[1]

3. Where does persistent database data live?

Services store and share persistent data in volumes.[1]

4. Why add a health check plus service_healthy?

A running container is not necessarily ready; the condition delays dependents until healthy.
