Layer cache and Dockerfile ordering

Docker · Lesson 0002 · step 4 of 12 · Foundation · ~10 minutes · Home · Docker ladder · Roadmap · Tiếng Việt

Today's win: order a Dockerfile so dependency installation stays cached when only source code changes.

The rule

"Each instruction in this Dockerfile translates to a layer in your final image." When a layer changes, its cache is invalidated, and "If a layer changes, all other layers that come after it are also affected."[1]

What follows from it

Put instructions that change rarely first, and those that change often last. The build-cache page states the invalidation rule; the ordering advice is the practical consequence of it (the docs page does not spell out the ordering recipe in the section I read, so treat this as derived reasoning, not a quote).

# slow: any source edit invalidates the dependency download
COPY . .
RUN ./download-dependencies.sh

# better: dependency descriptor first, source afterwards
COPY pom.xml .
RUN ./download-dependencies.sh
COPY src/ src/

With the second order, editing a file under src/ only invalidates layers from COPY src/ onward; the expensive dependency layer is reused.

A .dockerignore keeps files such as .git/ and build output out of the build context, so unrelated edits do not invalidate COPY layers either.

Retrieval practice

Answer from memory. One attempt each.

1. A layer changes. What about later layers?

If a layer changes, all layers after it are affected.[1]

2. Which instruction should come earliest?

Stable layers first keeps them cached.

3. You edit one source file only. Which layer reruns first?

Cache invalidation starts at the first changed layer, the source COPY, and continues downward.[1]

4. Why add a .dockerignore?

It excludes irrelevant files from the build context and layers.
