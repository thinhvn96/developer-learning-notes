A multi-stage image for a Java app

Docker · Lesson 0003 · step 6 of 12 · Core · ~10 minutes · Home · Docker ladder · Roadmap

Today's win: write a multi-stage Dockerfile that compiles in a JDK image and runs on a smaller JRE image, and prove the size difference.

Why multi-stage

Multi-stage builds help "anyone who has struggled to optimize Dockerfiles while keeping them easy to read and maintain." They give "a cleaner separation between the building of your image and the final output."[1][2] You can name a stage (FROM ... AS build) and copy artifacts out of it with COPY --from=build; docker build --target build stops at a chosen stage.[1]

The Java version

FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY src/ src/
RUN mkdir out && javac -d out src/Hello.java

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /src/out/ ./
CMD ["java", "-cp", ".", "Hello"]

Compiler and sources stay in the first stage; only class files reach the runtime image. Full files: Dockerfile and Dockerfile.naive.

Measured on this machine

hello-naive:latest 475MB   (JDK image, one stage)
hello-multi:latest 318MB   (JRE image, two stages)

A real Spring Boot fat jar adds its own size, but the JDK-to-JRE base saving is the same idea. Docker's docs also recommend minimal, trusted base images.[2]

Retrieval practice

Answer from memory. One attempt each.

1. What does COPY --from=build do?

It copies artifacts from a named earlier stage (or an external image).[1]

2. Why keep the JDK out of the final image?

Multi-stage builds separate building from the final output.[2]

3. How do you stop a build at stage build?

The --target flag halts the build at a specific stage.[1]

4. Purpose of AS build on FROM?

Naming stages keeps COPY --from working if stages are reordered.[1]
