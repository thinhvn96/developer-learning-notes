1.What are IoC and dependency injection? What is a bean?

Short answer: the container creates and wires objects; a bean is an object the container manages.

DI is a specialized form of IoC in which objects declare dependencies only through constructor arguments, factory-method arguments or properties, and the container injects them when it creates the bean, the inverse of the bean constructing or locating its own dependencies. A bean is "an object that is instantiated, assembled, and managed by a Spring IoC container."[1] Benefit: components depend on abstractions and can be tested with fakes.

Likely follow-up: BeanFactory vs ApplicationContext? (ApplicationContext is a sub-interface and complete superset adding AOP integration, message resources, event publication and web contexts.[1])

Learn it: IoC and beans

2.Constructor vs setter vs field injection: which do you use and why?

Short answer: constructor injection for mandatory dependencies.

The reference: use constructors for mandatory dependencies and setters for optional ones. The Spring team advocates constructor injection because it lets you build immutable components, guarantees required dependencies are not null, and returns fully initialized components. Setter injection suits optional dependencies with defaults, or third-party classes.[2] Constructor injection also makes unit tests simple: call new OrderService(fake) without a container. (The reference page I read does not discuss field injection; explain your objection from the testability and immutability points above.)

Likely follow-up: What about circular dependencies? (Constructor injection surfaces them as BeanCurrentlyInCreationException; setter injection on one bean can break the cycle, but redesign is better.[2])

Learn it: Constructor injection

3.How does Spring Boot auto-configuration work? How do you debug it?

Short answer: it configures beans conditionally from the jars on the classpath, and backs away when you define your own.

Boot "attempts to automatically configure your Spring application based on the jar dependencies that you have added" (with HSQLDB on the classpath and no connection beans, it configures an in-memory database). You opt in with @EnableAutoConfiguration or @SpringBootApplication. It is non-invasive: define your own DataSource and the default backs away. Start with --debug to log a conditions report of what was applied and why; exclude classes with exclude or spring.autoconfigure.exclude.[3]

Likely follow-up: How would you write your own starter? (Beyond the pages read here; the Boot reference has a section on creating auto-configuration.)

Learn it: Auto-configuration

4.How do you design a REST controller in Spring MVC?

Short answer: @RestController with composed mapping annotations, @PathVariable, @RequestBody and explicit status codes.

Prefer @GetMapping, @PostMapping, @PutMapping, @DeleteMapping, @PatchMapping over bare @RequestMapping, which by default matches all HTTP methods. @ResponseStatus(HttpStatus.CREATED) sets 201 for creation.[4] Mention idempotency (PUT and DELETE) because clients and gateways retry.

Likely follow-up: How do you validate input and handle errors globally? (Not covered by the pages read for this course; ask your teacher to extend the lesson.)

Learn it: REST controllers

5.How does @Transactional work, and what are the classic pitfalls?

Short answer: a proxy starts and commits/rolls back the transaction around external calls; pitfalls are self-invocation, visibility and checked exceptions.

Defaults: propagation REQUIRED, database default isolation, read-write, rollback on RuntimeException and Error but not checked exceptions (use rollbackFor = Exception.class). In default proxy mode only external calls through the proxy are intercepted, so a method calling another method on the same object bypasses the transaction; private methods are never transactional. AspectJ mode is the alternative if you need self-invocation.[5]

Likely follow-up: Your service method throws a checked exception but the row was committed. Why? (Default rollback rules.)

Learn it: @Transactional

6.REQUIRED vs REQUIRES_NEW vs NESTED?

Short answer: join, always-new independent transaction, or savepoint.

REQUIRED (default): one physical transaction; joins an existing outer one; an inner rollback-only marker affects the outer (possibly UnexpectedRollbackException). REQUIRES_NEW: an independent physical transaction with its own commit/rollback; it can exhaust the connection pool and deadlock if the pool is too small, since the outer connection stays bound. NESTED: one physical transaction with savepoints; the inner can roll back without the outer; works only with JDBC resource transactions.[6] Classic use: REQUIRES_NEW for an audit record that must persist even if the business transaction fails.

Likely follow-up: Why did my REQUIRES_NEW not start a new transaction? (Self-invocation bypassed the proxy.[5])

Learn it: Transaction propagation

7.How does Spring transaction isolation relate to the database?

Short answer: @Transactional's isolation defaults to the database's default; on PostgreSQL that is Read committed.

The attribute table lists isolation with default ISOLATION_DEFAULT.[5] PostgreSQL's default is Read committed and its Serializable level can fail with a serialization error that the application must retry.[7] So a Spring service using Serializable needs retry logic around the transactional method.

Likely follow-up: Where should the retry live? (Outside the transactional boundary, wrapping the whole call, so each attempt gets a new transaction.)

Learn it: @Transactional

8.What is a derived query method in Spring Data JPA, and when do you stop using them?

Short answer: Spring parses the method name (for example findByEmailAddressAndLastname) into a query; use @Query or other approaches when names get unwieldy.

Supported keywords include And, Or, Between, LessThan, Like, In, OrderBy. When derived queries become too complex, use @Query, named queries, custom repository methods, Query by Example or Specifications.[8] The N+1 query problem is a planned lesson in this course; the sources for it have not been gathered yet, so do not rely on this course for that topic yet.

Likely follow-up: What is the N+1 problem? (Prepare from Hibernate documentation; flagged as a gap in RESOURCES.md.)

Learn it: Spring Boot ladder

9.Singleton versus prototype scope. What goes wrong when a singleton depends on a prototype?

Short answer: the prototype is injected once, so the singleton keeps the same instance forever.

Singleton (default): one shared instance per container, not per class loader; prototype: a new instance per request, with no destruction callbacks. "When a singleton bean has a dependency on a prototype bean, the prototype bean is injected only once."[9] Verified in the demo project: injected prototype ids 1, 1; via ObjectProvider 4, 5. Also: singletons must be thread-safe.

Likely follow-up: How do you get a fresh prototype each call? (ObjectProvider or method injection.)

Learn it: Bean scopes

10.How does Spring Boot resolve configuration, and what are profiles?

Short answer: layered property sources where later ones win: files, env vars, system properties, command line; profiles activate environment-specific beans and files.

[10] Order (low to high): defaults, @PropertySource, config files, random, OS env vars, system properties, JNDI, servlet params, SPRING_APPLICATION_JSON, command-line arguments. Profiles segregate configuration; activate with spring.profiles.active, with a default profile when none is set.[11] Verified: a property set in the test annotation overrode application-dev.properties.

Likely follow-up: How do you configure a Spring Boot container in Kubernetes? (ConfigMap as env vars or a mounted properties file.)

Learn it: Configuration and profiles

11.@Value versus @ConfigurationProperties?

Short answer: type-safe binding of a property group to an object, immutable via constructor binding, with relaxed binding and validation.

[10] Works with records and @DefaultValue; @Validated enables constraint checks; relaxed binding maps my-project, myProject and MY_PROJECT. My demo bound app.name and a default greeting into a record.

Likely follow-up: Startup with a missing required property? (Fails with validation enabled per the docs; I did not run that case.)

Learn it: Configuration properties

12.How do you validate a request body and what does the client get on failure?

Short answer: constraint annotations plus @Valid; a failure raises MethodArgumentNotValidException and typically a 400.

[12] Verified in the demo: a blank name and negative age returned 400, a valid body 201.

Likely follow-up: Where else should the rule live? (In the database as a constraint too.)

Learn it: Validation

13.How do you expose health for Kubernetes, and what should liveness not check?

Short answer: Actuator liveness and readiness groups; liveness must not depend on external systems.

[13] Only health is exposed by default; groups at /actuator/health/liveness and /readiness; if liveness depends on the database, an outage can restart every instance and cascade. My test: liveness and readiness returned 200 UP, while /actuator/env and /actuator/beans returned 404 (not exposed).

Likely follow-up: What goes into readiness? (Essential shared dependencies, deliberately.)

Learn it: Actuator

14.How do you test a Spring Boot application efficiently?

Short answer: many slice tests (@WebMvcTest, @DataJpaTest), fewer full @SpringBootTest, and real-backend integration tests with Testcontainers.

[14] @SpringBootTest creates the full context and does not start a server by default (MOCK); RANDOM_PORT starts a real server. Slices load only part of the configuration. @MockitoBean replaces beans.[14] Testcontainers manages Docker-run backends, and @ServiceConnection supplies connection details automatically (I did not run Testcontainers here).[15] My demo ran 17 tests across both styles.

Likely follow-up: Why not H2 for everything? (Behavior differences from PostgreSQL: isolation, locking, dialect.)

Learn it: Testing
