Object-Oriented Programming (Java): interview questions and answers

Home · OOP · 14 questions · OOP ladder · Roadmap

OOP questions for Senior Java interviews, from the pillars to SOLID, each with a runnable example in the OOP ladder.

Try answering out loud first, then open the answer. Superscript links go to the source that backs the claim.

1.What are the four pillars of OOP and how does Java support each?

Short answer: encapsulation, inheritance, polymorphism, abstraction.

Encapsulation: "hiding internal state and requiring all interaction to be performed through an object's methods".[1] Java support: private fields, access levels.[2] Inheritance: one direct superclass with extends.[3] Polymorphism: the JVM calls the method of the object referred to, not of the variable's type (virtual method invocation).[4] Abstraction: interfaces as contracts enforced at build time, and abstract classes.[5][6] (The four-pillars framing is the usual interview wording; the tutorial pages define each idea separately.)

Likely follow-up: Which pillar do people over-use? (Inheritance; prefer composition.)

Learn it: Objects and encapsulation

2.Encapsulation versus abstraction?

Short answer: encapsulation protects state by hiding it behind methods; abstraction hides complexity behind a simpler contract.

Encapsulation is about data hiding and invariants: my BankAccount made balance private so "never negative" is enforced in two methods.[1] Abstraction is what an interface or abstract class gives: callers depend on the contract, not the implementation.[5]

Likely follow-up: Give an example where encapsulation is broken but abstraction is fine. (A getter returning a mutable internal list.)

Learn it: Access levels

3.Explain method overriding versus overloading, and hiding.

Short answer: overriding is runtime dispatch on the object's class; overloading is compile-time selection by declared parameter types; static methods and fields hide, they do not override.

An instance method with the same signature overrides (a covariant return is allowed; access may widen but not narrow; @Override makes the compiler check).[7] Static methods hide.[7] My demos: describe(Shape) was chosen for a Shape-typed variable holding a Circle (overload, compile time), while a.sound() ran Dog's version (override); a static call and a field were chosen by the static type.[4]

Likely follow-up: What is a covariant return type? (An override may return a subtype of the overridden method's return type.[7])

Learn it: Overriding and hiding

4.Abstract class or interface?

Short answer: interface for a capability that unrelated classes can offer; abstract class to share code and state among closely related classes.

Per the tutorial: abstract classes may have non-static, non-final fields and non-public methods and support single inheritance; interface fields are constants and methods are public, with multiple implementation possible. Choose an abstract class to share code among closely related classes, an interface when unrelated classes will implement it.[6] Since JDK 8 interfaces also carry default methods (conflict rules in the Java 8 lesson).

Likely follow-up: Can an interface have state? (Only constants; use an abstract class or composition for instance state.)

Learn it: Abstract vs interface

5.Why prefer composition over inheritance? Show a concrete failure of inheritance.

Short answer: inheritance couples a subclass to its parent's implementation; composition reuses behavior through a collaborator and stays flexible.

Composition "gives the design higher flexibility" and avoids tight coupling and the diamond problem; the cost is forwarding boilerplate.[8] Failure: my CountingSet extends HashSet counted 6 for 3 addAll elements because addAll calls add internally; the composed version counted 3.

Likely follow-up: When is inheritance still right? (A real is-a relationship with a base class designed for extension.)

Learn it: Composition over inheritance

6.What is the order of initialization for a subclass instance?

Short answer: class initialization (static blocks: parent then child) once; then per object: parent field initializers and instance blocks, parent constructor, child field initializers and instance blocks, child constructor.

Static blocks run once in source order; instance initializer blocks are copied into every constructor.[9] My run printed 1 Parent static, 2 Child static, 3 Parent field init, 4 Parent instance block, 5 Parent constructor, 6 Child field init, 7 Child instance block, 8 Child constructor. Trap: an overridable method called from a parent constructor sees the child's fields uninitialized.

Likely follow-up: Why is calling an overridable method in a constructor dangerous? (Child state does not exist yet.)

Learn it: Initialization order

7.What is the difference between a static nested class and an inner class?

Short answer: an inner class is tied to an outer instance and can read its private members; a static nested class is not.

[10] Reasons to nest: logical grouping, encapsulation, readability. Local and anonymous classes capture effectively-final locals. Prefer lambdas for one-method interfaces.

Likely follow-up: Memory leak risk with inner classes? (An inner instance holds a reference to its outer instance.)

Learn it: Nested classes

8.How do you make a class immutable? Is final enough?

Short answer: no; final class, final fields, no mutators, and defensive copies of mutable components.

My MutableTeam had a final list field but still changed when the caller mutated the list; ImmutableTeam used List.copyOf and an unmodifiable view. Records are shallowly immutable, so they need the same copying.

Likely follow-up: Why is String immutable? (Sharing safely; see the Java strings lesson.)

Learn it: Immutability

9.Explain SOLID.

Short answer: five principles from Robert C. Martin's 2000 paper (acronym by Michael Feathers).

  • SRP: "There should never be more than one reason for a class to change."
  • OCP: "open for extension, but closed for modification."
  • LSP: subtypes must be substitutable for their base types.
  • ISP: "Clients should not depend upon interface methods they do not use."
  • DIP: "depend upon abstractions, not concretes."[11]

Each has a runnable example in the OOP ladder (invoice split, discount interface, Square/Rectangle, fat interface, notifier injection).

Likely follow-up: Which is hardest to apply and why? (Discuss LSP: it is about behavior, not just signatures.)

Learn it: SOLID lessons

10.Give an example that violates the Liskov Substitution Principle and fix it.

Short answer: Square extends Rectangle with setters that change both sides.

LSP: objects of a type may be replaced by objects of a subtype "without altering any of the desirable properties of that program"; preconditions cannot be strengthened, postconditions and invariants cannot be weakened, and the history constraint applies.[12] My run: code that sets width 5 and height 4 expected area 20; Rectangle gave 20, Square gave 16. Fix: separate immutable types under a common Shape interface.

Likely follow-up: Another smell? (An override that throws UnsupportedOperationException for an inherited method.)

Learn it: Liskov

11.What is dependency inversion versus dependency injection versus IoC?

Short answer: DIP is the principle (depend on abstractions), DI is a technique (pass dependencies in), IoC is the general idea that a container or caller controls creation.

[11] My AlertService depended on a Notifier interface and got concrete senders (or a lambda test double) from main. Spring automates it: the IoC container instantiates, assembles and injects beans.

Likely follow-up: How does DI help testing? (Substitute a fake, as the coupling demo did.)

Learn it: DIP

12.Coupling and cohesion: what do you aim for, and what is the Law of Demeter?

Short answer: low coupling, high cohesion; talk only to your immediate friends.

"Low coupling is often thought to be a sign of a well-structured computer system ... combined with high cohesion, supports ... readability and maintainability."[13] The Law of Demeter: "each unit should only talk to its friends; don't talk to strangers", so avoid a.getB().getC().act(); prefer a.act().[14]

Likely follow-up: Are fluent APIs a violation? (Not in spirit when each call returns the same builder/stream; it is a guideline.)

Learn it: Law of Demeter

13.What is a God object and how do you refactor it?

Short answer: a class that knows or does too much; split by reason to change and inject collaborators.

A god object "references a large number of distinct types, has too many unrelated or uncategorized methods"; it violates SRP and everything becomes coupled to it.[15] Steps: list responsibilities, extract classes named for what they do, inject them, keep a thin coordinator (see GodObjectDemo).

Likely follow-up: Can a facade become one? (Yes; see Facade and Mediator cons.)

Learn it: God objects

14.When would you use an enum instead of constants or a class hierarchy?

Short answer: for a fixed set of instances; give them fields and even per-constant behavior.

Enums are type-safe sets of predefined constants that can have fields, methods and private constructors, and implicitly extend java.lang.Enum.[16] My Op enum gave each constant its own apply body. Use sealed types instead when variants carry different data.

Likely follow-up: Can an enum implement an interface? (Yes; enums can implement interfaces since they cannot extend a class.)

Learn it: Enums
