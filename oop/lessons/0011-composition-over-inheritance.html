Composition over inheritance

OOP (Object-Oriented Programming) · Lesson 0011 · step 11 of 22 · Core · ~12 minutes · Home · OOP (Object-Oriented Programming) ladder · Roadmap

Today's win: explain the fragile base class problem with a running example and fix it with composition and delegation.

The principle

Composition over inheritance achieves reuse by composing objects rather than building hierarchies: "Instead of having two child classes inherit functionality from a common parent, composition simulates inheritance by having the children include a copy of a 'pseudo-parent' class as a field." It gives flexibility and avoids tight coupling; the drawback is forwarding boilerplate.[1]

A bug that inheritance causes

java oop/examples/CompositionVsInheritance.java
inheritance: added 3 elements, addCount = 6   (expected 3)
composition: added 3 elements, addCount = 3   (expected 3)

The subclass of HashSet counts adds by overriding both add and addAll. But HashSet.addAll (inherited behavior) itself calls add for each element, so each element is counted twice: 6, not 3. The subclass depends on an internal implementation detail of its parent, which the parent may change (the fragile base class problem). The composed version holds a Set and forwards calls, so it is independent of how the wrapped class works. Source: CompositionVsInheritance.java.

Rule of thumb: inherit only for a true is-a relationship where the parent is designed and documented for extension; otherwise compose. Patterns that embody this: Strategy, Decorator, Bridge, State.

Retrieval practice

Answer from memory. One attempt each.

1. Composition reuses code by...?

The class includes the collaborator as a field.[1]

2. Count in the inheritance demo for three adds?

addAll called add again, double-counting.

3. Main cost of composition?

Methods may have to be forwarded by hand.[1]

4. Root of the fragile base class problem?

The subclass relied on how HashSet implements addAll.
