God objects and refactoring toward SOLID

OOP (Object-Oriented Programming) · Lesson 0022 · step 22 of 22 · Senior · ~12 minutes · Home · OOP (Object-Oriented Programming) ladder · Roadmap · Tiếng Việt

Today's win: recognize a God object and decompose it into cohesive collaborators.

The anti-pattern

A god object is "an object that references a large number of distinct types, has too many unrelated or uncategorized methods, or some combination of both." It violates the Single Responsibility Principle, is "tightly coupled to (referenced by) so much of the other code" that changes cascade, and makes the whole program depend on one bottleneck.[1] An anti-pattern is "any common but counterproductive solution to some class of problem"; the God object is one of the classic examples.[2]

Decompose

java oop/examples/GodObjectDemo.java
[god] INSERT order for ann
  [god] email ann: total 54
god processed 54
  [mailer] ann: total 54
processor processed 54

OrderManager validates, prices, persists and emails in one method. OrderProcessor coordinates two focused collaborators (Pricing, Mailer) received through its constructor, and produces the same result. Steps: (1) list the reasons to change, (2) extract each into a class with a name that says what it does, (3) inject them, (4) keep the coordinator thin. Source: GodObjectDemo.java. Refactoring.Guru also warns that Facade and Mediator can drift into god objects; see the patterns criticism lesson.

Retrieval practice

Answer from memory. One attempt each.

1. A god object is...?

It references many types or has too many unrelated methods.[1]

2. Which principle does it violate?

It concentrates functionality instead of dividing it.[1]

3. First refactoring step?

Identify the separate responsibilities first.

4. An anti-pattern is...?

It is any common but counterproductive solution to some class of problem.[2]
