Immutability and defensive copies

OOP (Object-Oriented Programming) · Lesson 0014 · step 14 of 22 · Advanced · ~10 minutes · Home · OOP (Object-Oriented Programming) ladder · Roadmap · Tiếng Việt

Today's win: turn a mutable class into an immutable one and explain defensive copying.

Why immutability

An immutable object cannot change after construction, so it can be shared freely (including between threads) and used as a map key without surprises: the same reasoning as String's constant values (strings lesson).

The leak, and the fix

java oop/examples/ImmutabilityDemo.java
MutableTeam after outside change   : [ann, intruder]
ImmutableTeam after outside change : [ann]
cannot modify the exposed list
Point[x=1, y=2] equals another Point(1,2): true, moved copy: Point[x=9, y=2]

MutableTeam has a final field but keeps the caller's list, so an outside change leaks in: final makes the reference constant, not the object. ImmutableTeam is a final class with a final field and a defensive copy (List.copyOf), and exposes an unmodifiable list. A record gives an immutable data carrier in one line: "shallowly immutable", so the same copy step is needed for collection components.[2] Checklist (standard practice, demonstrated above): final class, final fields, no setters, defensive copies in and out. Source: ImmutabilityDemo.java.
