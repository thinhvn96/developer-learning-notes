The bulk API and per-item errors

ELK Stack · Lesson 0010 · step 8 of 14 · Core · ~10 minutes · Home · ELK Stack ladder · Roadmap · Tiếng Việt

Today's win: index many documents in one request, and read per-item results instead of trusting the HTTP status.

Why bulk

The bulk API performs multiple indexing or delete operations in one call; it "reduces overhead and can greatly increase indexing speed". The body is NDJSON: an action line, then (for index/create/update) a source line; the last line must end with a newline. Actions: index (add or replace), create (only if absent), update (partial), delete.[1]

Errors are per item

The response has an errors flag and a status for each item, so a request can succeed as a whole while some items fail.[1]

POST _bulk   (4 index actions, then create of an existing _id)
errors flag: True
  index 1 201 ... index 4 201
  create 1 409 version_conflict_engine_exception

Always inspect each item; never assume "HTTP 200" means everything was indexed. Script: 03-analysis-bulk-aggs.sh. Pairs with refresh tuning: bulk loads usually raise refresh_interval while running (see exercise).

Retrieval practice

Answer from memory. One attempt each.

1. Bulk request body format?

The API requires newline-delimited JSON.[1]

2. Action that fails if the document exists?

create indexes only if the document does not exist (the run returned 409).[1]

3. HTTP 200 on a bulk call means...?

Per-item statuses and the errors flag report failures.[1]

4. Main benefit of bulk?

It reduces overhead and increases indexing speed.[1]
