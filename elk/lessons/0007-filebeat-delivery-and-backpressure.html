Filebeat: harvesters, registry and delivery guarantees

ELK Stack · Lesson 0007 · step 11 of 14 · Advanced · ~10 minutes · Home · ELK Stack ladder · Roadmap · Tiếng Việt

Today's win: explain how Filebeat resumes after restart, what delivery guarantee it gives, and what happens when the output is blocked.

Components

"A harvester is responsible for reading the content of a single file" line by line and sending it to the output. "An input is responsible for managing the harvesters and finding all sources to read from."[1]

Registry

"Filebeat keeps the state of each file and frequently flushes the state to disk in the registry file": the last offset read plus identifiers to recognize files, so it resumes where it stopped after a restart.[1]

Delivery

"Filebeat guarantees that events will be delivered to the configured output at least once and with no data loss." When the output is blocked and has not confirmed events, Filebeat "will keep trying to send events until the output acknowledges that it has received the events". Events not acknowledged before shutdown are resent on restart, which can create duplicates.[1]

Compare with the other systems in this course: Filebeat, Logstash persistent queues, RabbitMQ consumer acks and Kafka consumer commits all give at-least-once, so all of them push you toward idempotent writes. See retries and idempotency.

Retrieval practice

Answer from memory. One attempt each.

1. Where does Filebeat remember file progress?

State is flushed to the registry file.[1]

2. Filebeat's delivery guarantee?

Events are delivered at least once with no data loss.[1]

3. Output is blocked. Filebeat does what?

It keeps trying until the output acknowledges receipt.[1]

4. Why could duplicates appear after restart?

Events sent but unacknowledged before shutdown are resent.[1]
