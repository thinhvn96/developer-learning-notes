Near real-time search and refresh

ELK Stack · Lesson 0004 · step 6 of 14 · Core · ~10 minutes · Home · ELK Stack ladder · Roadmap · Tiếng Việt

Today's win: explain why a just-indexed document may not be searchable yet, what a refresh does, and its default schedule.

Near real-time

"A refresh makes all operations performed on an index since the last refresh available for search." It is lightweight: new segments are written to the filesystem cache and opened for search without a full commit to disk.[1] "Document changes are not visible to search immediately", hence near real-time.[1]

By default "Elasticsearch periodically refreshes indices every second, but only on indices that have received one search request or more in the last 30 seconds."[1]

See it

hits before refresh: 0
hits after  refresh: 2

The script indexes two documents, counts (0), calls _refresh, counts again (2). The first count is 0 because the idle index had not been refreshed yet, in line with the rule above; timing can vary, so if you see 2, the periodic refresh simply ran first.

Interview angle: "My test indexes a document then searches and finds nothing." Answer: call refresh in tests (or wait), and do not call refresh per document in production because refreshes cost throughput; tune refresh_interval for bulk loads.

Retrieval practice

Answer from memory. One attempt each.

1. What makes new documents searchable?

A refresh makes operations since the last refresh available for search.[1]

2. Default refresh cadence for active indices?

Indices are refreshed every second if searched in the last 30 seconds.[1]

3. Why 'near' real-time?

Document changes become visible within the refresh timeframe, not immediately.[1]

4. What does a refresh write?

It writes segments to the filesystem cache without a full commit.[1]
