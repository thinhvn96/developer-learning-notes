Today's win: write a Logstash pipeline with a grok filter, spot a parse failure, and explain what persistent queues guarantee.

Pipeline

Inputs (file, syslog, beats...), filters (grok, mutate, drop, geoip...) and outputs (elasticsearch, file...). Codecs act as stream filters attached to inputs or outputs, such as json or multiline.[1]

Grok

Grok is "a great way to parse unstructured log data into something structured and queryable." Patterns use %{SYNTAX:SEMANTIC}, for example %{NUMBER:duration}. When nothing matches, the event is tagged _grokparsefailure by default.[2]

grok { match => { "message" => "%{IP:client} %{WORD:method} %{URIPATH:path} %{NUMBER:status:int} %{NUMBER:duration_ms:int}" } }
cd elk/examples && ./02-logstash-grok.sh
"10.0.0.7 GET /orders/42 200 35"  -> client=10.0.0.7 method=GET path=/orders/42 status=200 duration_ms=35
"this is not an access log"       -> tags: [ "_grokparsefailure" ]

Files: logstash-grok.conf, 02-logstash-grok.sh.

Persistent queues

A persistent queue "helps protect against data loss during abnormal termination by storing the in-flight message queue to disk." After a restart Logstash "attempts to deliver messages stored in the persistent queue until delivery succeeds at least once." It can absorb bursts without an external buffer like Redis or Kafka, and applies backpressure to inputs when full.[3]

Note "at least once": duplicates are possible, so give events a stable id if duplicates matter downstream.

Retrieval practice

Answer from memory. One attempt each.

1. Grok pattern syntax?

Patterns are written %{SYNTAX:SEMANTIC}.[2]

2. Grok fails to match. What happens?

By default the _grokparsefailure tag is added.[2]

3. Persistent queue delivery guarantee?

Logstash delivers stored events until delivery succeeds at least once.[3]

4. Queue is full. What does Logstash do?

It stalls inputs until the queue drains.[3]
