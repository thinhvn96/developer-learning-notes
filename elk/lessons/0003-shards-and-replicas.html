Shards and replicas

ELK Stack · Lesson 0003 · step 5 of 14 · Core · ~10 minutes · Home · ELK Stack ladder · Roadmap · Tiếng Việt

Today's win: explain primaries and replicas, what is fixed at index creation, and why a one-node cluster shows yellow.

Shards

You add nodes to a cluster to increase capacity, and Elasticsearch "automatically distributes your data and query load across all of the available nodes." There are two kinds of shards: "Each document in an index belongs to one primary shard. A replica shard is a copy of a primary shard."[1]

Replicas "maintain redundant copies of your data across the nodes in your cluster", which protects against hardware failure and "increases capacity to serve read requests".[1]

What can change

"The number of primary shards in an index is fixed at the time that an index is created, but the number of replica shards can be changed at any time, without interrupting indexing or query operations."[1] Interview consequence: choose primary shard count with growth in mind (or plan to reindex).

Why yellow?

logs 0 p STARTED
logs 0 r UNASSIGNED
index health: yellow

That is the output of 01-elasticsearch-basics.sh on a single node with the default of one replica: the primary is started and the replica is unassigned, so the index is yellow. A replica exists to be a copy on another node, so with one node there is nowhere useful to put it (the page I read does not state the placement rule word for word; the run demonstrates the outcome).

Retrieval practice

Answer from memory. One attempt each.

1. Each document belongs to how many primary shards?

Each document in an index belongs to one primary shard.[1]

2. Which can change after index creation?

Replicas can change at any time; primaries are fixed at creation.[1]

3. Replicas provide what?

They protect against hardware failure and increase capacity to serve reads.[1]

4. Single node, one replica configured. Health?

The replica stays unassigned, so the index is yellow (observed in the run).
