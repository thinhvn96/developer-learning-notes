Java Interview Prep Lesson 0001 Reference sheet

How HashMap finds your value

And why equals() and hashCode() must work together.

Why this lesson? Interviewers often ask: "How does HashMap work?" You use HashMap every day. This lesson helps you explain it, in simple words.
Your goal. At the end, you can explain HashMap out loud in about 60 seconds.
bucket
One "box" inside the HashMap. A HashMap has many buckets. Each bucket holds some of the entries.
entry
One key and its value, stored together. For example "cat" → 1.
hash code
A number made from an object. You get it by calling hashCode(). HashMap uses it to choose a bucket.
collision
When two different keys go into the same bucket.
immutable
Cannot be changed after it is created. String is immutable.
O(1)
Read as "O of one". It means the time stays about the same, even when the map gets bigger.

Before you start

Try this first. Say out loud: "How does map.get(key) find the value?" Don't look anything up. It's OK if you don't know. Trying first helps you remember the lesson better. At the end, you will compare.

1. The picture: a wall of mailboxes

Imagine a wall with 16 mailboxes, numbered 0 to 15. Each mailbox is a bucket.

When you put something in the map, Java does not search for an empty place. It calculates the right mailbox from the key. When you get something, Java does the same calculation. It goes straight to the same mailbox.

This is why get() is fast. Java does not look in all 16 mailboxes. It looks in one. That's why interviewers say get() and put() are O(1) on average. HashMap javadoc

2. Follow one key, step by step

map.put("cat", 1);

Step 1  Java calls "cat".hashCode()        → 98262
Step 2  Java turns 98262 into a box number → 7
Step 3  Java stores the entry "cat" → 1 in box 7

map.get("cat");
        Same steps → box 7 → found → returns 1

How does Java turn 98262 into 7? It uses a fast math trick. You will learn it in the next lesson. For now, remember this: same key → same number → same box.

3. Two keys in the same box

There are only 16 boxes, but there are millions of possible keys. So sometimes two different keys go into the same box. This is called a collision. It is normal.

A real example: the strings "Aa" and "BB" have the same hash code (2112). So they go into the same box.

map.put("Aa", 1);
map.put("BB", 2);   // same box as "Aa"
map.get("BB");      // returns 2

How does Java find the right one? Inside the box, it checks each entry, one by one. For each entry, it asks two questions:

  1. Is the hash code the same? If not, skip it. (Comparing two numbers is very fast.)
  2. Is the key equal? Java calls equals(). If it returns true, this is the right entry. HashMap.java source

So hashCode() finds the box. equals() finds the right entry inside the box.

4. The rule: equal objects, same hash code

Because of this, Java has a rule. You can find it in the documentation of Object Object.hashCode:

If two objects are equal (equals() returns true), they must have the same hash code.

The opposite is not required. Two different objects may have the same hash code, like "Aa" and "BB". That's allowed. It only makes the map a little slower.

In interviews, people call this rule the equals/hashCode contract. "Contract" here just means "a rule you must follow".

What happens if you break the rule?

Here, the class overrides equals() but forgets hashCode():

class Point {
  final int x, y;
  Point(int x, int y) { this.x = x; this.y = y; }

  @Override public boolean equals(Object o) {
    return o instanceof Point p && p.x == x && p.y == y;
  }
  // hashCode() is missing!
}

map.put(new Point(1, 2), "A");
map.get(new Point(1, 2));   // almost always null!

Why? Without your own hashCode(), Java uses the default one from Object. The default gives each new object its own number, usually a different one. So the two Point objects have different numbers. Java looks in the wrong box, and finds nothing. There is no error message. You just get null.

The fix: always override both methods together. Or, even easier, use a record. A record writes equals() and hashCode() for you, based on its fields. Record javadoc

@Override public int hashCode() { return Objects.hash(x, y); }

// or, even easier:
record Point(int x, int y) {}

5. Don't change a key after you put it in

Back to the mailboxes. Imagine you write an address on a letter and put it in mailbox 7. Then you secretly change the address on the letter. Later you ask: "Where is my letter?" Java reads the new address, goes to a different mailbox, and finds nothing. The letter is still in mailbox 7, but nobody will find it.

That's what happens when you change a key after put(). Its hash code changes, so Java looks in the wrong box. The Java documentation warns about this Map javadoc dev.java.

The fix: use immutable keys, meaning keys that cannot change. Good examples are String, Integer, List.of(...) and records with immutable fields.

Practice

Answer from memory. Don't scroll up. The answers are in a different order every time you open the page.

Why is map.get(key) fast?

The hash code tells Java which bucket to use. Java looks in one bucket only, not all of them.

"Aa" and "BB" have the same hash code. After map.put("Aa", 1) and map.put("BB", 2), what does map.get("BB") return?

Both keys are in the same bucket (a collision). Inside the bucket, equals() finds the right key, "BB", so you get 2.

Which sentence is the Java rule?

The rule goes in one direction only: equal → same hash code. Different objects can share a hash code ("Aa" and "BB").

The Point class overrides equals() but not hashCode(). What does map.get(new Point(1, 2)) return after map.put(new Point(1, 2), "A")?

The default hashCode() gives each new object its own number. So Java looks in the wrong bucket. No error, just null.

Now Point is a record Point(int x, int y) {}. What does map.get(new Point(1, 2)) return after map.put(new Point(1, 2), "A")?

A record creates equals() and hashCode() from its fields. Two points with the same x and y are equal and have the same hash code.

You put a key in a HashMap. Then you change the key. Now get() cannot find it. What is the best way to avoid this?

Changing the key changes its hash code, so Java looks in the wrong bucket. Use immutable keys: String, records, List.of(...).

Example answer

"A HashMap stores entries in an array of buckets. When I call put, Java calls hashCode() on the key and uses that number to choose a bucket. When I call get, it does the same thing, so it goes straight to the right bucket. That's why get and put are O(1) on average. Sometimes two keys go into the same bucket. That's a collision. Then Java uses equals() to find the right key inside the bucket. This is why equal objects must have the same hash code. If they don't, Java looks in the wrong bucket. Also, keys should be immutable. If a key changes after I put it in, the map can't find it again."
