Rate limiting and the token bucket

System Design · Lesson 0006 · step 5 of 11 · Core · ~10 minutes · Home · System Design ladder · Roadmap

Today's win: explain rate limiting as a client-side discipline and run a token bucket.

The problem

Hammering a throttled service and retrying rejected requests multiplies traffic: the docs' example ingests 10,000 records into a service that accepts 2,000 per pass and ends up sending 30,000 records in total.[1] The Rate Limiting pattern controls "the rate at which your application sends requests to a service so that you stay within the service's throttling limits".[1]

How

  • Throttle on operations per second, data per minute, or cost of operations.
  • Prefer sending smaller batches more often (even out the flow) rather than one burst per period.
  • Put records into a durable messaging system and have job processors read at a controlled rate.
  • Coordinate retries with rate limiting: avoid retry storms, propagate back-pressure such as HTTP 429 with Retry-After, and use a limited number of retries with small random delays.[1]

A token bucket (my implementation of a common algorithm)

java system-design/examples/TokenBucketDemo.java     # burst 5, refill 10/s
20 requests fired instantly -> allowed=5 rejected=15
1 s of attempts every 10 ms -> allowed=9 (about the refill rate)

The Azure page describes the pattern; the token bucket is one common algorithm and is my example, not the docs'. Source: TokenBucketDemo.java. Not suitable when the operation needs immediate synchronous completion with very low latency, or when the bottleneck is concurrency rather than request rate.[1] See retries.
