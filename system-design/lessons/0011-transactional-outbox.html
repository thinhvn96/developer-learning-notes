The transactional outbox

System Design · Lesson 0011 · step 10 of 11 · Advanced · ~12 minutes · Home · System Design ladder · Roadmap

Today's win: explain the dual-write problem and how the transactional outbox solves it, including why consumers still need idempotence.

The problem

A service saves an order, then publishes an OrderCreated event. If the publish fails between the two steps (network error, broker outage, host failure), other services are never told, and "lost events can cause data inconsistencies across the application".[1]

The solution

The Transactional Outbox "saves events in a data store, typically in an outbox table in your database, before it pushes them to a message broker". Business object and events are saved in the same transaction, which "either commits everything or rolls back everything". A separate worker queries unhandled entries, publishes them and marks them processed.[1] Event order must be preserved; and the guide ties the pattern to idempotent message processing.[1]

cd postgresql/examples && ./run.sh ../../system-design/examples/05-outbox.sql
success : orders=1, outbox=1 (committed together)
failure : CHECK violation on the order -> ROLLBACK -> no outbox row for the failed order
relay   : SELECT unpublished -> publish -> UPDATE published = true

If the relay crashes after publishing but before the update, it publishes again: at-least-once, so consumers must be idempotent (see Kafka delivery semantics). Source: 05-outbox.sql. The Azure guide's implementation uses Cosmos DB's change feed and Service Bus; the relational version above is the general pattern. Alternatives named in the guide: libraries such as NServiceBus or MassTransit that provide an outbox.[1] Related: the saga.

Retrieval practice

Answer from memory. One attempt each.

1. Dual-write problem?

An error between saving and publishing loses the event.[1]

2. Where do events go first?

Events are saved with the business object in one transaction.[1]

3. Who publishes the events?

A worker queries the outbox and publishes.[1]

4. Relay crashes after publish, before marking. Result?

At-least-once delivery: consumers must be idempotent.[1]
