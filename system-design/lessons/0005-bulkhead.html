The bulkhead pattern

System Design · Lesson 0005 · step 4 of 11 · Core · ~10 minutes · Home · System Design ladder · Roadmap

Today's win: explain the bulkhead pattern and show a slow dependency starving a shared pool.

Idea

"Isolate the elements of an application into pools so that if one element fails, the others continue to function." Named for a ship's partitioned hull. Problem: a consumer calling an unresponsive service can exhaust its connection pool, and then its calls to other services fail too.[1]

How

Give each dependency its own pool (connection, thread, or semaphore); partition service instances by consumer load and availability needs. Benefits: isolates cascading failures, preserves some functionality, allows different quality-of-service levels. Consider combining with retry, circuit breaker and throttling; use containers or processes for service partitions; prefer platform limits (for example Kubernetes resource limits) over re-inventing them.[1]

java system-design/examples/BulkheadDemo.java
shared pool of 4 threads   : healthy calls took 2010 ms (stuck behind the slow service)
separate pools (bulkheads) : healthy calls took 20 ms

Four 2-second calls to a slow service filled the shared pool, so four 10 ms calls to a healthy service waited about 2 seconds. Separate pools kept them at about 20 ms. Source: BulkheadDemo.java. Related: thread pools and Kubernetes requests and limits as container-level bulkheads.[1]

Retrieval practice

Answer from memory. One attempt each.

1. Bulkhead isolates...?

Elements are isolated into pools so failure does not cascade.[1]

2. Slow service and shared pool. Effect on healthy calls?

The demo's healthy calls took about 2 seconds in the shared pool.[1]

3. Mechanisms to build bulkheads?

Processes, thread pools, semaphores and containers are named.[1]

4. Cost of bulkheads?

The pattern may not suit when less efficient resource use is unacceptable.[1]
