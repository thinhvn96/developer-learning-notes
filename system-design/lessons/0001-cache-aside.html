The cache-aside pattern

System Design · Lesson 0001 · step 1 of 11 · Core · ~10 minutes · Home · System Design ladder · Roadmap

Today's win: describe the cache-aside read and write flows, the order of steps on write, and the staleness that remains.

The flow

  1. The application tries to read from the cache.
  2. On a cache miss it reads from the data store.
  3. It adds the item to the cache and returns it.[1]

On update: "it writes the change to the data store and then invalidates the corresponding item in the cache."[1] Order matters: "Update the data store before removing the item from the cache"; otherwise a reader can re-cache the outdated item in the gap.[1]

java system-design/examples/CacheAsideDemo.java
read: v1  (store reads so far: 1)
read: v1  (store reads so far: 1)         # hit
after write+invalidate: v2  (store reads: 2)
after out-of-band change, cache still says: v2  (stale)

Source: CacheAsideDemo.java.

What it does not give you

  • Consistency: "doesn't guarantee consistency between the data store and the cache"; an outside change appears only when the item loads again.[1]
  • Expiration and eviction: too short causes repeated misses, too long causes stale data; caches evict, often least-recently-used.[1]
  • Local caches: each instance has its own copy, so they diverge; consider a shared distributed cache.[1]

Not suitable when most requests miss, or for sensitive data in a shared cache.[1]

Retrieval practice

Answer from memory. One attempt each.

1. On a cache miss, what does the app do?

It retrieves the item from the data store and adds it to the cache.[1]

2. On a write, correct order?

Update the data store before removing the cached item.[1]

3. Does cache-aside guarantee consistency?

The pattern does not guarantee consistency between the store and the cache.[1]

4. Expiry set far too long causes what?

Too long an expiration lets cached data become stale.[1]
