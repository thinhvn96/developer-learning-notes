Competing consumers

System Design · Lesson 0008 · step 7 of 11 · Core · ~10 minutes · Home · System Design ladder · Roadmap

Today's win: explain competing consumers and distinguish them from publish-subscribe.

Idea

"Enable multiple concurrent consumers to process messages received on the same messaging channel." The queue ensures each message goes to one consumer; the pool can grow and shrink with load. It differs from publish-subscribe: with competing consumers "one consumer receives each message"; with pub-sub "all consumers receive every message".[1]

Benefits and cautions

  • Load-leveled, more reliable (a failed instance does not block others), scales, no complex coordination; "the message queue ensures that each message is delivered at least once".[1]
  • Ordering is not guaranteed: design for idempotent processing.
  • Poison messages need capture (dead letter queue / delivery limit).
  • Results need a reply channel and correlation.
  • A single queue can become a bottleneck; partition or balance across queues.[1]

Where you have seen it in this course: RabbitMQ consumers on one queue with acks and prefetch (lesson), and a Kafka consumer group (each partition to one consumer in the group). Not suitable when tasks depend on each other or must run in a strict sequence.[1]

Retrieval practice

Answer from memory. One attempt each.

1. Competing consumers: how many get each message?

One consumer receives each message.[1]

2. Pub-sub: how many get each message?

All consumers receive every message.[1]

3. Ordering across competing consumers?

Processing order is not guaranteed.[1]

4. Consumer keeps crashing on a message. Use...?

Poison messages should be captured elsewhere, for example a dead-letter queue.[1]
