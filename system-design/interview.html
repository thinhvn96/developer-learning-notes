1.Explain the cache-aside pattern. In what order do you update the database and the cache?

Short answer: read: check cache, on miss load from the store and populate; write: update the store, then invalidate the cache entry.

The application tries the cache; on a miss it reads the data store, adds the item to the cache and returns it. On update it writes to the store, then invalidates the cached item. Order matters: if you remove the cache entry first, a reader can fetch the old value from the store and put it back, leaving stale data.[1] My CacheAsideDemo.java shows read-hit, write-then-invalidate, and staleness after an out-of-band change.

Likely follow-up: Does cache-aside guarantee consistency? (No: it does not guarantee consistency; expiry bounds staleness. Write-through gives read-after-write freshness at other costs.[1])

Learn it: Cache-aside

2.What are the failure modes of caching?

Short answer: staleness, bad expiration, eviction surprises, local-cache divergence, low hit rate.

Expiration too short causes constant refetching; too long causes stale data. Caches evict (often least-recently-used) when full. A local in-process cache diverges across instances; a shared distributed cache avoids that. Cache-aside is a poor fit if most requests miss, for sensitive data in shared caches, or for static data that fits entirely (prime it instead).[1]

Likely follow-up: How do you decide the TTL? (From the tolerated staleness and access pattern; measure hit rate.)

Learn it: Cache-aside

3.When should you retry a failed call, and how?

Short answer: only for transient faults, with growing delays, a cap on attempts, and idempotent operations.

Strategies: cancel when the fault is not transient, retry immediately for rare faults, retry after a delay for common busy/connectivity failures, increasing delays incrementally or exponentially up to a maximum. Choose delays so requests from many instances spread out.[2] My demo used random delays below an exponential cap (jitter), which implements that spreading. An aggressive retry policy can further degrade a busy service; after many failures stop calling and probe occasionally (Circuit Breaker).[2]

Likely follow-up: What if the request succeeded but the response was lost? (That is why idempotency matters: retrying a non-idempotent operation may execute it twice.[2])

Learn it: Retries and idempotency

4.Service A calls B calls C, and each layer retries 3 times. What happens when C is down?

Short answer: retry amplification: up to 3 x 3 = 9 calls to C per request to A (plus A's own attempts multiply again), long delays, and load on a service that is already struggling.

The Retry pattern's guidance: implement retries only where the full context is understood; with nested retry policies fail fast at the lower level and let the higher level decide, otherwise extra layers "can add long delays".[2] Also log early failures as informational and only the final failure as an error.[2] The arithmetic is mine; the guidance is the docs'.

Likely follow-up: How do you prevent this? (Single retry layer, retry budgets, circuit breakers, timeouts.)

Learn it: Retries and idempotency

5.RabbitMQ or Kafka for this system?

Short answer: depends on whether messages are units of work (queue) or the stream is the asset (log).

RabbitMQ: exchanges route copies to queues by bindings, consumers ack, un-acked messages are requeued.[4][5] Kafka: events are appended to partitions, ordered per partition, "not deleted after consumption", and consumers track an offset they can rewind.[3][6] So RabbitMQ fits task queues with flexible routing, retry and dead-lettering; Kafka fits multiple independent consumers, replay and per-key ordering. Both commonly give at-least-once delivery, so consumers must be idempotent. Throughput comparisons need your own benchmark; I have not cited any.

Likely follow-up: How do you guarantee ordering? (Kafka: same key, same partition, one consumer per partition in a group.[3])

Learn it: Queue versus log

6.Circuit breaker versus retry: how do they work together?

Short answer: retry repeats an operation expecting success; a breaker stops calling when failure is likely; use retries through a breaker and stop retrying when it is open.

Closed counts failures; Open fails fast; Half-Open lets a few trial calls through and returns to Closed on success or Open on failure.[7] My demo: after 3 failures the service received no further calls until the timeout.

Likely follow-up: Do you need one when using a message queue with a DLQ? (Often not, per the docs' not-suitable list.)

Learn it: Circuit breaker

7.What is a bulkhead and why do you want one?

Short answer: separate resource pools per dependency so a slow one cannot starve the rest.

[8] My demo: healthy calls took about 2010 ms behind slow ones in a shared pool and about 20 ms with separate pools.

Likely follow-up: How do containers relate? (Resource limits are bulkheads.)

Learn it: Bulkhead

8.How do you design a rate limiter? What should a client do when throttled?

Short answer: control the send rate (for example a token bucket); respect 429 with Retry-After; avoid naive retries.

[9] The docs' example shows blind retries sending 30,000 records for 10,000. My token bucket allowed a burst of 5 and then about the refill rate.

Likely follow-up: Distributed rate limits? (Coordinate through shared state; the docs describe lease-based partitioning of capacity.)

Learn it: Rate limiting

9.What is queue-based load leveling and competing consumers?

Short answer: a queue buffers bursts so the service works at its own pace; multiple consumers on one queue each take different messages.

[10] [11] Watch queue growth, idempotence, poison messages and ordering. My demo absorbed a 100-task burst instantly while the service never exceeded 2 concurrent tasks.

Likely follow-up: Ordering? (Not guaranteed with parallel consumers.)

Learn it: Load leveling

10.Explain the saga pattern and the transactional outbox. Why not two-phase commit?

Short answer: a saga chains local transactions with compensations across services; the outbox writes the event in the same transaction as the data so publishing is not lost.

Sagas: choreography or orchestration, pivot and retryable steps, no isolation (anomalies).[12] Outbox: solves the dual-write problem; relay publishes at least once, so consumers are idempotent.[13] The saga docs describe traditional transaction models like two-phase commit as often poorly suited to independently managed data stores.[12]

Likely follow-up: How do you compensate an email already sent? (Some steps are not compensable: pivot/irreversible, see the docs.)

Learn it: Saga

11.How do you shard a database and choose a shard key?

Short answer: pick an immutable, high-cardinality key aligned with your queries; choose lookup, range, hash or geographic strategy; prefer consistent hashing when shard count changes.

[14] My demo: adding a fifth shard moved 80.1 percent of keys with hash-mod-N and 18.2 percent with consistent hashing.

Likely follow-up: Cross-shard transactions? (Avoid; eventual consistency and sagas.)

Learn it: Sharding

Scenario prompts (practice out loud)

These integrate the stacks in this course. There is no single right answer; state assumptions and trade-offs.

  1. Design an order service: Spring Boot API, PostgreSQL storage, events to Kafka, deployed on Kubernetes. Where are the transaction boundaries? How do you avoid losing or duplicating events? (Start from the transaction lessons and delivery semantics.)
  2. Logs from 200 pods must be searchable within seconds. Choose components and explain delivery guarantees and duplicate handling. (ELK ladder.)
  3. A downstream payment API is flaky. Design retries, timeouts, and a dead-letter path. (Dead letter exchanges, retries.)
  4. The service is OOM-killed under load. Walk through JVM, container and Kubernetes settings. (Requests, limits and the JVM.)
