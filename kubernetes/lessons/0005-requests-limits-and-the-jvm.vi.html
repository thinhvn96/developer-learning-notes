Request, limit và JVM

Kubernetes · Bài 0005 · bước 9/15 · Advanced · ~12 phút · Trang chủ · Lộ trình Kubernetes · Lộ trình tổng · English

Thành quả hôm nay: đặt request và limit cho một container JVM sao cho nó được lập lịch đúng, không bị OOM-kill, và không bị bất ngờ vì CPU throttling.

Request và limit

Request là lượng tài nguyên container được đảm bảo, và "scheduler dùng request để quyết định node nào có thể chứa một Pod." Limit là mức tối đa nó được dùng, do kubelet thực thi.[1] CPU tính bằng core hoặc millicore (500m = 0.5 CPU); memory tính bằng byte (256Mi).[1]

Chuyện gì xảy ra khi vượt ngưỡng

  • CPU vượt limit: bị kernel throttle.[1]
  • Memory vượt limit: container có thể bị OOM-kill; việc thực thi mang tính phản ứng, xảy ra khi kernel phát hiện áp lực bộ nhớ.[1]

Nếu bạn đặt limit mà không đặt request, Kubernetes dùng limit làm request.[1]

Áp dụng cho Java

env:
- name: JAVA_TOOL_OPTIONS
  value: "-XX:MaxRAMPercentage=70"
resources:
  requests: { memory: "512Mi", cpu: "250m" }
  limits:   { memory: "512Mi", cpu: "1" }

JVM trên Linux mặc định nhận diện được limit của container, và MaxRAMPercentage đặt kích thước heap theo phần trăm của lượng memory đó.[2] Đặt 70 là để chừa chỗ cho memory ngoài heap (non-heap). (Bài Docker đã đo điều này bằng docker run --memory; cơ chế nhận diện của JVM ở đây cũng y hệt vì chính container runtime là thứ thực thi limit.) Con số 70 là điểm xuất phát để đo đạc, không phải quy tắc. Bản phác thảo đầy đủ nằm trong java-service.yaml.

Đã kiểm chứng: một lần OOM kill

kubectl apply -f examples/memory-hog.yaml     # limit 20Mi, container runs: tail /dev/zero
NAME         READY   STATUS      RESTARTS   AGE
memory-hog   0/1     OOMKilled   0          12s
reason=OOMKilled exit=137

Exit code 137 là 128 + 9 (SIGKILL). Xem memory-hog.yaml.

Câu hỏi senior: "Memory request có nên bằng memory limit không?" Đặt bằng nhau giúp lượng memory sử dụng dễ dự đoán và tránh việc node over-commit phần memory mà Pod có thể cần; tài liệu giải thích rằng request quyết định việc lập lịch còn limit quyết định việc thực thi.[1] Hãy nêu ra trade-off, đừng trả lời bằng khẩu hiệu.

Đã kiểm chứng: tôi đã apply các manifest trong examples/ lên một cluster kind dùng xong bỏ (Kubernetes v1.37.0, kubectl v1.37.1) và trích output từ lần chạy đó. Bản thân việc cài kind không nằm trong các trang tôi đã đọc; hãy làm theo tài liệu của chính dự án đó.

Luyện truy hồi

Trả lời theo trí nhớ. Mỗi câu chỉ một lần chọn.

1. Scheduler dựa vào gì để đặt một Pod?

Scheduler dùng request để quyết định node nào có thể chứa một Pod.[1]

2. Một container vượt CPU limit. Kết quả?

CPU limit được thực thi bằng cách throttle.[1]

3. Một container vượt memory limit. Kết quả?

Memory limit được thực thi bằng OOM kill.[1]

4. Vì sao MaxRAMPercentage nên dưới 100?

JVM dùng cả memory ngoài heap, và heap cộng phần đó phải nằm gọn dưới limit.
