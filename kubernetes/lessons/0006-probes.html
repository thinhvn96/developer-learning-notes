Liveness, readiness and startup probes

Kubernetes · Lesson 0006 · step 10 of 15 · Advanced · ~10 minutes · Home · Kubernetes ladder · Roadmap · Tiếng Việt

Today's win: pick the right probe for each job, and explain what a wrong probe does to a Java service that starts slowly.

Three probes, three consequences

ProbeQuestionOn failure[1]
LivenessIs it broken beyond recovery?the container is killed and restarted
ReadinessCan it take traffic now?removed from Service endpoints, not restarted
StartupHas it finished starting?liveness and readiness checks wait for it

The docs describe liveness probes for applications that "eventually transition to broken states, and cannot recover except by being restarted", and startup probes as protection for slow-starting containers.[1]

livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 3
  periodSeconds: 3

An HTTP probe succeeds on any status from 200 to 399.[1]

Why this matters for Java

A JVM app can take many seconds to start. A liveness probe that begins too early kills it before it is up, and it restarts in a loop. That follows from the liveness rule above; the fix the docs offer is a startup probe. The sketch in java-service.yaml uses all three probes.

Verified on a cluster

kubectl apply -f examples/probe-demo.yaml
liveness-demo    1/1 Running  ...  Warning Unhealthy: Liveness probe failed: cat: can't open '/tmp/healthy'
                                    Normal  Killing:   Container app failed liveness probe, will be restarted
readiness-demo   0/1 Running          # never Ready
kubectl get endpoints readiness-demo   # ENDPOINTS: (empty)

After the liveness failure the restart happened about 30 s later (RESTARTS 1, last exit code 137): the container's shell (PID 1) did not react to SIGTERM, so Kubernetes waited out the default terminationGracePeriodSeconds of 30 before killing it. That is the signal-handling point from the Docker hardening lesson, seen for real. Files: probe-demo.yaml.

Design rule for interviews: keep liveness cheap and independent of dependencies. If liveness fails when the database is down, restarting your Pods cannot fix it. Use readiness for "can I serve?".

Verified: I applied the manifests in examples/ to a throwaway kind cluster (Kubernetes v1.37.0, kubectl v1.37.1) and quote outputs from that run. The kind setup itself is not covered by the pages I read; follow the project's own docs.

Retrieval practice

Answer from memory. One attempt each.

1. Liveness probe fails. What happens?

Kubernetes kills and restarts the container.[1]

2. Readiness probe fails. What happens?

The container is removed from service endpoints but not restarted.[1]

3. Slow-starting JVM keeps restarting. Add which probe?

Startup probes delay liveness and readiness checks until initialization completes.[1]

4. HTTP probe returns 204. Result?

Any status from 200 up to 399 counts as success.[1]
