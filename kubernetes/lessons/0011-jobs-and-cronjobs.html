Jobs and CronJobs

Kubernetes · Lesson 0011 · step 8 of 15 · Core · ~10 minutes · Home · Kubernetes ladder · Roadmap

Today's win: choose Job versus CronJob, set restartPolicy and backoffLimit, and explain why scheduled jobs must be idempotent.

Job

A Job "creates one or more Pods and will continue to retry execution of the Pods until a specified number of them successfully terminate". Requirements: restartPolicy must be Never or OnFailure; backoffLimit defaults to 6; completions and parallelism default to 1.[1]

CronJob

"Creates Jobs on a repeating schedule", one object per crontab line, with standard cron syntax (0 3 * * 1 = Mondays at 03:00). concurrencyPolicy: Allow (default), Forbid (skip if the previous run is still going), Replace.[2]

Caveat: "in certain circumstances, a single CronJob can create multiple concurrent Jobs, even with Forbid", so Jobs "should be idempotent".[2]

kubectl apply -f examples/job-cronjob.yaml
hello-job  Complete  1/1  3s          logs: job ran on hello-job-pr6rb
nightly    0 3 * * *   SUSPEND False  ACTIVE 0
kubectl create job manual-run --from=cronjob/nightly   -> logs: generating report

The last command is the handy way to test a CronJob without waiting for its schedule. File: job-cronjob.yaml. Same idempotency theme as retries.

Retrieval practice

Answer from memory. One attempt each.

1. Allowed restartPolicy for a Job?

restartPolicy must be Never or OnFailure.[1]

2. Default backoffLimit?

The default backoffLimit is 6.[1]

3. Which policy skips a run if the last is active?

Forbid does not allow concurrent runs.[2]

4. Why must CronJob work be idempotent?

A CronJob can create multiple concurrent Jobs in some circumstances.[2]
