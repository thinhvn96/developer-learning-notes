Secrets: what they protect and what they do not

Kubernetes · Lesson 0010 · step 7 of 15 · Core · ~10 minutes · Home · Kubernetes ladder · Roadmap · Tiếng Việt

Today's win: say precisely how safe a Secret is by default and list the steps that make it safer.

What a Secret is

A Secret holds "a small amount of sensitive data such as a password, a token, or a key", so it need not go into a Pod spec or image. Like ConfigMaps, but "specifically intended to hold confidential data".[1]

The catch

"Kubernetes Secrets are, by default, stored unencrypted in the API server's underlying data store (etcd). Anyone with API access can retrieve or modify a Secret, and so can anyone with access to etcd." The values are base64-encoded, and base64 is not encryption.[1]

kubectl get secret db-credentials -o jsonpath='{.data.DB_PASSWORD}'            -> czNjcmV0
kubectl get secret db-credentials -o jsonpath='{.data.DB_PASSWORD}' | base64 -d -> s3cret

Minimum hygiene (from the docs)

  1. Enable encryption at rest for Secrets.
  2. Enable RBAC with least-privilege access to Secrets.
  3. Restrict access to specific containers.
  4. Consider external secret store providers.[1]

Example in configmap-secret.yaml: the Pod printed DB_PASSWORD=s3cret from the Secret. Compare the Docker advice not to bake secrets into ENV (Dockerfile lesson).

Verified: I applied the manifests in examples/ to a throwaway kind cluster (Kubernetes v1.37.0, kubectl v1.37.1) and quote outputs from that run. The kind setup itself is not covered by the pages I read; follow the project's own docs.

Retrieval practice

Answer from memory. One attempt each.

1. How are Secrets stored by default?

They are stored unencrypted in etcd by default.[1]

2. Is base64 encryption?

Base64 is encoding and provides no protection.[1]

3. One recommended safeguard?

Enable encryption at rest for Secrets.[1]

4. Who can read a Secret via the API?

Anyone with API access can retrieve a Secret unless RBAC restricts it.[1]
