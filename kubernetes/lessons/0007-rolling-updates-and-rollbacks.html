Rolling updates and rollbacks

Kubernetes · Lesson 0007 · step 11 of 15 · Advanced · ~10 minutes · Home · Kubernetes ladder · Roadmap

Today's win: describe how a rolling update works, what the default surge and unavailability are, and how to roll back.

Rolling update

A Deployment updates Pods gradually: it scales up a new ReplicaSet while scaling down the old one. The default strategy uses maxUnavailable: 25% and maxSurge: 25%.[1] maxSurge caps how many extra Pods may exist above the desired count during the update; maxUnavailable caps how many may be unavailable.

strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 25%
    maxSurge: 25%

Rollback

kubectl rollout undo deployment/nginx-deployment

rolls back to the previous revision.[1]

How probes make updates safe

During a rolling update, traffic should reach a new Pod only when it is ready. That is the job of the readiness probe from the previous lesson.

Verified: a bad release

kubectl set image deployment/nginx-deployment nginx=nginx:does-not-exist
kubectl rollout status ... --timeout=25s   -> error: timed out waiting for the condition
nginx-deployment-54fd...-4l88k  1/1 Running           # 3 old Pods kept
nginx-deployment-54fd...-hrldm  1/1 Running
nginx-deployment-54fd...-kqvcf  1/1 Running
nginx-deployment-5fb7...-q7v2l  0/1 ImagePullBackOff  # 1 new Pod, stuck
kubectl get endpoints nginx-service        -> the 3 old Pod addresses only
kubectl rollout undo deployment/nginx-deployment   -> rolled back; stuck Pod terminates

The rollout stalled instead of taking the service down: with 3 replicas Kubernetes created just one extra Pod and kept all three old ones serving, and the Service endpoints never changed.

Interview angle: "Zero-downtime deploy of a Java service?" Rolling update, readiness probe, a startup probe for slow boots, graceful shutdown on SIGTERM (see the Docker lesson on exec-form CMD), and a rollback plan.

Retrieval practice

Answer from memory. One attempt each.

1. Default rolling update numbers?

Default maxUnavailable and maxSurge are both 25 percent.[1]

2. Command to revert a bad release?

kubectl rollout undo deployment/name rolls back.[1]

3. What does maxSurge control?

It caps how many Pods may exist above the desired count during an update (see the Deployment docs).

4. Which probe gates traffic to new Pods?

Readiness decides whether a Pod receives Service traffic (probes lesson).
