Ingress: HTTP routing into the cluster

Kubernetes · Lesson 0014 · step 14 of 15 · Advanced · ~10 minutes · Home · Kubernetes ladder · Roadmap

Today's win: explain what Ingress does, why you need a controller, and why the docs now point to the Gateway API.

What it is

"Ingress exposes HTTP and HTTPS routes from outside the cluster to services within the cluster." Rules on the Ingress control routing. It can provide load balancing, TLS termination and name-based virtual hosting.[1] Each rule has an optional host and a list of paths, each with a backend Service name and port; host and path must both match.[1]

spec:
  ingressClassName: nginx-example
  rules:
  - http:
      paths:
      - path: /testpath
        pathType: Prefix
        backend: { service: { name: nginx-service, port: { number: 80 } } }

The controller requirement

"You must have an Ingress controller to satisfy an Ingress. Simply creating an Ingress resource has no effect."[1]

kubectl apply -f examples/ingress.yaml
NAME              CLASS           HOSTS   ADDRESS   PORTS   AGE
minimal-ingress   nginx-example   *                 80      20s      # ADDRESS empty: no controller

The object was accepted but got no address on my cluster, which has no Ingress controller installed. Also note: the docs recommend the Gateway API instead, saying the Ingress API "has been frozen since Kubernetes v1.19".[1] Compare Services: Ingress routes HTTP to Services. File: ingress.yaml.

Verified: I applied the manifests in examples/ to a throwaway kind cluster (Kubernetes v1.37.0, kubectl v1.37.1) and quote outputs from that run. The kind setup itself is not covered by the pages I read; follow the project's own docs.
