Kubernetes: interview questions and answers

Kubernetes questions for Senior backend interviews, framed around running a Java service. Note: no cluster was available while writing this course, so the manifests were syntax-checked but not applied.

Try answering out loud first, then open the answer. Superscript links go to the source that backs the claim.

1.Describe the Kubernetes architecture.

Short answer: a control plane (API server, etcd, scheduler, controller manager) and nodes (kubelet, kube-proxy, container runtime).

  • kube-apiserver: exposes the Kubernetes HTTP API.
  • etcd: consistent, highly available key-value store for all API server data.
  • kube-scheduler: assigns Pods not yet bound to a node to a suitable node.
  • kube-controller-manager: runs controllers implementing API behavior.
  • kubelet: ensures Pods and their containers are running.
  • kube-proxy: maintains network rules on nodes to implement Services.
  • Container runtime: runs containers.[1]

Kubernetes is declarative: you state desired state, controllers work toward it.[2]

Likely follow-up: Walk me through what happens on kubectl apply. (API server stores the object in etcd; controllers create dependent objects; scheduler binds Pods to nodes; kubelet starts containers via the runtime.)

Learn it: Cluster components

2.What is a Pod? Why not run bare Pods?

Short answer: the smallest deployable unit: one or more co-located containers sharing storage and network; Pods are disposable, so use a workload resource.

A Pod's contents are always co-located and co-scheduled and run in a shared context. Pods are "relatively ephemeral, disposable entities"; they stay on their node until finished, deleted, evicted for lack of resources, or the node fails. "You rarely create Pods directly": use Deployments, Jobs or StatefulSets.[3]

Likely follow-up: When would you use a multi-container Pod? (Tightly coupled helper containers, an advanced pattern; most Pods have one container.[3])

Learn it: Pods

3.How do Deployments, ReplicaSets and Pods relate? What ties them together?

Short answer: a Deployment manages ReplicaSets, which manage Pods; labels and selectors tie them.

A Deployment provides declarative updates for Pods and ReplicaSets; you describe desired state and the controller moves actual state toward it at a controlled rate. .spec.selector.matchLabels must match the labels in the Pod template.[4]

Likely follow-up: Deployment vs StatefulSet? (Deployments suit workloads that usually do not maintain state; StatefulSets are for stateful ones.[4][3])

Learn it: Deployments and labels

4.How do Services work, and what are the types?

Short answer: a Service is a stable endpoint for a changing set of Pods, selected by labels.

Pods are ephemeral with changing IPs; a Service exposes them over the network and finds them by selector, keeping EndpointSlices up to date. Types: ClusterIP (default, in-cluster only), NodePort (each node's IP at a static port), LoadBalancer (cloud load balancer), ExternalName (maps to an external DNS name). port is what the Service exposes; targetPort is the container port.[6]

Likely follow-up: Service can't reach Pods. What do you check? (Labels versus selector, endpoints list, port and targetPort, and readiness state; readiness failure removes a Pod from endpoints.[5])

Learn it: Services

5.Requests vs limits: what happens when a container exceeds each?

Short answer: requests drive scheduling; limits are enforced at runtime; CPU over limit is throttled, memory over limit can be OOM-killed.

Requests are what a container is guaranteed and what the scheduler uses to choose a node; limits are the maximum, enforced by the kubelet. CPU is enforced by throttling; memory by OOM kills, reactively when the kernel detects memory pressure. CPU uses cores or millicores (500m), memory bytes (256Mi). If you set a limit but no request, the limit becomes the request.[7]

Likely follow-up: Should request equal limit? (Discuss predictability versus utilization; equal memory values give predictable footprints. State the trade-off, not a slogan.)

Learn it: Requests, limits and the JVM

6.How do you configure a Java service's memory in Kubernetes?

Short answer: set memory request and limit, and set the JVM heap as a percentage of the limit below 100.

The JVM detects container limits on Linux by default and -XX:MaxRAMPercentage sizes the heap as a percentage of the memory it sees (default 25 percent).[8] With a 512Mi limit and MaxRAMPercentage=70 the heap can reach about 358 MiB, leaving the rest for metaspace, thread stacks and buffers. Verify under load; the memory limit is enforced by OOM kill.[7]

Likely follow-up: Pod restarts with OOMKilled but heap dumps look small. Why? (Non-heap memory pushed total above the limit.)

Learn it: Requests, limits and the JVM

7.Explain liveness, readiness and startup probes. What goes wrong with a slow-starting Spring Boot app?

Short answer: liveness failure restarts the container; readiness failure removes it from Service endpoints; startup delays the other two.

Liveness detects broken states that cannot recover except by restart; readiness controls traffic without restarting; startup protects slow-starting containers. HTTP probes succeed on status 200 to 399.[5] If liveness begins before the JVM finishes starting, the kubelet restarts the container repeatedly (a crash loop); a startup probe with a generous failure threshold fixes it. Keep liveness cheap and independent of downstream dependencies; use readiness for "can I serve now?".

Likely follow-up: Should liveness check the database? (Generally no: restarting the app cannot fix a database outage; use readiness.)

Learn it: Probes

8.How does a rolling update work and how do you roll back?

Short answer: the Deployment scales a new ReplicaSet up while scaling the old one down within maxSurge and maxUnavailable (both 25 percent by default); kubectl rollout undo reverts.

These defaults and the command come from the Deployment docs.[4] Readiness probes decide when new Pods receive traffic, so a broken release stalls instead of taking traffic (the probe docs define the readiness behavior[5]). For zero-downtime Java deploys also handle SIGTERM gracefully (exec-form CMD, shutdown hooks) and size maxUnavailable deliberately.

Likely follow-up: How do you release a risky change safely? (Beyond the sources read here: canary/blue-green are common answers; check the Deployment docs and your platform tooling.)

Learn it: Rolling updates and rollbacks

9.How do you pass configuration and secrets to a Pod? Are Secrets secure?

Short answer: ConfigMaps for non-confidential settings, Secrets for confidential ones, both as env vars or mounted files; Secrets are only base64 by default, so add encryption at rest and RBAC.

ConfigMaps (1 MiB max) can be consumed as command args, env vars or volume files; env vars do not update in running containers, mounted files eventually do.[9] Secrets are "by default, stored unencrypted in ... etcd", base64 is not encryption; enable encryption at rest, least-privilege RBAC, restrict access, consider external secret stores.[10] Verified on kind: the Pod printed DB_PASSWORD=s3cret and base64 -d decoded the stored value.

Likely follow-up: How do you roll out a config change to env-var consumers? (Restart the Pods, for example by a Deployment rollout.)

Learn it: ConfigMaps

10.What is a namespace for, and what is not a good use of one?

Short answer: isolating groups of resources; not for distinguishing versions (use labels).

[11] Names are unique per namespace; namespaces are not nested; PersistentVolumes and Nodes are cluster-scoped. Everyday symptom: kubectl get pod hello said "not found" because the Pod was in demo.

Likely follow-up: How do you limit what a team can consume? (Resource quotas per namespace; not covered by the pages read here.)

Learn it: Namespaces

11.Job versus CronJob, and what must you remember about scheduled work?

Short answer: Job runs Pods to completion with retries; CronJob creates Jobs on a schedule; make the work idempotent.

Jobs need restartPolicy Never or OnFailure, default backoffLimit 6.[12] CronJobs use cron syntax and concurrencyPolicy Allow/Forbid/Replace, and can still create concurrent Jobs in some circumstances, so Jobs "should be idempotent".[13] I tested a manual run with kubectl create job --from=cronjob/nightly.

Likely follow-up: A nightly job overruns into the next night. What do you set? (concurrencyPolicy Forbid or Replace.)

Learn it: Jobs and CronJobs

12.Explain PersistentVolume, PersistentVolumeClaim and StorageClass. What happens to data when a Pod is deleted?

Short answer: a PVC requests storage that a PV (often dynamically provisioned via a StorageClass) satisfies; data outlives Pods; the reclaim policy decides what happens when the claim is deleted.

[14] Access modes ReadWriteOnce, ReadOnlyMany, ReadWriteMany, ReadWriteOncePod; reclaim Retain or Delete. On kind, a PVC bound dynamically (StorageClass standard) and a second Pod on the same claim read the first Pod's data.

Likely follow-up: Which reclaim policy for production databases? (Discuss Retain versus Delete trade-offs.)

Learn it: Persistent volumes

13.Deployment versus StatefulSet?

Short answer: StatefulSets add stable identity, stable storage and ordered operations; Deployments suit stateless workloads.

[15] Requires a headless Service; scaling down or deleting does not delete volumes. On kind: Pods came up in order (web-0 then web-1), each had its own PVC, deleting web-0 recreated it with the same name and its data, and scale-down kept data-web-1. It does not replicate data by itself.

Likely follow-up: Would you run PostgreSQL in a StatefulSet? (Discuss operators and replication; beyond the sources read.)

Learn it: StatefulSets

14.How do you expose HTTP services outside the cluster?

Short answer: Service types (NodePort, LoadBalancer) or an Ingress with a controller; the docs now recommend the Gateway API.

[16] Ingress rules match host and path to Service backends; without a controller "creating an Ingress resource has no effect": my Ingress had an empty ADDRESS on a cluster with no controller. The Ingress API has been frozen since v1.19.

Likely follow-up: TLS termination? (Ingress can provide it; details beyond the excerpts.)

Learn it: Ingress

15.How does the Horizontal Pod Autoscaler compute replicas and what does it need?

Short answer: ceil(current x currentMetric / desiredMetric); needs resource requests and a metrics source.

[17] Example: 3 Pods at 90 percent against a 70 percent target gives ceil(3 x 90/70) = 4. On kind without a metrics server, the HPA showed cpu: <unknown>/70% and did nothing.

Likely follow-up: Why is CPU request important for HPA? (Utilization is computed against the request.)

Learn it: HPA
