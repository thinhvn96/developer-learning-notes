RabbitMQ: interview questions and answers

RabbitMQ questions for Senior backend interviews, from the AMQP model to reliability. Outputs quoted come from the example script run against a throwaway rabbitmq:4-management container.

Try answering out loud first, then open the answer. Superscript links go to the source that backs the claim.

1.Explain the RabbitMQ (AMQP 0-9-1) model.

Short answer: publishers send to exchanges; exchanges route copies to queues via bindings; consumers read from queues.

"Messages are published to exchanges ... Exchanges then distribute message copies to queues using rules called bindings." Consumers get messages from queues by subscription (push) or polling (discouraged). The default exchange is a nameless direct exchange that binds each new queue with the queue name as routing key.[1]

Likely follow-up: What happens to an unroutable message? (My example's API returned routed:false; publishers should detect it. See publisher confirms and handling in the docs.)

Learn it: AMQP model

2.Direct vs fanout vs topic vs headers exchanges?

Short answer: exact key, broadcast, pattern, header values.

Direct routes by exact routing-key match (unicast); fanout copies to all bound queues ignoring the key; topic matches routing-key patterns; headers routes on header values.[1] In my run: a direct binding error received only error; fanout copied to both queues; topic pattern orders.eu.* received orders.eu.created but not orders.us.created.

Likely follow-up: Design routing for audit + regional queues. (Fanout for audit, topic for regions.)

Learn it: Exchange types

3.How do acknowledgements work? What if a consumer crashes?

Short answer: the consumer acks after processing; un-acked deliveries are requeued if the consumer disconnects.

basic.ack, basic.nack, basic.reject identify deliveries by tag; multiple=true acknowledges all outstanding tags up to that one. "Any delivery that was not acked is automatically requeued", flagged redelivered, so consumers "be implemented with idempotence in mind". Automatic ack "should be considered unsafe".[2] My run: first get redelivered=false, after requeue redelivered=true.

Likely follow-up: What is prefetch and what value do you pick? (Limits unacked messages; 0 is unlimited; docs suggest 100 to 300 for throughput, lower for fairness.[2])

Learn it: Acks and prefetch

4.How do you make sure a message is not lost?

Short answer: durable queue + persistent message + publisher confirms + manual consumer acks (+ replicated queue).

"Both the queue and messages must be marked durable" to avoid data loss on restart.[1] Publisher confirms make the broker acknowledge receipt asynchronously with basic.ack (or basic.nack if it cannot take responsibility).[2] On the consumer side use manual acks. For node failure use a replicated queue: quorum queues, based on Raft, are the recommended default for replicated queues.[3]

Likely follow-up: What about messages published to a non-existent binding? (Unroutable; detect with return or confirm handling.)

Learn it: Publisher confirms

5.What is a dead letter exchange and when is a message dead-lettered?

Short answer: an exchange that receives messages a queue gave up on: rejected with requeue=false, TTL expired, queue length exceeded, or quorum delivery limit exceeded.

Configure with a policy (dead-letter-exchange, optional routing key) or queue arguments (x-dead-letter-exchange); policies are preferred because they can change without redeploying applications.[4]

Likely follow-up: How do you build a delayed retry? (TTL retry queue that dead-letters back to the main exchange; guard against infinite loops.)

Learn it: Dead letter exchanges

6.Quorum queues vs classic queues? How do you handle poison messages?

Short answer: quorum queues are replicated (Raft) and the default choice for HA; use a delivery limit and DLX for poison messages.

"Quorum queues should be considered the default choice when needing a replicated, highly available queue"; classic mirroring was removed in RabbitMQ 4.0. They track redeliveries in x-delivery-count and apply a default delivery limit of 20; past it a message is discarded or dead-lettered if a DLX is configured. At-least-once dead lettering retains dead-lettered messages until acknowledged.[3][4] Consumers still need to be idempotent.

Likely follow-up: Where do quorum queues not fit? (Temporary queues and some transient use cases per the docs.[3])

Learn it: Quorum queues

7.RabbitMQ versus Kafka?

Short answer: queue of work items versus durable log of events.

See the system-design comparison: RabbitMQ has exchanges, acks and DLX; Kafka retains events after consumption and lets consumers rewind offsets. Pick by the semantics you need and back it with a benchmark.

Likely follow-up: Can you use both? (Yes; typical when you need routing/tasks and an event log.)

Learn it: Queue versus log

8.How does message TTL work?

Short answer: x-message-ttl per queue or expiration per message; the lower wins; expired messages can be dead-lettered.

[5] Caveat for classic queues with per-message TTL: expired messages behind live ones are only discarded at the head. My run: a queue with TTL 2000 ms and a DLX moved both messages to the dead-letter queue within 4 s.

Likely follow-up: Build a delayed retry? (TTL queue dead-lettering back to the main exchange.)

Learn it: Message TTL

9.What is a RabbitMQ stream and how is it different from a queue?

Short answer: an append-only replicated log with non-destructive reads and replay from an offset.

[6] Good for large fan-outs, replay, throughput and large backlogs; consumers choose x-stream-offset (first, last, offset, timestamp). In my run basic.get was rejected for a stream queue.

Likely follow-up: Stream or Kafka topic? (They overlap; compare operational fit and ecosystem.)

Learn it: Streams

10.How does RabbitMQ clustering work, and why odd node counts?

Short answer: nodes share definitions; classic queues live on one node unless you use a replicated type; odd node counts give a majority for consensus.

[7] In my three-node run, stopping the node hosting both queues left the classic queue unavailable while the quorum queue still held its 3 messages.

Likely follow-up: Why avoid two-node clusters? (No majority after a partition.)

Learn it: Clustering
