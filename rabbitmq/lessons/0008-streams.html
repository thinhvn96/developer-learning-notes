Streams: an append-only log inside RabbitMQ

RabbitMQ · Lesson 0008 · step 8 of 9 · Advanced · ~10 minutes · Home · RabbitMQ ladder · Roadmap · Tiếng Việt

Today's win: explain how a stream differs from a queue (non-destructive reads, replay) and when to choose one.

What it is

A stream is "a persistent replicated data structure that can complete the same tasks as queues" but with an append-only log and "non-destructive consumer semantics". Queues delete messages when consumed; streams keep them until retention applies, so many consumers can read the same messages independently.[1]

When to choose streams

  1. Large fan-outs: many subscribers reading the same messages without a queue per consumer.
  2. Replay: consumers attach at any point of the log.
  3. Throughput higher than traditional persistent queues.
  4. Large backlogs held cheaply.[1]

Consumers choose where to start with the x-stream-offset argument: first, last, a specific offset, a timestamp, or a time interval.[1]

What I observed

declare queue with x-queue-type=stream, publish 3 messages
rabbitmqctl list_queues -> q.stream  type=stream
basic.get against it -> {"error":"bad_request","reason":"540 basic.get not supported by stream queues"}

A stream is declared like a queue (x-queue-type: stream) but is consumed differently, with basic.consume and an offset, not basic.get. I could not demonstrate non-destructive replay with the HTTP tooling used here, so the replay behavior above is from the docs only. Compare with Kafka's log: queue versus log (streams make RabbitMQ overlap with that model). Source: 02-ttl-and-streams.sh.
