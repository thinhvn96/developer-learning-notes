MVCC

With Multiversion Concurrency Control "reading never blocks writing and writing never blocks reading": locks taken for querying do not conflict with locks taken for writing. Each statement sees a snapshot of the data.[1]

The four levels in PostgreSQL

Read committed is the default. PostgreSQL's Read uncommitted "behaves like Read Committed", and its Repeatable read does not allow phantom reads.[2] Serializable transactions may fail with "could not serialize access"; applications "must be prepared to retry transactions".[2]

Two sessions, live

cd postgresql/examples && ./06-isolation.sh

A first read : 100
A second read: 200       # B committed in between: a non-repeatable read
=== session A isolation level: REPEATABLE READ
A first read : 100
A second read: 100       # A keeps its snapshot

Retrieval practice

Answer from memory. One attempt each.

1. MVCC principle in PostgreSQL?

Reading never blocks writing and writing never blocks reading.[1]

2. Default PostgreSQL isolation level?

Read committed is the default.[2]

3. A re-read sees another session's committed change. Name?

A non-repeatable read finds data modified by a transaction that committed since the first read.[2]

4. Serializable transaction fails with a serialization error. Do what?

Applications must be prepared to retry serialization failures.[2]
