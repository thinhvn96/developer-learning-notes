Indexes: what they buy and what they cost

PostgreSQL · Lesson 0004 · step 7 of 13 · Core · ~10 minutes · Home · PostgreSQL ladder · Roadmap

Today's win: explain why an index makes a lookup fast, what it costs on writes, and prove it with a before/after plan.

Why an index helps

Without one, "the system would have to scan the entire table, row by row". With an index on the searched column, "it might only have to walk a few levels deep into a search tree."[1]

What it costs

"After an index is created, the system has to keep it synchronized with the table. This adds overhead to data manipulation operations." So "indexes that are seldom or never used in queries should be removed."[1]

Before and after (200,000 rows)

CREATE INDEX test1_id_index ON test1 (id);

   Index Cond: (id = 123456)
   Execution Time: 0.028 ms

Timings are from one run on this machine; the shape (a full scan reading every row versus a few tree hops) is the point. For deeper treatment of composite indexes, sorting and joins, the free web book Use The Index, Luke[2] covers PostgreSQL among other databases.

Retrieval practice

Answer from memory. One attempt each.

1. Query with no index on the filtered column?

Without an index the system scans the table row by row.[1]

2. What is the cost of an extra index?

The index must be kept in sync with the table, adding overhead to data changes.[1]

3. What should you do with an unused index?

Indexes seldom or never used should be removed.[1]

4. After CREATE INDEX, what did the plan show?

The lookup used test1_id_index in the example run.
