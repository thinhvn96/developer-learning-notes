Reading EXPLAIN and EXPLAIN ANALYZE

PostgreSQL · Lesson 0005 · step 10 of 13 · Advanced · ~12 minutes · Home · PostgreSQL ladder · Roadmap

Today's win: read a plan node (type, cost, rows), tell estimates from actuals, and use EXPLAIN ANALYZE safely on writes.

What EXPLAIN prints

A plan is a tree of nodes. Each shows a node type (Seq Scan, Index Scan...), a startup cost, a total cost, estimated rows, and estimated row width.[1] Costs are "arbitrary units"; by convention a sequential page fetch costs 1.0. A parent node's cost includes its children's costs.[1]

Seq Scan on tenk1  (cost=0.00..445.00 rows=10000 width=244)

EXPLAIN ANALYZE runs the query

EXPLAIN ANALYZE "actually executes the query" and adds real numbers: actual time, loops, buffer statistics, planning and execution time.[1] For data-changing statements, wrap it in a transaction and roll back:

BEGIN;
EXPLAIN ANALYZE UPDATE test1 SET content = 'changed' WHERE id < 100;
ROLLBACK;

The example script does exactly this and then counts rows still equal to 'changed': zero.

How to read one in an interview

  1. Find the most expensive node (costs accumulate upward).
  2. Compare rows= estimated with actual rows=; big gaps mean stale statistics or a poor estimate.
  3. Check the scan type: Seq Scan on a big table with a selective filter suggests a missing index; the docs note sequential scans are fine for small tables or large result sets.[1]

Caveat from the docs: plans from a small test table do not necessarily extrapolate to production scale.[1]

Retrieval practice

Answer from memory. One attempt each.

1. What unit are plan costs measured in?

Costs are in arbitrary units set by planner cost parameters.[1]

2. Does EXPLAIN ANALYZE run the statement?

It actually executes the query, including INSERT/UPDATE/DELETE.[1]

3. Safe way to analyze an UPDATE?

Use BEGIN, EXPLAIN ANALYZE, ROLLBACK.[1]

4. Estimated rows 10, actual rows 100000. Suspect?

Large estimate gaps point to bad statistics or estimation (senior-level reading habit; try ANALYZE).
