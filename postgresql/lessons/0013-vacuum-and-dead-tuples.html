VACUUM, dead tuples and autovacuum

PostgreSQL · Lesson 0013 · step 13 of 13 · Senior · ~12 minutes · Home · PostgreSQL ladder · Roadmap · Tiếng Việt

Today's win: explain why UPDATEs leave dead tuples, what VACUUM does, and why autovacuum is on by default.

Why vacuum exists

PostgreSQL's MVCC keeps old row versions so readers do not block writers.[2] Those versions must be cleaned. The docs give four reasons to vacuum: recover or reuse space of updated or deleted rows; update planner statistics; update the visibility map (speeds index-only scans); protect against transaction ID wraparound.[1]

Autovacuum

An optional but "highly recommended" feature that automates VACUUM and ANALYZE; in the default configuration it is enabled with appropriate parameters.[1]

Watch dead tuples appear

cd postgresql/examples && ./run.sh 12-vacuum.sql     # autovacuum disabled on the table for the demo
after 100k inserts:            n_dead_tup = 0
after UPDATE of every row:     n_live_tup = 100000, n_dead_tup = 100000   size 7872 kB
after VACUUM:                  n_dead_tup = 0
after DELETE + VACUUM FULL:    size 48 kB

Plain VACUUM marks dead space reusable; VACUUM FULL rewrites the table and shrinks the file (the size drop is from the run; its locking costs are beyond the pages read here, so check the docs before using it in production). Source: 12-vacuum.sql.

Retrieval practice

Answer from memory. One attempt each.

1. Why do updates create dead tuples?

MVCC keeps old row versions until they can be cleaned.[2]

2. One reason to VACUUM?

To recover or reuse disk space of updated or deleted rows.[1]

3. Autovacuum default state?

In the default configuration autovacuuming is enabled.[1]

4. VACUUM also protects against what?

It protects against transaction ID wraparound.[1]
