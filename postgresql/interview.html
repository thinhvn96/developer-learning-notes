PostgreSQL: interview questions and answers

Home · PostgreSQL · 14 questions · PostgreSQL ladder · Roadmap

PostgreSQL questions for Senior backend interviews, with the reasoning interviewers listen for. Numbers quoted (row counts, timings) come from my runs of the example scripts in a throwaway postgres:18 container.

Try answering out loud first, then open the answer. Superscript links go to the source that backs the claim.

1.Why put constraints in the database instead of only in application code?

Short answer: every writer must obey them, and they are atomic with the data; app-level checks race.

PostgreSQL supports CHECK, NOT NULL, UNIQUE, PRIMARY KEY (unique and not null, at most one per table) and FOREIGN KEY with ON DELETE RESTRICT or CASCADE.[1] My script showed each failing with a specific error. A "check then insert" in Java can be interleaved with another request; a unique constraint cannot, because the database enforces it during the write.

Likely follow-up: How do you handle the duplicate-key error in Java? (Catch the constraint violation and treat as 'already exists'; consider retry logic and idempotency.)

Learn it: Tables and constraints

2.What is the difference between INNER JOIN and LEFT JOIN, and what is the classic WHERE trap?

Short answer: inner keeps matches only; left keeps every left row with NULLs for the missing right side; a WHERE on right-table columns turns a left join back into an inner join.

Left outer join: "the table mentioned on the left of the join operator will have each of its rows in the output at least once"; unmatched rows get NULLs for right columns.[2] In my run, an inner join gave 2 rows, the left join 3, and adding WHERE cities.location IS NOT NULL gave 2 again. Move the condition into ON to keep the left rows.

Likely follow-up: Write a query for customers with no orders. (LEFT JOIN orders and WHERE orders.id IS NULL, or NOT EXISTS.)

Learn it: Joins

3.What is a window function and how do you get the top earner per department?

Short answer: a calculation across related rows that does not collapse them; use row_number() OVER (PARTITION BY dept ORDER BY salary DESC) in a subquery and filter rn = 1.

A window function computes across rows related to the current row without grouping them into one output row; OVER marks it, PARTITION BY splits groups, ORDER BY inside OVER orders within a partition.[3] Window functions cannot be filtered directly in WHERE, so wrap in a subquery. With ties (two employees at 4800) row_number() picks one arbitrarily; use rank() or dense_rank() when ties matter.

Likely follow-up: Difference between rank and dense_rank? (rank leaves gaps after ties, dense_rank does not; confirm in the docs' window function reference.)

Learn it: Window functions

4.When does an index help, and what does it cost?

Short answer: it speeds selective lookups, joins and search conditions; it costs write overhead and space.

Without an index the system scans the whole table row by row; with one it can "walk a few levels deep into a search tree." After creation "the system has to keep it synchronized with the table. This adds overhead to data manipulation operations", so unused indexes should be removed.[5] In my test on 200,000 rows a lookup went from a sequential scan (about 5 ms, removing 199,999 rows by filter) to an index scan (about 0.03 ms). For depth on composite indexes, sorting and joins see Use The Index, Luke.[6]

Likely follow-up: Why might PostgreSQL ignore your index? (Small table or non-selective condition can make a sequential scan cheaper; the EXPLAIN docs note seq scans are efficient for small tables or large result sets.[4])

Learn it: Indexes

5.How do you diagnose a slow query?

Short answer: EXPLAIN (ANALYZE), find the expensive node, compare estimated and actual rows, check scan type and indexes.

EXPLAIN shows a tree of plan nodes with startup cost, total cost, estimated rows and width; costs are arbitrary units and a parent includes its children.[4] EXPLAIN ANALYZE actually executes the query and adds actual time, loops, buffers and planning/execution time. For UPDATE/DELETE wrap it: BEGIN; EXPLAIN ANALYZE ...; ROLLBACK; (my script confirmed zero changed rows after rollback). Large gaps between estimated and actual rows suggest stale statistics (try ANALYZE). Plans from small test tables may not extrapolate to production.[4]

Likely follow-up: Is EXPLAIN ANALYZE safe on production writes? (Only inside a transaction you roll back; it really runs the statement.)

Learn it: Reading EXPLAIN

6.Explain MVCC.

Short answer: readers and writers do not block each other because each statement sees a snapshot.

"Reading never blocks writing and writing never blocks reading": locks acquired for querying do not conflict with locks for writing, even at the strictest isolation level (Serializable Snapshot Isolation).[7] Each SQL statement sees a snapshot of data as of some time ago.[7]

Likely follow-up: What is the cost of MVCC? (Old row versions must be cleaned up; the mechanics of vacuum are beyond the sources read here.)

Learn it: MVCC and isolation

7.List the isolation levels and anomalies. What is PostgreSQL's default?

Short answer: Read committed by default; Repeatable read prevents non-repeatable and phantom reads in PostgreSQL; Serializable prevents everything but may require retries.

Anomalies: dirty read, non-repeatable read, phantom read, serialization anomaly. PostgreSQL implements three distinct levels: Read uncommitted behaves like Read committed, and its Repeatable read does not allow phantom reads. Read committed is the default and a SELECT sees only data committed before the query began. Serializable can fail with "could not serialize access due to read/write dependencies", and applications "must be prepared to retry transactions."[8] My two-session demo showed a non-repeatable read under Read committed (100 then 200) and a stable snapshot under Repeatable read (100 then 100).

Likely follow-up: In Spring, how do you retry on serialization failure? (Retry the whole transaction; connect with the Spring @Transactional lessons.)

Learn it: MVCC and isolation

8.Two requests both check 'does username exist?' then insert. What goes wrong and how do you fix it?

Short answer: a race: both see 'not exists' and both insert; fix with a UNIQUE constraint (and handle the violation).

Under Read committed each statement sees data committed before it began, so two concurrent transactions can both see no row.[8] A UNIQUE or PRIMARY KEY constraint makes the second insert fail atomically.[1] Alternatively use Serializable and retry, but the constraint is simpler and cheaper.

Likely follow-up: What about INSERT ... ON CONFLICT? (A PostgreSQL feature worth knowing; check the docs before relying on details, not covered in the sources I read.)

Learn it: Tables and constraints

9.WHERE versus HAVING?

Short answer: WHERE filters rows before grouping; HAVING filters groups after aggregation.

"WHERE selects input rows before groups and aggregates are computed ... whereas HAVING selects group rows after"; aggregates are not allowed in WHERE (PostgreSQL answered aggregate functions are not allowed in WHERE in my run); use a subquery for "rows equal to the max".[9]

Likely follow-up: Cities whose maximum low temperature is under 40? (GROUP BY city HAVING max(temp_lo) < 40.)

Learn it: Aggregates

10.What does a transaction guarantee? How do you undo part of one?

Short answer: all-or-nothing; savepoints allow partial rollback.

Bundled steps are all-or-nothing and intermediate states are invisible to others; statements outside BEGIN are implicit transactions; ROLLBACK TO savepoint discards only later work and the savepoint stays defined.[10] In my run an error inside a block aborted it, and the later COMMIT was answered with ROLLBACK, leaving balances unchanged.

Likely follow-up: How does Spring map NESTED propagation? (To savepoints on JDBC.)

Learn it: Transactions

11.When do you use a CTE, and what is a recursive CTE?

Short answer: to name intermediate results; recursive CTEs walk hierarchies.

CTEs are like temporary tables for one query; recursive ones have a non-recursive term, UNION [ALL], and a recursive term, looping until no rows are produced; a side-effect-free CTE used once is inlined, MATERIALIZED forces separate evaluation.[11] My example listed a manager chain: dev, lead, vp, ceo.

Likely follow-up: How do you prevent infinite recursion on cyclic data? (Track visited ids or depth; the exercise asks for it.)

Learn it: CTEs

12.Which index types does PostgreSQL offer and when would you pick each? Multicolumn and partial indexes?

Short answer: B-tree default (equality and ranges), hash (equality), GIN (arrays, full-text), BRIN (physically correlated big tables), GiST/SP-GiST (geometry etc.).

[12] Multicolumn B-trees work best with equality on leading columns plus a range on the next; more than three columns is rarely helpful.[13] A partial index covers a predicate, avoiding indexing common values (mine: 64 kB versus 1352 kB for a multicolumn index).[14] The docs also note a skip-scan optimization for few distinct leading values; my second-column-only query still used the index, consistent with that.

Likely follow-up: You added an index but the planner ignores it. Why? (Low selectivity or small table; check EXPLAIN and statistics.)

Learn it: Multicolumn and partial indexes

13.What is SELECT ... FOR UPDATE and how do deadlocks arise and get fixed?

Short answer: it locks the selected rows against other writers; deadlocks come from opposite lock order and are detected and aborted by PostgreSQL; fix with a consistent order and retries.

[15] My two-session run: the second writer waited about 2.1 s on the locked row; opposite update order produced ERROR: deadlock detected for one session while the other committed.

Likely follow-up: Implement a job queue with row locks? (Beyond the pages read here; SKIP LOCKED is not covered by the sources I fetched.)

Learn it: Row locks

14.What is VACUUM for, and what are dead tuples?

Short answer: reclaim space from old row versions, update statistics and the visibility map, and prevent transaction ID wraparound; autovacuum does it by default.

[16] MVCC keeps old row versions, so an UPDATE of every row left 100,000 dead tuples and doubled the file until VACUUM cleaned them (my run, autovacuum disabled on that table).

Likely follow-up: Why should you not disable autovacuum? (It is enabled by default and highly recommended by the docs.)

Learn it: VACUUM
