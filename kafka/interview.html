Kafka: interview questions and answers

Home · Kafka · 22 questions · Kafka ladder · Roadmap · Tiếng Việt

Kafka questions for Senior backend interviews. Commands and outputs mentioned come from a throwaway single-node apache/kafka container; production topics should use replication factor 3.

Try answering out loud first, then open the answer. Superscript links go to the source that backs the claim.

1.What is Kafka, and how is it different from a traditional message queue?

Short answer: a distributed event-streaming platform that stores events durably in an append-only log per partition; consumption does not delete events.

Kafka publishes and subscribes to event streams, stores them durably and processes them as they occur or retrospectively. "Events are not deleted after consumption"; retention is configured per topic.[1] Because a consumer's position is just an offset it can rewind and reprocess data.[2] A classic queue removes a message once acknowledged.

Likely follow-up: When would a queue be better? (Task distribution with per-message routing, retry and dead-lettering; see the RabbitMQ comparison lesson.)

Learn it: Events, topics and partitions

2.How does Kafka guarantee ordering?

Short answer: per partition only; events with the same key go to the same partition.

A topic is spread over partitions on different brokers. Events with the same key are written to the same partition, and consumers of a partition read them in the order written.[1] There is no global order across partitions. To keep per-entity order, key by entity id. In my run all three u1 events went to one partition.

Likely follow-up: What happens to per-key ordering if you add partitions later? (The default partitioner's mapping changes and existing data is not moved, so one key's events end up in two partitions; partitions cannot be reduced.)[9]

Learn it: Events, topics and partitions · Partitioning and partition count

3.Explain consumer groups, partition assignment and rebalancing.

Short answer: within a group each partition goes to exactly one consumer; membership changes trigger rebalances.

"Each partition is assigned to exactly one consumer in the group"; group membership is dynamic and partitions rebalance when consumers join or leave.[3] So consumers beyond the partition count sit idle (a consequence of that rule). Failure detection: with session.timeout.ms, no heartbeat means the broker removes the client and rebalances; max.poll.interval.ms bounds the gap between poll() calls.[4] A KafkaConsumer instance is not thread-safe.[3]

Likely follow-up: Consumer lag keeps growing. What do you check? (Processing time versus poll interval, partition count versus consumers, kafka-consumer-groups.sh --describe.)

Learn it: Consumer groups

4.At-most-once, at-least-once, exactly-once: how do you get each?

Short answer: the order of processing and committing the offset decides between at-most and at-least once; exactly-once needs idempotence or transactions.

If the consumer saves its position and then processes, a crash loses messages (at-most-once). Process first, then save the position: at-least-once, with possible redelivery.[2] commitSync() after the work gives at-least-once.[3] Since 0.11.0.0 the idempotent producer prevents duplicates from resends, and transactions write atomically to multiple partitions.[2] External side effects (email, other databases) still need idempotent handling.

Likely follow-up: How do you make a database write idempotent? (Unique event id as a key; upsert; check processed-events table in the same transaction.)

Learn it: Delivery semantics

5.What does acks=all do, and how do you avoid data loss?

Short answer: acks=all waits for the full set of in-sync replicas; combine with replication and min.insync.replicas.

acks=0: no wait. acks=1: leader writes locally and responds. acks=all: waits for all in-sync replicas and the record is not lost "as long as at least one in-sync replica remains alive".[5] Only committed messages (received by all in-sync replicas) are given to consumers; min.insync.replicas ensures the write is acknowledged by at least that many in-sync replicas.[2] Replication factor 3 is a common production setting.[1] A durable producer: acks=all, idempotence (default true in 4.3 docs), sensible delivery.timeout.ms.[5]

Likely follow-up: What is unclean leader election? (Letting an out-of-sync replica lead favors availability over consistency and can lose data.[2])

Learn it: Replication and durability

6.What is the ISR?

Short answer: the set of replicas that are in sync with the leader.

Each partition has a leader that receives writes; followers replicate by pulling. The leader keeps the set of in-sync replicas (ISR). A message is committed when all in-sync replicas have it, and only committed messages reach consumers.[2]

Likely follow-up: What if a follower falls behind? (It leaves the ISR; what determines that is in the design docs beyond the excerpts used.)

Learn it: Replication and durability

7.What does the idempotent producer guarantee? Transactions?

Short answer: no duplicates from producer retries; atomic multi-partition writes.

The idempotent option "guarantees that resending will not result in duplicate entries"; it is on by default in the 4.3 config docs. Transactions let a producer write to multiple partitions atomically: all or none.[2][5] They do not extend exactly-once to systems outside Kafka.

Likely follow-up: How does this interact with consumers? (Consumers must be idempotent or read transactionally; the details are in the design docs' delivery-semantics section.)

Learn it: Idempotence and transactions

8.Producer tuning: what do linger.ms and batch.size do?

Short answer: they trade a little latency for larger batches and better throughput.

The producer batches records for the same partition into fewer requests up to batch.size (default 16384 bytes); linger.ms (default 5 ms in these docs) adds a small delay so more records join a batch.[5] Measure end-to-end latency and throughput; I have not benchmarked this.

Likely follow-up: What bounds how long a record can be delayed? (delivery.timeout.ms, default 120000.[5])

Learn it: Producers and acks

9.How long does Kafka keep data, and what is log compaction?

Short answer: by default 7 days (cleanup.policy=delete, retention.ms=604800000); compaction keeps at least the latest value per key.

[6] Deletion works per segment file. Compaction: "always retain at least the last known value for each message key"; offsets stay stable; a null value is a tombstone that deletes the key and is itself cleaned after delete.retention.ms (24 h default).[2] My run (with aggressive demo settings): keys u1 and u2 with several updates compacted to the latest values, and a tombstone removed u2.

Likely follow-up: Compacted topic for an audit trail? (No: it forgets history; use delete retention.)

Learn it: Log compaction

10.What is Kafka Streams, and how do streams differ from tables?

Short answer: a client library for stream processing; a KStream is an unbounded record stream, a KTable is a table snapshot; stateful work uses state stores with exactly-once processing available.

[7] My WordCount run produced kafka 1 then kafka 2: the changelog of a KTable of counts.

Likely follow-up: How does it scale? (Run more instances of the application; tasks are distributed among them; details are in the docs beyond the excerpts.)

Learn it: Kafka Streams

11.What is Kafka Connect?

Short answer: a framework to stream data between Kafka and other systems using source and sink connectors, tasks and converters, managed by a REST API.

[8] Distributed mode gives fault tolerance and scaling; standalone does not. My run moved lines from a file into a topic and out to another file with the bundled FileStream connectors.

Likely follow-up: How would you stream PostgreSQL changes to Elasticsearch? (Source connector, topic, sink connector; design exercise.)

Learn it: Kafka Connect

12.How do you choose a key and the number of partitions for a topic?

Short answer: key by the entity whose events must stay ordered; size partitions for future peak consumer parallelism, because growing later remaps keys and shrinking is impossible.

The default partitioner hashes the key; keyless records use a sticky partition per batch. Adding partitions changes the key mapping and Kafka does not move existing data; reducing partitions is not supported.[9] Partitions also cap consumers per group. In my run, keys u1, u3, u6 moved from partition 1 to 4 after going from 3 to 6 partitions.

Likely follow-up: Your keyed topic must grow 4×. How do you migrate? (New topic with more partitions, switch producers, drain the old topic before consumers switch, so a key is never processed by two consumers at once.)

Learn it: Partitioning

13.Why are rebalances a problem, and how do you reduce them?

Short answer: classic rebalances are client-driven and can pause the whole group; use cooperative sticky assignment and static membership, or the new KIP-848 protocol.

group.instance.id makes a consumer a static member, so a quick restart keeps its partitions. KIP-848 (group.protocol=consumer, GA in 4.0) moves assignment to the broker with a fully incremental design and no global synchronization barrier; session.timeout.ms and partition.assignment.strategy are not supported with it.[10]

Likely follow-up: When does the new protocol become the client default? (5.0; in 6.0 the client supports only it.)

Learn it: Rebalancing

14.A record keeps failing in your consumer. What do you do?

Short answer: classify the error; retry transient failures with bounded backoff; send permanent failures (poison pills) to a dead letter topic with error headers; alert and replay.

In Spring Kafka, DefaultErrorHandler retries (default 9 retries, no delay) then logs; with DeadLetterPublishingRecoverer it publishes to <topic>-dlt on the same partition. Deserialization and conversion errors are fatal by default and are not retried.[11] Retry topics (@RetryableTopic) keep the partition flowing but give up strict per-key order.

Likely follow-up: How do you avoid a poison pill crashing the consumer on deserialization? (ErrorHandlingDeserializer around the real deserializer.)

Learn it: Error handling

15.How do you evolve message formats safely?

Short answer: schemas in a registry with a compatibility mode; BACKWARD (default) means upgrade consumers first and only add fields with defaults.

BACKWARD: consumers on the new schema read data written with the last one. FORWARD: old consumers read new data, upgrade producers first. FULL: both. Transitive variants check all earlier versions. Adding a field with a default is fully compatible in Avro and Protobuf.[12]

Likely follow-up: Why would a compacted topic need BACKWARD_TRANSITIVE? (New consumers replay from the beginning and must read every historic version.)

Learn it: Schemas

16.What is KRaft and why 3 controllers?

Short answer: Kafka's built-in Raft metadata quorum that replaced ZooKeeper; a majority of controllers must be alive, so 3 tolerate 1 failure and 5 tolerate 2.

Nodes take process.roles broker, controller or both; combined mode is not recommended for critical environments. The last bridge release for migrating from ZooKeeper is 3.9.[13] kafka-metadata-quorum.sh describe --status shows leader, voters and follower lag.

Likely follow-up: Why not 4 controllers? (A majority of 4 is 3, so it still tolerates only 1 failure.)

Learn it: KRaft

17.Which metrics do you alert on for a Kafka cluster?

Short answer: under-replicated partitions, under-min-ISR partitions, offline partitions, active controller count, handler/network idle ratios, and consumer lag trend.

UnderReplicatedPartitions and UnderMinIsrPartitionCount should be 0, exactly one node should report ActiveControllerCount 1, and request handler and network processor idle should stay above 0.3. TotalTimeMs splits latency into queue, local, remote and response time.[14]

Likely follow-up: Lag grows but brokers look fine. Next step? (Check processing time per record, max.poll.interval, rebalances, partition skew per consumer.)

Learn it: Monitoring

18.Can Kafka work like a queue now? What are share groups?

Short answer: yes, since 4.2 share groups (KIP-932) are production-ready: many consumers share one partition, records are locked and acknowledged individually, at the cost of ordering.

Records are acquired with a time-limited lock (30 s default); consumers ACCEPT, RELEASE, REJECT or RENEW each record; there is a delivery attempt limit (default 5); share groups trade ordering for flexible sharing.[15] In my run two share consumers split 20 records from a single partition, 8 and 12.

Likely follow-up: When would you still choose RabbitMQ? (Rich routing via exchanges, per-message TTL and priorities, existing AMQP ecosystem.)

Learn it: Share groups

19.How do you secure a Kafka cluster?

Short answer: TLS for encryption, SASL (SCRAM or OAUTHBEARER) or mTLS for authentication, StandardAuthorizer with least-privilege ACLs, and quotas for noisy clients.

With an authorizer and no matching ACL only super users get access. kafka-acls.sh --producer / --consumer --group grant the needed operations.[16] Clients get unlimited quotas by default; set producer_byte_rate, consumer_byte_rate and request_percentage per user.[9]

Likely follow-up: What breaks the moment you enable the authorizer? (Every non-super-user client without ACLs; add ACLs first.)

Learn it: Security

20.How do you survive losing a whole region?

Short answer: MirrorMaker 2 (built on Connect) replicates topics and consumer offsets to another cluster; replication is asynchronous, so expect a small data loss window.

Topologies are active/passive or active/active; mirrored topics are prefixed with the source alias (us-west.foo); consumer offsets are replicated through checkpoints; exactly-once is supported for dedicated MirrorMaker clusters since 3.5.0.[17]

Likely follow-up: How would you cut storage cost for a year of retention? (Tiered storage to object storage, except compacted topics.)

Learn it: Multi-cluster

21.Kafka Streams: windows, joins and exactly-once in one answer?

Short answer: windowed aggregations with a grace period for late data; equi-joins need co-partitioned inputs; processing.guarantee=exactly_once_v2 makes read-process-write atomic.

KStream-KStream joins are always windowed; GlobalKTable and foreign-key joins do not need co-partitioning; groupBy always repartitions, and key-changing operations mark the stream for repartitioning.[18]

Likely follow-up: Why prefer mapValues over map? (No key change, so no repartition topic.)

Learn it: Streams windows and joins

22.When does Spring Kafka commit offsets, and what does that mean for your listener?

Short answer: auto-commit is disabled; the container commits by AckMode, default BATCH after the whole poll is processed: at-least-once, so the listener must be idempotent.

RECORD commits per record, MANUAL / MANUAL_IMMEDIATE leave it to Acknowledgment.acknowledge(); concurrency creates one consumer per container and is capped by partitions.[19]

Likely follow-up: Why is one KafkaProducer shared but one KafkaConsumer per thread? (The producer is thread-safe; the consumer is not.)[20]
