Events, topics and partitions

Kafka · Lesson 0001 · step 1 of 10 · Foundation · ~10 minutes · Home · Kafka ladder · Roadmap

Today's win: explain what Kafka stores, why a topic has partitions, and what ordering Kafka does and does not guarantee.

What Kafka is

Event streaming is "the practice of capturing data in real-time from event sources ... in the form of streams of events." Kafka combines three functions: publish and subscribe to event streams, store them durably, and process them as they occur or retrospectively.[1]

Topics and partitions

Events are organized in topics. A topic is "spread over a number of 'buckets' located on different Kafka brokers": these are partitions, which is how Kafka scales. Events with the same key go to the same partition, and consumers read a partition's events in the order they were written.[1]

Ordering is therefore per partition, not per topic. The key is how you get ordering for one entity (say, all events for one user).

Not a classic queue

"Events are not deleted after consumption." Retention is set per topic.[1] Consuming does not remove events, so many consumers can read the same data independently.

Which partition each key maps to is decided by Kafka; only the "same key, same partition" property is the guarantee. Source: 01-topics-keys-groups.sh (starts a throwaway apache/kafka container).

Retrieval practice

Answer from memory. One attempt each.

1. Where does Kafka guarantee event order?

Events with the same key go to the same partition and are read in written order.[1]

2. A consumer reads an event. What happens to it?

Events are not deleted after consumption; retention is configured per topic.[1]

3. Why do topics have partitions?

A topic is spread over buckets on different brokers for scalability.[1]

4. Common production replication factor per docs?

A common production setting is a replication factor of 3.[1]
