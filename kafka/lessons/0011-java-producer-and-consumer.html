Your first Java producer and consumer

Kafka · Lesson 0011 · step 3 of 23 · Foundation · ~12 minutes · Home · Kafka ladder · Roadmap · Tiếng Việt

Today's win: write and run a plain Java producer and consumer with kafka-clients, and explain the poll loop, callbacks and thread-safety rules an interviewer will ask about.

The producer: send is asynchronous

"The send() method is asynchronous. When called, it adds the record to a buffer of pending record sends" and returns at once; a background I/O thread ships batches to the brokers.[1] You learn the outcome through the returned Future or a Callback. Callbacks "will generally execute in the I/O thread of the producer and so should be reasonably fast".[1]

try (Producer<String, String> producer = new KafkaProducer<>(props)) {
    producer.send(new ProducerRecord<>("orders", "u1", "created"), (meta, ex) -> {
        if (ex != null) log.error("send failed", ex);       // after retries + delivery.timeout.ms
        else log.info("p{} offset {}", meta.partition(), meta.offset());
    });
    producer.flush();   // block until buffered records are sent
}

"The producer is thread safe and sharing a single producer instance across threads will generally be faster" than one per thread.[1] Create one per application and close it on shutdown, otherwise buffered records are lost.

The consumer: the poll loop

consumer.subscribe(List.of("orders"));
while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
    for (var r : records) process(r);
    consumer.commitSync();          // process, then commit: at-least-once
}

The opposite rule applies: "The consumer is not thread-safe."[2] Use one consumer per thread. poll() is also how the consumer stays in its group: if you take longer than max.poll.interval.ms (default 5 minutes) between polls, the consumer is considered failed and its partitions are reassigned.[2]

Run it

java-clients/run.sh copies kafka-clients 4.3.1 from the Kafka image and runs the two single-file programs with JDK 21. Real output:

=== producer
sent key=u2 value=created  -> partition 0 offset 0
sent key=u2 value=paid     -> partition 0 offset 1
sent key=u1 value=created  -> partition 1 offset 0
sent key=u1 value=paid     -> partition 1 offset 1
sent key=u3 value=created  -> partition 1 offset 2
sent key=u1 value=shipped  -> partition 1 offset 3
=== consumer, classic protocol
[classic] p0@0 u2=created
[classic] p0@1 u2=paid
[classic] p1@0 u1=created
...

Look at the producer lines: the code sent u1 first, yet the u2 callbacks printed first. Order is guaranteed per partition ("Callbacks for records being sent to the same partition are guaranteed to execute in order"[1]), not across partitions. Every u1 event kept its order inside partition 1.

Interview answer: "One shared KafkaProducer per service, async send with a callback that logs or metrics failures, flush/close on shutdown. One KafkaConsumer per thread, keep the processing inside max.poll.interval.ms, commit after processing."

Retrieval practice

Answer from memory. One attempt each.

1. Can several threads share one KafkaProducer?

The Javadoc says the producer is thread safe and sharing one instance is generally faster.[1]

2. What does producer.send() do when called?

send() adds the record to a buffer of pending sends and returns immediately.[1]

3. Can several threads share one KafkaConsumer?

The consumer is not thread-safe.[2]

4. Processing takes longer than max.poll.interval.ms. Result?

The consumer is considered failed and the group rebalances its partitions.[2]
