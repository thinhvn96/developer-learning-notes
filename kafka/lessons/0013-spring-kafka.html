Spring Kafka: KafkaTemplate, @KafkaListener and commits

Kafka · Lesson 0013 · step 8 of 23 · Core · ~12 minutes · Home · Kafka ladder · Roadmap · Tiếng Việt

Today's win: wire a Spring Boot service to Kafka with KafkaTemplate and @KafkaListener, and explain exactly when Spring commits offsets.

The minimal app

With Spring Boot you add spring-boot-starter-kafka and Boot manages a compatible version.[1] The quick tour's consumer is this small:[1]

@Bean
public NewTopic topic() {
    return TopicBuilder.name("topic1").partitions(10).replicas(1).build();
}

@KafkaListener(id = "myId", topics = "topic1")
public void listen(String in) {
    System.out.println(in);
}

"The NewTopic bean causes the topic to be created on the broker; it is not needed if the topic already exists."[1] Producing is template.send("topic1", key, value) on an injected KafkaTemplate, which returns a future like the plain producer.

When are offsets committed?

Spring does not use Kafka's auto-commit: "the framework sets enable.auto.commit to false unless explicitly set in the configuration."[2] The listener container commits according to its AckMode; "The default AckMode is BATCH".[2]

AckModeCommits[2]
RECORDwhen the listener returns after processing each record
BATCH (default)when all records returned by the poll() have been processed
MANUALyour code calls Acknowledgment.acknowledge(), then BATCH semantics apply
MANUAL_IMMEDIATEimmediately when acknowledge() is called

So the default is process-then-commit: at-least-once. A crash mid-batch redelivers the processed part of that batch, which is why your listener must be idempotent.

Concurrency

concurrency=3 creates three KafkaMessageListenerContainers, each with its own consumer (a KafkaConsumer is not thread-safe[3]), and Kafka splits partitions among them.[2] Concurrency above the partition count leaves consumers idle. With several topics the default RangeAssignor can also leave consumers idle: three topics of five partitions with concurrency=15 gives "only five active consumers".[2]

Interview answer: "Spring Kafka turns off auto-commit and commits per AckMode, default BATCH after the listener handles the whole poll. That's at-least-once, so the listener is idempotent. Concurrency is capped by partitions."

Retrieval practice

Answer from memory. One attempt each.

1. Default AckMode of a Spring Kafka container?

The default AckMode is BATCH.[2]

2. Spring Kafka sets enable.auto.commit to what?

Since 2.3 the framework sets it to false unless explicitly configured.[2]

3. Six partitions, concurrency ten. Active consumers?

Each partition goes to one consumer in the group, so four sit idle.[2]

4. Default commit order gives which guarantee?

BATCH commits after the records are processed, so a crash causes redelivery, not loss.[2]
