Today's win: choose acks, batching and retry settings for a producer and say what each trades off.

acks: how much confirmation to wait for

acksMeaning[1]
0"the producer will not wait for any acknowledgment from the server at all"; the record is considered sent once in the socket buffer
1the leader writes to its local log and responds "without awaiting full acknowledgement from all followers"
all / -1the leader waits for "the full set of in-sync replicas"; the record will not be lost "as long as at least one in-sync replica remains alive"

Batching and timeouts

  • batch.size (default 16384 bytes): the producer batches records for the same partition into fewer requests.[1]
  • linger.ms (default 5 ms in these 4.3 docs): a small artificial delay so more records join a batch.[1]
  • delivery.timeout.ms (default 120000): an upper bound on the whole send including retries.[1]
  • enable.idempotence: default true, so retries do not create duplicate records.[1]

Config sketch: reliable-producer.properties (not run here).

Interview answer: "For data I cannot lose: acks=all with idempotence on, and min.insync.replicas set on the topic (see the replication lesson). For fire-and-forget metrics I might accept acks=1 or lower and buy latency."

Retrieval practice

Answer from memory. One attempt each.

1. Which acks value risks silent loss the most?

With 0 the producer does not wait for any acknowledgment.[1]

2. What does acks=all wait for?

The leader waits for the full set of in-sync replicas.[1]

3. What does linger.ms do?

It adds a small artificial delay so sends can be batched.[1]

4. Default for enable.idempotence in 4.3 docs?

The docs list the default as true.[1]
