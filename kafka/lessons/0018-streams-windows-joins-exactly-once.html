Kafka Streams: windows, joins and exactly-once

Kafka · Lesson 0018 · step 17 of 23 · Senior · ~15 minutes · Home · Kafka ladder · Roadmap · Tiếng Việt

Today's win: choose a window type, explain co-partitioning and repartition topics for joins, and turn on exactly-once in a Kafka Streams app.

Three table-like abstractions

  • KStream: every record is an independent fact ("self-contained datum").[1]
  • KTable: every record is an "UPDATE" of the last value for its key; a null value deletes.[1]
  • GlobalKTable: every instance holds a full copy, "populated with data from all partitions of the topic".[1] Good for small reference data.

Windows and late data

Aggregations over time need a window. The DSL offers tumbling (TimeWindows.ofSizeWithNoGrace), hopping, sliding (SlidingWindows.ofTimeDifferenceAndGrace) and session windows (SessionWindows.ofInactivityGapWithNoGrace).[1] Tumbling: fixed, non-overlapping (orders per minute). Hopping: fixed size, overlapping (5-minute window every minute). Session: grows while events keep arriving within an inactivity gap (user sessions).

Time is stream time, driven by record timestamps, and it "only advances when new records arrive". Records can arrive out of order; the grace period says how long a window still accepts them, and records after it are dropped.[2]

orders.groupByKey()
      .windowedBy(TimeWindows.ofSizeAndGrace(Duration.ofMinutes(1), Duration.ofSeconds(30)))
      .count();   // orders per key per minute, late records accepted for 30 s

Joins need co-partitioning

  • "KStream-KStream joins are always windowed joins." KStream-KTable and KStream-GlobalKTable support inner and left, not outer.[1]
  • "For equi-joins, input data must be co-partitioned": same key, same partition count, same partitioner. GlobalKTable and foreign-key joins do not need it.[1]
  • Changing the key (selectKey, map) marks the stream for repartitioning; the next groupByKey or join writes through an internal repartition topic. "groupBy always causes data re-partitioning." Prefer mapValues when the key does not change.[1]

Exactly-once in Streams

Default is at-least-once. Set processing.guarantee=exactly_once_v2 and the input offset commit, state store updates and output writes "will be completed atomically", using Kafka transactions.[2] This is the strongest exactly-once Kafka offers, because the whole read-process-write loop stays inside Kafka. Local state stores are restored from changelog topics after a failure.[2]

Interview answer: "Windowed count with a grace period for late data; for joins I check co-partitioning first, or use a GlobalKTable for small dimension data; exactly_once_v2 when outputs feed money-related logic."

Retrieval practice

Answer from memory. One attempt each.

1. KStream-KStream joins are always...?

KStream-KStream joins are always windowed joins.[1]

2. Which join does NOT need co-partitioning?

GlobalKTable and foreign-key joins do not require co-partitioned inputs.[1]

3. A record arrives after the grace period. Result?

Records arriving after the grace period are discarded.[2]

4. Which value enables exactly-once in Streams?

Set processing.guarantee to exactly_once_v2.[2]
