Partitioning: keys, the partitioner and partition count

Kafka · Lesson 0012 · step 7 of 23 · Core · ~12 minutes · Home · Kafka ladder · Roadmap · Tiếng Việt

Today's win: predict which partition a record goes to, choose a key, and explain why adding partitions later breaks per-key ordering.

Who picks the partition

"The client controls which partition it publishes messages to"; Kafka exposes "semantic partitioning by allowing the user to specify a key to partition by".[1] The default partitioner in the 4.3 producer:[2]

  • Record has a key: hash of the key, modulo the partition count. Same key, same partition, so same order.
  • No key: a "sticky" partition that changes after batch.size bytes are produced to it, so batches stay full. With partitioner.adaptive.partitioning.enable=true (default) it sends more to partitions on faster brokers.
  • partitioner.class lets you plug in your own; partitioner.ignore.keys=true stops using keys.

The trap: adding partitions

Because the mapping depends on the partition count, the operations guide warns that "the default partitioner's mapping logic changes when the partition count increases", and "Kafka will not attempt to automatically redistribute existing data".[3] You also cannot go back: "Kafka does not currently support reducing the number of partitions for a topic."[3]

$ ./05-add-partitions.sh
=== 3 partitions          === 6 partitions (same keys)
  u1 -> Partition:1         u1 -> Partition:4
  u2 -> Partition:0         u2 -> Partition:0
  u3 -> Partition:1         u3 -> Partition:4
  u5 -> Partition:2         u5 -> Partition:5
=== try to shrink back to 3
Error ... The topic users currently has 6 partition(s); 3 would not be an increase.

After the change, old u1 events sit in partition 1 and new ones in partition 4. Two consumers can now process u1 events in parallel, out of order.

Choosing a key and a partition count

  • Key by the entity whose events must stay ordered (orderId, accountId). A random UUID key gives no useful ordering; a key with few values (country) creates hot partitions.
  • Partition count caps consumer parallelism in one group (one partition, one consumer). Size for the peak throughput you expect over the topic's life, because increasing later reshuffles keys.
  • If you must grow a keyed topic, the safe path is a new topic with more partitions plus a controlled migration of producers and consumers.
The sizing rule "plan for future peak" is engineering judgement built on the two documented facts above (mapping changes, no shrinking), not a formula from the docs.

Retrieval practice

Answer from memory. One attempt each.

1. Default partitioner, record with a key. Partition?

The default partitioner hashes the key when one is present.[2]

2. Default partitioner, record without key. Partition?

Keyless records use a sticky partition that switches after batch.size bytes.[2]

3. You add partitions to a keyed topic. Existing data?

Kafka will not redistribute existing data; only new records use the new mapping.[3]

4. Can you reduce a topic's partition count?

Reducing partitions is not supported.[3]
