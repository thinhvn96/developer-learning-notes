Replication, ISR and durability

Kafka · Lesson 0005 · step 7 of 10 · Advanced · ~12 minutes · Home · Kafka ladder · Roadmap

Today's win: explain leaders, followers, the ISR and min.insync.replicas, and pick settings so an acknowledged write survives a broker failure.

The replication model

  • Each partition has one leader that takes all writes; followers pull and replicate like consumers.[1]
  • The leader tracks the in-sync replicas (ISR).[1]
  • A message is committed once all in-sync replicas have received it, and "only committed messages are ever given out to the consumer".[1]
  • min.insync.replicas makes a write acknowledged only by "at least this many in-sync replicas", trading availability for consistency.[1]
  • Unclean leader election: by default Kafka waits for an ISR member to recover; the override picks the first replica that comes back, favoring availability over consistency and risking lost data.[1]

Putting it together

A common recipe: replication factor 3 (the introduction page calls it a common production setting), producer acks=all ("will not be lost as long as at least one in-sync replica remains alive"[2]), and topic min.insync.replicas=2 so a write needs two copies. With only 1 replica in sync, acks=all writes are rejected rather than accepted with weak durability. (The specific value 2 is a conventional choice, not a documented rule; check the design page for the exact semantics before you defend it.)

In the throwaway broker of this course (--replication-factor 1), describe shows Replicas: 1 Isr: 1 per partition: one copy, no fault tolerance, which is fine for learning and wrong for production.

Retrieval practice

Answer from memory. One attempt each.

1. Who receives all writes for a partition?

Each partition has one leader that receives all writes.[1]

2. When is a message committed?

A message is committed once all in-sync replicas received the write.[1]

3. Unclean leader election favors what?

It lets an out-of-sync replica lead, prioritizing availability.[1]

4. What does min.insync.replicas enforce?

Writes are acknowledged by at least that many in-sync replicas.[1]
