Schemas, Schema Registry and compatibility

Kafka · Lesson 0017 · step 14 of 23 · Advanced · ~12 minutes · Home · Kafka ladder · Roadmap · Tiếng Việt

Today's win: explain why topics need a schema contract, how Schema Registry serializers work, and which compatibility mode decides who upgrades first.

Why a schema

To Kafka a record is bytes. Producers and consumers are deployed independently, often by different teams, so the real contract is the payload format. Without enforcement, one producer renaming a JSON field breaks every consumer at runtime.

How Schema Registry works

Schema Registry is a separate service (Confluent, not part of Apache Kafka) that stores versioned schemas. Avro, Protobuf and JSON Schema serializers are supported.[1]

  • The serializer registers or looks up the schema and writes a small header: a version byte 0, then a 4-byte big-endian schema ID, then the data.[1] The consumer reads the ID and fetches (and caches) the schema.
  • Schemas live under a subject. The default TopicNameStrategy derives it from the topic (e.g. orders-value).[1]
  • Serializers "automatically register schemas by default" (auto.register.schemas); in production many teams turn this off and register schemas from CI.[1]

Compatibility decides the upgrade order

ModeGuarantee[2]Upgrade first
BACKWARD (default)consumers on the new schema can read data written with the last schemaconsumers
FORWARDdata written with the new schema can be read by consumers on the last schemaproducers
FULLboth, between new and lasteither
*_TRANSITIVEsame, against all earlier versions, not just the lastas above
NONEno checksyou are on your own

In Avro, adding a field with a default keeps compatibility: old data gets the default when read with the new schema. Adding one without a default breaks backward compatibility.[2] Because compacted and long-retention topics are replayed from the start, transitive modes matter there: a new consumer may read data written with schema version 1.

Interview answer: "Avro or Protobuf with Schema Registry, subject per topic value, BACKWARD or BACKWARD_TRANSITIVE for event topics, upgrade consumers first, only add fields with defaults, register schemas in CI and disable auto-register in prod."

Retrieval practice

Answer from memory. One attempt each.

1. Default compatibility mode in Schema Registry?

The default compatibility mode is BACKWARD.[2]

2. Under BACKWARD, which side upgrades first?

New-schema consumers can read old data, so consumers upgrade first.[2]

3. What follows the magic byte in the wire format?

Byte 0 is the format version, bytes 1-4 the big-endian schema ID.[1]

4. Which Avro change stays fully compatible?

Adding or removing a field with a default value is a fully compatible change.[2]
