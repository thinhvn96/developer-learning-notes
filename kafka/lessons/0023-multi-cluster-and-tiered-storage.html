Multi-cluster replication and tiered storage

Kafka · Lesson 0023 · step 23 of 23 · Senior · ~12 minutes · Home · Kafka ladder · Roadmap · Tiếng Việt

Today's win: design disaster recovery across data centres with MirrorMaker 2, and cut storage cost for long retention with tiered storage.

Why more than one cluster

Replication inside a cluster survives broker and rack failures, not the loss of a region. Cross-cluster mirroring covers disaster recovery, geo-proximity, aggregating edge clusters into a central one, cloud migration and legal data placement.[1]

MirrorMaker 2

  • "MirrorMaker is built on top of the Kafka Connect framework"; flows are written source->target.[1]
  • Active/passive: one flow, primary->secondary, the standby takes over on failure. Active/active: A->B, B->A, both serve traffic.[1]
  • Replicated topics are renamed: topic foo from cluster us-west becomes us-west.foo (DefaultReplicationPolicy). The prefix is what prevents infinite loops in active/active.[1]
  • Consumer group offsets are replicated through checkpoints so applications can fail over and resume near where they were.[1] Offsets differ between clusters, which is why translation is needed at all.
  • Exactly-once is supported for dedicated MirrorMaker clusters since 3.5.0.[1]
Replication between clusters is asynchronous: on failover the last seconds of data may be missing in the standby (a non-zero RPO). Say this explicitly in a design interview.

Tiered storage

Long retention on broker disks is expensive and slows broker replacement (a new broker must copy everything). Tiered storage splits the log: "The local tier is the same as the current Kafka that uses the local disks", and the "remote tier uses external storage systems, such as HDFS or S3" for completed segments.[2]

  • Broker: remote.log.storage.system.enable=true; topic: remote.storage.enable=true.[2]
  • local.retention.ms / local.retention.bytes decide how much stays local before moving to remote; retention.ms still decides total retention.[2]
  • Kafka ships the RemoteStorageManager interface but no production plugin; you need one for S3, GCS or HDFS.[2]
  • Limitation: "No support for compacted topics".[2]
Interview answer: "Inside a region: RF 3 across racks. Across regions: MirrorMaker 2 active/passive with checkpointed offsets, accepting a small RPO. For months of retention: tiered storage to S3 with a short local retention, except for compacted topics."

Retrieval practice

Answer from memory. One attempt each.

1. MirrorMaker 2 is built on what?

MirrorMaker is built on top of the Kafka Connect framework.[1]

2. Topic foo mirrored from us-west is named?

The default format is {source}.{source_topic_name}.[1]

3. Which topics cannot use tiered storage?

Tiered storage has no support for compacted topics.[2]

4. What moves to the remote tier?

The remote tier stores completed log segments.[2]
