Retention and topic configuration

Kafka · Lesson 0007 · step 4 of 23 · Core · ~10 minutes · Home · Kafka ladder · Roadmap · Tiếng Việt

Today's win: explain how long Kafka keeps data, which topic configs control it, and why 'consumed' does not mean 'deleted'.

Retention, not consumption

"Events are not deleted after consumption"; retention is set per topic.[2] The topic configs that decide (defaults from the 4.3 docs):[1]

ConfigMeaning and default[1]
cleanup.policydelete (default) discards old segments when their time or size limit is reached
retention.msmaximum time to keep a log: 604800000 (7 days)
retention.bytesmaximum partition size before old segments are discarded: -1 (no limit)
segment.bytessegment file size: 1073741824 (1 GiB); "retention and cleaning is always done a file at a time"
min.insync.replicasminimum in-sync replicas for a write to succeed when acks=all: 1
max.message.byteslargest record batch: 1048588
cd kafka/examples && ./02-retention-and-compaction.sh
cleanup.policy=delete   retention.ms=604800000   retention.bytes=-1

That output is kafka-configs.sh --describe --all on a fresh topic. Note the retention granularity: because deletion works per segment file, data can outlive retention.ms until its segment is closed and eligible (derived from the segment note above). Source: 02-retention-and-compaction.sh.

Retrieval practice

Answer from memory. One attempt each.

1. Default cleanup.policy?

The delete policy is the default.[1]

2. Default retention.ms?

604800000 ms is seven days.[1]

3. After a consumer reads an event...?

Events are not deleted after consumption.[2]

4. Retention deletion works on what unit?

Retention and cleaning are done a file at a time.[1]
