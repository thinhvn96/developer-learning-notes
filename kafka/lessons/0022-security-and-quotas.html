Security and quotas

Kafka · Lesson 0022 · step 22 of 23 · Senior · ~12 minutes · Home · Kafka ladder · Roadmap · Tiếng Việt

Today's win: secure a Kafka cluster with TLS, SASL authentication and ACLs, and protect it from noisy clients with quotas.

Off by default

"Security is optional - non-secured clusters are supported."[1] A fresh broker accepts anyone on its PLAINTEXT listener. Production needs three layers:[1]

  • Encryption in transit: SSL/TLS between clients and brokers (and between brokers). It costs CPU and disables zero-copy transfer.
  • Authentication: TLS client certificates or SASL mechanisms: GSSAPI (Kerberos), PLAIN, SCRAM-SHA-256/512, OAUTHBEARER. Typical pairs: SASL_SSL with SCRAM or OAUTHBEARER.
  • Authorization: ACLs on read/write operations, pluggable for external systems.

ACLs

In KRaft set authorizer.class.name=org.apache.kafka.metadata.authorizer.StandardAuthorizer on all nodes.[2] An ACL reads: "Principal P is [Allowed|Denied] Operation O From Host H on any Resource R matching ResourcePattern RP".[2] With an authorizer and no matching ACL, "only super users are allowed to access it" (unless you set allow.everyone.if.no.acl.found=true, which you should not).[2]

kafka-acls.sh --bootstrap-server localhost:9092 --add --allow-principal User:Bob --producer --topic Test-topic
kafka-acls.sh --bootstrap-server localhost:9092 --add --allow-principal User:Bob --consumer --topic Test-topic --group Group-1

The consumer shortcut needs a group because consuming also requires access to the consumer group resource.[2] Grant per service, least privilege, prefixed topic patterns per team.

Quotas

In a shared cluster one bad client can saturate brokers. "Having quotas protects against these issues and is all the more important in large multi-tenant clusters."[4] Two kinds: network bandwidth (bytes/sec) and request rate (percentage of request-handler thread time), applied per user, per client-id or both; brokers throttle clients that exceed them.[4] "By default, clients receive an unlimited quota."[3]

kafka-configs.sh --bootstrap-server localhost:9092 --alter \
  --add-config 'producer_byte_rate=1024,consumer_byte_rate=2048,request_percentage=200' \
  --entity-type users --entity-name user1
Interview answer: "SASL_SSL listeners, SCRAM or OAuth per service principal, StandardAuthorizer with least-privilege ACLs and no allow-everyone fallback, quotas per user in multi-tenant clusters, and secured JMX."

2. Authorizer on, no matching ACL. Who gets access?

Without ACLs only super users can access the resource.[2]

3. Default client quota?

By default clients receive an unlimited quota.[3]

4. Which SASL mechanism uses Kerberos?

GSSAPI is the Kerberos mechanism.[1]
