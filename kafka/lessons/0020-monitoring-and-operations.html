Today's win: name the handful of metrics that tell you a Kafka cluster or consumer is unhealthy, and the CLI steps for lag, partition moves and safe restarts.

Broker health: the alert list

Metric[1]HealthyMeans when bad
UnderReplicatedPartitions0a follower fell out of the ISR: less redundancy
UnderMinIsrPartitionCount0ISR below min.insync.replicas: acks=all writes fail
OfflinePartitionsCount0no leader: partition unavailable
ActiveControllerCount1 on exactly one nodeno controller, or split brain
IsrShrinksPerSec0 except during restartsflapping followers, slow disks or network
RequestHandlerAvgIdlePercent, NetworkProcessorAvgIdlePercentabove 0.3broker threads saturated

Request latency is TotalTimeMs per request type, broken into queue, local, remote and response-send time, which tells you where the time goes.[1] Remote JMX is off by default and unauthenticated when enabled, so secure it.[1]

Consumer health: lag

Lag is log-end offset minus committed offset per partition. Watch it from outside with kafka-consumer-groups.sh --describe --group <g>, which shows "how far behind the end of the log they are".[2] From inside, the client metric records-lag-max is the max lag in the window, based on the current position.[1] Alert on lag that keeps growing, not on a fixed number: a short spike after a deploy is normal.

Day-2 operations

  • Safe restarts: controlled.shutdown.enable=true moves leadership off a broker before it stops; it "will only succeed if all the partitions hosted on the broker have replicas".[2] Roll one broker at a time and wait for under-replicated = 0.
  • Leader balance: Kafka restores leadership to preferred replicas by default; otherwise run kafka-leader-election.sh --election-type preferred.[2]
  • Adding brokers: new brokers get no existing partitions. Move them with kafka-reassign-partitions.sh (--generate, --execute, --verify); "the admin has to figure out which topics or partitions should be moved".[2] Throttle the move so replication traffic does not starve clients.
Interview answer: "Four alerts first: under-replicated, under-min-ISR, offline partitions, active controller count. Then thread idle ratios and request latency breakdown. For apps, consumer lag trend per group. Rolling restarts one broker at a time, waiting for full ISR between each."

Retrieval practice

Answer from memory. One attempt each.

1. UnderMinIsrPartitionCount above zero means?

ISR is below min.insync.replicas, so writes needing that many replicas are rejected.[1]

2. Request handler idle ratio should stay above?

The docs give an ideal of above 0.3.[1]

3. You add a broker. Existing partitions?

You must move partitions with the reassignment tool yourself.[2]

4. Best consumer lag alert?

Lag naturally spikes and recovers; sustained growth means consumers cannot keep up.
