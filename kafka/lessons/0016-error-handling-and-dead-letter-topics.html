Error handling: retries, poison pills, dead letter topics

Kafka · Lesson 0016 · step 13 of 23 · Advanced · ~13 minutes · Home · Kafka ladder · Roadmap · Tiếng Việt

Today's win: handle a failing record without blocking the partition forever: separate transient from permanent errors, retry with backoff, and park poison pills in a dead letter topic.

The problem

A partition is an ordered log and your consumer commits a position. If record 42 always throws and you never commit past it, the partition is stuck: every record behind it waits. If you skip it silently, you lose data. You need a policy.

  • Transient errors (timeout, database briefly down): retry with backoff.
  • Permanent errors (cannot deserialize, validation fails): retrying is pointless; move the record aside.

Spring Kafka's building blocks

  • DefaultErrorHandler: by default FixedBackOff(0L, 9), so "after ten failures, the failed record is logged" and the consumer moves on.[1]
  • DeadLetterPublishingRecoverer: instead of logging, publishes to "<originalTopic>-dlt" and "to the same partition as the original record", so the DLT "must have at least as many partitions as the original topic".[1]
  • Fatal by default, no retries: DeserializationException, MessageConversionException, ClassCastException and a few others, "since these exceptions are unlikely to be resolved on a retried delivery".[1] Add your own with addNotRetryableExceptions(...).
  • ErrorHandlingDeserializer wraps your real deserializer so a malformed payload becomes a handled exception (in headers) instead of a crash loop.[1]
@Bean
DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
    var recoverer = new DeadLetterPublishingRecoverer(template);       // -> orders-dlt, same partition
    var handler = new DefaultErrorHandler(recoverer, new FixedBackOff(1000L, 2L)); // 3 attempts, 1 s apart
    handler.addNotRetryableExceptions(IllegalArgumentException.class); // validation: straight to DLT
    return handler;
}

This retries in place ("blocking" retries): the partition waits during backoff. @RetryableTopic gives "non-blocking" retries through separate retry topics, at the price of losing strict per-key order.[1]

Same idea elsewhere

Kafka Connect has it built in: errors.tolerance=all, errors.deadletterqueue.topic.name, errors.deadletterqueue.context.headers.enable=true and errors.retry.timeout.[2] Kafka Streams added DLQ support to its exception handlers in 4.2.

Interview answer: "Classify errors. Transient: bounded retries with backoff. Permanent: DLT with the original record plus exception headers, alert on DLT traffic, and have a replay tool. If per-key order matters, retry in place; otherwise retry topics keep the partition flowing."

Retrieval practice

Answer from memory. One attempt each.

1. Spring's default DLT name for topic orders?

By default the dead-letter record goes to <originalTopic>-dlt.[1]

2. Why must the DLT have enough partitions?

The default resolver publishes to the same partition as the original record.[1]

3. DeserializationException with DefaultErrorHandler?

It is fatal by default, so the recoverer is invoked on the first failure.[1]

4. Retry topics trade away what?

Records retried on another topic can be overtaken by later records with the same key.
