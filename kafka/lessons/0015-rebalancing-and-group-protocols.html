Rebalancing: classic vs the new consumer protocol

Kafka · Lesson 0015 · step 12 of 23 · Advanced · ~14 minutes · Home · Kafka ladder · Roadmap · Tiếng Việt

Today's win: explain what a rebalance costs, how cooperative and static membership reduce it, and what the new consumer group protocol (KIP-848, GA in 4.0) changes.

Why rebalances hurt

When a consumer joins, leaves or misses its deadline, the group's partitions are redistributed. In the classic protocol the clients do this themselves: a leader consumer runs the assignor and the group passes through a synchronization barrier. With eager assignment every consumer gives up its partitions first, so the whole group pauses. Rolling a 20-instance deployment can mean 20 pauses.

Classic protocol: the mitigations

  • Cooperative rebalancing. The default partition.assignment.strategy is [RangeAssignor, CooperativeStickyAssignor]; it uses Range by default and lets you switch to cooperative sticky with a rolling bounce that removes Range from the list.[1] Cooperative sticky only moves the partitions that must move, so the others keep processing.
  • Static membership. Set group.instance.id and "the consumer is treated as a static member": a restart within session.timeout.ms (default 45 s) keeps its partitions, with no rebalance.[1] Good for Kubernetes StatefulSets with stable names.
  • Liveness. Heartbeats every heartbeat.interval.ms (3 s), failure after session.timeout.ms, and separately max.poll.interval.ms (5 min) between polls.[1]

The new protocol (KIP-848)

The next-generation protocol "improves the scalability of consumer groups while simplifying consumers", uses a "fully incremental design" and "no longer relies on a global synchronization barrier".[2] Assignment moves to the broker's group coordinator. It is GA and enabled on the server since 4.0; clients opt in with group.protocol=consumer.[2]

  • Server-side assignors: uniform (default) and range, chosen with group.remote.assignor. CooperativeSticky, Sticky and RoundRobin map to uniform.[2]
  • Not supported with it: heartbeat.interval.ms, session.timeout.ms, partition.assignment.strategy, enforceRebalance().[2] Timing moves to the group config (consumer.session.timeout.ms 45 s, consumer.heartbeat.interval.ms 5 s).[3]
  • Default timeline: in 5.0 KafkaConsumer defaults to the new protocol; in 6.0 the client supports only it.[2]
  • Migration: online, by rolling out the config, if the classic group uses an assignor without custom metadata.[2]

Our example consumer ran with both protocols; --describe --state shows the server-side assignor:

GROUP            COORDINATOR (ID)  ASSIGNMENT-STRATEGY STATE #MEMBERS
billing-consumer localhost:9092 (1) uniform            Empty 0
billing-classic  localhost:9092 (1) -                  Empty 0
Interview answer: "Classic rebalances are client-driven and can stop the world; I'd use CooperativeSticky plus static membership. On 4.x I'd move to group.protocol=consumer: incremental, broker-side assignment, no global barrier."

Retrieval practice

Answer from memory. One attempt each.

1. Which config makes a consumer a static member?

If group.instance.id is set, the consumer is treated as a static member.[1]

2. How do clients enable the KIP-848 protocol?

group.protocol must be set to consumer.[2]

3. Where does KIP-848 compute assignments?

Assignment moves to the server; client-side assignors are not used.[2]

4. Which client config is unsupported under KIP-848?

heartbeat.interval.ms, session.timeout.ms and partition.assignment.strategy are unsupported.[2]
