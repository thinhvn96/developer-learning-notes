Criticism of patterns, and anti-patterns

Design Patterns · Lesson 0003 · step 3 of 30 · Core · ~10 minutes · Home · Design Patterns ladder · Roadmap

Today's win: state the three main criticisms of patterns, name anti-patterns, and avoid using a pattern where a simpler design works.

Three fair criticisms

  1. Kludges for weak languages: "the need for patterns arises when people choose a programming language or a technology that lacks the necessary level of abstraction." (Lambdas make several patterns nearly free in Java: see modern Java.)
  2. Inefficient solutions: people implement patterns "to the letter, without adapting them to the context of their project."
  3. Unjustified use: "If all you have is a hammer, everything looks like a nail": novices add patterns and complexity where simpler code would do.[1]

Anti-patterns

An anti-pattern is "any common but counterproductive solution to some class of problem"; the term was coined in 1995 by Andrew Koenig, inspired by Design Patterns. Examples on the page: God object, magic number, poltergeist, Big Ball of Mud.[2] A God object "references a large number of distinct types, has too many unrelated or uncategorized methods", violating the Single Responsibility Principle and tightly coupling the codebase to it.[3] See the OOP lesson God objects and refactoring.

Rule: name the problem first ("I need to vary the algorithm at runtime"), then choose the pattern. Several patterns' own pages list "may be overkill for a simple case" among their cons.

Retrieval practice

Answer from memory. One attempt each.

1. A criticism of patterns?

Novices apply them indiscriminately.[1]

2. An anti-pattern is...?

Any common but counterproductive solution to a class of problem.[2]

3. Which is an anti-pattern example?

God object is listed among anti-patterns.[2]

4. Best first step before picking a pattern?

Choose from the problem, not from the pattern list.
