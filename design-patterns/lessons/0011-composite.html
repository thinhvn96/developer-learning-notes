Composite

Design Patterns · Lesson 0011 · step 11 of 30 · Core · ~10 minutes · Home · Design Patterns ladder · Roadmap

Today's win: treat a leaf and a group of leaves through one interface, and compute over a tree recursively.

Intent

Composite is "a structural design pattern that lets you compose objects into tree structures and then work with these structures as if they were individual objects." Use it for tree-like object structures and when client code should treat simple and complex elements uniformly.[1]

Example

java design-patterns/examples/CompositeDemo.java
total size = 75
root/ (75)
  a.txt (10)
  src/ (65)
    Main.java (40)
    Util.java (25)
  empty/ (0)

Folder.size() sums its children through the same Node interface; the client calls tree.size() without knowing whether it holds a file or a folder. Source: CompositeDemo.java. The same shape appears in expression trees, UI component trees and org charts (compare the recursive CTE in PostgreSQL).

Pros and cons

Pros

  • Complex hierarchies via polymorphism and recursion
  • Open/Closed: new element types fit in

Cons

  • Hard to define a common interface when components differ a lot
  • Over-general interfaces reduce clarity

(From the pattern's page.)[1] Builder can construct Composite trees, Iterator and Visitor traverse them, Flyweight can share leaves; Decorator is similar recursively but adds a responsibility to one child, while Composite aggregates children's results.

Retrieval practice

Answer from memory. One attempt each.

1. Composite treats...?

Client code treats simple and complex elements uniformly.[1]

2. Typical structure?

Tree-like object structures.[1]

3. Operation on a folder uses...?

Folder.size sums children via the same interface.

4. Composite vs Decorator?

Composite sums children's results; Decorator adds behavior to one wrapped object.[1]
