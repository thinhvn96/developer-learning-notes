Observer

Design Patterns · Lesson 0021 · step 21 of 30 · Core · ~10 minutes · Home · Design Patterns ladder · Roadmap

Today's win: implement publish/subscribe, know why java.util.Observable is deprecated, and use the JDK's Flow API.

Intent

Observer is "a behavioral design pattern that lets you define a subscription mechanism to notify multiple objects about any events that happen to the object they're observing." Use it when a change in one object may require changing others whose set is unknown or dynamic, for GUI hooks, and for temporary observation.[1]

Example

java design-patterns/examples/ObserverDemo.java

--- Flow API (Publisher/Subscriber with back-pressure)
Flow got 1
Flow got 2

A subscriber list, subscribe/unsubscribe at runtime. The JDK's original Observable/Observer are deprecated: "the event model ... is quite limited, the order of notifications delivered by Observable is unspecified, and state changes are not in one-for-one correspondence with notifications", with java.beans, java.util.concurrent and the Flow API as alternatives.[2] Flow defines "Publishers produce items consumed by one or more Subscribers, each managed by a Subscription", and flow control through request(n) "to avoid resource management problems in push based systems".[3] Source: ObserverDemo.java. Messaging systems are Observer at architecture scale (Kafka, RabbitMQ).

Pros and cons

Pros

  • Open/Closed: add subscribers without changing the publisher
  • Relations between objects at runtime

Cons

  • Subscribers are notified in random order

(From the pattern's page.)[1] Chain of Responsibility, Command, Mediator and Observer connect senders and receivers in different ways; Mediator can be built with Observer.
