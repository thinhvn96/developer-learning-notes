Singleton

Design Patterns · Bài 0008 · bước 8/30 · Core · ~10 phút · Trang chủ · Lộ trình Design Patterns · Lộ trình tổng · English

Thành quả hôm nay: cài đặt một singleton thread-safe trong Java, và giải thích vì sao nó gây khó cho việc test và khi nào không nên dùng.

Mục đích

Singleton là "một creational design pattern cho phép bạn đảm bảo một class chỉ có đúng một instance, đồng thời cung cấp một điểm truy cập toàn cục tới instance đó." Nó giải quyết hai vấn đề cùng lúc: kiểm soát số lượng instance, và truy cập toàn cục một cách an toàn.[1]

Ví dụ

java design-patterns/examples/SingletonDemo.java
enum singleton same instance      : true
holder singleton same instance    : true
JDK Runtime.getRuntime() same     : true
distinct holder instances across 8 threads: 1
test B sees leftover state         : test-A

Hai cách viết an toàn: một enum chỉ có một phần tử (JVM đảm bảo chỉ khởi tạo một lần) và lazy holder class (việc khởi tạo class là thread-safe). Runtime của JDK được tài liệu mô tả là "một instance duy nhất của class Runtime", lấy ra bằng getRuntime().[2] Dòng cuối cùng là cái giá phải trả: trạng thái toàn cục có thể thay đổi bị rò rỉ giữa các test ("test B sees leftover state"). Hãy ưu tiên truyền một instance duy nhất qua constructor (dependency injection) và để container quản lý scope: singleton scope của Spring tính theo container, không theo class loader (bài bean scope). Mã nguồn: SingletonDemo.java.

Ưu và nhược điểm

Ưu điểm

  • Đảm bảo chỉ có một instance
  • Một điểm truy cập toàn cục có kiểm soát
  • Có thể khởi tạo lazy

Nhược điểm

  • Vi phạm Single Responsibility Principle (giải quyết hai vấn đề)
  • Có thể che giấu thiết kế tồi và tạo ra phụ thuộc không đáng có
  • Cần xử lý đặc biệt trong code đa luồng
  • Khó unit test

(Theo trang mô tả pattern.)[1] Facade, Flyweight, Abstract Factory, Builder và Prototype đều có thể được cài đặt dưới dạng Singleton.
