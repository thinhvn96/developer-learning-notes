Composite

Design Patterns · Bài 0011 · bước 11/30 · Core · ~10 phút · Trang chủ · Lộ trình Design Patterns · Lộ trình tổng · English

Thành quả hôm nay: xử lý một lá và một nhóm lá qua cùng một interface, và tính toán đệ quy trên một cây.

Mục đích

Composite là "một structural design pattern cho phép bạn ghép các object thành cấu trúc cây rồi làm việc với các cấu trúc đó như thể chúng là từng object riêng lẻ." Hãy dùng nó cho các cấu trúc object dạng cây và khi code phía client cần xử lý phần tử đơn giản lẫn phức tạp theo cùng một cách.[1]

Ví dụ

java design-patterns/examples/CompositeDemo.java
total size = 75
root/ (75)
  a.txt (10)
  src/ (65)
    Main.java (40)
    Util.java (25)
  empty/ (0)

Folder.size() cộng dồn kích thước các con thông qua cùng interface Node; client gọi tree.size() mà không cần biết mình đang cầm file hay folder. Mã nguồn: CompositeDemo.java. Hình dạng này cũng xuất hiện ở cây biểu thức, cây UI component và sơ đồ tổ chức (so sánh với recursive CTE trong PostgreSQL).

Ưu và nhược điểm

Ưu điểm

  • Xử lý hệ phân cấp phức tạp nhờ đa hình và đệ quy
  • Open/Closed: loại phần tử mới vẫn lắp vừa

Nhược điểm

  • Khó định nghĩa interface chung khi các component khác nhau quá nhiều
  • Interface quá chung chung làm giảm độ rõ ràng

(Theo trang mô tả pattern.)[1] Builder có thể dựng cây Composite, Iterator và Visitor dùng để duyệt cây, Flyweight có thể dùng chung các lá; Decorator cũng đệ quy tương tự nhưng chỉ thêm trách nhiệm cho một con, còn Composite tổng hợp kết quả từ các con.

Luyện truy hồi

Trả lời theo trí nhớ. Mỗi câu chỉ một lần chọn.

1. Composite xử lý...?

Code phía client xử lý phần tử đơn giản và phức tạp theo cùng một cách.[1]

2. Cấu trúc điển hình?

Cấu trúc object dạng cây.[1]

3. Thao tác trên folder dùng...?

Folder.size cộng dồn các con qua cùng một interface.

4. Composite so với Decorator?

Composite cộng dồn kết quả của các con; Decorator thêm hành vi cho một object được bọc.[1]
