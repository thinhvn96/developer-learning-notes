Singleton

Design Patterns · Lesson 0008 · step 8 of 30 · Core · ~10 minutes · Home · Design Patterns ladder · Roadmap · Tiếng Việt

Today's win: implement a thread-safe singleton in Java, and explain why it hurts testing and when not to use it.

Intent

Singleton is "a creational design pattern that lets you ensure that a class has only one instance, while providing a global access point to this instance." It solves two problems at once: control over the number of instances, and safe global access.[1]

Example

java design-patterns/examples/SingletonDemo.java
enum singleton same instance      : true
holder singleton same instance    : true
JDK Runtime.getRuntime() same     : true
distinct holder instances across 8 threads: 1
test B sees leftover state         : test-A

Two safe idioms: a one-element enum (the JVM guarantees single initialization) and the lazy holder class (class initialization is thread-safe). The JDK's Runtime is documented as "a single instance of class Runtime" obtained with getRuntime().[2] The last line is the price: mutable global state leaks between tests ("test B sees leftover state"). Prefer passing a single instance through the constructor (dependency injection) and letting a container manage the scope: Spring's singleton scope is per container, not per class loader (bean scopes lesson). Source: SingletonDemo.java.

Pros and cons

Pros

  • Guarantees a single instance
  • A controlled global access point
  • Lazy initialization possible

Cons

  • Violates the Single Responsibility Principle (solves two problems)
  • Can mask bad design and create inappropriate coupling
  • Needs special handling in multithreaded code
  • Hard to unit test

(From the pattern's page.)[1] Facade, Flyweight, Abstract Factory, Builder and Prototype can all be implemented as Singletons.
