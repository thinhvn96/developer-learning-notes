Mediator

Design Patterns · Lesson 0019 · step 19 of 30 · Advanced · ~10 minutes · Home · Design Patterns ladder · Roadmap · Tiếng Việt

Today's win: centralize how objects communicate so they depend on the mediator, not on each other.

Intent

Mediator is "a behavioral design pattern that lets you reduce chaotic dependencies between objects." Use it when classes are tightly coupled and hard to change, when components cannot be reused because of dependencies, or when you create many subclasses just to reuse behavior.[1]

Example

java design-patterns/examples/MediatorDemo.java
ann says: hi all
  bob got 'hi all' from ann
  cy got 'hi all' from ann
bob says: hello ann
  ann got 'hello ann' from bob
  cy got 'hello ann' from bob
each user knows only the room, not the other 2 users

Users know only the ChatRoom; adding a user changes no other user. Source: MediatorDemo.java. Compare Observer: a mediator's purpose "is to eliminate mutual dependencies among a set of system components" by making them depend on one mediator, while Observer sets up dynamic one-way subscriptions.[1]

Pros and cons

Pros

  • Communication consolidated in one place
  • New mediators without changing components
  • Less coupling; components are reusable

Cons

  • A mediator can become a God object

(From the pattern's page.)[1] Mediator can be implemented with Observer; Facade only simplifies access while Mediator centralizes communication.
