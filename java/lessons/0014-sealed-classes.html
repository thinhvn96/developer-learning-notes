Sealed classes: a guest list for subclasses

How JDK 17 lets you say "a Shape is a Circle, a Square or a Rect, and nothing else", and why the compiler cares.

Java (JDK 8, 17, 21) · Lesson 0014 · step 40 of 46 · Advanced · ~20 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? Real domains have closed sets: a payment is a card, a transfer or a voucher; an API result is a success or an error. Interviewers ask "What are sealed classes for? How are they different from an enum or a final class?" This lesson gives you that answer and prepares the JDK 21 switch of the next lessons.
Today's win: declare a sealed hierarchy, explain the three modifiers final, sealed and non-sealed, and say why sealing lets the compiler check that you handled every case.
extend / implement
Making a new type based on an existing one: a class extends a class, a class implements an interface.
subclass
The new type, for example Circle under Shape. The original is the superclass (or superinterface).
interface
A type that only lists methods (a contract). Classes and records can implement it.
hierarchy
The family tree of a type and all its subtypes.
sealed
A type that names exactly which subtypes are allowed. Nobody else may extend it.
permits
The keyword that lists the allowed subtypes: the guest list.
exhaustive
Covers every possible case. With a sealed type the compiler can check this.

Before you start

Say out loud: "In JDK 8, how can I make sure that only my three classes can extend Shape?" Think of at least one way, and what is wrong with it. You will compare in section 1.

1. The JDK 8 problem: open or locked, nothing in between

Think of a party. In JDK 8 the door has two settings. Open: anybody walks in. Locked (final): nobody walks in, not even your friends. There is no guest list.

// JDK 8: Shape is open to the whole world
public abstract class Shape {}
public final class Circle extends Shape { ... }
public final class Square extends Shape { ... }

// somebody else, in another package, months later:
public class Triangle extends Shape { ... }    // compiles fine

static double area(Shape s) {
    if (s instanceof Circle) { ... }
    if (s instanceof Square) { ... }
    throw new IllegalStateException();          // Triangle lands here, at runtime
}

The JDK 8 tricks (a package-private constructor, comments saying "do not extend") only half work, and the compiler still cannot know the full list. So every if chain needs a throw at the end "just in case".

JDK 17 adds the guest list. JEP 409 lists its goals: let the author "control which code is responsible for implementing" a class or interface, provide "a more declarative way than access modifiers to restrict the use of a superclass", and lay "a foundation for the exhaustive analysis of patterns".JEP 409 It was a preview in JDK 15 and 16 and became final in JDK 17.JEP 409

2. Write the guest list: sealed and permits

public sealed interface Shape permits Circle, Square, Rect {}
record Circle(double r) implements Shape {}     // records are implicitly final
record Square(double side) implements Shape {}
record Rect(double w, double h) implements Shape {}
  1. sealed says "this type has a guest list".
  2. permits Circle, Square, Rect is the list. Only these three may implement Shape.
  3. Each record is implicitly final, so the tree stops there.JEP 409

What the compiler does, step by step

Now somebody adds Triangle without changing the list. I compiled it with javac 21:

final class Triangle implements Shape {}
Step 1  javac sees "implements Shape"
Step 2  Shape is sealed, so javac reads its permits list
Step 3  Triangle is not on the list → error
error: class is not allowed to extend sealed class: Shape (as it is not listed in its 'permits' clause)

The list is also visible at runtime. JEP 409 added two methods to java.lang.Class: isSealed() and getPermittedSubclasses().JEP 409 On the hierarchy above they print:

Shape.class.isSealed()                 true
Shape.class.getPermittedSubclasses()   Circle, Square, Rect

If all the subclasses are in the same source file, you may leave out permits: "the Java compiler will infer the permitted subclasses from the declarations in the source file".JEP 409

3. Every guest must say what happens next

A guest on the list may bring their own guests, or not. Java makes each permitted subclass decide, out loud. "Exactly one of the modifiers final, sealed, and non-sealed must be used by each permitted subclass."JEP 409

  • final: no further extension. The branch ends here.
  • sealed: further extension, but again only through its own permits list.
  • non-sealed: open again; any class may extend this branch.
sealed interface Vehicle permits Car, Truck, Bike {}
final class Car implements Vehicle {}
sealed class Truck implements Vehicle permits DumpTruck {}
final class DumpTruck extends Truck {}
non-sealed class Bike implements Vehicle {}
class EBike extends Bike {}                    // allowed: Bike is open again

This compiles on JDK 21. Remove the modifier from Bike and javac says error: sealed, non-sealed or final modifiers expected.

Two more rules (and the trap)

"The sealed class and its permitted subclasses must belong to the same module", or, without modules, "to the same package". And "Every permitted subclass must directly extend the sealed class."JEP 409

Trap: you list a class in permits but put it in another package of a normal (non-module) application. It does not compile. The fix: keep a sealed hierarchy together in one package; it is one closed concept anyway.

4. Why it matters: records + sealed = closed data types

Records are a natural fit: a record is a shallowly immutable, transparent carrier of values.Record javadoc JEP 409 says "Sealed classes work well with record classes", and "Record classes are implicitly final".JEP 409 A sealed interface plus records gives you an algebraic data type: a closed set of variants, each with its own fields.

The course example defines exactly this hierarchy. On JDK 17 it still uses an instanceof chain with a throw at the end:

$ java java/examples/jdk17/Jdk17Features.java
...
3.14 4.00 6.00        ← area of Circle(1), Square(2), Rect(2, 3)

On JDK 21, a switch over the interface needs no default, because the compiler knows the full set (lesson 15). The payoff comes when someone adds a new shape. I added Triangle to the permits list but forgot it in the switch:

static double area(Shape s) {
    return switch (s) {                         // JDK 21
        case Circle c -> Math.PI * c.r() * c.r();
        case Square q -> q.side() * q.side();
    };                                          // Triangle missing
}
error: the switch expression does not cover all possible input values

In JDK 8 that bug was an exception in production. With sealed types it is a compile error on your laptop.

Interview angle: sealed vs enum vs final. Enum: a closed set of instances of one type, all with the same fields. Sealed: a closed set of types, each with its own shape of data. Final: no subclasses at all.

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

Which keyword lists the subtypes that may extend a sealed type?

A sealed class or interface uses a permits clause naming the allowed subtypes.

Which modifier must a permitted subclass use?

Each permitted subclass must say how the tree continues: stop (final), restrict again (sealed) or reopen (non-sealed).

Which modifier opens a branch of a sealed hierarchy to any class again?

non-sealed reverts that branch to open extension, like a normal class.

Shape permits Circle and Square. Someone writes final class Triangle implements Shape. What happens?

javac checks the permits list: "class is not allowed to extend sealed class". The error is at compile time.

Why can a JDK 21 switch over a sealed interface skip the default?

Sealing makes the set of subtypes closed and known, so the compiler can check exhaustiveness and report a missing case.

You need "a payment is a Card with a number, or a Voucher with a code". Which fits best?

The variants carry different data, so you need a closed set of types. An enum is a closed set of instances of one type.

In which release did sealed classes become a final (non-preview) feature?

Sealed classes were previews in JDK 15 and 16 and were finalized in JDK 17 with no changes.

An interviewer asks: "What are sealed classes, and when would you use one instead of an enum?" Start a timer. Answer out loud, in full sentences. Then click the button.

Example answer

"Sealed classes, final since JDK 17, let me control who can extend a type. I write sealed interface Shape permits Circle, Square, Rect, and any other class that tries to implement Shape is a compile error. Each permitted subclass has to say final, sealed with its own list, or non-sealed to open that branch again; records are implicitly final, so they fit perfectly. The big benefit is that the compiler knows the complete set of subtypes. So in JDK 21 I can switch over a Shape without a default, and if someone adds a new shape, every switch that forgets it stops compiling. Compared to an enum: an enum is a fixed set of instances of one type with the same fields; a sealed hierarchy is a fixed set of types, each with its own data, like Card(number) versus Voucher(code)."
