CompletableFuture: a chain of steps that runs on other threads

Start work in the background, say what to do when it finishes, and handle the failure, without blocking your own thread.

Java (JDK 8, 17, 21) · Lesson 0010 · step 28 of 46 · Advanced · ~30 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? A backend often has to call two or three services and combine the answers. Doing them one after another is slow; CompletableFuture lets them run at the same time. Interviewers ask "Which thread runs supplyAsync?", "What is the difference between join and get?" and "How do you handle an error in the chain?"
Today's win: build a chain with supplyAsync and thenApply, recover from a failure with exceptionally, and say which thread pool runs async steps by default and how join and get report errors differently.
thread
One line of work the computer runs. Several threads can run at the same time.
thread pool
A team of ready threads that take tasks from a queue, so you don't create a new thread per task.
executor
Java's word for "something that runs tasks", usually a thread pool.
Future
A receipt for a result that is not ready yet. You can wait for it later.
async
"Asynchronous": started now, finished later, while the caller does something else.
block
A thread blocks when it stops and waits, for example for a network answer or for join().
checked exception
An exception the compiler forces you to catch or declare (like ExecutionException). Unchecked ones (like CompletionException) are not forced.

Before you start

Say out loud: "I call CompletableFuture.supplyAsync(() -> callService()). Which thread runs callService()? And what happens to an exception it throws?"

1. The picture: a café buzzer with instructions

At a café you order, and the cashier gives you a buzzer. You don't stand at the counter; you sit down and read. That buzzer is a Future: a promise of a coffee later.

Now imagine a smarter buzzer. You can attach instructions to it: "when the coffee is ready, add sugar, then bring it to table 5; if the machine breaks, bring tea instead". You never wait at the counter. That is a CompletableFuture: a Future "that may be explicitly completed" and that also acts as a CompletionStage, supporting dependent functions and actions triggered on its completion.CompletableFuture javadoc

CompletableFuture<String> ok = CompletableFuture
    .supplyAsync(() -> "hello")       // order the coffee: runs on another thread
    .thenApply(String::toUpperCase);  // instruction: when ready, transform it
System.out.println(ok.join());        // wait here for the final result
// HELLO

2. Which threads do the work?

This is the question interviewers care most about. The Javadoc gives two rules:CompletableFuture javadoc

  • "All async methods without an explicit Executor argument are performed using the ForkJoinPool.commonPool()" (unless that pool's parallelism is below two, in which case a new thread is created per task).
  • Non-async steps like thenApply "may be performed by the thread that completes the current CompletableFuture, or by any other caller of a completion method".

Trace it step by step

Step 1  main: supplyAsync hands () -> "hello" to the common pool, returns a future at once
Step 2  main: thenApply attaches an instruction to that future, returns a new future
Step 3  worker: runs the supplier → "hello" → completes the first future
Step 4  worker (or main): runs toUpperCase → "HELLO" → completes the second future
Step 5  main: join() was waiting → wakes up with "HELLO"

The trap: blocking work in the common pool

The common pool is shared: it "is used by any ForkJoinTask that is not explicitly submitted to a specified pool", and its docs warn that its thread adjustments are not "guaranteed in the face of blocked I/O".ForkJoinPool javadoc So if your async steps make slow blocking calls (HTTP, JDBC), they hold the pool's threads and can starve every other task that uses it. The fix: pass your own Executor for blocking calls, using the overloads that take one, e.g. supplyAsync(supplier, ioExecutor). On JDK 21, consider virtual threads (see lesson 0006).

3. Combining several futures

Back at the café: you ordered coffee and a sandwich from two counters. You want to eat when both are ready. The Javadoc describes the main tools:CompletableFuture javadoc

MethodWhat it doesCafé version
thenApply(fn)Transform the resultadd sugar
thenCompose(fn)Next step is itself async: "completed with the same value as the CompletionStage returned by the given function"with the receipt, order a refill
thenCombine(other, fn)"when this and the other given stage both complete normally", call fn with both resultscoffee + sandwich → meal
allOf(cf...)"completed when all of the given CompletableFutures complete"wait for the whole order
orTimeout(t, unit)Completes exceptionally with a TimeoutException if not done in time (JDK 9+)give up after 5 minutes
completeOnTimeout(v, t, unit)Completes with a fallback value if not done in time (JDK 9+)take a water instead
CompletableFuture<User>  user  = CompletableFuture.supplyAsync(() -> userApi.get(id), io);
CompletableFuture<Order> order = CompletableFuture.supplyAsync(() -> orderApi.last(id), io);

CompletableFuture<Page> page = user
    .thenCombine(order, (u, o) -> new Page(u, o))   // both calls run at the same time
    .orTimeout(2, TimeUnit.SECONDS);                // JDK 9+: fail instead of hanging

On JDK 8 there is no orTimeout; people used get(timeout, unit) on the caller side instead. Exercise 0010 practises exactly this pattern.

4. When something goes wrong

An exception inside a step doesn't crash your program. It travels down the chain, like a "machine broken" note passed from station to station. The CompletionStage docs: if a stage's computation throws, "all dependent stages requiring its completion complete exceptionally as well, with a CompletionException holding the exception as its cause".CompletionStage javadoc So normal steps such as thenApply are skipped, until a step that handles errors picks it up:CompletableFuture javadoc

  • exceptionally(fn) runs only when the stage "completes exceptionally", with the exception as argument. It lets you recover with a fallback value.
  • handle(fn) runs in both cases and receives "this stage's result and exception".

join() throws the unchecked CompletionException; get() throws the checked ExecutionException; both carry the original cause.CompletableFuture javadoc Use join() inside lambdas and streams, where a checked exception would not compile.

$ java java/examples/jdk8/CompletableFutureDemo.java
HELLO
recovered: -1
join() throws CompletionException, cause: java.lang.IllegalStateException: boom
get()  throws ExecutionException,  cause: java.lang.IllegalStateException: boom

Source: CompletableFutureDemo.java (compiles with javac --release 8).

Two more facts interviewers like

  • Only one completion wins. If several threads try to complete, completeExceptionally or cancel the same future, only one of them succeeds.CompletableFuture javadoc
  • Cancel does not stop the work. Cancellation "is treated as just another form of exceptional completion": cancel() has the same effect as completeExceptionally(new CancellationException()). The class "has no direct control over the computation", and the mayInterruptIfRunning flag "has no effect in this implementation because interrupts are not used to control processing". So a task that is already running keeps running.CompletableFuture javadoc

Common mistakes

  • Calling join() right after every supplyAsync. Then the calls run one after another and you gained nothing. Start all of them first, then combine.
  • Forgetting to handle errors. Nobody sees the exception until someone calls join. Add exceptionally or handle, and a timeout.
  • Slow I/O on the common pool. Pass your own executor.

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

Which executor runs supplyAsync(supplier) when you don't pass one?

"All async methods without an explicit Executor argument are performed using the ForkJoinPool.commonPool()" (unless its parallelism is below two).

A future failed with IllegalStateException("boom"). What does join() throw?

join() throws the unchecked CompletionException; get() throws the checked ExecutionException. Both wrap the original cause.

Which method lets you replace a failure with a fallback value?

exceptionally(fn) runs when the stage completes exceptionally and its result replaces the error. thenApply is skipped on failure.

Two threads call complete(...) on the same future with different values. What happens?

Of competing complete, completeExceptionally or cancel calls, only one succeeds. The others return false.

What is wrong with this? var a = supplyAsync(callA).join(); var b = supplyAsync(callB).join();

join() blocks until that future is done. Start both futures first, then combine with thenCombine or allOf.

Each async step makes a slow JDBC call. Why is the default pool a bad choice?

The common pool is shared by the JVM; blocking it starves other tasks. Pass your own Executor (or use virtual threads on JDK 21).

You call cancel(true) on a CompletableFuture whose supplier is running. What happens?

Cancellation is just exceptional completion with a CancellationException; the class "has no direct control over the computation".

An interviewer asks: "How does CompletableFuture work, and what do you watch out for in production?" Start a timer. Answer out loud, in full sentences. Then click the button.

Tick only the points you really said:

Example answer

"CompletableFuture, from JDK 8, is a Future that I can complete and also chain, because it implements CompletionStage. I start work with supplyAsync, transform results with thenApply, chain another async call with thenCompose, and run two calls in parallel and merge them with thenCombine or allOf. If I don't pass an executor, async steps run on ForkJoinPool.commonPool(), which is shared, so for blocking I/O I pass my own executor, or on Java 21 I'd consider virtual threads. Exceptions travel down the chain and skip normal steps; I recover with exceptionally or handle. When I wait, join throws an unchecked CompletionException and get a checked ExecutionException, both with the real cause inside. And in production I always add a timeout with orTimeout, because cancel only completes the future; it doesn't stop the running work."
