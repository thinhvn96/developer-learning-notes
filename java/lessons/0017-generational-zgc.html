Generational ZGC: tiny pauses, now with young and old (JDK 21)

Why ZGC learned to treat new objects differently, how to turn it on in JDK 21, and how to read its log.

Java (JDK 8, 17, 21) · Lesson 0017 · step 45 of 46 · Senior · ~20 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? When a service has a strict latency target ("99% of requests under 50 ms"), garbage collection pauses can break it. Senior interviews often ask "Which GC would you choose, and why?" Knowing what generational ZGC is, and when it beats the default G1, lets you give a measured answer instead of folklore.
Today's win: say what generational ZGC is, how to enable it on JDK 21, and what workload it targets.
heap
The memory area where Java keeps your objects (lesson 0007).
garbage collector (GC)
The part of the JVM that finds objects nobody uses any more and frees their memory.
pause
A moment when the GC stops all your threads. While paused, your service answers nobody.
concurrent
"At the same time": GC work that runs while your threads keep running.
generation
A part of the heap for objects of a certain age: young for new objects, old for objects that have lived a long time.
allocation stall
Your thread wants memory for a new object, but the GC has not freed enough yet, so the thread has to wait.
G1
The default collector on server-class machines since JDK 9: a balance of throughput and short pauses.

Before you start

Say out loud: "In a web service, which objects die quickly, and which live for a long time?" Think of a request object, a JSON string, a cache, a database connection pool. Your answer is the idea behind this whole lesson.

1. The idea: most objects die young

Think of your kitchen. The bin fills up every day with wrappers, peels and paper: you empty it daily, it takes a minute. The attic holds things you keep for years: you clear it maybe once a year, and that takes a whole afternoon. It would be silly to search the attic every time the kitchen bin is full.

Java objects behave the same way. "The weak generational hypothesis states that young objects tend to die young, while old objects tend to stick around."JEP 439 A request's JSON string, its DTOs and temporary lists die when the request ends. A cache or a connection pool lives as long as the application.

So a GC that keeps young and old objects apart can clean the young part often and cheaply, and leave the old part alone most of the time. G1 already does this (lesson 0007). ZGC, before JDK 21, did not.

2. The old way: ZGC without generations

ZGC is the low-pause collector. It became a product feature in JDK 15JEP 377, so it is available on JDK 17 too. Its trick is to do almost all the work concurrently, while your threads run.

But it had one weakness. JEP 439: "ZGC currently stores all objects together, regardless of age, so it must collect all objects every time it runs." That "works well as long as there are sufficient resources (i.e., memory and CPU) available".JEP 439 In the kitchen picture: every time the bin is full, you also search the whole attic.

I ran the course's GC demo with non-generational ZGC on JDK 21, with a deliberately small 64 MB heap:

$ java -XX:+UseZGC -Xmx64m -Xlog:gc java/examples/GcDemo.java
[0.018s][info][gc] Using The Z Garbage Collector
[0.138s][info][gc] GC(0) Garbage Collection (Warmup) 8M(12%)->6M(9%)
[0.344s][info][gc] GC(1) Garbage Collection (Warmup) 20M(31%)->12M(19%)
max heap (MB): 64
[0.390s][info][gc] Allocation Stall (main) 9.720ms
[0.391s][info][gc] GC(2) Garbage Collection (Allocation Stall) 64M(100%)->12M(19%)
[0.404s][info][gc] Allocation Stall (main) 7.194ms
[0.405s][info][gc] GC(3) Garbage Collection (Allocation Stall) 64M(100%)->12M(19%)

Every cycle is a full "Garbage Collection" of the whole heap. The heap reached 100%, and the main thread had to wait almost 10 ms for memory: an allocation stall. ZGC's pauses are tiny, but a stall still makes your code wait.

3. The new way: young and old generations (JDK 21)

JEP 439 aims to "improve application performance by extending the Z Garbage Collector to maintain separate generations for young and old objects."JEP 439 "The young generation is for recently allocated objects while the old generation is for long-lived objects", and "Each generation is collected independently of the other, so ZGC can focus on collecting the profitable young objects."JEP 439

The JEP's goals: applications "should enjoy" lower risks of allocation stalls, lower required heap memory overhead and lower GC CPU overhead, "without significant throughput reduction compared to non-generational ZGC". The essential properties stay: "Pause times should not exceed 1 millisecond", heap sizes "from a few hundred megabytes up to many terabytes", and "Minimal manual configuration".JEP 439 You do not set the size of the generations or how long objects stay young.JEP 439

4. Turning it on in JDK 21

java -XX:+UseZGC -XX:+ZGenerational -jar app.jar

Both flags together enable the generational mode in JDK 21.JEP 439 This is the classic trap: "The -XX:+UseZGC command-line option will select non-generational ZGC" in JDK 21; the generational mode was made "available alongside non-generational ZGC".JEP 439

After 21: JEP 474, delivered in JDK 23, made generational the default mode of ZGC, so there -XX:+UseZGC alone is enough and ZGenerational is deprecated.JEP 474 If you upgrade later, drop the extra flag.

JDK 8 vs 17 vs 21

  • JDK 8: no ZGC. The default on servers was the Parallel GC; G1 became the default only in JDK 9.JEP 248
  • JDK 17: G1 by default; ZGC available, non-generational only.
  • JDK 21: G1 by default; ZGC in both modes, generational with the extra flag.

5. Try it and read the log

java -XX:+UseZGC -XX:+ZGenerational -Xmx64m -Xlog:gc java/examples/GcDemo.java

The demo allocates two million 1 KB arrays that die at once: pure "young garbage". My run on JDK 21 (first lines):

[0.019s][info][gc] Using The Z Garbage Collector
[0.156s][info][gc] GC(0) Major Collection (Warmup)
[0.184s][info][gc] GC(0) Major Collection (Warmup) 8M(12%)->8M(12%) 0.028s
...
max heap (MB): 64
[0.407s][info][gc] GC(3) Minor Collection (Allocation Rate)
[0.417s][info][gc] Allocation Stall (main) 4.328ms
[0.420s][info][gc] GC(3) Minor Collection (Allocation Rate) 44M(69%)->58M(91%) 0.013s

Read it line by line:

  1. Major Collection: young and old together. The first ones are "Warmup" cycles while the JVM starts.
  2. Minor Collection: young generation only. Trigger: "Allocation Rate", the program creates objects fast.
  3. The last number (0.013s) is how long the whole cycle took. Most of it runs concurrently; it is not a pause.
  4. Allocation Stall still appears: 64 MB is too small for this allocation rate. ZGC needs headroom.

To see the real pauses, add the gc+phases tag. I gave it 256 MB this time:

$ java -XX:+UseZGC -XX:+ZGenerational -Xmx256m -Xlog:gc,gc+phases java/examples/GcDemo.java
[0.437s][info][gc       ] GC(3) Minor Collection (Allocation Rate)
[0.437s][info][gc,phases] GC(3) y: Young Generation
[0.437s][info][gc,phases] GC(3) y: Pause Mark Start 0.007ms
[0.439s][info][gc,phases] GC(3) y: Concurrent Mark 1.514ms
[0.439s][info][gc,phases] GC(3) y: Pause Mark End 0.006ms
...
[0.442s][info][gc       ] GC(3) Minor Collection (Allocation Rate) 78M(30%)->64M(25%) 0.005s

The pauses are about 0.007 ms, far below the 1 ms goal; the 1.5 ms of marking runs concurrently. With 256 MB the full run printed no allocation stall at all. For comparison, the default G1 on the same demo with 64 MB:

$ java -Xmx64m -Xlog:gc java/examples/GcDemo.java
[0.001s][info][gc] Using G1
max heap (MB): 64
[0.348s][info][gc] GC(0) Pause Young (Normal) (G1 Evacuation Pause) 24M->3M(64M) 3.235ms

6. How does it work without long pauses? (Senior detail)

Moving objects while your threads use them sounds impossible. ZGC solves it with small pieces of code it adds to your program. "A load barrier is a fragment of code injected by ZGC into the application" when it reads a reference, and ZGC uses colored pointers: "A colored pointer is a pointer to an object in the heap" with extra bits that tell the barrier what state the object is in.JEP 439

Generations add one problem: to clean the young part alone, ZGC must know which old objects point to young ones (the dashed arrow in the first diagram). So "Generational ZGC also uses store barriers": "The remembered set contains all memory addresses in the old generation that potentially contain pointers to objects in the young generation", and "Store barriers add entries to the remembered set."JEP 439 Unlike the old mode, it no longer needs multi-mapped memory: "Generational ZGC instead uses explicit code in the load and store barriers".JEP 439

Trap: "ZGC is always better"

Barriers cost a little CPU on every reference read and write, and ZGC wants free heap to work concurrently (you saw the stall at 64 MB). For a batch job that only cares about total throughput, G1 or Parallel may finish sooner. Choose by your target, and measure.

Interview answer shape: "Default G1 for balanced throughput. If the SLA is sub-millisecond pauses on large heaps, evaluate generational ZGC on JDK 21, measured against my workload's GC logs, not by folklore."

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

What did JDK 21 add to ZGC?

Generational ZGC maintains separate generations for young and old objects (JEP 439).

How do you enable generational ZGC on JDK 21?

Both flags together. On JDK 21, -XX:+UseZGC alone selects non-generational ZGC.

What pause-time goal does generational ZGC keep?

"Pause times should not exceed 1 millisecond" is one of the preserved properties. My runs showed pauses near 0.007 ms.

Which collector does JDK 21 use on a server-class machine when you pass no GC flag?

G1 on server-class machines, Serial otherwise. G1 has been the server default since JDK 9; before that it was Parallel.

Why does it pay to collect the young generation more often than the old one?

The weak generational hypothesis: "young objects tend to die young". Old objects can point to young ones; that is what the remembered set tracks.

In a ZGC log, Minor Collection ... 0.013s. What is 0.013 s?

The number is the duration of the cycle; most of it runs alongside the app. The real pauses show up with -Xlog:gc+phases as "Pause Mark Start" and similar, around 0.007 ms here.

The final test: say it in 60 seconds

An interviewer asks: "What is generational ZGC, and when would you use it instead of G1?" Start a timer. Answer out loud, in full sentences. Then click the button.

Tick only the points you really said:

Example answer

"ZGC is the low-latency collector: it marks and moves objects concurrently, using load barriers and colored pointers, so pauses stay under a millisecond even on very large heaps. Until JDK 21 it had no generations, so every cycle had to collect the whole heap, which needs a lot of spare memory and CPU and can cause allocation stalls. JEP 439 in JDK 21 adds a young and an old generation, based on the idea that most objects die young: it collects the young generation often and cheaply, and uses store barriers and a remembered set to track old-to-young pointers. On 21 I enable it with -XX:+UseZGC -XX:+ZGenerational, because UseZGC alone still gives the old mode. I'd keep G1, the default, for most services, and evaluate generational ZGC when the SLA needs very short pauses on a big heap, comparing GC logs from my own workload."
