Collectors: sorting a stream into boxes

groupingBy, partitioningBy, joining and toMap, and the one that throws when two keys collide.

Java (JDK 8, 17, 21) · Lesson 0022 · step 26 of 46 · Core · ~25 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? Real services build reports all the time: orders per customer, total salary per department, "active vs inactive" users. In Java you write these with collectors. Interviewers often give a list of employees and ask you to group them live, then ask "What happens if toMap sees a duplicate key?"
Today's win: write groupingBy, partitioningBy, joining and toMap pipelines from memory, and say exactly when toMap throws and how to fix it.
collector
A recipe that tells collect(...) how to pack stream elements into one result: a list, a map, a number, a string.
classifier
A function that gives each element its group key, e.g. Emp::dept.
downstream collector
A second collector that runs inside each group, e.g. "sum the salaries of this group".
record
A short way (JDK 16+) to write a data class: record Emp(String name, String dept, int salary) {}.
merge function
A function that says how to combine two values that ended up with the same key.
unmodifiable
A collection you can read but not change; add throws an exception.

Before you start

Say out loud: "Two employees both earn 4800. I build a map from salary to name with Collectors.toMap(Emp::salary, Emp::name). What happens?" Pick one: first wins, last wins, or an exception.

1. The picture: a post office sorting room

At a post office, letters arrive on a belt. A worker reads the city on each letter and drops it into the bin for that city. If a city has no bin yet, the worker opens a new one. At the end you have one bin per city.

That is groupingBy. The city is the classifier; each bin is a map entry. Its Javadoc calls it a "group by" operation, like SQL.Collectors javadoc All examples in this lesson use this data:

record Emp(String name, String dept, int salary) {}

List<Emp> emps = List.of(
    new Emp("ann", "dev", 5200), new Emp("bob", "dev", 4200),
    new Emp("cy",  "ops", 4800), new Emp("dee", "ops", 4800));

2. groupingBy, with and without a downstream collector

emps.stream().collect(Collectors.groupingBy(Emp::dept));
// {ops=[Emp[cy..], Emp[dee..]], dev=[Emp[ann..], Emp[bob..]]}  bins of whole Emps

emps.stream().collect(Collectors.groupingBy(Emp::dept,
        Collectors.mapping(Emp::name, Collectors.toList())));
// {ops=[cy, dee], dev=[ann, bob]}   each bin keeps only the names

emps.stream().collect(Collectors.groupingBy(Emp::dept,
        Collectors.summingInt(Emp::salary)));
// {ops=9600, dev=9400}              each bin becomes one number

The second argument is the downstream collector: it decides what happens inside each bin. Common ones are counting(), summingInt(...), mapping(...) and toList().Collectors javadoc

Trace it step by step

groupingBy(Emp::dept, summingInt(Emp::salary))
Step 1  ann → key "dev" → no bin yet → new bin, sum = 5200
Step 2  bob → key "dev" → bin exists  → sum = 5200 + 4200 = 9400
Step 3  cy  → key "ops" → new bin     → sum = 4800
Step 4  dee → key "ops" → bin exists  → sum = 4800 + 4800 = 9600
Result  {ops=9600, dev=9400}

Why is ops printed before dev? The result is a plain map, and the docs give "no guarantees on the type, mutability, serializability, or thread-safety of the Map".Collectors javadoc Need sorted keys? Use the three-argument form: groupingBy(Emp::dept, TreeMap::new, downstream).

3. partitioningBy and joining

partitioningBy is a sorting room with exactly two bins: "yes" and "no". You give it a test (a Predicate) instead of a classifier. The result is a Map<Boolean, ...> that "always contains mappings for both false and true keys", even if one bin is empty.Collectors javadoc

emps.stream().collect(Collectors.partitioningBy(e -> e.salary() >= 5000,
                                                Collectors.counting()));
// {false=3, true=1}

With groupingBy(e -> e.salary() >= 5000) instead, a missing group would simply be absent. That is the difference interviewers look for.

joining threads strings like beads on a string. joining(delimiter, prefix, suffix) "concatenates the input elements, separated by the specified delimiter, with the specified prefix and suffix, in encounter order".Collectors javadoc

emps.stream().map(Emp::name).collect(Collectors.joining(", ", "[", "]"));
// [ann, bob, cy, dee]

4. toMap: one key, one value, or it throws

Think of a phone book where every name may appear only once. toMap(keyMapper, valueMapper) builds such a book. If two elements produce the same key, Java doesn't silently pick one. The docs: "If the mapped keys contain duplicates (according to Object.equals(Object)), an IllegalStateException is thrown when the collection operation is performed."Collectors javadoc

The fix: "If the mapped keys might have duplicates, use toMap(Function, Function, BinaryOperator) instead."Collectors javadoc The third argument is the merge function: it receives the old value and the new value and returns the one to keep.

Map<Integer, String> merged = emps.stream().collect(
    Collectors.toMap(Emp::salary, Emp::name, (x, y) -> x + "+" + y));
Step 1  ann: 5200 new → put "ann"
Step 2  bob: 4200 new → put "bob"
Step 3  cy:  4800 new → put "cy"
Step 4  dee: 4800 exists → merge("cy", "dee") → "cy+dee"

Common merge choices: (a, b) -> a keeps the first, (a, b) -> b keeps the last, Integer::sum adds them. Pick one on purpose; "duplicates can't happen" is the assumption the exception protects you from.

$ java java/examples/CollectorsDemo.java
groupingBy      : {ops=[cy, dee], dev=[ann, bob]}
sum by dept     : {ops=9600, dev=9400}
partitioningBy : {false=3, true=1}

toMap w/ merge  : {4200=bob, 4800=cy+dee, 5200=ann}

The last line is printed through a TreeMap so the keys come out sorted. Compare all of this with SQL GROUP BY in the PostgreSQL ladder.

5. What kind of list or map do you get?

Collectors.toList() and toSet() give "no guarantees on the type, mutability, serializability, or thread-safety"; if you need control, use toCollection(Supplier), e.g. toCollection(ArrayList::new).Collectors javadoc

Common mistakes

  • toMap on data that can repeat a key. It works in tests and throws in production. Fix: pass a merge function, or use groupingBy if you want all values.
  • Relying on the order of a groupingBy map. Fix: pass TreeMap::new or LinkedHashMap::new as the map factory.
  • Adding to the result of stream.toList(). It throws UnsupportedOperationException. Fix: toCollection(ArrayList::new).

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

toMap sees two equal keys and you gave no merge function. What happens?

Duplicate keys throw IllegalStateException unless you pass a merge function as the third argument.

What does groupingBy(Emp::dept, summingInt(Emp::salary)) return for the lesson's data?

The classifier makes one bin per department; the downstream summingInt reduces each bin to one number.

Which collector always gives you both a true and a false key?

partitioningBy's map "always contains mappings for both false and true keys". groupingBy on a boolean only has the keys it saw.

Which collector builds "[ann, bob, cy, dee]" from a stream of names?

joining(delimiter, prefix, suffix) concatenates elements in encounter order with the delimiter, prefix and suffix.

Does Collectors.toList() guarantee a mutable ArrayList?

The docs give "no guarantees on the type, mutability, serializability, or thread-safety". Use toCollection(ArrayList::new) for control.

You need departments in alphabetical order in the result map. What do you change?

The map type is not guaranteed. The three-argument groupingBy takes a map factory, so TreeMap::new gives sorted keys.

Example answer

"I'd stream the employees and call collect(Collectors.groupingBy(Emp::dept, Collectors.summingInt(Emp::salary))). The first argument is the classifier, which picks the group key; the second is a downstream collector that runs inside each group, so I get a map from department to total. If I only need two groups, like high and low earners, I use partitioningBy, which always has both true and false keys. The main pitfall with toMap is duplicate keys: by default it throws IllegalStateException, so if keys can repeat I pass a merge function as the third argument, for example to keep the first or sum the values. And the docs don't guarantee the type of the map or list, so if I need sorted keys or a mutable list, I pass TreeMap::new or use toCollection."
