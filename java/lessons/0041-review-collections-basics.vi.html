Ôn tập 2: collection cơ bản và HashMap

Bốn bài học trộn lẫn với nhau: cây phả hệ collection, chọn list, xóa trong lúc lặp, và cách HashMap tìm ra value.

Java (JDK 8, 17, 21) · Bài 0041 · bước 10/46 · Review · ~25 phút · Trang chủ · Lộ trình Java (JDK 8, 17, 21) · Lộ trình tổng · English

Vì sao có bài này? Trong interview, câu hỏi về collection đến dồn dập: "Bạn dùng list nào?", rồi "Vì sao vòng lặp này crash?", rồi "HashMap hoạt động thế nào?". Bài ôn tập này trộn các bài 0028, 0002, 0029 và 0001 theo đúng cách đó, để bạn luyện chuyển qua lại giữa chúng. Ở đây không có kiến thức mới.
Thành quả hôm nay: trả lời đúng từ 10 trên 12 câu hỏi trộn trở lên, tìm ra ba bug trong bài tập trộn, và nói được cả ba câu trả lời 60 giây với ít nhất 5 ý trong checklist mỗi câu.
interface
Danh sách các method mà một kiểu hứa sẽ có, không chứa dữ liệu, như List hay Map. Bạn viết code dựa trên nó (bài 0028).
implementation
Một class thật giữ lời hứa đó bằng một cấu trúc dữ liệu thật, như ArrayList hay HashMap.
amortized O(1)
Thường là tức thì, đôi khi chậm (mảng được chép sang mảng lớn hơn), nhưng tính trung bình qua nhiều lần gọi thì nhanh (bài 0002).
fail-fast
Iterator ném ConcurrentModificationException khi phát hiện collection bị đổi sau lưng nó (bài 0029).
bucket
Một "hộp thư" bên trong HashMap. Hash code của key chọn bucket (bài 0001).
contract
Một quy tắc mà method phải tuân theo. Ở đây: object bằng nhau phải có cùng hash code.

Trước khi bắt đầu

Không nhìn lại bài cũ, hãy nói thành lời ba câu hỏi để chọn một collection, và hai method mà key của HashMap cần có. Ghi lại bạn chắc chắn đến mức nào (0 đến 100%). Cuối bài, so với điểm quiz: người ta thường tự tin hơn mức nên có, và khoảng cách đó chính là thứ bài ôn tập sửa lại.

1. Cây phả hệ (bài 0028)

Hãy nghĩ đến sơ đồ tổ chức của một công ty. Chức danh (interface) nói một người phải làm gì; con người cụ thể (implementation) làm việc đó theo cách riêng. Bạn tuyển theo chức danh: bạn khai báo List<Order>, không phải ArrayList<Order>, để sau này có thể đổi người mà không phải sửa code ở chỗ gọi.

Ba điều cần giữ lại từ bài 0028:

  1. Map không phải là Collection. Nó cung cấp keySet(), values() và entrySet() dưới dạng view.
  2. Cái tên cho biết thứ tự. Hash*: không hứa thứ tự nào. Linked*: thứ tự thêm vào. Tree*: thứ tự đã sắp xếp.
  3. Một số thao tác là tùy chọn (optional). Một implementation có thể ném UnsupportedOperationException thay vì hỗ trợ chúng; đó là cách list không sửa được vẫn khớp với cùng interface List.

Bài 0028 chọn cấu trúc bằng ba câu hỏi: tra theo key? trùng lặp? thứ tự? Sau đó bài 0002 chọn giữa các loại list. Đây là toàn bộ quyết định gom vào một luồng:

Các sự thật đằng sau bài 0002, lấy từ Javadoc:

Cả ba đều không synchronized. Bài 0002 có đầy đủ trích dẫn.

3. Xóa trong lúc lặp (bài 0029)

Nhớ lại cô giáo đọc tờ điểm danh có số phiên bản trên đầu. List đếm structural change trong modCount; iterator nhớ giá trị đó dưới tên expectedModCount và so sánh ở mỗi lần next(). Vòng for-each là một iterator, nên list.remove(x) bên trong nó làm hai con số lệch nhau:

$ java java/examples/collections/IteratorsAndFailFast.java
1. for-each + list.remove        -> ConcurrentModificationException
2. remove 2nd-to-last in for-each -> no exception, list=[ann, cid]  (loop silently skipped 'cid')
3. Iterator.remove()              -> [ann, cid, dan]
4. removeIf (JDK 8)               -> [ann, cid, dan]
5. ListIterator set + add         -> [ANN, ann!, BOB, bob!]
6. entry.setValue while iterating -> {a=10, b=20}
7. map.put new key while iterating -> ConcurrentModificationException

Dòng 2 là dòng cần giải thích được trong interview: xóa phần tử áp chót làm cursor == size, nên hasNext() là false trước khi có phép kiểm tra nào chạy. Đây là best-effort, không phải đảm bảo. Cách sửa: removeIf, Iterator.remove(), ListIterator.

4. HashMap tìm value của bạn như thế nào (bài 0001)

Bức tường 16 hộp thư: hashCode() chọn hộp thư, equals() chọn lá thư bên trong. Object bằng nhau phải có cùng hash code; chiều ngược lại không bắt buộc ("Aa" và "BB" chung số 2112). Phá quy tắc này thì map lặng lẽ trả về null:

$ java java/examples/LostKey.java
BadKey  lookup: null
GoodKey lookup: value

Và key không được thay đổi sau put: địa chỉ trên lá thư đã đổi, nên Java tìm ở một hộp thư khác. Hãy dùng key immutable hoặc một record.

5. Bài tập trộn: tìm ba bug

Đọc đoạn code này như một reviewer. Có ba bug, mỗi bug từ một bài khác nhau. Tìm ra chúng, gọi tên bài học, và nói cách sửa trước khi mở đáp án.

class Visit {
    final String user, page;
    Visit(String user, String page) {
        this.user = user;
        this.page = page;
    }
    @Override public boolean equals(Object o) {
        return o instanceof Visit v
            && v.user.equals(user) && v.page.equals(page);
    }
}

class Tracker {
    private final Map<Visit, Integer> counts = new HashMap<>();
    private final Deque<String> recentPages = new ArrayDeque<>();
    private final List<String> users = new ArrayList<>();

    // page is null for the home page
    void record(String user, String page) {
        Visit v = new Visit(user, page);
        Integer c = counts.get(v);
        counts.put(v, c == null ? 1 : c + 1);    // (A)
        recentPages.push(page);                  // (B)
        users.add(user);
    }

    void ban(String user) {
        for (String u : users)                   // (C)
            if (u.equals(user)) users.remove(u);
    }
}
Hiện ba bug

(A) Bài 0001. Visit override equals() nhưng không override hashCode(). Mỗi Visit mới có hash code mặc định riêng, nên counts.get(v) gần như luôn tìm sai bucket và mọi bộ đếm đều đứng ở 1. Cách sửa: record Visit(String user, String page) {}, hoặc thêm hashCode() với Objects.hash(user, page). (Một page null cũng làm hỏng equals này; Objects.equals xử lý được null.)

(B) Bài 0002. ArrayDeque không nhận null, nên push(null) cho trang chủ sẽ ném NullPointerException. Cách sửa: lưu một giá trị thật như "/", hoặc bỏ qua các trang null.

(C) Bài 0029. users.remove(u) trong vòng for-each ném ConcurrentModificationException, hoặc, khi phần tử khớp nằm ở vị trí áp chót, lặng lẽ bỏ qua user cuối cùng. Cách sửa: users.removeIf(user::equals).

Luyện tập

Trả lời theo trí nhớ, đừng cuộn lên. Thứ tự đáp án thay đổi mỗi lần bạn mở trang.

Vì sao map.get(key) không phải xem qua mọi entry?

Cùng key → cùng số → cùng bucket. Chỉ bucket đó được tìm. Xem bài 0001.

Câu nào về Map là đúng?

Map chứa các cặp, nên nó đứng ngoài Collection và cung cấp keySet(), values(), entrySet(). Xem bài 0028.

Một vòng for-each trên [ann, bob, cid, dan] gọi list.remove("bob"). Chuyện gì xảy ra?

modCount tăng lên, còn expectedModCount của iterator thì không, và next() kiểm tra hai số đó. Xem bài 0029.

Bạn cần một stack (push và pop). Javadoc khuyên dùng class nào?

Theo tài liệu, ArrayDeque "có khả năng nhanh hơn Stack khi dùng làm stack". Nó không nhận phần tử null. Xem bài 0002.

Point override equals() nhưng không override hashCode(). Sau map.put(new Point(1, 2), "A"), map.get(new Point(1, 2)) trả về gì?

Hash code mặc định khác nhau, nên Java tìm sai bucket. Không lỗi gì, chỉ là null. Xem bài 0001.

Vì sao nên viết List<Order> orders = new ArrayList<>() thay vì khai báo kiểu là ArrayList<Order>?

Viết code dựa trên interface; cấu trúc bên dưới có thể đổi sau. Xem bài 0028.

List là [ann, bob, cid]. Một vòng for-each xóa bob. Kết quả là gì?

Size giảm còn 2 và cursor là 2, nên hasNext() là false và không có phép kiểm tra nào chạy. Fail-fast chỉ là best-effort. Xem bài 0029.

linkedList.get(i) làm gì?

Theo tài liệu, "các thao tác truy cập theo chỉ số sẽ duyệt list từ đầu hoặc từ cuối, tùy phía nào gần hơn". Đi từng bước, không nhảy thẳng. Xem bài 0002.

Câu nào là equals/hashCode contract?

Chỉ một chiều. "Aa" và "BB" chung số 2112 mà vẫn khác nhau. Xem bài 0001.

Bạn cần contains nhanh, không trùng lặp, và giữ phần tử theo thứ tự thêm vào. Dùng class nào?

Hash* không hứa thứ tự, Tree* sắp xếp, Linked* giữ thứ tự thêm vào. Xem bài 0028.

Bên trong vòng lặp qua map.entrySet(), lời gọi nào được phép?

Đổi value không phải structural change; thêm hoặc xóa key thì có. Xem bài 0029.

Bạn put một key vào HashMap rồi sửa một field của nó. Vì sao get() không tìm thấy nó nữa?

Entry vẫn nằm ở bucket cũ, nhưng lần tra cứu đi tới bucket mới. Hãy dùng key immutable. Xem bài 0001.

Bài kiểm tra cuối: nói trong 60 giây

Ba câu hỏi mà người phỏng vấn có thể hỏi liền nhau. Làm từng câu một, nói thành lời, có bấm giờ.

Câu 1: "HashMap hoạt động thế nào?" Bấm giờ. Trả lời thành lời, bằng câu đầy đủ. Sau đó bấm nút.

Chỉ tick những ý bạn thật sự đã nói:

Câu trả lời mẫu

"HashMap là một mảng bucket. Khi put, Java gọi hashCode() trên key và dùng nó để chọn bucket; get làm lại đúng phép tính đó và đi thẳng tới đó, nên cả hai là O(1) trung bình. Hai key có thể rơi vào cùng bucket, khi đó equals() chọn ra key đúng. Vì vậy object bằng nhau phải có cùng hash code, nên em override cả hai hoặc dùng luôn record. Và em giữ key immutable, vì key bị sửa sẽ khiến lần tra cứu đi sai bucket."

Câu 2: "ArrayList hay LinkedList? Còn queue thì bạn dùng gì?" Bấm giờ. Trả lời thành lời, bằng câu đầy đủ. Sau đó bấm nút.

Chỉ tick những ý bạn thật sự đã nói:

Câu trả lời mẫu

"Mặc định em dùng ArrayList. Nó là mảng tự lớn lên, nên get và set là hằng số, còn add là hằng số amortized: thỉnh thoảng phải chép mảng, nhưng tính trung bình thì rẻ. LinkedList.get(i) phải đi từng node từ đầu gần hơn, nên em cần lý do cụ thể mới chọn nó. Cho queue hay stack thì em dùng ArrayDeque; Javadoc nói nó có khả năng nhanh hơn Stack và LinkedList. Một điểm cần nhớ: nó không nhận null. Không cái nào thread safe cả, và em khai báo bằng List hay Deque để sau này đổi implementation được."

Câu 3: "Một thread có bị ConcurrentModificationException không? Tránh nó thế nào?" Bấm giờ. Trả lời thành lời, bằng câu đầy đủ. Sau đó bấm nút.

Chỉ tick những ý bạn thật sự đã nói:

Câu trả lời mẫu

"Có ạ. Tên thì nói concurrent, nhưng một thread là đủ: nếu em gọi list.remove trong vòng for-each, iterator ẩn của vòng lặp sẽ phát hiện. List đếm structural change trong modCount, iterator nhớ giá trị cũ, và ở next() nó so sánh rồi ném exception. Nhưng đó chỉ là best-effort: xóa phần tử áp chót làm hasNext() thành false, nên phần tử cuối bị bỏ qua mà không báo gì. Em dùng removeIf, hoặc Iterator.remove(), hoặc ListIterator. Còn đổi value của map bằng setValue thì không sao vì đó không phải structural change."
