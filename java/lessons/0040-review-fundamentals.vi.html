Trước khi bắt đầu

Không nhìn lại, hãy nói thành tiếng mỗi bài một bug compile được bình thường nhưng hỏng hoặc chạy sai lúc runtime. Nếu bạn chỉ tìm được hai, điều đó đã cho bạn biết cần xem lại chỗ nào trong bảng ở cuối bài.

1. Bức tranh lớn: ai bắt được bug?

Hãy nghĩ tới hai tấm lưới an toàn. Tấm thứ nhất là compiler: nó chặn bug trước khi chương trình kịp chạy. Tấm thứ hai là chương trình đang chạy: bug lộ ra muộn, thường là trên production, dưới dạng kết quả sai hoặc exception. Nhiều bài trong phần này xoay quanh cùng một ý: ưu tiên code để tấm lưới thứ nhất bắt được bug.

Dành mười giây cho mỗi ô và nói vì sao nó nằm ở cột đó. Nếu ô nào chưa rõ, số bài nằm ngay đó.

Luyện tập

Trả lời theo trí nhớ, đừng cuộn lên. Thứ tự đáp án thay đổi mỗi lần bạn mở trang.

String a = "hi"; String b = new String("hi"); Vậy a == b là gì?

== so reference, và new tạo object riêng. Xem bài 0018.

Compiler bắt bạn catch hoặc khai báo những exception nào?

Unchecked = RuntimeException, Error và lớp con; còn lại là checked. Xem bài 0019.

Một method phải nhận được List<Integer> và List<Double>, và chỉ đọc chúng. Dùng kiểu tham số nào?

Producer ("in") dùng extends; List<Number> sẽ từ chối cả hai (invariance). Xem bài 0021.

try-with-resources mở A, rồi B. Phần thân ném X, và close() của B ném Y. Catch thấy gì?

Đóng theo thứ tự ngược, exception của phần thân thắng, exception của close bị nén lại. Xem bài 0019.

Vì sao List<Integer> không phải List<Number>?

Cho phép thì phá vỡ type safety. Xem bài 0020.

Đoạn này in ra gì? String s = "a"; s.toUpperCase(); System.out.println(s);

String là bất biến; string mới từ toUpperCase() đã bị bỏ đi. Xem bài 0018.

Lúc chạy, điều gì đúng về List<String> và List<Integer> cùng được tạo bằng ArrayList?

Type erasure không tạo class mới cho parameterized type. Xem bài 0021.

Method của bạn đọc file config, và bên gọi có thể dùng giá trị mặc định nếu thiếu file. Checked hay unchecked?

Hướng dẫn của tutorial: phục hồi được → checked; không phục hồi được → unchecked. Xem bài 0019.

Number[] arr = new Integer[2]; arr[0] = 1.5; Chuyện gì xảy ra?

Mảng là covariant và được kiểm tra lúc chạy; generic là invariant và được kiểm tra lúc compile. Xem bài 0020.

Dòng nào là cách an toàn nhất để kiểm tra input của người dùng?

So nội dung bằng equals, literal đứng trước để null chỉ cho ra false. Xem bài 0018.

Một method chỉ add Integer vào list do bên gọi đưa vào. Kiểu nào cho phép bên gọi truyền List<Object>?

Consumer ("out") dùng super. Xem bài 0021.

Lý do tốt nhất để ghép một string dài bằng StringBuilder trong vòng lặp là gì?

String là bất biến; StringBuilder ghi vào một buffer (và nó không thread-safe). Xem bài 0018.

Bài kiểm tra cuối: nói trong 60 giây

Lần này có ba câu hỏi. Làm từng câu một, có bấm giờ, nói thành tiếng.

Câu 1: "Vì sao String là immutable, và dùng == thì hỏng ở đâu?"

Chỉ tick những ý bạn thật sự đã nói:

Câu trả lời mẫu

"String là immutable, nên mọi thay đổi đều cho em một string mới. Nhờ vậy nó dùng chung an toàn, và Java giữ được một pool mà các literal giống nhau là cùng một object. Đó là cái bẫy của ==: nó so reference, nên đúng với hai literal nhưng sai với string lấy từ request. Em luôn so bằng "x".equals(value), còn trong vòng lặp thì ghép chữ bằng StringBuilder."

Câu 2: "Checked và unchecked exception khác nhau thế nào, và try-with-resources xử lý ra sao khi có lỗi?"

Chỉ tick những ý bạn thật sự đã nói:

Câu trả lời mẫu

"Runtime exception và error là unchecked; mọi exception khác là checked, nên em phải catch hoặc khai báo bằng throws. Em làm exception thành checked khi bên gọi có thể phục hồi hợp lý. Với resource thì em dùng try-with-resources: nó đóng theo thứ tự ngược trước khi catch chạy, và nếu cả phần thân lẫn close đều hỏng, em nhận exception của phần thân, còn cái của close được gắn vào dạng suppressed."

Câu 3: "List<Integer> có phải List<Number> không? Giải thích wildcard và erasure."

Chỉ tick những ý bạn thật sự đã nói:

Câu trả lời mẫu

"Không. Generic là invariant: nếu List<Integer> là List<Number> thì em add được Double vào nó. Mảng cho phép chuyện đó và hỏng lúc chạy với ArrayStoreException. Để nhận nhiều kiểu list, em dùng wildcard: ? extends cho list em đọc ra, ? super cho list em ghi vào, như trong Collections.copy. Và generic bị xóa sau khi compile, nên lúc chạy mọi ArrayList là một class và em không kiểm tra được instanceof List<String>."

Bài tập trộn: tìm bug

Class nhỏ này compile được (giả sử Order là record có id()). Nó giấu bốn vấn đề từ ba bài khác nhau. Tìm ít nhất ba, nói mỗi cái thuộc bài nào và cách sửa. Rồi mới mở đáp án.

class ReportService {
    String build(List<Order> orders) {
        String report = "";
        for (Order o : orders) report += o.id() + "\n";
        return report;
    }

    boolean isAdmin(String role) {           // role comes from a request
        return role == "ADMIN";
    }

    void save(String text) {
        try {
            FileWriter w = new FileWriter("report.txt");
            w.write(text);
            w.close();
        } catch (IOException e) { }
    }

    double total(List<Number> amounts) {     // callers have List<Integer>
        double t = 0;
        for (Number n : amounts) t += n.doubleValue();
        return t;
    }
}
Hiện đáp án
  1. report += trong vòng lặp (0018): mỗi order một String mới. Dùng một StringBuilder.
  2. role == "ADMIN" (0018): so reference; string tạo lúc chạy là object mới. Dùng "ADMIN".equals(role).
  3. Writer không được đóng nếu write hỏng, và lỗi bị nuốt mất (0019): dùng try (FileWriter w = new FileWriter(...)) và log hoặc ném lại trong catch.
  4. Tham số List<Number> (0020, 0021): bên gọi có List<Integer> sẽ bị lỗi compile. Dùng List<? extends Number>.

Tiếp theo là gì

Phần tiếp theo là Collections Framework. Ở đó generic có mặt khắp nơi (List<E>, Map<K, V>), và wildcard cũng vậy (Collections.copy, addAll(Collection<? extends E>)). Bắt đầu với bài 0028: bản đồ Collections Framework.
