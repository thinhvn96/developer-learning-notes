Records: one line instead of forty

What a record writes for you, and the one word, shallow, that can still bite you.

Java (JDK 8, 17, 21) · Lesson 0003 · step 39 of 46 · Core · ~20 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? Modern Java services use records for DTOs, events, map keys and query results. Interviewers ask "What is a record? Is it immutable?" The expected answer is "yes, but only shallowly", and you should be able to show the fix.
Today's win: list what a record generates, explain why a record holding an ArrayList is not really immutable, and fix it with a compact constructor and List.copyOf.
field
A variable that belongs to an object, like x inside a Point.
final
On a field: it can be set only once, in the constructor. On a class: nobody can extend (subclass) it.
immutable
Cannot change after it is created. String is immutable; ArrayList is not.
reference
A field of object type does not hold the object itself, only an arrow pointing to it in memory.
constructor
The special method that runs when you write new Point(1, 2). It sets the fields.
accessor
A method that returns a field's value. JDK 8 code calls it a getter: getX().
record component
One of the values listed in a record's header, like x and y in record Point(int x, int y).

Before you start

Say out loud: "If every field of a class is final, is the object immutable?" Yes or no, and why? You will check in section 4.

1. The JDK 8 way: a lot of typing for two numbers

Think of a parcel label. It holds a few values (name, street, city) and you only read them. You never "do" anything with a label. Many classes in a backend are like that: an order event, a price, a coordinate. They just carry data.

In JDK 8, even a two-number label needs all this code:

// JDK 8: a correct immutable value class
public final class Point {
    private final int x;
    private final int y;

    public Point(int x, int y) { this.x = x; this.y = y; }

    public int getX() { return x; }
    public int getY() { return y; }

    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Point)) return false;
        Point p = (Point) o;
        return x == p.x && y == p.y;
    }
    @Override public int hashCode() { return Objects.hash(x, y); }
    @Override public String toString() { return "Point[x=" + x + ", y=" + y + "]"; }
}

// JDK 16+: the same thing
record Point(int x, int y) {}

The JDK 8 version is easy to get wrong. Add a field z later and forget to update equals or hashCode, and you get the silent HashMap bug from lesson 0001. Records were finalized in JDK 16, so you have them on 17 and 21.JEP 395

2. What a record generates

The Javadoc defines it: "A record class is a shallowly immutable, transparent carrier for a fixed set of values, called the record components."Record javadoc From the header record Point(int x, int y) the compiler creates:

The Javadoc lists these "mandated members": a canonical constructor, "a private final field corresponding to each component", and "a public accessor method corresponding to each component, whose name and return type are the same as that of the component".Record javadoc And the implicit equals, hashCode and toString "are derived from all of the component fields".Record javadoc

That connects to lesson 0001: a record honours the equals/hashCode contractObject javadoc for free, which makes it a good HashMap key, as long as its components are themselves safe. (The last two lines are for section 4.)

Note the accessor names: p.x(), not p.getX(). Code that expects JDK 8 style getX() names will not find them on a record.

3. The rules: what a record cannot do

A record only carries data, so JEP 395 gives it a few hard limits:JEP 395

  1. "A record class is implicitly final, and cannot be abstract." Nobody can extend it.
  2. "The superclass of a record class is always java.lang.Record." You cannot write extends.
  3. "A record class cannot explicitly declare instance fields". All state lives in the header.
  4. But "A record class can implement interfaces", and it "can declare static methods, fields, and initializers".

I tried the forbidden ones with javac 21:

record P(int x) { int y; }
error: field declaration must be static

System.out.println(P.class.getSuperclass() + " final=" + Modifier.isFinal(P.class.getModifiers()));
class java.lang.Record final=true

You may write an accessor yourself (for example to return a copy). JEP 395 allows it, as long as the return type matches exactly.JEP 395

4. The word that matters: shallow

Imagine a locked glass case in a museum. Inside is a card with the address of a house. Nobody can change the card: it is locked. But the house at that address can still be repainted. The case protects the card, not the house.

A final field is that locked card. If the field is a reference to an ArrayList, the field will always point to the same list, but anybody holding that list can still add to it. That is what "shallowly immutable" means.Record javadoc So the answer to "Before you start" is no: all-final fields are not enough when a field points to something mutable.

record LeakyTeam(String name, List<String> members) {}

List<String> shared = new ArrayList<>(List.of("ann"));
LeakyTeam leaky = new LeakyTeam("a", shared);
shared.add("bob");                         // change the list from outside
leaky.members();                           // [ann, bob]: the record changed!
Step 1  shared points to a list [ann]
Step 2  the record's members field gets a copy of the ARROW, not of the list
Step 3  shared.add("bob") changes the one list both arrows point to
Step 4  leaky.members() follows its arrow and finds [ann, bob]

The fix: a compact constructor with a defensive copy

A record can have a compact constructor: you write the record name and a body, without repeating the parameter list. JEP 395 says the parameters are declared for you, and the fields are assigned automatically at the end.JEP 395 It is the perfect place to validate and copy:

record Team(String name, List<String> members) {
    Team {
        if (name == null || name.isBlank()) throw new IllegalArgumentException("name");
        members = List.copyOf(members);    // replace the parameter with a copy
    }                                      // fields are assigned here, from the parameters
}
$ java java/examples/RecordDemo.java
...
LeakyTeam sees outside change: [ann, bob]
Team (copyOf) is protected:    [ann]

Why List.copyOf and not new ArrayList<>(members)? List.copyOf returns an "unmodifiable List", and "If the given Collection is subsequently modified, the returned List will not reflect such modifications".List javadoc Because it is unmodifiable, a caller who does team.members().add("x") also fails. I ran it: UnsupportedOperationException. A plain ArrayList copy would block the outside change, but not this one.

Trap: nulls inside the list

List.copyOf throws NullPointerException "if coll is null, or if it contains any nulls".List javadoc Usually that is what you want for a value object (fail early). If nulls are legal in your data, decide that explicitly and document it.

The Record Javadoc is the source for what is generated. The compact-constructor pattern is standard practice; the demo above shows it working rather than citing it.

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

What is the implicit equals() of a record based on?

equals, hashCode and toString are derived from all the component fields: same record class and every component equal.

For record Point(int x, int y), what fields does the compiler create?

The Javadoc mandates a private final field for each component, plus a public accessor with the same name.

How do you read x from Point p when Point is a record?

The accessor has the same name as the component, with no get prefix. The field itself is private.

What happens with record P(int x) { int y; }?

A record cannot declare instance fields; all state lives in the header. Only static fields are allowed in the body.

A record has an ArrayList component that the caller still holds. Is the record immutable?

The final field always points to the same list, but the list itself can still change from outside.

What is the best fix for that leaky list component?

List.copyOf stores an unmodifiable copy, so neither the outside caller nor members().add() can change it.

Can a record extend another class, like record P(int x) extends Base?

A record always extends java.lang.Record and is implicitly final. It can implement interfaces, though.

An interviewer asks: "What is a Java record, and is it immutable?" Start a timer. Answer out loud, in full sentences. Then click the button.

Tick only the points you really said:

Example answer

"A record, final since JDK 16, is a class whose job is to carry data. I write record Point(int x, int y) and the compiler generates private final fields, a canonical constructor, accessors x() and y(), and equals, hashCode and toString based on all components. So it replaces about forty lines of JDK 8 code and it's a safe map key. It's implicitly final, extends java.lang.Record, and can't declare extra instance fields, but it can implement interfaces. Is it immutable? Only shallowly. The fields are final, but if a component is an ArrayList, the caller can still change that list. So in the compact constructor I validate the input and do members = List.copyOf(members); that gives the record its own unmodifiable list."
