Review 4: navigable, priority, special and concurrent collections

Six lessons, one question: "which collection, and what does it cost?" Practise answering it fast.

Why this lesson? Senior interviews rarely ask "what is a TreeMap?". They describe a problem (fee tiers, the 10 slowest requests, counting per status, a shared listener list) and wait for you to pick the structure and name its trap. This review mixes lessons 0034 to 0039 so you practise exactly that. There are no new facts here.
Today's win: score 10 or more of the 12 mixed questions, find the three bugs in the mixed task, and say all three 60-second answers with at least 5 checklist points each.
NavigableMap
A sorted map that can find the nearest key (floor, ceiling) and ranges (subMap). TreeMap is one (lesson 0034).
heap
A half-sorted tree where every parent is ≤ its children, so the smallest item is always on top (lesson 0035).
identity
"The same object in memory", tested with ==, as opposed to "equal", tested with equals (lesson 0036).
remapping function
The function you give to merge or compute; returning null removes the entry (lesson 0037).
boxing
Wrapping an int in an Integer object so a collection can hold it (lesson 0038).
snapshot iterator
An iterator that walks a frozen copy, so it never sees later changes and never throws (lesson 0039).

1. One decision tree for the whole block

Think of a toolbox. A hammer is the default (HashMap), but some jobs need pliers. The first question is always "will several threads use it?"; the second is "what do I need besides exact-key lookup?".

3. Mixed task: find the three bugs

Read this class like a reviewer. Several request threads call it at the same time. There are three bugs, each from a different lesson. Name the lesson and the fix before opening the answer.

class Monitor {
    // listeners register at runtime, from any thread
    private final List<Listener> listeners = new ArrayList<>();               // (A)

    void register(Listener l) { listeners.add(l); }
    void fire(Event e)        { for (Listener l : listeners) l.on(e); }

    // report the 10 slowest response times, slowest first
    List<Long> slowest10(List<Long> millis) {
        PriorityQueue<Long> pq = new PriorityQueue<>(Comparator.reverseOrder());
        pq.addAll(millis);                                                      // (B)
        return new ArrayList<>(pq).subList(0, 10);
    }

    boolean isAdmin(Long userId, Long adminId) { return userId == adminId; }   // (C)
}
Show the three bugs

(A) Lesson 0039. A plain ArrayList shared by threads loses adds silently, and fire can throw ConcurrentModificationException while another thread registers. Listener lists are read far more than written: use CopyOnWriteArrayList, whose snapshot iterators never throw.

(B) Lesson 0035, two problems in one. Copying a PriorityQueue into a list gives heap order, not sorted order, so subList(0, 10) is not the top 10. And a max-heap of everything costs O(n) memory. Fix: a min-heap of size 10 (offer, and poll the head when a bigger value arrives), then sort the 10 results.

(C) Lesson 0038. == on two Long objects compares references. It works for small IDs in tests and fails for real ones above 127. Fix: userId.equals(adminId), or Objects.equals if either may be null.

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

Fee tiers start at 0, 200,000 and 500,000. Which call finds the tier for an order total?

The tier is the greatest start ≤ the total, which is exactly floor. See lesson 0034.

You print a PriorityQueue built from 7, 3, 9, 1, 5, 8. What is guaranteed about the output?

toString walks the heap array: [1, 3, 8, 7, 5, 9]. Only polling gives sorted order. See lesson 0035.

Which map should count orders per enum Status?

EnumMap is an array indexed by ordinal: compact, fast, declaration order. See lesson 0036.

The remapping function in merge returns null. What happens to the entry?

If a remapping function returns null, the mapping is removed. See lesson 0037.

Integer a = 1000, b = 1000; A test checks a == b. What is true?

Identity of boxed values is guaranteed only in -128..127. See lesson 0038.

A listener list is read on every event and changed once a day by any thread. Which list?

Traversals vastly outnumber mutations, and snapshot iterators never throw. See lesson 0039.

You keep the 10 largest values of a huge stream. What does the head of your heap hold?

A min-heap of size K: its head is the one a newcomer must beat. See lesson 0035.

A memoized fib calls memo.computeIfAbsent(n, k -> fib(k-1) + fib(k-2)) on a HashMap. What happens?

The mapping function must not modify the same map. Compute first, then put. See lesson 0037.

Keys are 5, 12, 20, 33. What does subMap(10, 33) contain?

subMap(from, to) includes from and excludes to. It is also a live view. See lesson 0034.

A WeakHashMap value holds a reference to its own key. What is the effect?

Values are held strongly, so value → key keeps the key reachable. See lesson 0036.

A producer is much faster than its consumer. Which queue protects the heap?

A bounded queue makes put block when full: backpressure. See lesson 0039.

You will put 2,000,000 entries into a HashMap on JDK 21. Which line avoids every resize?

newHashMap(n) accounts for the 0.75 load factor; a capacity of 2,000,000 still resizes past 75%. See lesson 0038.

The final test: say it in 60 seconds

Recall 1. "When would you use TreeMap, and when PriorityQueue? Give one real example each." Start a timer. Answer out loud, then click.

Tick only the points you really said:

Example answer

"I use a TreeMap when I need order: it's a red-black tree, so keys stay sorted and get and put are log n, guaranteed. My favourite example is fee tiers: the key is where each tier starts, and floorEntry of the order total returns the right tier in one call. subMap gives me a time window, and it's a live view. I use a PriorityQueue when I only need the smallest item next, not full order. It's a binary heap: offer and poll are log n, peek is constant. The classic case is top K: I keep a min-heap of size K, and a new value replaces the head only if it's bigger, so it's n log k time and K memory. Careful: iterating a PriorityQueue isn't sorted. For threads I'd switch to ConcurrentSkipListMap or PriorityBlockingQueue."

Recall 2. "Which special-purpose maps and Map methods do you use, and what are their traps?"

Tick only the points you really said:

Example answer

"For enum keys I use EnumMap, which is just an array indexed by ordinal, and EnumSet, a bit vector; neither takes nulls. IdentityHashMap compares keys with double equals, so it breaks the Map contract on purpose; I'd only use it for things like deep copy, where I track physical objects. WeakHashMap drops an entry once its key is unreachable, but the values are strong, so a value pointing to its key leaks, and it's not a size-limited cache. For everyday code I use the Java 8 methods: merge with Integer::sum to count, computeIfAbsent to build a multimap. Traps: putIfAbsent builds its argument anyway, a function returning null means no mapping or removal, and the function must not modify the same map, so no recursive memo inside computeIfAbsent. And they're only atomic on ConcurrentHashMap."

Recall 3. "Your service is slow and uses too much memory, and it shares collections between threads. What do you check?"

Tick only the points you really said:

Example answer

"For memory I first look at boxing: a List of Integer stores a reference plus an Integer object per element, roughly 19 MB per million against 4 for an int array, and LinkedList or HashSet are worse, so hot data goes into primitive arrays or primitive collections. Then resizing: I presize ArrayList and use HashMap.newHashMap on Java 19 and later. Boxing also hides bugs, like comparing Longs with double equals, which only works up to 127. For the threads, plain collections lose updates without any error, so I pick the right concurrent one: ConcurrentHashMap for maps, ConcurrentSkipListMap if sorted, CopyOnWriteArrayList for read-mostly lists like listeners, and a bounded BlockingQueue between producers and consumers so a fast producer can't fill the heap. If I keep a synchronized wrapper, I lock it myself while iterating."
