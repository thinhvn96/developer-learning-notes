switch "mở hộp" object như thế nào (JDK 21)

Pattern matching cho switch và record pattern: kiểm tra kiểu, lấy các field ra, và để compiler kiểm tra giúp bạn không sót trường hợp nào.

Java (JDK 8, 17, 21) · Bài 0015 · bước 42/46 · Advanced · ~25 phút · Trang chủ · Lộ trình Java (JDK 8, 17, 21) · Lộ trình tổng · English

Vì sao có bài này? Code thực tế hay nhận vào "một trong vài loại": một payment là thẻ hoặc chuyển khoản, một event là created, paid hoặc cancelled. Trước JDK 21, bạn xử lý bằng chuỗi if / else if / instanceof dài. Người phỏng vấn hay hỏi "JDK 21 thêm gì vào switch, và vì sao nó quan trọng khi đi cùng sealed type và record?" Bài này trả lời câu đó.
Thành quả hôm nay: viết một switch JDK 21 có destructure record, dùng guard when và case null, và không cần default khi switch trên một kiểu sealed.
selector
Giá trị bạn đặt trong ngoặc của switch (...). Java so sánh nó với từng case.
pattern
Một "phép thử hình dạng" nhỏ trong case, ví dụ String s. Nếu giá trị có hình dạng đó, phép thử thành công và Java gán giá trị vào biến.
type pattern
Pattern kiểm tra kiểu: case Integer i nghĩa là "nếu nó là Integer thì gọi nó là i".
record pattern
Pattern kiểm tra một kiểu record và lấy các field ra cùng lúc: case Point(int x, int y).
guard
Điều kiện thêm sau when. Case chỉ khớp khi pattern khớp và điều kiện đúng.
exhaustive
"Vét cạn": bao phủ mọi giá trị có thể. Compiler từ chối một switch dùng pattern nếu có giá trị nào đó không khớp case nào.
sealed type
Class hoặc interface liệt kê đủ mọi subtype được phép bằng permits (bài 0014), nên compiler biết danh sách đầy đủ.

Trước khi bắt đầu

Hãy nói thành tiếng: "Mình có một Object. Nó có thể là Integer, String hoặc null. Trong Java 8, làm sao in ra một thông báo khác nhau cho mỗi loại?" Đừng tra cứu gì cả. Cuối bài bạn sẽ so sánh với cách của JDK 21.

1. Cách cũ: một chuỗi câu hỏi

Hãy hình dung một nhân viên bưu điện phân loại bưu kiện. Với mỗi bưu kiện, cô ấy hỏi: "Có phải thư không? Không. Hộp nhỏ? Không. Hộp lớn? Đúng, để vào đây." Mỗi câu hỏi viết riêng lẻ, và nếu cô ấy quên một loại bưu kiện thì chẳng ai nhắc.

Đó chính là code Java kiểu cũ. JEP 441 minh hoạ nó với comment "Prior to Java 21":JEP 441

static String formatter(Object obj) {
    String formatted = "unknown";
    if (obj instanceof Integer i) {
        formatted = String.format("int %d", i);
    } else if (obj instanceof Long l) {
        formatted = String.format("long %d", l);
    } else if (obj instanceof String s) {
        formatted = String.format("String %s", s);
    }
    return formatted;
}

Đoạn này đã dùng instanceof pattern của JDK 16 trong bài 0013. Ở JDK 8 nó còn dài hơn: if (obj instanceof Integer) { Integer i = (Integer) obj; ... }, mỗi nhánh một lần kiểm tra rồi một lần cast.

Ba vấn đề: code lặp lại, thứ tự các if dễ sai, và compiler không thể báo cho bạn biết là bạn quên một loại.

2. Cách mới: pattern ngay trong case

JDK 21 cho phép đặt type pattern trong case label, nên selector được kiểm tra với nhiều pattern, mỗi pattern có một hành động riêng.JEP 441 Phương thức trên trở thành:

static String formatter(Object obj) {
    return switch (obj) {
        case Integer i -> String.format("int %d", i);
        case Long l    -> String.format("long %d", l);
        case String s  -> String.format("String %s", s);
        default        -> "unknown";   // needed: Object has endless subtypes
    };
}

Đọc case Integer i -> là: "nếu obj là Integer thì gọi nó là i và chạy code bên phải." Mũi tên -> nghĩa là không fall-through, giống hệt switch expression ở bài 0013.

Java chọn case như thế nào? Theo JEP, "case label đầu tiên trong switch block áp dụng được cho giá trị sẽ được chọn".JEP 441 Cùng trace formatter(42L):

formatter(42L);
Step 1  Is 42L an Integer?  no  → try the next case
Step 2  Is 42L a Long?      yes → bind l = 42L
Step 3  Run the right side  → String.format("long %d", 42L)
        returns "long 42"

3. Guard với when, và vì sao thứ tự quan trọng

Đôi khi biết kiểu thôi là chưa đủ. Bạn muốn "một String, nhưng chỉ khi nó rỗng". Hãy thêm guard bằng when: nó thu hẹp một pattern.JEP 441

static String nullSafe(Object o) {
    return switch (o) {
        case null -> "null handled inside the switch";
        case String str when str.isBlank() -> "blank string";
        case String str -> "string " + str;
        case Integer i  -> "int " + i;
        default         -> "other";
    };
}

Thứ tự quan trọng, giống các khối catch. Một case không được bị một case trước nó dominate (lấn át): theo JEP, "sẽ là lỗi compile nếu một case label trong switch block bị bất kỳ case label nào đứng trước lấn át".JEP 441 Vậy hãy đặt pattern cụ thể hơn lên trước.

Bẫy: case tổng quát đứng trước

String cũng là một CharSequence. Nếu case CharSequence đứng trước thì case String không bao giờ được chạm tới. Mình đã compile đoạn này trên JDK 21:

return switch (o) {
    case CharSequence cs -> "cs";
    case String s        -> "s";      // can never be reached
    default              -> "o";
};

$ javac Dom.java
error: this case label is dominated by a preceding case label

Cách sửa: đổi chỗ. Cụ thể (String, hoặc case có guard) đứng trước, tổng quát (CharSequence, default) đứng sau.

4. Còn null thì sao?

Ở mọi phiên bản Java trước 21, switch (null) ném NullPointerException. JDK 21 thêm case null: "Nếu biểu thức selector có giá trị null thì bất kỳ case null nào cũng được coi là khớp."JEP 441

Nhưng nếu bạn không viết nó thì hành vi cũ vẫn giữ nguyên: "Nếu switch block không có label như vậy thì switch ném NullPointerException, như trước đây."JEP 441 default không bắt null. Muốn cả hai, bạn có thể viết chung case null, default -> ...; JEP cho phép "null case label đi kèm một default tuỳ chọn".JEP 441

switch (o) { case String s -> ...; default -> ...; }
// o == null → NullPointerException

switch (o) { case null -> ...; case String s -> ...; default -> ...; }
// o == null → the null case runs

5. Record pattern: mở hộp ngay trong case

Hãy nghĩ tới một bưu kiện có dán danh sách hàng bên ngoài: "gồm: một điểm, một bán kính". Record pattern đọc danh sách đó và đưa bạn từng món theo tên. Record pattern dùng để "phân rã (deconstruct) giá trị record".JEP 440

Cách cũ và cách mới, cả hai đều lấy từ JEP 440:JEP 440

record Point(int x, int y) {}

// As of Java 16: test the type, then call the accessors yourself
if (obj instanceof Point p) {
    int x = p.x();
    int y = p.y();
    System.out.println(x + y);
}

// As of Java 21: the pattern declares x and y for you
if (obj instanceof Point(int x, int y)) {
    System.out.println(x + y);
}

Pattern có thể lồng nhau: record trong record, mở ra trong một dòng, ví dụ Rectangle(ColoredPoint(Point(var x, var y), var c), var lr).JEP 440 Bạn có thể viết var thay cho kiểu của component: "Record pattern có thể dùng var để khớp với một record component mà không cần ghi kiểu của component đó."JEP 440

Một chi tiết: "Giá trị null không khớp với bất kỳ record pattern nào."JEP 440 Vì vậy case Circle(var c, var r) không bao giờ chạy với null; bạn cần case null cho trường hợp đó.

6. Sealed type: không cần default, và compiler kiểm tra giúp bạn

Quay lại bưu điện. Nếu bưu điện tuyên bố "chúng tôi chỉ nhận ba cỡ bưu kiện, hết", thì một nhân viên có ba ngăn đã bao phủ mọi thứ. Sealed type (bài 0014) chính là lời hứa đó trong Java.

Switch dùng pattern phải exhaustive. Với kiểu sealed, "việc kiểm tra độ bao phủ kiểu có thể tính đến mệnh đề permits của sealed class", và "kết quả là không cần default label".JEP 441 Đây là ví dụ đầy đủ của khoá học:

sealed interface Shape permits Circle, Rect {}
record Point(int x, int y) {}
record Circle(Point center, double r) implements Shape {}
record Rect(Point topLeft, Point bottomRight) implements Shape {}

static String describe(Shape s) {
    return switch (s) {   // no default: Circle and Rect are the only Shapes
        case Circle(Point(var x, var y), var r) when r > 100
            -> "huge circle at " + x + "," + y;
        case Circle(Point(var x, var y), var r)
            -> "circle r=" + r + " at " + x + "," + y;
        case Rect(Point(var x1, var y1), Point(var x2, var y2))
            -> "rect width " + (x2 - x1) + " height " + (y2 - y1);
    };
}

Chạy trên JDK 21:

$ java java/examples/jdk21/Jdk21Features.java
circle r=5.0 at 1,2
huge circle at 0,0
rect width 4 height 3
null handled inside the switch | blank string | string x | int 7
a c [c, b, a]
one=1 two=2 {two=2, one=1}

Bốn dòng đầu thuộc bài này. Hai dòng cuối là sequenced collection, bài tiếp theo.

Vì sao "không có default" là một tính năng, không phải lười

Giả sử ai đó thêm record Triangle(...) implements Shape vào danh sách permits. Mọi switch trên Shape không có default giờ sẽ không compile được, nên compiler chỉ cho bạn mọi chỗ cần cập nhật. Mình đã xoá case Rect để xem thông báo:

$ javac Miss.java
error: the switch expression does not cover all possible input values

Nếu bạn viết default, Triangle mới sẽ lặng lẽ rơi vào default và bạn mất lời cảnh báo đó. Còn nếu một class file thay đổi sau khi compile, "trong trường hợp này compiler sẽ chèn một mệnh đề default tổng hợp (synthetic) để ném exception", nên chương trình hỏng một cách rõ ràng thay vì im lặng không làm gì.JEP 441

JDK 17 và 21

JDK 17 có sealed class, record, switch expression và instanceof pattern, nhưng không có pattern trong switch và không có record pattern. Mình đã compile ví dụ với --release 17:

$ javac --release 17 java/examples/jdk21/Jdk21Features.java
error: patterns in switch statements are not supported in -source 17

Đây là một ý hữu ích khi phỏng vấn: đây là tính năng của 21 (chính thức trong JDK 21 qua JEP 441 và JEP 440). JDK 8 thì không có gì cả: bạn viết instanceof rồi cast, hoặc dùng Visitor pattern.

Luyện tập

Trả lời theo trí nhớ, đừng cuộn lên. Thứ tự đáp án thay đổi mỗi lần bạn mở trang.

Selector là null, switch có default nhưng không có case null. Chuyện gì xảy ra?

Không có case null thì switch "ném NullPointerException, như trước đây". default không bắt null.

Mệnh đề when thêm gì vào một case?

Guard thu hẹp pattern: case chỉ khớp khi pattern khớp và điều kiện when đúng.

Lỗi ở đâu? case CharSequence cs -> ...; case String s -> ...;

Java chọn case đầu tiên áp dụng được, nên case String không bao giờ chạy. Compiler báo "this case label is dominated by a preceding case label". Cụ thể đứng trước.

Selector là một sealed interface và mọi subtype được phép đều có case. Có cần default không?

Việc kiểm tra độ bao phủ dùng mệnh đề permits, nên "không cần default label". Bỏ default còn giúp compiler cảnh báo khi có subtype mới.

Với record Point(int x, int y), khi khớp thì obj instanceof Point(int x, int y) làm gì?

Record pattern phân rã record: nó kiểm tra kiểu và gán từng component vào một biến mới.

Code có case Circle(Point(var x, var y), var r) được compile bằng javac --release 17. Kết quả?

Pattern matching cho switch và record pattern chính thức ở JDK 21. javac báo "patterns in switch statements are not supported in -source 17".

Bài kiểm tra cuối: nói trong 60 giây

Người phỏng vấn hỏi: "JDK 21 thêm gì vào switch, và nó hoạt động thế nào với sealed type và record?" Bấm giờ. Trả lời thành tiếng, nói thành câu đầy đủ. Sau đó bấm nút.

Chỉ tick những ý bạn thật sự đã nói:

Câu trả lời mẫu

"Từ JDK 21, switch có thể match theo kiểu chứ không chỉ theo hằng số. Em viết case Circle c, hoặc record pattern như case Circle(Point(var x, var y), var r), vừa check kiểu vừa lấy field ra trong một bước. Các case được thử từ trên xuống và case khớp đầu tiên thắng, nên em để case cụ thể lên trước; compiler sẽ báo lỗi nếu một case bị case trước nó dominate. Em có thể thêm guard bằng when, và có thể viết case null; nếu không có thì switch vẫn ném NullPointerException. Điểm mạnh nhất là khi dùng với sealed type: switch phải exhaustive, mà compiler biết hết các subtype được permit nên em không cần default. Sau này ai thêm subtype mới thì mọi switch chưa xử lý nó sẽ không compile được, đúng cái em muốn. Sealed interface cộng record cộng pattern switch cho Java kiểu algebraic data type thực sự, và nó chính thức ở 21, không có trên 17."

Tiếp theo là gì

Người phỏng vấn senior có thể hỏi: "Bạn còn dùng Visitor pattern không? Khi thêm subtype thì các switch cũ ra sao? Sao không đặt một method trên mỗi class?" Một câu trả lời tốt: method trên mỗi class là tốt nhất khi hành vi thuộc về chính kiểu đó; pattern switch tốt nhất khi thao tác nằm ngoài các kiểu (format, tính giá, serialize), và sealed giúp nó an toàn. Ôn lại sealed type ở bài 0014 và record ở bài 0003, rồi tiếp tục với sequenced collection.
