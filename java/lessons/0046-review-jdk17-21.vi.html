Ôn tập 7: JDK 17 và 21 đã thêm gì

Chín bài, một dòng thời gian: các tính năng ngôn ngữ bạn viết mỗi ngày kể từ 17, và bốn thay đổi lớn của 21.

Java (JDK 8, 17, 21) · Bài 0046 · bước 46/46 · Review · ~30 phút · Trang chủ · Lộ trình Java (JDK 8, 17, 21) · Lộ trình tổng · English

Vì sao có bài này? Người phỏng vấn rất thích hỏi "Java đã thay đổi gì kể từ 8?" và "Vì sao nên nâng cấp lên 21?" Câu trả lời nhảy qua lại giữa các phiên bản và chủ đề: một record, rồi virtual thread, rồi một flag GC. Bài ôn tập này trộn các bài 0012, 0013, 0003, 0014, 0027, 0015, 0016, 0006 và 0017 theo đúng cách đó. Ở đây không có kiến thức mới.
Thành quả hôm nay: trả lời đúng ít nhất 11 trên 13 câu hỏi trộn, tìm ra ba lỗi trong bài tập trộn, và nói đủ cả ba câu trả lời 60 giây, mỗi câu đạt ít nhất 5 ý trong checklist.
LTS
"Long-term support" (hỗ trợ dài hạn): bản phát hành được các vendor vá lỗi trong nhiều năm. JDK 8, 17 và 21 là những bản các công ty chạy trên production.
final (feature)
Tính năng đã hoàn thiện và cố định trong một bản phát hành, không phải bản "preview" phải tự bật.
record
Một class chỉ để chở dữ liệu; Java tự viết constructor, accessor, equals, hashCode và toString (bài 0003).
sealed type
Class hoặc interface liệt kê mọi subtype được phép bằng permits (bài 0014).
pattern
Một phép thử trong instanceof hoặc case, kiểm tra hình dạng và đặt tên cho các phần, như String s hay Point(int x, int y).
virtual thread
Thread Java rẻ, chỉ mượn một OS thread thật trong lúc chạy code (bài 0006).
generation
Một phần của heap dành cho object trẻ hoặc già; generational ZGC tách riêng chúng (bài 0017).

Trước khi bắt đầu

Không nhìn lại bài cũ, hãy kể một tính năng cho mỗi bản: 10, 14, 15, 16, 17 và 21. Rồi ghi lại bạn chắc chắn bao nhiêu (0 tới 100%). Cuối bài, so với điểm của bạn: khoảng cách giữa "chắc chắn" và "đúng" chính là thứ bài ôn tập sửa.

1. Một dòng thời gian cho tất cả

Hãy nghĩ tới một ngôi nhà được sửa từng phòng một. Nếu bạn chỉ ghé vào những ngày khánh thành, bạn bỏ lỡ phần việc ở giữa. Các công ty nhảy từ LTS này sang LTS kế tiếp (8, rồi 17, rồi 21), nên "JDK 17" nghĩa là mọi tính năng đã chính thức cho tới 17, không chỉ những gì riêng bản 17 thêm vào (bài 0013).

2. Bộ ba mô hình hoá: record + sealed + pattern switch

Ba bài thật ra là một ý tưởng. Record nói một biến thể chứa dữ liệu gì. Interface sealed nói có những biến thể nào. Pattern switch xử lý từng biến thể, và compiler kiểm tra bạn đã xử lý đủ. Hãy nghĩ tới một thực đơn có danh sách món cố định, mỗi món có một thẻ công thức riêng: nhà bếp có thể kiểm tra món nào cũng có người nấu.

Cách cũ đặt cạnh cách mới, cho cùng một việc:

// JDK 8: open class hierarchy, test and cast, a default "just in case"
if (s instanceof Circle) { Circle c = (Circle) s; return Math.PI * c.r() * c.r(); }
else if (s instanceof Rect) { Rect r = (Rect) s; return ...; }
else throw new IllegalStateException("unknown shape");

// JDK 17: sealed + records + instanceof patterns
//         (switching on types is not allowed yet)
if (s instanceof Circle c) return Math.PI * c.r() * c.r();

// JDK 21: pattern switch, exhaustive, no default
return switch (s) {
    case Circle(var c, var r) -> Math.PI * r * r;
    case Rect(var a, var b)   -> ...;
};

Hai cái bẫy nối các bài với nhau. Record chỉ bất biến nông, nên component kiểu List cần List.copyOf trong compact constructor (0003). Và một switch không có case null vẫn ném NullPointerException; trên 17 và 21, thông báo của nó cho biết biểu thức nào bị null (0015, 0027).

3. Cặp đôi runtime: virtual thread và generational ZGC

Hai thay đổi còn lại của JDK 21 không đổi cú pháp của bạn; chúng thay đổi cách JVM chạy code của bạn. Cả hai trả lời cùng một chủ đề phỏng vấn: throughput và latency.

4. Bài tập trộn: tìm ba lỗi

Đọc đoạn code JDK 21 này như một reviewer. Có ba lỗi, mỗi lỗi từ một bài khác nhau. Hãy tìm chúng, gọi tên bài, và nói cách sửa trước khi mở đáp án.

sealed interface Payment permits Card, Transfer {}

// (A) a card is a value object: nobody may change it after creation
record Card(String number, List<String> tags) implements Payment {}
record Transfer(String iban) implements Payment {}

// (B) label every payment
static String label(Payment p) {
    return switch (p) {
        case Payment x  -> "payment";
        case Card c     -> "card " + c.number();
        case Transfer t -> "transfer " + t.iban();
    };
}

// (C) the bank API allows at most 10 calls at once
ExecutorService calls = Executors.newFixedThreadPool(10, Thread.ofVirtual().factory());
Hiện ba lỗi

(B) Bài 0015. Các case được thử từ trên xuống, và case Payment x khớp với mọi thứ, nên các case sau bị lấn át (dominated). Nó thậm chí không compile; mình đã kiểm tra trên JDK 21: "this case label is dominated by a preceding case label". Cách sửa: xoá case tổng quát. Vì Payment là sealed, Card và Transfer đã bao phủ đủ, không cần default.

(A) Bài 0003. Record chỉ bất biến nông. Bên gọi vẫn giữ list tags và có thể thêm vào, thế là thẻ "bị đổi". Cách sửa: compact constructor Card { tags = List.copyOf(tags); }.

(C) Bài 0006. Đó là một pool virtual thread, dùng để giới hạn mức đồng thời. "Đừng bao giờ pool virtual thread"; hãy giới hạn bằng Semaphore: new Semaphore(10), acquire() trước lời gọi, release() trong finally, và chạy mỗi task trên newVirtualThreadPerTaskExecutor().

Luyện tập

Trả lời theo trí nhớ, đừng cuộn lên. Thứ tự đáp án thay đổi mỗi lần bạn mở trang.

Ở đâu KHÔNG được dùng var?

var chỉ dành cho biến local có giá trị khởi tạo và chỉ số vòng lặp; không cho tham số, field, kiểu trả về hay tham số catch. Xem bài 0012.

Một switch trên Shape sealed có case cho mọi record được phép. Trên JDK 21, có cần default không?

Switch dùng pattern phải exhaustive, và với kiểu sealed việc kiểm tra dùng mệnh đề permits. Xem bài 0015 và 0014.

record Team(String name, List<String> members). Bên gọi giữ lại list đã truyền vào và thêm một tên. Team thấy gì?

Field là final, nhưng nó trỏ tới cùng một list có thể thay đổi. Sửa bằng List.copyOf trong compact constructor. Xem bài 0003.

Service của bạn chạy 10.000 lời gọi HTTP blocking trên virtual thread, nhưng đối tác chỉ cho 20 lời gọi cùng lúc. Bạn thêm gì?

Đừng pool virtual thread; giới hạn mức đồng thời bằng Semaphore. Block synchronized chỉ cho một lời gọi và còn pin carrier trên 21. Xem bài 0006.

Từ khoá nào mở lại một nhánh của cây sealed để ai cũng có thể extend?

Mỗi subtype được phép phải là final, sealed hoặc non-sealed; non-sealed mở lại nhánh đó. Xem bài 0014.

Bạn khởi động một service JDK 21 chỉ với -XX:+UseZGC. Collector nào chạy?

Trên JDK 21 bạn cần -XX:+UseZGC -XX:+ZGenerational cho chế độ generational. Xem bài 0017.

Arrow label case 6, 7 -> "weekend"; làm gì sau khi chạy xong?

Với -> chỉ code bên phải chạy. yield dùng để trả giá trị từ một block. Xem bài 0013.

rev = list.reversed() trên [1, 2, 3], rồi list.add(4). rev là gì?

reversed() trả về một view, không phải bản copy, nên nó thấy phần tử mới. Xem bài 0016.

Trên JDK 21 bạn thấy Cannot invoke "String.trim()" because "<local2>[0]" is null. Vì sao là <local2> chứ không phải tên biến?

Tên biến local cần debug info; với javac -g thông báo sẽ là "names[0]". Bản thân thông báo không cần flag trên 21. Xem bài 0027.

Việc nào được lợi nhiều nhất từ virtual thread?

Virtual thread cho khả năng mở rộng với việc blocking, không cho tốc độ với việc nặng CPU. Xem bài 0006.

Selector của một switch JDK 21 là null; switch có default nhưng không có case null. Kết quả?

Không có case null thì switch ném NPE "như trước đây"; default không bắt null. Xem bài 0015.

Sau if (!(obj instanceof String s)) return;, dòng tiếp theo có dùng được s không?

Flow scoping: biến pattern có phạm vi ở nơi chắc chắn đã khớp, kể cả sau một lệnh return sớm có phủ định. Xem bài 0013.

Vì sao generational ZGC thu gom young generation thường xuyên hơn?

Giả thuyết thế hệ yếu: object trẻ thường chết sớm. Con trỏ từ old sang young vẫn có; remembered set theo dõi chúng. Xem bài 0017.

Bài kiểm tra cuối: nói trong 60 giây

Câu 1. Người phỏng vấn hỏi: "Từ Java 8 tới 17 có gì thay đổi mà bạn dùng hằng ngày?" Bấm giờ. Trả lời thành tiếng, rồi bấm nút.

Chỉ tick những ý bạn thật sự đã nói:

Câu trả lời mẫu

"Từ 8 lên 17 chủ yếu thay đổi lượng code em phải viết. Em dùng var cho biến local khi vế phải đã rõ kiểu; nó vẫn là static typing. Text block cho em dán JSON hay SQL mà không phải escape. Switch trở thành expression với arrow label, nên không còn chuyện quên break, và nó phải exhaustive. instanceof giờ vừa check vừa cast trong một bước. Record thay gần hết boilerplate của DTO, equals và hashCode lấy từ mọi component, nhưng nó chỉ bất biến nông, nên em copy list trong compact constructor. Sealed class cho em đóng một hierarchy bằng permits. Còn trên production, NullPointerException giờ nói rõ biểu thức nào bị null, đỡ mất rất nhiều thời gian debug."

Câu 2. Người phỏng vấn hỏi: "Record, sealed type và pattern matching phối hợp với nhau thế nào trong Java 21?" Bấm giờ. Trả lời thành tiếng, rồi bấm nút.

Chỉ tick những ý bạn thật sự đã nói:

Câu trả lời mẫu

"Kết hợp lại chúng cho Java kiểu algebraic data type. Em khai báo một sealed interface, ví dụ Payment permits Card, Transfer, và mỗi biến thể là một record giữ dữ liệu riêng. Rồi em xử lý bằng pattern switch: case Card(var number, var tags) vừa check kiểu vừa lấy field ra, và pattern có thể lồng nhau. Vì interface là sealed, compiler biết hết các biến thể, nên switch exhaustive mà không cần default, và nếu ai thêm biến thể thứ ba thì mọi switch chưa xử lý nó sẽ không compile được. Các case được thử từ trên xuống, case bị case trước dominate là lỗi compile, và em có thể thêm guard bằng when. Null vẫn ném exception trừ khi em viết case null. Sealed và record có từ 17, nhưng switch theo pattern thì cần 21."

Câu 3. Người phỏng vấn hỏi: "Vì sao nâng cấp backend từ 17 lên 21? Bạn sẽ cẩn thận điều gì?" Bấm giờ. Trả lời thành tiếng, rồi bấm nút.

Chỉ tick những ý bạn thật sự đã nói:

Câu trả lời mẫu

"21 là LTS tiếp theo và nó mang lại bốn lợi ích thật. Thứ nhất là virtual thread: em giữ được code blocking đơn giản, mỗi request một thread, mà xử lý được nhiều request đồng thời hơn hẳn, vì virtual thread unmount khỏi carrier trong lúc chờ. Đó là throughput, không phải tốc độ. Em sẽ để ý ba điều: không bao giờ pool chúng, dùng Semaphore để bảo vệ downstream service, và tìm chỗ bị pinning, vì trên 21 I/O lâu bên trong synchronized sẽ chặn luôn carrier. Thứ hai, generational ZGC cho pause dưới một mili giây với chi phí thấp hơn ZGC cũ, nhưng trên 21 phải thêm -XX:+ZGenerational, và em chỉ đổi khỏi G1 sau khi so sánh GC log. Thứ ba, pattern matching cho switch và record pattern làm code domain với sealed type gọn hơn nhiều. Và sequenced collection cuối cùng cho một API chung để lấy đầu, cuối và đảo ngược."
