Before you start

Without looking back, say out loud one bug from each of the four lessons that compiles fine but fails or misbehaves at run time. If you can only find two, that already tells you where to look in the table at the end.

1. The big picture: who catches the bug?

Think of two safety nets. The first is the compiler: it stops a bug before the program ever runs. The second is the running program: the bug shows up later, often in production, as a wrong answer or an exception. Many lessons in this section are about the same idea: prefer code where the first net catches the bug.

Take ten seconds per box and say why it lands in that column. If one is unclear, the lesson number is right there.

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

String a = "hi"; String b = new String("hi"); What is a == b?

== compares references, and new creates a separate object. See lesson 0018.

Which exceptions does the compiler force you to catch or declare?

Unchecked = RuntimeException, Error and their subclasses; the rest are checked. See lesson 0019.

A method must accept List<Integer> and List<Double> and only reads them. Which parameter type?

A producer ("in") uses extends; List<Number> would reject both (invariance). See lesson 0021.

try-with-resources opens A, then B. The body throws X, and B's close() throws Y. What does the catch see?

Reverse close order, and the body's exception wins with the close exception suppressed. See lesson 0019.

Why is List<Integer> not a List<Number>?

Allowing it would break type safety. See lesson 0020.

What does this print? String s = "a"; s.toUpperCase(); System.out.println(s);

Strings are immutable; the new string from toUpperCase() was thrown away. See lesson 0018.

What is true at run time about List<String> and List<Integer> created as ArrayLists?

Type erasure creates no new classes for parameterized types. See lesson 0021.

Your method reads a config file and the caller could fall back to defaults if it is missing. Checked or unchecked?

The tutorial's guideline: recoverable → checked; not recoverable → unchecked. See lesson 0019.

Number[] arr = new Integer[2]; arr[0] = 1.5; What happens?

Arrays are covariant and checked at run time; generics are invariant and checked at compile time. See lesson 0020.

The final test: say it in 60 seconds

Three questions this time. Do them one by one, with a timer, out loud.

Question 1: "Why is String immutable, and what goes wrong with ==?"

Tick only the points you really said:

Example answer

"Strings are immutable, so any change gives me a new string. That makes them safe to share, and lets Java keep a pool where equal literals are one object. That's the trap with ==: it compares references, so it works for two literals but fails for a string from a request. I always compare with "x".equals(value), and in a loop I build text with a StringBuilder."

Question 2: "Checked versus unchecked exceptions, and how does try-with-resources behave when things fail?"

Tick only the points you really said:

Example answer

"Runtime exceptions and errors are unchecked; every other exception is checked, so I must catch it or declare it with throws. I make an exception checked when the caller can reasonably recover. For resources I use try-with-resources: it closes them in reverse order before my catch runs, and if both the body and close fail, I get the body's exception with the close one attached as suppressed."

Question 3: "Is a List<Integer> a List<Number>? Explain wildcards and erasure."

Tick only the points you really said:

Example answer

"No. Generics are invariant: if a List<Integer> were a List<Number>, I could add a Double into it. Arrays allow that and fail at run time with ArrayStoreException. To accept several list types I use wildcards: ? extends for a list I read from, ? super for one I write into, like in Collections.copy. And generics are erased after compilation, so at run time all ArrayLists are one class and I can't check instanceof List<String>."

Mixed task: find the bugs

This small class compiles (assume Order is a record with an id()). It hides four problems from three different lessons. Find at least three, say which lesson each comes from, and how to fix it. Then open the answer.

class ReportService {
    String build(List<Order> orders) {
        String report = "";
        for (Order o : orders) report += o.id() + "\n";
        return report;
    }

    boolean isAdmin(String role) {           // role comes from a request
        return role == "ADMIN";
    }

    void save(String text) {
        try {
            FileWriter w = new FileWriter("report.txt");
            w.write(text);
            w.close();
        } catch (IOException e) { }
    }

    double total(List<Number> amounts) {     // callers have List<Integer>
        double t = 0;
        for (Number n : amounts) t += n.doubleValue();
        return t;
    }
}
Show the answer
  1. report += in a loop (0018): a new String per order. Use one StringBuilder.
  2. role == "ADMIN" (0018): compares references; a run-time string is a new object. Use "ADMIN".equals(role).
  3. Writer not closed if write fails, and the error is swallowed (0019): use try (FileWriter w = new FileWriter(...)) and log or rethrow in the catch.
  4. List<Number> parameter (0020, 0021): callers with List<Integer> get a compile error. Use List<? extends Number>.
