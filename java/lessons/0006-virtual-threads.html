Virtual threads: scale, not speed

How JDK 21 runs ten thousand waiting tasks on a handful of real threads, and the two rules that keep it working.

Java (JDK 8, 17, 21) · Lesson 0006 · step 44 of 46 · Advanced · ~25 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? A typical backend service spends most of its time waiting: for the database, for another HTTP service, for a queue. Virtual threads, final in JDK 21, change how many of those waits one server can handle. It is now one of the most common senior Java questions: "What are virtual threads, when do they help, and what can go wrong?"
Today's win: explain what a virtual thread is, when it helps, and the two rules: don't pool them, and use a Semaphore to limit concurrency.
thread
One line of work running inside your program. Several threads can run at the same time, each with its own steps.
OS thread
A thread managed by the operating system. It is expensive: the OS gives each one its own memory, so you can only have a few thousand.
platform thread
The classic Java thread. Each one is "a thin wrapper around an operating system (OS) thread".
virtual thread
A lightweight Java thread that borrows an OS thread only while it is actually running code.
carrier thread
The platform thread a virtual thread is currently running on.
blocking I/O
A call that waits for the outside world: a database query, an HTTP call, reading a file, Thread.sleep.
throughput
How many tasks finish per second. Latency is how long one task takes.

Before you start

Say out loud: "My server has a pool of 200 threads. Each request calls a database that answers in 1 second. How many requests per second can it handle at most?" Keep your number; you will check it in section 3.

1. The old way: one waiter per table

Imagine a restaurant where each waiter takes an order, walks to the kitchen and then stands there until the food is ready. With 200 waiters you can serve 200 tables at once. Table 201 waits at the door, even though most waiters are doing nothing but standing.

That is a classic Java server. Each request gets a platform thread, and "A platform thread is implemented as a thin wrapper around an operating system (OS) thread."core libraries guide OS threads are costly, so we keep a fixed pool of them (lesson 0023):

// JDK 8 / 17 style: a fixed pool of 200 platform threads
// (try-with-resources on an executor needs JDK 19+;
//  on 8 and 17 call shutdown() instead)
try (var pool = Executors.newFixedThreadPool(200)) {
    for (int i = 0; i < 10_000; i++) {
        pool.submit(() -> {
            Thread.sleep(Duration.ofSeconds(1));   // holds its OS thread
            return null;
        });
    }
}

While a thread waits for the database, it holds its OS thread and does nothing. Only 200 tasks run at a time, so 10,000 one-second tasks need about 10,000 / 200 × 1 s = 50 seconds. That was your answer to "Before you start": at most 200 requests per second.

2. The new way: waiters who don't stand around

Now the waiters take an order, hand it to the kitchen, and go serve another table. When the food is ready, any free waiter picks it up. A few waiters can serve hundreds of tables, because nobody stands still.

That is a virtual thread. "Like a platform thread, a virtual thread is also an instance of java.lang.Thread. However, a virtual thread isn't tied to a specific OS thread." When code in a virtual thread calls a blocking I/O operation, the runtime suspends it and frees the OS thread for other virtual threads.core libraries guide

JEP 444 names the parts. The JDK runs a virtual thread "by mounting the virtual thread on a platform thread", and "The platform thread to which the scheduler assigns a virtual thread is called the virtual thread's carrier." When the virtual thread blocks, it "can unmount from its carrier".JEP 444

Who decides which virtual thread runs on which carrier? A scheduler: "The JDK's virtual thread scheduler is a work-stealing ForkJoinPool that operates in FIFO mode." Its parallelism, the number of carriers, is "By default ... equal to the number of available processors".JEP 444 On an 8-core machine you get about 8 carriers, however many virtual threads you create.

3. Ten thousand sleeps in one second

Here is the course example. Compare it with the pool code in section 1: only one line changed.

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 10_000; i++) {
        executor.submit(() -> {
            Thread.sleep(Duration.ofSeconds(1)); // blocks: v-thread unmounts
            return null;
        });
    }
} // close() waits for all tasks
$ java java/examples/VirtualThreadsDemo.java
10,000 one-second tasks finished in 1065 ms

Ten thousand one-second sleeps finish in about one second. With a fixed pool of 200 platform threads the same job would take about 50 seconds (10,000 / 200 × 1 s); try it in the exercise. Follow one task:

Step 1  submit() creates a new virtual thread v1 for the task
Step 2  the scheduler mounts v1 on a free carrier; v1 starts running
Step 3  v1 calls Thread.sleep(1 s): it unmounts, the carrier is free again
Step 4  the carrier runs v2, v3, ... which also sleep and unmount
Step 5  after 1 s, v1 is ready: it mounts on any free carrier and returns
        all 10,000 wait at the same time, so the whole job takes ~1 s

You can also create virtual threads directly. JEP 444: "Thread.Builder, Thread.ofVirtual(), and Thread.ofPlatform() are new APIs to create virtual and platform threads", and "Thread.startVirtualThread(Runnable) is a convenient way to create and then start a virtual thread."JEP 444 Also, "Virtual threads are always daemon threads", so they do not keep the JVM alive on their own.JEP 444

4. Scale, not speed

"Virtual threads are not faster threads; they do not run code any faster than platform threads. They exist to provide scale (higher throughput), not speed (lower latency)."core libraries guide They suit thread-per-request servers with lots of blocking I/O; write simple blocking code.

Back to the restaurant: smart waiters don't make the kitchen cook faster. One dish still takes ten minutes. What changes is how many tables you serve at once. JEP 444 puts it formally: "The scalability of server applications is governed by Little's Law".JEP 444 In simple words, requests per second ≈ requests in progress ÷ time per request. With 1-second waits, 200 threads give 200 per second; 10,000 virtual threads give about 10,000 per second.

Trap: CPU-heavy work

If each task computes for 1 second (hashing, image resizing) instead of waiting, it never blocks, so it never unmounts. You still have only as many carriers as CPU cores, and the job takes just as long as with a platform pool. Virtual threads help with waiting, not with computing.

5. Two rules: don't pool them, limit with a Semaphore

Rule 1: "Never pool virtual threads." Use one virtual thread per task: Executors.newVirtualThreadPerTaskExecutor().core libraries guide The guide explains why: "Pools are designed to share scarce resources, and virtual threads aren’t scarce and therefore should never be pooled!"core libraries guide Creating one is cheap; JEP 444 shows a program that creates 10,000 and talks about being able to "create 1,000,000 virtual threads that run concurrently".JEP 444

Rule 2: limit concurrency with a Semaphore, not a pool.core libraries guide Old code often used a pool of 10 threads also to protect a slow service from more than 10 calls at once. Without the pool you still need that limit. A semaphore is a bowl of 10 tickets: take one before the call, give it back after. The guide's example:core libraries guide

Semaphore sem = new Semaphore(10);
...
Result foo() {
    sem.acquire();      // wait for a ticket (an 11th caller waits here)
    try {
        return callLimitedService();
    } finally {
        sem.release();  // always give the ticket back
    }
}

One more caution from JEP 444: since you may have millions of virtual threads, "use thread locals only after careful consideration".JEP 444 A big object cached in a ThreadLocal used to exist 200 times; now it may exist once per task.

6. The catch: pinning

Sometimes a virtual thread cannot unmount while it waits. It is then pinned to its carrier, for example in native calls, which hurts scalability but not correctness.core libraries guide On JDK 21 the guide lists two cases: "The virtual thread runs code inside a synchronized block or method" and "The virtual thread runs a native method or a foreign function".core libraries guide

In the restaurant: a waiter who holds the only key to the wine cellar while waiting at the kitchen can't hand the key over, so he must stand there. That waiter is pinned.

You can see it. "The system property jdk.tracePinnedThreads triggers a stack trace when a thread blocks while pinned."JEP 444 I ran a virtual thread that sleeps inside synchronized (lock) on JDK 21:

$ java -Djdk.tracePinnedThreads=short Pin.java
VirtualThread[#20]/runnable@ForkJoinPool-1-worker-1 reason:MONITOR
    Pin.lambda$main$0(Pin.java:6) <== monitors:1
virtual? true, daemon? true

Read it: virtual thread #20, running on carrier ForkJoinPool-1-worker-1, blocked while holding a monitor (a synchronized lock) at line 6. The last line confirms it was virtual and a daemon.

The fix on JDK 21: for synchronized blocks that run often and wrap long I/O, use a ReentrantLock (lesson 0024).core libraries guide

// Before: pins the carrier thread during frequentIO()
synchronized(lockObj) {
    frequentIO();
}

// After
lock.lock();
try {
    frequentIO();
} finally {
    lock.unlock();
}

After 21: JEP 491, delivered in JDK 24, lets virtual threads unmount inside synchronized, which "will eliminate nearly all cases of virtual threads being pinned". Native calls can still pin.JEP 491 This course targets 21, so the ReentrantLock advice still applies to you.

JDK 8 vs 17 vs 21

Virtual threads are final in JDK 21 (JEP 444). JDK 8 and 17 have only platform threads, so you size a pool (lesson 0023) or go asynchronous with CompletableFuture (lesson 0010). On 21 you can write plain blocking code again and still scale.

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

What is the main benefit of virtual threads?

They provide scale (throughput), not speed. One task takes as long as before; many more run at once.

How should you manage virtual threads?

Represent every task as a virtual thread; never pool them. They are cheap, and pools exist to share scarce resources.

Your service may call a partner API at most 10 times at once. With virtual threads, how do you enforce it?

The docs recommend a Semaphore to limit concurrency, not a pool.

Which workload gains the least from virtual threads?

CPU-bound work does not block, so unmounting brings no benefit; virtual threads run code no faster.

On JDK 21, a virtual thread calls a slow HTTP API inside a synchronized block. What happens?

In JDK 21, code inside synchronized pins the virtual thread. The result is still correct, but the carrier can't serve others. Use ReentrantLock for long I/O there.

A pool of 200 platform threads runs 10,000 tasks that each sleep 1 second. About how long does it take?

200 tasks at a time, 1 second each: 10,000 / 200 × 1 s = 50 s. With virtual threads it took about 1 s.

Tick only the points you really said:

Example answer

"A virtual thread is a normal java.lang.Thread, but it isn't tied to an OS thread. The JDK mounts it on a carrier thread from a small ForkJoinPool, and when it blocks on I/O, like a database call, it unmounts and the carrier runs another virtual thread. So I can have one thread per request, even tens of thousands, and write simple blocking code. It's about throughput, not speed: one request is not faster, and CPU-heavy work gains nothing. Two rules: I never pool them, I use newVirtualThreadPerTaskExecutor, and if I need to limit calls to a downstream service I use a Semaphore instead of a small pool. The main pitfall on JDK 21 is pinning: inside synchronized or native code the virtual thread can't unmount, so for frequent long I/O under a lock I switch to ReentrantLock, and I find those spots with -Djdk.tracePinnedThreads."
