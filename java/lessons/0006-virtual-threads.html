Virtual threads: scale, not speed

Java (JDK 8, 17, 21) · Lesson 0006 · step 26 of 27 · Advanced · ~10 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap

Today's win: explain what a virtual thread is, when it helps, and the two rules: don't pool them, and use a Semaphore to limit concurrency.

What they are

"Like a platform thread, a virtual thread is also an instance of java.lang.Thread. However, a virtual thread isn't tied to a specific OS thread." When code in a virtual thread calls a blocking I/O operation, the runtime suspends it and frees the OS thread for other virtual threads.[1]

Scale, not speed

"Virtual threads are not faster threads; they do not run code any faster than platform threads. They exist to provide scale (higher throughput), not speed (lower latency)."[1] They suit thread-per-request servers with lots of blocking I/O; write simple blocking code.

Two rules

  • "Never pool virtual threads." One virtual thread per task: Executors.newVirtualThreadPerTaskExecutor().[1]
  • To limit concurrency (say, calls to a downstream service), use a Semaphore, not a pool.[1]

Caveat: virtual threads can be pinned to their carrier, for example in native calls, which hurts scalability but not correctness.[1]

Ten thousand one-second sleeps finish in about one second. With a fixed pool of 200 platform threads the same job would take about 50 seconds (10,000 / 200 x 1 s); try it in the exercise.

Retrieval practice

Answer from memory. One attempt each.

1. Main benefit of virtual threads?

They provide scale (throughput), not speed.[1]

2. How should you manage virtual threads?

Represent every task as a virtual thread; never pool them.[1]

3. How do you cap concurrent downstream calls?

The docs recommend a Semaphore to limit concurrency.[1]

4. Which workload gains least from virtual threads?

CPU-bound work does not block, so unmounting brings no benefit; they run code no faster.[1]
