Why one thread may not see another thread's write

Threads, shared memory, CPU caches, and the happens-before rule that makes a write visible.

Java (JDK 8, 17, 21) · Lesson 0005 · step 30 of 46 · Advanced · ~25 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? Every backend service runs many threads at once, and bugs between threads are the hardest to find: they appear once a week, only in production. Interviewers test this with "What does volatile do?" and "What is happens-before?" This lesson gives you the picture behind both answers.
Today's win: explain why a thread can miss another thread's write, and name three ways to create a happens-before edge.
thread
One line of work inside your program. A program can run several threads at the same time, like several cooks in one kitchen.
shared memory
Memory that all threads of a program can read and write, for example a field of an object that two threads both use.
CPU cache
A small, very fast memory inside each processor core. The core keeps copies of recently used values there so it does not have to go to main memory every time.
visibility
Whether a value written by one thread can be seen by another thread.
data race
Two threads touch the same variable, at least one of them writes, and nothing puts the two accesses in order.
happens-before
A rule from the Java specification: if A happens-before B, then B is guaranteed to see what A wrote.
volatile
A keyword you put on a field. Writes to it become visible to every later read of it, in any thread.
synchronized
A keyword that lets only one thread at a time run a block of code, guarded by a lock on an object.

Before you start

Say out loud: "Thread W runs while (!stop) {}. The main thread later sets stop = true. Is W guaranteed to stop?" Guess, and give a reason. You will check your answer in section 3.

1. What is a thread?

Think of a restaurant kitchen. The kitchen is your program. Each cook is a thread: they follow their own list of steps, at their own speed, at the same time as the others.

The Oracle tutorial says it the same way: "Threads exist within a process — every process has at least one." When your program starts, you have one thread, "called the main thread".Java tutorial: threads You can start more:

Thread worker = new Thread(() -> {
    System.out.println("hello from the worker");
});
worker.start();   // the worker now runs at the same time as main
worker.join();    // main waits here until the worker has finished
  • new Thread(...) creates the thread. The code inside () -> { ... } (a lambda, a small piece of code you pass around) is the work it will do.
  • start() makes it run. From now on two cooks work in parallel.
  • join() makes the main thread wait until the worker is done.

2. Shared memory and CPU caches

All the cooks share one whiteboard on the wall: that is shared memory. "Threads share the process's resources, including memory and open files", which the tutorial calls "efficient, but potentially problematic".Java tutorial: threads

Walking to the whiteboard is slow, so each cook copies the values they need onto a personal notepad. That notepad is the CPU cache. A cook may keep reading the notepad and never look at the whiteboard again. Another cook may write a new value on their notepad and copy it to the whiteboard much later.

This picture is a mental model. The Java specification does not talk about caches at all; it only says which reads are guaranteed to see which writes. Caches, the compiler and the CPU are all allowed to reorder or delay things, as long as a single thread cannot notice. Another thread can notice.

The Oracle tutorial shows the simplest case: thread A runs counter++, then thread B prints counter. The value printed "might well be "0", because there's no guarantee that thread A's change to counter will be visible to thread B — unless the programmer has established a happens-before relationship between these two statements."Java tutorial: memory consistency

The Java Language Specification (JLS) gives this situation a name. Two accesses to the same variable are conflicting if at least one is a write, and a program with "two conflicting accesses that are not ordered by a happens-before relationship" contains a data race.JLS 17.4.5 Without that ordering the reader is not guaranteed to see the write, and the JVM is free to reorder.

3. Watch it: the stop flag

Here is the example program, StopFlag.java, slightly shortened:

static volatile boolean stop = false;

Thread worker = new Thread(() -> {
    long spins = 0;
    while (!stop) spins++;                 // keep reading stop
    System.out.println("worker saw stop after spinning");
});
worker.start();
Thread.sleep(200);                         // main waits 0.2 s
stop = true;                               // volatile write
worker.join(2000);                         // wait at most 2 s for the worker

Follow it step by step:

Step 1  main starts the worker                   start() happens-before the worker's actions
Step 2  worker reads stop → false, spins, reads again, again…
Step 3  main writes stop = true                  a volatile write
Step 4  worker's next read of stop               a volatile read that comes later
        → the rule says it must see true          → the loop ends
Step 5  main's join() returns                    the worker has finished
$ java java/examples/StopFlag.java
worker saw stop after spinning
worker finished

Now imagine you delete volatile. Step 4 loses its guarantee. The worker may see true quickly, much later, or never: the compiler is even allowed to read stop once and keep the value. The specification does not promise a hang or a success; that is exactly the point. You will try it in the exercise.

4. The rule: happens-before

Back to the kitchen. A cook writes "table 5 is ready" on the whiteboard and then rings a bell. Any cook who hears the bell and then looks at the board is guaranteed to see the note, and everything written before the bell. The bell is a happens-before edge.

The JLS builds the rule from small pieces:JLS 17.4.5

  • Program order: "If x and y are actions of the same thread and x comes before y in program order, then hb(x, y)." Inside one thread, earlier lines happen-before later lines.
  • Synchronization edges between threads (the list below).
  • Transitivity: "If hb(x, y) and hb(y, z), then hb(x, z)." Edges chain together.

Trace the chain in the picture:

Step 1  data = 42      hb  stop = true       program order in main
Step 2  stop = true    hb  read stop → true  volatile write, later volatile read
Step 3  read stop      hb  read data         program order in worker
Step 4  transitivity:  data = 42  hb  read data   →  the worker sees 42

This is the common "publish then flag" pattern: prepare the data with plain writes, then do one volatile write as the signal.

What creates a happens-before edge

  • An unlock of a monitor happens-before every later lock of that same monitor (synchronized).JLS 17.4.5
  • A write to a volatile field happens-before every later read of that field.JLS 17.4.5
  • Thread.start() happens-before the started thread's actions; a thread's actions happen-before another thread returns from join() on it.JLS 17.4.5
  • Library edges: putting an object into a concurrent collection, submitting to an Executor, Future.get(), Lock.unlock/lock, CountDownLatch.countDown/await.java.util.concurrent: Memory Consistency Properties

So with synchronized the bell is "unlock, then the next lock of the same object". If the writer and the reader use different lock objects, there is no edge.

The payoff: "If a program is correctly synchronized, then all executions of the program will appear to be sequentially consistent."JLS 17.4.5 In plain words: remove every data race and you can reason about your program as if the threads' steps were simply interleaved, one at a time. You reason about interleavings, not reorderings.

JDK 8 vs 17 vs 21: these rules are the same in all three versions. What changed around them is the tooling (for example virtual threads in JDK 21, lesson 0006), not the memory model.

5. Traps that interviewers like

Trap 1: "volatile makes count++ safe"

It does not. volatile gives visibility and ordering, not atomicity of count++, which is three steps: read, add one, write. Two threads can both read 5 and both write 6. That is the next interview follow-up, and lesson 0024 shows the lost updates and the fix.

Trap 2: torn long and double

A non-volatile long or double write may be treated as two 32-bit writes, so a reader can see a torn value: half from one write, half from another. "Writes and reads of volatile long and double values are always atomic."JLS 17.7

Trap 3: "it worked on my laptop"

A racy program can pass every test on your machine and fail on a server with more cores or after the JIT compiler optimizes the loop. A test that passes proves nothing about a data race. The fix is to create the edge on purpose: volatile, synchronized, a lock, or a java.util.concurrent class.

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

According to the JLS, what makes two conflicting accesses a data race?

A data race is two conflicting accesses (at least one write) that no happens-before relationship orders (JLS 17.4.5).

Which of these does NOT create a happens-before edge between two threads?

Plain accesses give no cross-thread ordering by themselves. The other three are listed edges in JLS 17.4.5.

What does volatile NOT give you?

count++ is read, add, write: three steps. volatile makes each step visible but does not glue them together.

Main writes data = 42 (plain), then ready = true (volatile). The worker reads ready and gets true, then reads data. What does it see?

Program order in main + the volatile edge + program order in the worker, joined by transitivity, give hb(data = 42, read data).

You remove volatile from the stop flag. What does the specification promise?

Without a happens-before edge there is no guarantee either way. That is why a passing test proves nothing.

What does the JLS promise for a correctly synchronized program?

That is the JLS guarantee for programs free of data races: you may reason about simple interleavings. It says nothing about deadlock or speed.

The final test: say it in 60 seconds

An interviewer asks: "What is happens-before, and when do you need volatile?" Start a timer. Answer out loud, in full sentences. Then click the button.

Tick only the points you really said:

Example answer

"Threads share the heap, but each core can cache values and the compiler can reorder code, so without some ordering one thread may never see another thread's write. The Java memory model defines that ordering as happens-before: if action A happens-before B, B sees what A wrote. If two threads access the same variable, one writes, and there's no happens-before between them, that's a data race. I create edges with a volatile write followed by a read, with unlock and lock of the same monitor, with Thread.start and join, or with java.util.concurrent classes like executors and latches. Edges chain with program order, so I can write data normally and then set a volatile flag to publish it. I use volatile for simple flags and publication, but not for count++, because volatile doesn't make read-modify-write atomic; for that I use an atomic or a lock."
