Sharing a map between threads: ConcurrentHashMap

A thread-safe map does not make your code thread-safe. Its atomic methods do.

Java (JDK 8, 17, 21) · Lesson 0025 · step 32 of 46 · Advanced · ~22 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? Caches, session stores, counters per user, per endpoint, per error code: services keep shared maps everywhere. Interviewers ask "HashMap vs ConcurrentHashMap?" and then the real question: "Can you still lose updates with a ConcurrentHashMap?"
Today's win: use ConcurrentHashMap atomic methods correctly and explain its null rule and weakly consistent iterators.
thread-safe
A class is thread-safe if many threads can call its methods at the same time and it still behaves correctly.
check-then-act
Code that first looks at a value ("is the key there?") and then acts on what it saw ("then put it"). Another thread can change things in between.
atomic method
A method that does its whole job as one step that other threads cannot interrupt halfway.
iterator
The object a for (x : map.keySet()) loop uses behind the scenes to walk through the entries one by one.
fail-fast
An iterator that throws ConcurrentModificationException as soon as it notices the map was changed under it.
weakly consistent
An iterator that never throws for concurrent changes; it may or may not show changes made after it started.
LongAdder
A thread-safe counter built for many threads adding at once (from lesson 0024).

Before you start

Say out loud: "Two threads run map.put(word, map.get(word) + 1) on a ConcurrentHashMap. Can a count be lost?" Decide yes or no and give a reason. Section 3 has the answer.

1. Why a plain HashMap is not enough

Picture one notebook in an office where everybody writes down orders. If two people write on the same page at the same moment, the page gets messy. A plain HashMap is that notebook. Its Javadoc says: "Note that this implementation is not synchronized. If multiple threads access a hash map concurrently, and at least one of the threads modifies the map structurally, it must be synchronized externally."HashMap javadoc

ConcurrentHashMap (often "CHM") is a notebook designed for a crowd. Several people can read and write different pages at the same time, safely.

2. What ConcurrentHashMap promises

  • Reads don't lock. "Retrieval operations (including get) generally do not block", and "retrieval operations do not entail locking". A read sees "the results of the most recently completed update operations holding upon their onset"; updates enjoy high expected concurrency.CHM javadoc
  • No whole-table lock. There is "not any support for locking the entire table in a way that prevents all access".CHM javadoc
  • Visibility comes for free. Actions in a thread before putting an object into a concurrent collection happen-before actions after another thread reads or removes it (the edge from lesson 0005).java.util.concurrent: memory consistency

So each single call is safe. The trap is in combining calls.

3. Thread-safe map, racy code

Here is the counter from "Before you start":

Integer old = map.get("hits");              // step 1: read
map.put("hits", old == null ? 1 : old + 1); // step 2: write

Each call is thread-safe, but between them another thread can do the same thing. It is the same lost update as count++ in lesson 0024, one level up. This pattern is called check-then-act, and it races even on a concurrent map.

The fix: the atomic compound methods

CHM gives you methods that do the read and the write as one step: putIfAbsent, computeIfAbsent, computeIfPresent, compute, merge. For merge and computeIfAbsent the Javadoc says: "The entire method invocation is performed atomically."CHM javadoc

map.merge("hits", 1, Integer::sum);

Read it as: "if hits has no value, put 1; otherwise replace the old value with old + 1". Trace two threads:

Step 1  A calls merge: hits absent → put 1         (one step)
Step 2  B calls merge: hits = 1 → sum(1, 1) = 2    (one step)
Step 3  If B arrives while A is inside merge for the same key,
        B may wait a moment. It never sees a half-done update.
$ java java/examples/ChmDemo.java
merge() total   : 400000 (expected 400000)
null key        : NullPointerException
modified while iterating: no exception, size=9
HashMap          : ConcurrentModificationException

The first line: four threads each called merge("hits", 1, Integer::sum) 100,000 times, and no count was lost.

The scalable counter idiom

For a frequency map with very many threads, the Javadoc's own idiom is:CHM javadoc

ConcurrentHashMap<String, LongAdder> freqs = new ConcurrentHashMap<>();
freqs.computeIfAbsent(key, k -> new LongAdder()).increment();

computeIfAbsent creates the counter once, atomically; then increment() on the LongAdder is thread-safe by itself.

Rules for the function you pass

While the function runs, "some attempted update operations on this map by other threads may be blocked", "so the computation should be short and simple". The mapping function "must not modify this map during computation", and the merge function "must not attempt to update any other mappings of this Map".CHM javadoc So: no database call, no HTTP call, no map.put inside computeIfAbsent.

JDK 8 vs 17 vs 21: merge, compute* and putIfAbsent-style default methods on Map exist since JDK 8 (Since: 1.8)Map javadoc, so this lesson's code works the same on 8, 17 and 21.

4. No nulls allowed

"Like Hashtable but unlike HashMap, this class does not allow null to be used as a key or value."CHM javadoc You saw it in the output: counts.put(null, 1) throws NullPointerException.

A practical way to remember why it helps: if nulls are impossible, then get(key) returning null can only mean "the key is absent". With a HashMap you would also have to ask "or is the value null?", and between those two questions another thread could change the map.

5. Iterating while others write

A HashMap iterator is fail-fast: if the map is structurally changed after the iterator is created (other than through the iterator itself), it throws ConcurrentModificationException.HashMap javadoc CHM iterators are weakly consistent: they return elements "reflecting the state of the hash table at some point at or since the creation of the iterator", and "They do not throw ConcurrentModificationException. However, iterators are designed to be used by only one thread at a time."CHM javadoc

The demo adds keys while looping over a 3-key map. CHM finishes with 9 entries and no exception (some new keys were visited and added more; on another run or JDK the number could differ). The HashMap version throws.

Trap: size() is a snapshot, not a fact

Results of "size, isEmpty, and containsValue are typically useful only when a map is not undergoing concurrent updates"; otherwise they are fine "for monitoring or estimation purposes, but not for program control".CHM javadoc So if (map.size() < 100) map.put(...) is another check-then-act race.

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

What happens on concurrentHashMap.put(null, 1)?

Unlike HashMap, CHM does not allow null keys or values.

You add keys to a CHM while a for-each loop walks its keys. What happens?

CHM iterators are weakly consistent: they never throw CME and reflect the map at some point at or since they were created.

Two threads count words in a CHM. Which line is safe?

merge runs atomically. The others are check-then-act: two safe calls with a gap where another thread can write.

What is the rule for the function you pass to computeIfAbsent?

Other updates may block while it runs, and the function must not modify the map during computation.

The code does if (map.size() < 100) map.put(k, v) from many threads. What is the bug?

size() during concurrent updates is for monitoring, not program control, and the gap between check and put lets the map grow past 100.

Which statement about reads in CHM is true?

Retrievals do not entail locking and reflect the most recently completed updates. There is no whole-table lock at all.

The final test: say it in 60 seconds

An interviewer asks: "HashMap vs ConcurrentHashMap: what's the difference, and can you still lose updates with ConcurrentHashMap?" Start a timer. Answer out loud, in full sentences. Then click the button.

Tick only the points you really said:

Example answer

"HashMap isn't synchronized, so if several threads modify it I'd need external locking, and its iterators are fail-fast. ConcurrentHashMap is built for concurrency: every single call is thread-safe, gets don't lock, and there's no lock on the whole table. But yes, I can still lose updates if I do check-then-act, like get then put: two threads read the same value and one put overwrites the other. So I use the atomic methods: merge for counters, computeIfAbsent to create a value once, for example with a LongAdder for hot counters. The function I pass must be short and must not touch the map. Two more differences: ConcurrentHashMap doesn't allow null keys or values, and its iterators are weakly consistent, so they never throw ConcurrentModificationException. And size is only an estimate while other threads are writing."
