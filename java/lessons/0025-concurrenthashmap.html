ConcurrentHashMap: atomic updates and weak consistency

Java (JDK 8, 17, 21) · Lesson 0025 · step 15 of 27 · Advanced · ~10 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap

Today's win: use ConcurrentHashMap atomic methods correctly and explain its null rule and weakly consistent iterators.

Behavior

  • "Retrieval operations (including get) do not entail locking" and reflect the most recently completed updates; updates enjoy high expected concurrency.[1]
  • Iterators are weakly consistent and do not throw ConcurrentModificationException; use them from one thread at a time.[1] Compare HashMap, whose iterators are fail-fast.[2]
  • Null keys and values are not permitted (NullPointerException).[1]
  • Atomic compound methods: putIfAbsent, computeIfAbsent, computeIfPresent, compute, merge. Functions passed to them must be short and must not modify the map.[1]
  • size(), isEmpty() are only useful without concurrent updates.[1]
java java/examples/ChmDemo.java
merge() total   : 400000 (expected 400000)
null key        : NullPointerException
modified while iterating: no exception, size=9
HashMap          : ConcurrentModificationException

The docs' frequency-count idiom: map.computeIfAbsent(key, k -> new LongAdder()).increment().[1] A "check then put" with a plain get/put is a race even on a concurrent map; use the atomic methods. Source: ChmDemo.java.

Retrieval practice

Answer from memory. One attempt each.

1. Can ConcurrentHashMap hold a null key?

Null keys and values are not permitted.[1]

2. Do its iterators throw ConcurrentModificationException?

Iterators are weakly consistent and do not throw CME.[1]

3. Atomic way to count occurrences?

merge (or computeIfAbsent with LongAdder) is atomic; get-then-put races.[1]

4. Mapping functions in compute methods must...?

They should be short and must not update the map.[1]
