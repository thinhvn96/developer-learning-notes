How switch takes objects apart (JDK 21)

Pattern matching for switch and record patterns: test the type, unpack the fields, and let the compiler check you forgot nothing.

Java (JDK 8, 17, 21) · Lesson 0015 · step 42 of 46 · Advanced · ~25 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? Real code often receives "one of several kinds of thing": a payment that is a card or a bank transfer, an event that is created, paid or cancelled. Before JDK 21 you handled that with long if / else if / instanceof chains. Interviewers ask "What did JDK 21 add to switch, and why does it matter with sealed types and records?" This lesson answers it.
Today's win: write a JDK 21 switch that destructures records, uses when guards and case null, and needs no default on a sealed type.
selector
The value you put in the brackets of switch (...). Java compares it with each case.
pattern
A small "shape test" in a case, such as String s. If the value has that shape, the test succeeds and Java fills in the variable.
type pattern
A pattern that tests the type: case Integer i means "if it is an Integer, call it i".
record pattern
A pattern that tests for a record type and unpacks its fields in one go: case Point(int x, int y).
guard
An extra condition after when. The case matches only if the pattern matches and the condition is true.
exhaustive
"Covers every possible value." The compiler refuses a pattern switch that could fall through without any case matching.
sealed type
A class or interface that lists all its allowed subtypes with permits (lesson 0014), so the compiler knows the full list.

Before you start

Say out loud: "I have an Object. It can be an Integer, a String or null. How do I print a different message for each one in Java 8?" Don't look anything up. You will compare with the JDK 21 way at the end.

1. The old way: a chain of questions

Picture a post office worker sorting parcels. For each parcel she asks: "Is it a letter? No. Is it a small box? No. Is it a big box? Yes, put it there." Every question is written separately, and if she forgets a kind of parcel, nobody warns her.

That is the old Java code. JEP 441 shows it with a comment "Prior to Java 21":JEP 441

static String formatter(Object obj) {
    String formatted = "unknown";
    if (obj instanceof Integer i) {
        formatted = String.format("int %d", i);
    } else if (obj instanceof Long l) {
        formatted = String.format("long %d", l);
    } else if (obj instanceof String s) {
        formatted = String.format("String %s", s);
    }
    return formatted;
}

This already uses the JDK 16 instanceof pattern from lesson 0013. In JDK 8 it is even longer: if (obj instanceof Integer) { Integer i = (Integer) obj; ... }, a test and then a cast for every branch.

Three problems: the code repeats itself, the order of the ifs is easy to get wrong, and the compiler cannot tell you that you forgot a kind.

2. The new way: patterns inside case

JDK 21 lets you put type patterns in case labels, so the selector is tested against several patterns with an action for each.JEP 441 The same method becomes:

static String formatter(Object obj) {
    return switch (obj) {
        case Integer i -> String.format("int %d", i);
        case Long l    -> String.format("long %d", l);
        case String s  -> String.format("String %s", s);
        default        -> "unknown";   // needed: Object has endless subtypes
    };
}

Read case Integer i -> as: "if obj is an Integer, call it i and run the code on the right." The -> arrow means no fall-through, exactly like the switch expressions of lesson 0013.

How does Java pick a case? "The first case label appearing in a switch block that applies to a value is chosen."JEP 441 Let's trace formatter(42L):

formatter(42L);
Step 1  Is 42L an Integer?  no  → try the next case
Step 2  Is 42L a Long?      yes → bind l = 42L
Step 3  Run the right side  → String.format("long %d", 42L)
        returns "long 42"

3. Guards with when, and why order matters

Sometimes the type is not enough. You want "a String, but only if it is blank". Add a guard with when: it refines a pattern.JEP 441

static String nullSafe(Object o) {
    return switch (o) {
        case null -> "null handled inside the switch";
        case String str when str.isBlank() -> "blank string";
        case String str -> "string " + str;
        case Integer i  -> "int " + i;
        default         -> "other";
    };
}

Order matters, like catch blocks. A case may not be dominated by an earlier one: "It is a compile-time error for a case label in a switch block to be dominated by any preceding case label".JEP 441 So put more specific patterns first.

Trap: the general case first

A String is also a CharSequence. If the CharSequence case comes first, the String case can never be reached. I compiled this on JDK 21:

return switch (o) {
    case CharSequence cs -> "cs";
    case String s        -> "s";      // can never be reached
    default              -> "o";
};

$ javac Dom.java
error: this case label is dominated by a preceding case label

The fix: swap them. Specific (String, or a guarded case) first, general (CharSequence, default) last.

4. What about null?

In every Java version before 21, switch (null) throws NullPointerException. JDK 21 adds case null: "If the selector expression evaluates to null then any null case label is said to match."JEP 441

But the old behaviour stays when you don't write it: "If there is no such label associated with the switch block then the switch throws NullPointerException, as before."JEP 441 A default does not catch null. If you want both, you can write them together as case null, default -> ...; the JEP allows "null case labels to have an optional default".JEP 441

switch (o) { case String s -> ...; default -> ...; }
// o == null → NullPointerException

switch (o) { case null -> ...; case String s -> ...; default -> ...; }
// o == null → the null case runs

5. Record patterns: open the box in the case

Think of a parcel with a packing list on the front: "contains: one point, one radius". A record pattern reads that list and hands you each item by name. Record patterns "deconstruct record values".JEP 440

Old way and new way, both from JEP 440:JEP 440

record Point(int x, int y) {}

// As of Java 16: test the type, then call the accessors yourself
if (obj instanceof Point p) {
    int x = p.x();
    int y = p.y();
    System.out.println(x + y);
}

// As of Java 21: the pattern declares x and y for you
if (obj instanceof Point(int x, int y)) {
    System.out.println(x + y);
}

Patterns can be nested: a record inside a record, unpacked in one line, for example Rectangle(ColoredPoint(Point(var x, var y), var c), var lr).JEP 440 You may write var instead of the component type: "A record pattern can use var to match against a record component without stating the type of the component."JEP 440

One detail: "The null value does not match any record pattern."JEP 440 So case Circle(var c, var r) never runs for null; you need case null for that.

6. Sealed types: no default, and the compiler checks you

Back to the post office. If the post office says "we only accept three parcel sizes, full stop", a worker with three slots has covered everything. A sealed type (lesson 0014) is that promise in Java.

A pattern switch must be exhaustive. For a sealed type, "the type coverage check can take into account the permits clause of the sealed class", and "As a result, no default label is needed."JEP 441 Here is the full example from this course:

sealed interface Shape permits Circle, Rect {}
record Point(int x, int y) {}
record Circle(Point center, double r) implements Shape {}
record Rect(Point topLeft, Point bottomRight) implements Shape {}

static String describe(Shape s) {
    return switch (s) {   // no default: Circle and Rect are the only Shapes
        case Circle(Point(var x, var y), var r) when r > 100
            -> "huge circle at " + x + "," + y;
        case Circle(Point(var x, var y), var r)
            -> "circle r=" + r + " at " + x + "," + y;
        case Rect(Point(var x1, var y1), Point(var x2, var y2))
            -> "rect width " + (x2 - x1) + " height " + (y2 - y1);
    };
}

Run it on JDK 21:

$ java java/examples/jdk21/Jdk21Features.java
circle r=5.0 at 1,2
huge circle at 0,0
rect width 4 height 3
null handled inside the switch | blank string | string x | int 7
a c [c, b, a]
one=1 two=2 {two=2, one=1}

The first four lines belong to this lesson. The last two are sequenced collections, the next lesson.

Why "no default" is a feature, not laziness

Imagine someone adds record Triangle(...) implements Shape and the permits list. Every switch over Shape without a default now fails to compile, so the compiler shows you every place to update. I removed the Rect case to see the message:

$ javac Miss.java
error: the switch expression does not cover all possible input values

If you write default, the new Triangle silently goes to default and you lose that warning. And if a class file changes after compiling, "the compiler will in this case insert a synthetic default clause that throws", so the program fails loudly instead of doing nothing.JEP 441

JDK 17 vs 21

JDK 17 has sealed classes, records, switch expressions and instanceof patterns, but not patterns in switch and not record patterns. I compiled the example with --release 17:

$ javac --release 17 java/examples/jdk21/Jdk21Features.java
error: patterns in switch statements are not supported in -source 17

That is a handy interview fact: this is a 21 feature (final in JDK 21 through JEP 441 and JEP 440). On JDK 8 you have none of it: you write instanceof plus a cast, or the Visitor pattern.

The selector is null, and the switch has a default but no case null. What happens?

Without a case null the switch "throws NullPointerException, as before". default does not catch null.

What does a when clause add to a case?

A guard refines a pattern: the case matches only if the pattern matches and the when condition is true.

What is the bug? case CharSequence cs -> ...; case String s -> ...;

Java picks the first case that applies, so the String case could never run. The compiler reports "this case label is dominated by a preceding case label". Specific first.

The selector is a sealed interface and every permitted subtype has a case. Do you need default?

The coverage check uses the permits clause, so "no default label is needed". Leaving it out also makes the compiler warn you when a new subtype appears.

With record Point(int x, int y), what does obj instanceof Point(int x, int y) do when it matches?

A record pattern deconstructs the record: it tests the type and binds each component to a new variable.

Code with case Circle(Point(var x, var y), var r) is compiled with javac --release 17. Result?

Pattern matching for switch and record patterns are final in JDK 21. javac says "patterns in switch statements are not supported in -source 17".

Example answer

"In JDK 21, switch can match on types, not just constants. I write case Circle c or even a record pattern like case Circle(Point(var x, var y), var r), which checks the type and unpacks the fields in one step. Cases are tried from top to bottom and the first match wins, so I put specific ones first; the compiler rejects a case that is dominated by an earlier one. I can add a guard with when, and I can write case null; without it the switch still throws a NullPointerException. The big win is with sealed types: the switch must be exhaustive, and because the compiler knows all permitted subtypes I don't need a default. If someone adds a new subtype later, every switch that doesn't handle it stops compiling, which is exactly what I want. That combination, sealed interface plus records plus pattern switch, gives Java real algebraic data types, and it's final in 21, not available in 17."

What's next

A senior interviewer may ask: "Would you still use the Visitor pattern? What happens to old switches when you add a subtype? Why not just put a method on each class?" A good answer: a method on each class is best when the behaviour belongs to the type; a pattern switch is best when the operation lives outside the types (formatting, pricing, serialising), and sealing makes it safe.
