Thread pools: core, max, queue and rejection

Java (JDK 8, 17, 21) · Lesson 0023 · step 16 of 27 · Advanced · ~12 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap

Today's win: predict when a ThreadPoolExecutor creates threads, queues tasks or rejects them.

The rules

  1. Fewer than corePoolSize threads running: start a new thread, even if others are idle.
  2. corePoolSize or more running: prefer to queue the task.
  3. Queue full and fewer than maximumPoolSize: start another thread.
  4. Otherwise: the task is rejected.[1]

Queue choices

  • Direct handoff (SynchronousQueue): a good default; needs an unbounded max size to avoid rejection; risk of unbounded thread growth.
  • Unbounded queue: never more than core threads, so max has no effect; risk of unbounded queue growth.
  • Bounded queue: helps prevent resource exhaustion but is harder to tune.[1]

Rejection

Default AbortPolicy throws RejectedExecutionException. CallerRunsPolicy makes the submitting thread run the task, "a simple feedback control mechanism that slows down the rate that new tasks are submitted".[1] DiscardPolicy and DiscardOldestPolicy silently drop work and are rarely acceptable.[1]

java java/examples/PoolDemo.java     # core 2, max 4, queue 2, seven blocking tasks
task 1-2: accepted, pool 1..2      (core threads)
task 3-4: accepted, queue 1..2     (queued)
task 5-6: accepted, pool 3..4      (extra threads up to max)
task 7  : REJECTED

Source: PoolDemo.java. Compare with virtual threads, where you do not pool at all.

Retrieval practice

Answer from memory. One attempt each.

1. Core threads busy, queue has room. What happens?

At or above core size the executor prefers queuing.[1]

2. Unbounded queue with max 10. Threads created?

With an unbounded queue no more than core threads are created.[1]

3. Default rejection policy?

AbortPolicy throws RejectedExecutionException.[1]

4. Which policy slows down the submitter?

The submitting thread runs the task itself.[1]
