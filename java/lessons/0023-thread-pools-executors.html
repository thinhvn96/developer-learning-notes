How a thread pool decides: run, queue or reject

Core size, queue, max size and the rejection policy, traced one task at a time.

Java (JDK 8, 17, 21) · Lesson 0023 · step 33 of 46 · Advanced · ~25 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? Almost every Java service runs its work on thread pools: web request handlers, @Async methods, Kafka consumers, scheduled jobs. A badly configured pool gives you out-of-memory errors or requests that wait forever. Interviewers ask "Explain corePoolSize, maximumPoolSize and the queue" and "What happens when the pool is full?"
Today's win: predict when a ThreadPoolExecutor creates threads, queues tasks or rejects them.
task
A small piece of work to run, usually a Runnable (code with a run() method) or a lambda.
thread pool
A group of threads that are created once and reused for many tasks, instead of starting a new thread for every task.
executor
The Java object you hand tasks to; it decides which thread runs them. ThreadPoolExecutor is the main one.
corePoolSize
The number of threads the pool tries to keep, even when they have nothing to do.
work queue
A waiting line for tasks when the core threads are busy.
maximumPoolSize
The hard upper limit on the number of threads.
rejection
What happens to a task the pool cannot take: by default an exception.

Before you start

Say out loud: "A pool has core 2, max 4, and a queue that holds 2 tasks. Seven slow tasks arrive at once. How many threads start, how many tasks wait, and what happens to task 7?" Write your numbers down. Section 3 runs it.

1. The picture: a bank with tellers

A bank has 2 regular tellers (the core threads), a waiting area with 2 chairs (the queue), and 2 extra tellers who come in only on very busy days (up to max 4). When all 4 tellers are busy and all chairs are taken, the guard at the door turns new customers away (rejection).

The surprising part: the bank calls the extra tellers only after the chairs are full, not before. Many people expect the pool to grow to max first and queue later. It is the other way round.

Why pool at all? Creating a platform thread is expensive, so you create a few and reuse them. (With virtual threads in JDK 21 the trade-off changes; see lesson 0006.)

ThreadPoolExecutor pool = new ThreadPoolExecutor(
        2,                               // corePoolSize
        4,                               // maximumPoolSize
        1, TimeUnit.SECONDS,             // extra threads die after 1 s idle
        new ArrayBlockingQueue<>(2),     // bounded queue: 2 places
        new ThreadPoolExecutor.AbortPolicy());  // what to do when full
pool.execute(() -> doWork());            // hand over a task

2. The rules, in order

Every time you call execute(task), the pool asks these questions in this order:ThreadPoolExecutor javadoc

  1. Fewer than corePoolSize threads running: start a new thread, even if others are idle.
  2. corePoolSize or more running: prefer to queue the task.
  3. Queue full and fewer than maximumPoolSize: start another thread.
  4. Otherwise: the task is rejected.

3. Trace seven tasks

The example PoolDemo.java builds exactly the pool above (core 2, max 4, queue 2). Each task blocks until the end, so no thread becomes free during the test. Follow the rules:

Task 1  running 0 < core 2      → new thread (pool = 1)
Task 2  running 1 < core 2      → new thread (pool = 2)
Task 3  core full, queue 0/2    → queued     (queue = 1)
Task 4  core full, queue 1/2    → queued     (queue = 2)
Task 5  queue full, 2 < max 4   → extra thread (pool = 3)
Task 6  queue full, 3 < max 4   → extra thread (pool = 4)
Task 7  queue full, pool = max  → REJECTED
$ java java/examples/PoolDemo.java

task 2: accepted  pool=2 queue=0
task 3: accepted  pool=2 queue=1
task 4: accepted  pool=2 queue=2
task 5: accepted  pool=3 queue=2
task 6: accepted  pool=4 queue=2
task 7: REJECTED (RejectedExecutionException)
  task 1 ran on pool-1-thread-1
  task 5 ran on pool-1-thread-3
  task 2 ran on pool-1-thread-2
  task 6 ran on pool-1-thread-4
  task 3 ran on pool-1-thread-1
  task 4 ran on pool-1-thread-3

The "accepted" lines are always the same. The "ran on" lines come from four threads at once, so their order and thread names change from run to run.

Trap: a new extra thread takes the task that caused it to be created ("a new thread is created to handle the request"ThreadPoolExecutor javadoc), not the oldest waiting task. So a pool is not strictly first-in, first-out.

4. Choosing the queue

The Javadoc describes three strategies:ThreadPoolExecutor javadoc

  • Direct handoff (SynchronousQueue): no waiting chairs at all; each task goes straight to a thread. A good default; needs an unbounded max size to avoid rejection; risk of unbounded thread growth.
  • Unbounded queue (for example LinkedBlockingQueue without a capacity): never more than core threads, so max has no effect; risk of unbounded queue growth.
  • Bounded queue (for example ArrayBlockingQueue): helps prevent resource exhaustion but is harder to tune.

Trap: the "fixed" pool from Executors

Executors.newFixedThreadPool(n) "reuses a fixed number of threads operating off a shared unbounded queue".Executors javadoc If tasks arrive faster than n threads finish them, the queue keeps growing until memory runs out. It never rejects. newCachedThreadPool() is the opposite: it "creates new threads as needed", so a burst can create a huge number of threads.Executors javadoc For a production service, build a ThreadPoolExecutor with a bounded queue and a chosen rejection policy, so the limits are written down.

5. When the pool is full: rejection policies

Back at the bank: what does the guard do with the customer who cannot get in?

  • AbortPolicy (default): throws RejectedExecutionException. "Sorry, come back later," and your code must handle it.
  • CallerRunsPolicy: the thread that called execute runs the task itself, "a simple feedback control mechanism that will slow down the rate that new tasks are submitted". The guard serves the customer personally, and while he does, he can't let anyone else in.
  • DiscardPolicy and DiscardOldestPolicy: silently drop work and are rarely acceptable.ThreadPoolExecutor javadoc

Tasks are also rejected after the pool "has been shut down".ThreadPoolExecutor javadoc shutdown() lets already submitted tasks finish but accepts no new ones, and it "does not wait"; call awaitTermination for that, as the demo does.

JDK 8 vs 17 vs 21: ThreadPoolExecutor works the same in all three. JDK 21 adds Executors.newVirtualThreadPerTaskExecutor(), which "starts a new virtual Thread for each task" with no pool and no queueExecutors javadoc; lesson 0006 compares the two.

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

All core threads are busy and the queue has room. A new task arrives. What happens?

At or above core size the executor prefers queuing. Extra threads come only when the queue is full.

Core 2, max 10, unbounded LinkedBlockingQueue. Under heavy load, how many threads do you get?

With an unbounded queue no more than core threads are ever created, so max has no effect. The queue grows instead.

Core 2, max 4, queue 2, all tasks slow. Which task number is the first one rejected?

2 core threads + 2 queued + 2 extra threads = 6 tasks. The 7th has nowhere to go.

What is the default rejection policy of ThreadPoolExecutor?

The default AbortPolicy throws RejectedExecutionException.

Which policy slows down the code that submits tasks, giving natural back-pressure?

The submitting thread runs the task itself, so it cannot submit more while it is busy.

A service uses Executors.newFixedThreadPool(8) and slowly runs out of memory under load. What is the most likely cause?

The fixed pool works off an unbounded queue: it never rejects, so waiting tasks pile up when work arrives faster than it is done.

The final test: say it in 60 seconds

An interviewer asks: "How does a ThreadPoolExecutor handle a new task? What happens when it's full?" Start a timer. Answer out loud, in full sentences. Then click the button.

Tick only the points you really said:

Example answer

"When I submit a task, if fewer than corePoolSize threads are running, the pool starts a new thread for it, even if other threads are idle. Once core is reached, it prefers to put the task in the work queue. Only when the queue is full does it add threads, up to maximumPoolSize. If it's at max and the queue is full, the task is rejected. The default AbortPolicy throws RejectedExecutionException; CallerRunsPolicy makes the submitting thread run the task, which slows the producer down, so it's a simple back-pressure. A common trap is newFixedThreadPool: it uses an unbounded queue, so it never rejects and max is irrelevant, and under load the queue can grow until we run out of memory. In a real service I'd use a ThreadPoolExecutor with a bounded queue and an explicit rejection policy, and monitor the queue size."
