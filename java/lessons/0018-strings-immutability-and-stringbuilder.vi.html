Vì sao String trong Java không bao giờ thay đổi

Tính bất biến, string pool, cái bẫy ==, và khi nào nên dùng StringBuilder.

Java (JDK 8, 17, 21) · Bài 0018 · bước 1/46 · Foundation · ~20 phút · Trang chủ · Lộ trình Java (JDK 8, 17, 21) · Lộ trình tổng · English

Vì sao có bài này? String có mặt ở mọi dòng code backend: ID, JSON, SQL, log. Interviewer rất thích hỏi "Vì sao String là immutable?" và "== khác equals() thế nào?", vì trả lời sai sẽ sinh ra những bug thật, lúc có lúc không.
Thành quả hôm nay: giải thích trong khoảng 60 giây vì sao == trên string là cái bẫy, string pool là gì, và khi nào dùng StringBuilder.
object
Một thứ chương trình tạo ra trong bộ nhớ, ví dụ một String chứa chữ "abc".
reference
Một biến trỏ tới object, giống địa chỉ ghi trên tấm thẻ. Hai biến có thể trỏ cùng một object.
immutable
Bất biến: không đổi được sau khi tạo. Muốn giá trị khác thì phải tạo object mới.
literal
Giá trị viết thẳng trong code, như "abc" nằm giữa hai dấu nháy kép.
string pool
Một danh sách string dùng chung do class String tự giữ, để các literal giống nhau dùng chung một object.
==
Với object, nó hỏi "hai biến có trỏ vào cùng một object không?". Nó không nhìn vào nội dung chữ.
equals()
Method hỏi "hai string này có chứa cùng các ký tự không?".

Trước khi bắt đầu

Nói thành tiếng: "String a = "abc"; String c = new String("abc"); Vậy a == c in ra gì, và vì sao?" Cứ đoán trước, dù chưa chắc. Bạn sẽ kiểm tra lại ở phần 3.

1. Hình dung: một cái nhãn đã in

Hãy nghĩ tới cái nhãn đã in dán trên thùng hàng. Bạn không tẩy chữ trên đó được. Muốn nội dung khác, bạn in một nhãn mới rồi dán lên. Nhãn cũ vẫn còn đó cho tới khi có người vứt đi.

String trong Java cũng vậy. Theo tài liệu, "String là hằng; giá trị của chúng không thể thay đổi sau khi được tạo."String javadoc Những method trông như đang sửa string, ví dụ concat, toUpperCase hay replace, thực ra đều trả về một string mới.

String s = "x";
String t = s.concat("y");
Bước 1  s trỏ tới object "x"
Bước 2  concat tạo một object MỚI "xy" và trả nó về
Bước 3  t trỏ tới "xy"; s vẫn trỏ tới "x"
System.out.println(s + ", " + t);   // x, xy

Ví dụ chạy được in ra đúng như vậy:

$ java java/examples/StringDemo.java
...
s after concat  : x, t = xy

Bẫy: gọi method rồi bỏ quên kết quả

String name = "anna";
name.toUpperCase();              // result thrown away
System.out.println(name);        // still "anna"

name = name.toUpperCase();       // fix: keep the new string

Vì string không bao giờ đổi, bạn phải lưu kết quả vào một biến. Quên điều này là bug kinh điển của người mới.

2. Vì sao bất biến lại là ý hay

Tài liệu nêu lý do chính trong một câu: "Vì các object String là bất biến nên chúng có thể được dùng chung."String javadoc Nếu không ai sửa được object, thì nhiều biến (và nhiều thread) cùng trỏ vào nó cũng không có rủi ro gì.

  • Dùng chung an toàn. Bạn truyền string vào bất kỳ method nào. Method đó không thể lén sửa bản của bạn.
  • Key an toàn cho map. Ở bài 0001 bạn đã thấy một key bị đổi sẽ bị lạc trong HashMap. Key là string thì không đổi được, nên không bị lạc.
  • Có thể có pool dùng chung. Vì dùng chung là an toàn, Java có thể giữ một bản duy nhất cho mỗi literal. Đó là phần tiếp theo.

3. String sống ở đâu: string pool

Hãy tưởng tượng một văn phòng có một cuốn từ điển chung trên kệ. Ai cần thì đi tới cùng cái kệ đó. Không ai mua thêm cuốn thứ hai, vì không ai được phép viết vào nó.

Class String giữ một cái kệ như thế. Tài liệu của intern() viết: "Một pool các string, ban đầu rỗng, được class String duy trì một cách riêng tư." và "Mọi string literal và mọi biểu thức hằng có giá trị string đều được intern."String javadoc Đặc tả ngôn ngữ nói cùng điều đó từ phía bên kia: "một string literal luôn tham chiếu tới cùng một instance của class String".JLS §3.10.5

Giờ chạy ví dụ và đi theo từng dòng:

String a = "abc";
String b = "abc";               // same literal
String c = new String("abc");   // explicitly a new object

$ java java/examples/StringDemo.java
a == b          : true
a == c          : false
a.equals(c)     : true
a == c.intern() : true
  1. a == b là true. Cả hai đều là literal "abc", nên cùng trỏ tới một object trong pool.
  2. a == c là false. new luôn tạo object mới, nên c trỏ chỗ khác. Chữ giống nhau, nhưng object thì không.
  3. a.equals(c) là true. equals so sánh các ký tự, không so địa chỉ.
  4. a == c.intern() là true. intern() tìm trong pool, thấy một string bằng nó, và trả về bản trong pool. Theo tài liệu, với hai string bất kỳ, "s.intern() == t.intern() là true khi và chỉ khi s.equals(t) là true".String javadoc

String tạo lúc chạy là object mới

Đặc tả còn nói các string nối từ hằng số "được tính lúc compile rồi được xem như literal", nhưng "các string được tính bằng phép nối lúc chạy là mới tạo, vì thế là khác biệt."JLS §3.10.5 Ví dụ của chính đặc tả:

String hello = "Hello", lo = "lo";
hello == ("Hel" + "lo")   // true: two constants, joined by javac
hello == ("Hel" + lo)     // false: lo is a variable → new object

Đây là lý do == trên string nguy hiểm: nó thỉnh thoảng chạy đúng (trong test nhỏ dùng literal), rồi hỏng trên production, nơi string đến từ request, file hay database.

4. Quy tắc: so sánh nội dung bằng equals

So sánh nội dung string bằng equals(). Không bao giờ dùng ==.

equals được định nghĩa: "Kết quả là true khi và chỉ khi đối số khác null và là một object String biểu diễn cùng dãy ký tự với object này."String javadoc

Bẫy: kiểm tra input của người dùng

// answer comes from an HTTP request: built at run time
String answer = request.getParameter("confirm");

if (answer == "yes") { ... }        // bug: almost never true
if (answer.equals("yes")) { ... }   // NPE if answer is null
if ("yes".equals(answer)) { ... }   // best: null gives false

Dòng cuối đặt literal lên trước. Vì đối số có thể null và equals chỉ đơn giản trả về false khi gặp null, bạn tránh được NullPointerException.

Có nên gọi intern() khắp nơi để == chạy đúng không? Không. Đó là một lần tra cứu trong pool dùng chung, nó không cứu được chỗ code quên gọi nó, còn equals thì rõ ràng và đúng. Hãy hiểu intern() làm gì; đừng dùng nó để sửa phép so sánh.

5. Ghép string: + hay StringBuilder

Quay lại chuyện nhãn in. Nếu mỗi lần thêm một chữ bạn lại in nguyên một nhãn mới, bạn sẽ vứt đi rất nhiều nhãn. Tốt hơn: dùng một tấm bảng trắng, viết hết các chữ, rồi in một lần ở cuối. StringBuilder chính là tấm bảng trắng đó.

Tài liệu gọi nó là "một dãy ký tự có thể thay đổi" và khuyên dùng nó thay cho StringBuffer cũ "vì nó sẽ nhanh hơn trên hầu hết các implementation". Cái giá phải trả: "Các instance của StringBuilder không an toàn khi dùng bởi nhiều thread."StringBuilder javadoc Điều đó không sao, vì bình thường bạn ghép string bên trong một method, trên một thread.

Đi theo vòng lặp trong ví dụ:

StringBuilder sb = new StringBuilder();
for (int i = 0; i < 5; i++) sb.append(i).append(',');
Bước 1  new StringBuilder(): buffer rỗng, đủ chỗ cho 16 ký tự
Bước 2  mỗi append ghi vào cùng buffer đó (không có String mới)
Bước 3  in sb sẽ gọi toString(): tạo một String ở cuối

$ java java/examples/StringDemo.java
...
StringBuilder   : 0,1,2,3,4,

Con số "16 ký tự" lấy từ tài liệu của constructor: "dung lượng ban đầu là 16 ký tự".StringBuilder javadoc Nếu bạn append nhiều hơn, builder tự lớn lên.

Vậy + là xấu à? JDK 8 so với 9+

Không. Với một biểu thức như "id=" + id + ", name=" + name, cứ dùng + cho dễ đọc. Việc + được compile ra sao là do compiler quyết định: "compiler javac có thể hiện thực toán tử này bằng StringBuffer, StringBuilder, hoặc java.lang.invoke.StringConcatFactory tùy theo phiên bản JDK."String javadoc Nên bytecode của + trên JDK 8 khác với JDK 17 và 21, nhưng source code của bạn vẫn giữ nguyên.

Vấn đề nằm ở += trong vòng lặp. Mỗi vòng tạo một string mới và chép toàn bộ ký tự cũ vào, nên khối lượng công việc tăng dần theo từng vòng (đây là hệ quả của tính bất biến). Trong vòng lặp, hãy dùng một StringBuilder rõ ràng. Như mọi khi: đo trước khi tối ưu những trường hợp nhỏ.

Luyện tập

Trả lời theo trí nhớ, đừng cuộn lên. Thứ tự đáp án thay đổi mỗi lần bạn mở trang.

Sau String s = "x"; s.concat("y"); thì s là gì?

String là hằng. concat trả về một string mới; nếu bỏ qua kết quả thì không có gì thay đổi.

Với hai literal giống hệt nhau, "abc" == "abc" in ra gì?

"Một string literal luôn tham chiếu tới cùng một instance của class String" (JLS §3.10.5). Demo in ra a == b : true.

String a = "abc"; String c = new String("abc"); Vậy a == c là gì?

== so địa chỉ. new tạo một object riêng, nên địa chỉ khác nhau dù chữ giống nhau.

Bug trong if (status == "ACTIVE") là gì, khi status được đọc từ database?

String tính lúc chạy là object mới, nên == ra false. Dùng "ACTIVE".equals(status).

intern() trả về gì?

Nó trả về "một biểu diễn chuẩn": string trong pool bằng với string này, nếu cần thì thêm vào pool trước.

Bạn dựng một báo cáo 10 000 dòng trong vòng for. Cách nào tốt nhất?

Mỗi += tạo string mới và chép lại chữ cũ. StringBuilder ghi vào một buffer; đó là lựa chọn được tài liệu khuyên dùng khi ghép trên một thread.

Bài kiểm tra cuối: nói trong 60 giây

Interviewer hỏi: "Vì sao String trong Java là immutable, và == khác equals() thế nào?" Bấm giờ. Trả lời thành tiếng, nói thành câu đầy đủ. Rồi bấm nút.

Chỉ tick những ý bạn thật sự đã nói:

Câu trả lời mẫu

"String trong Java là immutable: tạo ra rồi thì ký tự bên trong không bao giờ đổi, mấy method như concat hay toUpperCase đều trả về string mới. Lợi ích lớn nhất là string dùng chung được một cách an toàn, giữa các thread và làm key cho HashMap. Nhờ vậy Java mới có string pool: mọi literal cùng nội dung đều trỏ về một object chung, và intern() trả cho mình bản trong pool. Đó cũng chính là lý do == là cái bẫy. == so reference, nên hai literal thì trông như bằng nhau, nhưng string tạo bằng new hay lấy từ request là object khác, và == ra false. Để so nội dung thì em luôn dùng equals, thường viết "yes".equals(input) cho an toàn với null. Còn khi ghép string trong vòng lặp thì em dùng StringBuilder, vì mỗi lần += lại tạo một string mới và chép lại mọi thứ."

Tiếp theo là gì

Interviewer cấp senior có thể hỏi tiếp: "StringBuilder có thread-safe không? Vì sao object bất biến tốt cho concurrency? Bạn làm class của mình thành immutable thế nào?" Câu đầu đã có ở trên (không, hãy dùng nó trên một thread). Các câu còn lại, xem bài 0032 về collection bất biến và bài 0005 về chia sẻ dữ liệu giữa các thread. Bài tiếp theo trong lộ trình: chuyện gì xảy ra khi có lỗi, ở bài 0019.
