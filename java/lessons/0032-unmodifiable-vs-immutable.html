Lists nobody can change (or can they?)

Arrays.asList, unmodifiableList, List.of and List.copyOf look alike. They are not.

Java (JDK 8, 17, 21) · Lesson 0032 · step 13 of 46 · Core · ~20 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? A class returns its internal list, a caller adds to it, and your object's state is now wrong. Interviewers test this with "How do you return a list that nobody can change?" and then "What's the difference between unmodifiable and immutable?" After this lesson you can answer both, and predict which call throws.
Today's win: tell apart Arrays.asList, Collections.unmodifiableList, List.of and List.copyOf, and predict which call throws.
reference
A variable holding an object does not hold the object itself, only its address. Two lists can hold the address of the same object.
view
A collection that has no data of its own; it reads through to another collection, so it shows that collection's changes.
unmodifiable
The collection refuses add, remove and set. It says nothing about the elements inside.
immutable
Nothing can ever change: not the collection, not the elements, not through any other reference.
UnsupportedOperationException
The exception a collection throws when you call a method it chose not to support, like add on a fixed-size list. Often shortened to UOE.
defensive copy
Copying data before handing it out (or after taking it in), so outside code cannot change your object's state.

Before you start

Predict: List<String> view = Collections.unmodifiableList(backing); then somebody calls backing.add("c"). Does view now contain "c"? Yes or no, and why? The answer is in section 2.

1. Four things that look alike

Picture a shop with a shelf of goods. There are four ways to let a customer "see" it:

  • A frame around the shelf (Arrays.asList): the shelf has a fixed number of slots. The customer cannot add slots, but can swap what is in a slot, and that changes the real shelf.
  • Glass in front of the shelf (Collections.unmodifiableList): the customer cannot touch anything. But the shopkeeper behind the glass can still rearrange, and the customer sees it.
  • A photo of the shelf (List.of, List.copyOf): frozen. Nobody can change the photo, and later changes to the shelf do not appear in it.

Why can a List refuse add at all? Because add is an "optional operation" in the List interface: an implementation may throw UnsupportedOperationException instead (lesson 0028).

2. Trace it: who sees which change?

String[] arr = {"a", "b", "c"};
List<String> asList = Arrays.asList(arr);
asList.set(0, "X");     // ok: writes into arr → arr is [X, b, c]
asList.add("d");        // UnsupportedOperationException: fixed size

List<String> backing = new ArrayList<>(List.of("a", "b"));
List<String> view = Collections.unmodifiableList(backing);
List<String> copy = List.copyOf(backing);
view.add("x");          // UnsupportedOperationException

Step 1  backing = [a, b]   view reads backing   copy holds its own [a, b]
Step 2  backing.add("c")   backing = [a, b, c]
Step 3  print view         reads through        → [a, b, c]
Step 4  print copy         own data             → [a, b]

The Javadoc says the same in words:

  • Arrays.asList returns "a fixed-size list backed by the specified array".Arrays javadoc
  • unmodifiableList returns an "unmodifiable view"; queries "'read through' to the specified list".Collections javadoc Whoever holds the original list can still change what you see.
  • List.of (JDK 9) and List.copyOf (JDK 10): "Elements cannot be added, removed, or replaced", "They disallow null elements", and they are value-based, so do not rely on identity or lock on them.List javadoc copyOf of an already-unmodifiable list may return the same instance, as the run shows (same instance? true).
  • Map.of rejects duplicate keys with IllegalArgumentException, rejects nulls, and its "iteration order of mappings is unspecified and is subject to change".Map javadoc

Trap: List.of is strict about null even when you only ask: List.of("a").contains(null) threw NullPointerException in the run. Arrays.asList("a", null) is fine.

3. Unmodifiable is not immutable

Think of a printed address book. Nobody can add or cross out a line: the book is unmodifiable. But the houses at those addresses can still be repainted. The book holds addresses (references), not houses.

All of these lists are shallow: "if the contained elements are themselves mutable, this may cause the List's contents to appear to change".List javadoc

List<StringBuilder> sbs = List.of(new StringBuilder("hi"));
sbs.add(new StringBuilder());   // throws UOE: list is locked
sbs.get(0).append(" there");    // allowed: element is mutable
System.out.println(sbs);        // [hi there]

True immutability needs immutable elements too (records of immutable fields, String, LocalDate), as in lesson 0003.

4. Returning internal state safely

class Cart {
  private final List<Item> items = new ArrayList<>();

  // bad: the caller can add to your list
  List<Item> itemsBad()  { return items; }
  // read-only, but live: sees later changes
  List<Item> itemsView() { return Collections.unmodifiableList(items); }
  // frozen snapshot (JDK 10+)
  List<Item> items()     { return List.copyOf(items); }
}

The first leaks your state. The second is read-only but live: fine if callers should see updates, wrong if they expect a snapshot. The third is a frozen snapshot.

JDK 8 vs 17 vs 21

JDK 8 has only Arrays.asList, Collections.unmodifiable*, emptyList/singletonList. List/Set/Map.of arrived in 9, copyOf in 10, Stream.toList() in 16, so all are available on 17 and 21.List javadoc The last line of the run shows that Stream.toList() gives an unmodifiable list too.

Interview answer for returning internal state: return List.copyOf(items); (17/21) or Collections.unmodifiableList(new ArrayList<>(items)) (8).

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

What does Arrays.asList(arr).set(0, "X") do?

The list is backed by the array, so set writes through: the run printed array now [X, b, c].

And Arrays.asList(arr).add("d")?

It is a fixed-size list: you may replace elements but not add or remove them.

You return Collections.unmodifiableList(backing). Later the class calls backing.add("c"). What does the caller see?

Queries "read through" to the source list. Use List.copyOf for a snapshot.

What does List.of("a", null) do?

List.of disallows null elements. Arrays.asList("a", null) would be fine.

What does Map.of("k", 1, "k", 2) do?

Duplicate keys are rejected when the map is created.

List.of(new StringBuilder("hi")), then get(0).append(" there"). What does printing the list show?

Unmodifiable is shallow. The list's slots are locked, but the StringBuilder they point to is still mutable.

On JDK 8, how do you return a snapshot of items that callers cannot change?

Copy first, then wrap. Wrapping alone is a live view; List.copyOf needs JDK 10; Arrays.asList still allows set.

The final test: say it in 60 seconds

An interviewer asks: "How do you return a list nobody can change? And is it immutable?" Start a timer. Answer out loud, in full sentences. Then click the button.

Tick only the points you really said:

Example answer

"There are a few options that look similar. Arrays.asList is just the array in a list: I can't add, but set writes into the array. Collections.unmodifiableList is a read-only view: callers can't change it, but if my class changes the original list, they see it, so it's not a snapshot. List.of and List.copyOf hold their own data and reject nulls; any change throws UnsupportedOperationException. So to return internal state I write return List.copyOf(items), or on Java 8, Collections.unmodifiableList(new ArrayList<>(items)). But that's unmodifiable, not immutable: it's shallow. If the elements are mutable, like a StringBuilder, they can still change. For real immutability the elements must be immutable too, for example records with immutable fields."
