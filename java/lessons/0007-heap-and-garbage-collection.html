Where your objects live, and who cleans them up

The heap, its generations, the default sizes, and how to read one line of a GC log.

Java (JDK 8, 17, 21) · Lesson 0007 · step 35 of 46 · Senior · ~25 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? "The service was killed with OutOfMemoryError", "latency spikes every few minutes", "the pod keeps restarting": these are memory problems, and a Senior engineer is expected to reason about them. Interviewers ask "How does garbage collection work in Java?" and "What is the default heap size?"
Today's win: state the default heap size and collector rules, read one line of a GC log, and know which knob to turn first.
heap
The big memory area where Java stores every object you create with new. All threads share it.
garbage
An object that no running code can reach any more, so nobody can ever use it again.
garbage collector (GC)
The part of the JVM that finds garbage and gives its memory back, so you never free memory by hand.
generation
A part of the heap for objects of a certain age: a young one for new objects, an old one for objects that lived long.
pause
A short moment when the GC stops your application threads to do its work. Users feel long pauses as latency.
-Xmx
A java command-line option that sets the maximum heap size, for example -Xmx512m.
GC log
Lines the JVM prints about each collection when you start it with -Xlog:gc.

Before you start

Say out loud: "You start java -jar app.jar with no memory options on a machine with 16 GB of RAM. How big can the heap get?" Give a number. Section 3 has the documented rule, and a check on a real machine.

1. The heap and the garbage collector

Think of the heap as a big shared warehouse. Every new Order(...) puts a box on a shelf. Your code keeps labels (references, held in variables and fields) that point to boxes. When no label points to a box any more, nobody can ever find it again: it is garbage.

The JVM specification: the heap "is shared among all Java Virtual Machine threads" and is "the run-time data area from which memory for all class instances and arrays is allocated". Its storage "is reclaimed by an automatic storage management system (known as a garbage collector); objects are never explicitly deallocated."JVMS 2.5.3

The garbage collector allocates memory, hands it to the application, "determines which parts of that memory is still in use", and reclaims the rest.GC tuning: introduction "An object is considered garbage and its memory can be reused by the VM when it can no longer be reached from any reference of any other live object in the running program."GC tuning: implementation

static Object sink;
for (int i = 0; i < 2_000_000; i++) {
    sink = new byte[1024];   // the previous array loses its only label → garbage
}

That loop from GcDemo.java creates about 2 GB of arrays in total, yet it runs fine in a 64 MB heap, because each array becomes garbage one step later.

2. Most objects die young: generations

Checking every box in the warehouse each time would take forever. So HotSpot (the JVM in OpenJDK and Oracle JDK) uses an observation called the weak generational hypothesis, "which states that most objects survive for only a short period of time". For example, "iterator objects are often only alive for the duration of a single loop."GC tuning: implementation HotSpot collectors use "generational scavenging in conjunction with aging" to concentrate effort where reclaimable memory is most likely.GC tuning: introduction

Follow one object through its life:

Step 1  new byte[1024]           → allocated in eden ("Most objects are initially allocated in eden")
Step 2  eden fills up            → a minor collection: only the young generation is collected
Step 3  object still reachable?  → copied to the empty survivor space; eden is now empty
Step 4  next minor GCs           → copied S0 ↔ S1 again, getting "older" each time
Step 5  copied enough times      → moved to the old generation ("aging")
Step 6  old generation fills up  → a major collection of the entire heap: much slower

All from the GC tuning guide: "a young generation full of dead objects is collected very quickly", while major collections "usually last much longer than minor collections because a significantly larger number of objects are involved".GC tuning: implementation The key insight: the cost of a minor GC depends on the objects that survive, not on the garbage. Dead objects cost almost nothing.

G1, the default collector, keeps the same idea but splits the heap into many equal regions: "G1 partitions the heap into a set of equally sized heap regions", and the young generation is a set of eden and survivor regions.GC tuning: G1

3. Defaults you should be able to recite

  • Collector: G1 on a "server-class machine" (two or more processors and at least 1792 MB physical memory), otherwise the Serial collector.GC tuning: ergonomics
  • Initial heap: 1/64 of physical memory. Maximum heap: 1/4 of physical memory.GC tuning: ergonomics
  • -XX:MaxRAMPercentage sets the maximum heap as a percentage of the max memory the JVM sees; default 25 percent.java command

Check it on a real machine. This laptop (JDK 21) has 15,716 MB of RAM and 12 CPUs:

$ java -XX:+PrintFlagsFinal -version | grep -E " MaxHeapSize | UseG1GC "
   size_t MaxHeapSize = 4120903680   {product} {ergonomic}
     bool UseG1GC     = true         {product} {ergonomic}

4,120,903,680 bytes is about 3,930 MB: one quarter of 15,716 MB. And G1 is on, because the machine is "server-class". (Spaces in the output shortened.)

JDK 8 vs 17 vs 21: in JDK 8 the default was the throughput-oriented Parallel collector; JEP 248 made G1 the default in JDK 9JEP 248, so JDK 17 and 21 both default to G1. JDK 21 also adds Generational ZGC (lesson 0017).

Trap: containers. In a container, "physical memory" means the memory the JVM sees, usually the container's limit. Only 25% of it becomes heap by default, and the heap is only part of the process's memory (threads, metaspace, buffers also use some). The Docker and Kubernetes lessons revisit this.

4. Read a GC log line

Run the demo with a 64 MB heap and GC logging on:

$ java -Xmx64m -Xlog:gc java/examples/GcDemo.java
[0.002s][info][gc] Using G1
max heap (MB): 64
[0.361s][info][gc] GC(0) Pause Young (Normal) (G1 Evacuation Pause) 24M->3M(64M) 3.213ms
[0.369s][info][gc] GC(1) Pause Young (Normal) (G1 Evacuation Pause) 38M->3M(64M) 2.740ms
[0.376s][info][gc] GC(2) Pause Young (Normal) (G1 Evacuation Pause) 38M->3M(64M) 2.086ms
...                                                  (55 collections in total, all young)
[0.592s][info][gc] GC(54) Pause Young (Normal) (G1 Evacuation Pause) 40M->3M(64M) 0.228ms
done

Timestamps and pause times change on every run and every machine; the shape stays the same.

Reading it: collection number 0, a young-generation pause, heap occupancy went from 24 MB to 3 MB out of 64 MB, taking about 3 ms. The demo allocates short-lived arrays, so almost everything is reclaimed. (Log format is from running the example on this machine with JDK 21.)

What would worry you? A "3M" after-value that keeps growing from line to line (live data piling up: a leak or a cache without limits), pauses that get longer, or "Pause Full" lines. If live data finally needs more than the heap, the JVM gives up: "If a computation requires more heap than can be made available by the automatic storage management system, the Java Virtual Machine throws an OutOfMemoryError."JVMS 2.5.3 Exercise 0007 makes this happen on purpose.

Same program with the Serial collector, for comparison (first lines only):

$ java -XX:+UseSerialGC -Xmx64m -Xlog:gc java/examples/GcDemo.java
[0.002s][info][gc] Using Serial
[0.349s][info][gc] GC(0) Pause Young (Allocation Failure) 18M->4M(61M) 7.715ms
max heap (MB): 61

Different collector, different cause text ("Allocation Failure": eden was full), and slightly different heap accounting (61 MB). The way to read the line is the same.

5. The interview move

Interview move: before touching collector flags, set the heap size on purpose (-Xmx or MaxRAMPercentage) and turn on GC logging. The Docker and Kubernetes lessons revisit this: heap is only part of a container's memory.

The GC tuning guide itself says to use the defaults "before using the more detailed controls described in subsequent sections".GC tuning: ergonomics So the order is: measure (GC log), size the heap, and only then consider a different collector or its flags.

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

With no heap flags, what is the default maximum heap size?

Maximum heap defaults to 1/4 of physical memory (initial heap: 1/64). MaxRAMPercentage defaults to 25 percent.

Which collector is the default on a server-class machine in JDK 17 and 21?

G1 on server-class machines, Serial otherwise. (JDK 8 defaulted to Parallel; G1 became default in JDK 9.)

What counts as a "server-class" machine for these defaults?

Two or more processors and physical memory of at least 1792 MB.

A log line ends with 24M->3M(64M) 3.213ms. What is 64M?

Before → after (total heap capacity), then the pause time.

Why is a minor GC of a young generation full of dead objects so fast?

Minor collections cost roughly in proportion to the live objects collected; dead objects are just left behind and eden is reused.

In a GC log, the "after" value grows every collection: 3M, 9M, 20M, 41M… What does it suggest?

"After" is what survived. If it keeps climbing, objects stay reachable (a leak or an unbounded cache), and an OutOfMemoryError may follow.

The final test: say it in 60 seconds

An interviewer asks: "How does garbage collection work in Java, and how would you size the heap?" Start a timer. Answer out loud, in full sentences. Then click the button.

Tick only the points you really said:

Example answer

"All objects live in the heap, which every thread shares. The garbage collector finds objects that are no longer reachable from live references and reuses their memory. HotSpot collectors are generational, because most objects die young: new objects go into eden; when it fills, a minor GC copies the few live ones into a survivor space, and objects that survive several times are promoted to the old generation. A minor GC is cheap because it only pays for live objects; a major GC of the whole heap is much slower. Since JDK 9 the default is G1 on server-class machines, and the default max heap is a quarter of physical memory, which in a container is often too small or misunderstood. So first I set the heap size on purpose with -Xmx or MaxRAMPercentage and turn on -Xlog:gc. In the log I look at before → after and the pause time; if the after-value keeps growing, live data is piling up, which points to a leak, not to a GC setting."
