TreeMap and NavigableMap: range and nearest-key queries

When "find this exact key" is not enough: find the closest key, or every key between two values, in O(log n).

Java (JDK 8, 17, 21) · Lesson 0034 · step 16 of 46 · Advanced · ~22 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? Real systems ask questions like "which shipping fee applies to an order of 230,000?" or "which events happened between minute 10 and minute 40?". A HashMap cannot answer them. Interviewers use exactly these questions to see whether you know TreeMap and its floor/ceiling/subMap methods.
Today's win: solve 'find the tier', 'next event after time T' and 'events in a window' with floorEntry, ceilingEntry and subMap in O(log n), and explain when you would pick TreeMap over HashMap.
sorted map
A map that always keeps its keys in order, smallest first, like words in a dictionary.
interface
A list of methods a class promises to have. NavigableMap is an interface; TreeMap is a class that provides it.
binary search tree
Nodes linked like a family tree: everything on the left of a node is smaller, everything on the right is bigger.
red-black tree
A binary search tree that rebalances itself after each insert or delete, so it never becomes a long, slow chain.
O(log n)
Read "O of log n": doubling the map adds only one more step. A million keys need about 20 steps.
view
A collection that has no copy of its own; it shows part of another collection, live (you met it in lesson 0032).
floor / ceiling
Like rounding: floor is the nearest key at or below a value, ceiling the nearest key at or above it.

Before you start

Say out loud how you would solve this with the tools you already know: "Fees: orders from 0 cost 30,000, from 200,000 cost 15,000, from 500,000 are free. What is the fee for an order of 499,999?" Would a HashMap help? Keep your answer; you will meet a one-line solution in section 2.

1. The picture: a sorted shelf with a smart librarian

A HashMap is like a wall of mailboxes: it finds an exact name instantly, but it has no idea which name comes "next". A TreeMap is like a library shelf sorted by number, with a librarian who can jump to the middle, decide "left or right?", and halve the search every time.

The Javadoc describes it as "A Red-Black tree based NavigableMap implementation" with "guaranteed log(n) time cost for the containsKey, get, put and remove operations".TreeMap javadoc The keys are kept sorted by their natural order (Comparable) or by a Comparator you pass in.

Because the tree stays balanced, the path from the top to any key is short: about log2(n) steps. That is why TreeMap promises O(log n) for get and put, while HashMap promises O(1) on average. TreeMap is slower for exact lookups, but it can do something a HashMap cannot: answer questions about order.

Two rules come with sorting. The comparator must be consistent with equals, because the map treats two keys that compare as 0 as the same key ("two keys that are deemed equal by this method are, from the standpoint of the sorted map, equal"TreeMap javadoc; see lesson 0031). And a null key throws NullPointerException with natural ordering, because null cannot be compared.TreeMap javadoc

2. Nearest-key questions: floor, ceiling, lower, higher

The real value of TreeMap is the NavigableMap interface: "navigation methods returning the closest matches for given search targets".java.util summary Think of a number line with your keys marked on it. You stand at a value and ask "what is the nearest key on my left, or on my right?"

MethodReturnsTreeMap javadoc
floorKey(k) / floorEntry(k)greatest key ≤ k
ceilingKey(k) / ceilingEntry(k)least key ≥ k
lowerKey(k) / higherKey(k)strictly < k / strictly > k

Trace: the shipping-fee tier

Here is the "Before you start" problem in one line. Each key is the start of a tier; the right tier is the greatest start that is ≤ the order total, which is exactly floorEntry.

NavigableMap<Integer, Integer> feeFrom =
    new TreeMap<>(Map.of(0, 30_000, 200_000, 15_000, 500_000, 0));
int fee = feeFrom.floorEntry(499_999).getValue();
Step 1  The keys are kept sorted: 0, 200,000, 500,000
Step 2  floorEntry(499,999) looks for the greatest key ≤ 499,999
Step 3  500,000 is too big; 200,000 fits → entry 200,000 = 15,000
Step 4  getValue() → 15,000

Without TreeMap, "find the tier for this amount" becomes a sorted list plus binary search, or a loop over all tiers. Adding a new tier is one put; the order takes care of itself.

3. Ranges are live views

Picture a window cut into a long shelf: through it you see only books 10 to 39. If someone slips a new book 15 onto the shelf, it appears in your window at once. subMap, headMap and tailMap are such windows: views, not copies.

TreeMap<Integer, String> events = ...;     // minutes 5, 12, 20, 33, 47, 58
SortedMap<Integer, String> window = events.subMap(10, 40);   // [10, 40)
events.put(15, "late");                    // added to the map, not the window
System.out.println(window);                // shows 15 too

The run below shows all three real problems of this lesson: the fee tiers, the next event after a time, and the window.

TreeMap null key : NullPointerException

Three details interviewers like:

  • Ends: subMap(from, to) includes from and excludes to. headMap(toKey) is "strictly less than toKey" and tailMap(fromKey) is "greater than or equal to fromKey"; overloads with a boolean inclusive let you choose.TreeMap javadoc
  • Writes outside the window fail: "The returned map will throw an IllegalArgumentException on an attempt to insert a key outside its range."TreeMap javadoc
  • Entries are snapshots: entries from floorEntry, firstEntry, pollFirstEntry and friends "represent snapshots of mappings as of the time of the call" and do not support setValue.TreeMap javadoc Use put to change a value.

4. Traps

Trap 1: a comparator with ties

The leaderboard in the run sorts players by score, highest first. Lan and Minh both have 90. If the comparator stopped at the score, they would compare as 0 and the sorted set would keep only one of them, silently. The example adds a tie-breaker:

Comparator.comparingInt(Player::score).reversed()
          .thenComparing(Player::name)      // without this line, minh disappears

Trap 2: floorEntry can return null

If no key is ≤ your value, you get null, and floorEntry(x).getValue() throws NullPointerException.TreeMap javadoc The fee table above is safe because it starts at key 0; a negative total would still break it. Check for null, or make sure the smallest key covers every input.

Trap 3: sharing it between threads

"Note that this implementation is not synchronized", and its iterators are fail-fast.TreeMap javadoc For a sorted map that many threads use, see section 5.

5. HashMap, TreeMap or ConcurrentSkipListMap?

  • Only exact-key lookups: HashMap, O(1) expected.
  • Sorted iteration, ranges, nearest key: TreeMap, O(log n) guaranteed.
  • Same, shared by many threads: ConcurrentSkipListMap, "expected average log(n)" and weakly consistent iterators.ConcurrentSkipListMap javadoc You will meet it again in lesson 0039.

JDK 8 vs 17 vs 21. Everything above works the same on 8, 17 and 21. On JDK 21 TreeMap also implements SequencedMap (lesson 0016), but its putFirst and putLast throw UnsupportedOperationException: "The encounter order of mappings is determined by the comparison method; therefore, explicit positioning is not supported."TreeMap javadoc

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

What does TreeMap promise for get and put?

TreeMap guarantees log(n) for containsKey, get, put and remove, because its red-black tree stays balanced.

Keys are 5, 12, 20, 33. What does floorKey(21) return?

floorKey returns the greatest key ≤ the given key. 20 ≤ 21, and 33 is too big.

Keys are 5, 12, 20, 33. What does lowerKey(20) return?

lower means strictly less, so 20 itself does not count. floorKey(20) would return 20.

Does subMap(10, 40) include the key 40?

subMap(from, to) goes from inclusive to exclusive. The overload with booleans lets you include the end.

You take w = map.subMap(10, 40), then call map.put(15, "x"). What does w show?

subMap, headMap and tailMap are views backed by the map. The run showed the late event 15 appearing in the window.

A leaderboard TreeSet sorts by score only. Two players have 90 points. What is the bug?

Sorted collections decide duplicates with the comparator. Add .thenComparing(Player::name) as a tie-breaker.

Which map do you choose for a sorted map shared by many threads?

ConcurrentSkipListMap is a concurrent NavigableMap with expected average log(n) cost. ConcurrentHashMap is not sorted; TreeMap is not synchronized.

The final test: say it in 60 seconds

An interviewer asks: "When would you use a TreeMap instead of a HashMap? Give an example." Start a timer. Answer out loud, in full sentences. Then click the button.

Tick only the points you really said:

Example answer

"A HashMap is the default for exact-key lookups: O(1) on average, but no order. A TreeMap is a red-black tree, so the keys are always sorted and every get or put is O(log n), guaranteed. I pick it when the question is about order. For example, shipping-fee tiers: I put the start of each tier as the key, and floorEntry of the order total gives me the right tier in one call. Or a time series: ceilingEntry gives the next event after a time, and subMap gives all events in a window. Those range methods return live views, not copies. Two cautions: the comparator decides what counts as the same key, so I always add a tie-breaker; and TreeMap isn't thread-safe, so for a shared sorted map I'd use ConcurrentSkipListMap."
