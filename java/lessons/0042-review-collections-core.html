Review 3: HashMap internals, ordering and immutability

Four lessons, one map in your head: how a key finds its bucket, who decides "equal", who may change a list, and which map remembers order.

Why this lesson? In a real interview the questions come mixed: "How does HashMap resize?" is followed by "Why did my TreeSet lose an element?" and "How do you return a list nobody can change?". This review mixes lessons 0030, 0031, 0032 and 0033 the same way, so you practise switching between them. There are no new facts here.
Today's win: answer 10 or more of the 12 mixed questions, find the three bugs in the mixed task, and say all three 60-second answers with at least 5 checklist points each.
bucket (bin)
One slot of the array inside a HashMap. The key's hash code chooses the slot (lesson 0030).
load factor
How full the map may get before it grows. The default is 0.75, so 16 buckets hold 12 entries before a resize.
treeify
Turning one long bucket chain into a small sorted tree, so a lookup stays fast even with many collisions.
comparator
An object that compares two values and says which comes first. Sorted collections use it to decide order and sameness (lesson 0031).
view
A collection that does not hold its own copy; it reads through to another collection, so it shows that collection's changes (lesson 0032).
access order
A LinkedHashMap mode where every read moves the entry to the end, so the first entry is the least recently used one (lesson 0033).

1. The whole path of one key

Think of a post office again. The postcode (hash code) picks the right mailbox wall (bucket); the name on the letter (equals) picks the right letter in it. When a wall is too full, the post office builds a wall twice as big. When one mailbox gets absurdly full, it stops stacking letters and files them in a small sorted cabinet (a tree). Here is the whole path from lesson 0030 in one picture.

Three sentences to keep from this picture:

  1. Only the low bits pick the bucket, so Java first mixes the high bits into the low ones. With n a power of two, (n - 1) & hash equals hash % n, but cheaper.
  2. Resizing doubles the table and each entry either stays at index i or moves to i + old n: one extra bit decides.
  3. A tree is the emergency plan, not the normal case: with good hash codes, buckets stay tiny. If keys are Comparable, the tree can use compareTo to break ties, which made 20,000 colliding keys go from about 3,658 ms to 69 ms in that lesson's single run.

Need the details again? Lesson 0030 traces every step with real output.

2. Who decides "equal"? It depends on the collection

This is the idea that connects lessons 0001, 0030, 0031 and 0033. A HashMap and a HashSet ask hashCode() and equals(). A TreeMap and a TreeSet never call equals() at all: they ask compareTo() or your comparator, and a result of 0 means "same key".

That is why a comparator must end with a unique tie-breaker (for example .thenComparing(Employee::name)), and why new BigDecimal("4.0") and new BigDecimal("4.00") give a HashSet of size 2 but a TreeSet of size 1. And never write (a, b) -> a - b: with Integer.MIN_VALUE it overflows; use Integer.compare or Comparator.comparingInt. Re-read lesson 0031 if any of this feels new.

Two more things a senior answer adds: unmodifiable is shallow (a List.of(new StringBuilder("hi")) still let us append " there"), and the JDK version matters: List.of is JDK 9, copyOf JDK 10, Stream.toList() JDK 16. On JDK 8 the defensive copy is Collections.unmodifiableList(new ArrayList<>(items)). See lesson 0032.

4. Which map remembers order, and the LRU trick

From lesson 0033: a HashSet is a HashMap whose values are one shared dummy object, so it inherits everything from section 1. LinkedHashMap threads a doubly linked list through the entries. In the default mode the list keeps insertion order, and re-putting a key does not move it. With the constructor flag accessOrder = true, every get moves the entry to the end, and overriding removeEldestEntry turns it into an LRU cache:

class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;
    LruCache(int capacity) { super(16, 0.75f, true); this.capacity = capacity; }
    @Override protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;   // called by put/putAll after inserting
    }
}
$ java java/examples/collections/LruCache.java
insertion order (re-put 'a' keeps its place): {c=3, a=10, b=2}
HashSet: [java, kafka, redis, docker, sql]   LinkedHashSet: [kafka, java, docker, sql, redis]
LRU after get(a), put(d): [c, a, d]     // b was least recently used
LRU after put(e):         [a, d, e]

The trap: in access-order mode even get is a structural change, so threads that share it need a lock (or a cache library such as Caffeine). See lesson 0033.

5. Mixed task: find the three bugs

Read this code like a reviewer. There are three bugs, each from a different lesson. Find them, name the lesson, and say the fix before opening the answer.

record Order(String id, int cents) {}

class OrderBook {
    // (A) we expect about 1,000 orders and never want a resize
    private final Map<String, Order> byId = new HashMap<>(1000);

    // (B) cheapest first
    private final Set<Order> byPrice =
        new TreeSet<>((a, b) -> a.cents() - b.cents());

    private final List<Order> all = new ArrayList<>();

    void add(Order o) { byId.put(o.id(), o); byPrice.add(o); all.add(o); }

    // (C) callers must get a snapshot that never changes
    List<Order> snapshot() { return Collections.unmodifiableList(all); }
}
Show the three bugs

(B) Lesson 0031, the worst one. The TreeSet decides duplicates with the comparator. Two different orders with the same price compare as 0, so the second one is silently dropped. Also a - b can overflow. Fix: Comparator.comparingInt(Order::cents).thenComparing(Order::id).

(C) Lesson 0032. unmodifiableList is a view: callers cannot change it, but they see every later add. That is not a snapshot. Fix: List.copyOf(all) (JDK 10+) or Collections.unmodifiableList(new ArrayList<>(all)) on JDK 8.

(A) Lesson 0030. The table size must be a power of two, so capacity 1000 becomes 1024 buckets, and 1024 × 0.75 = 768, so the map still resizes when it passes 768 entries. Fix: HashMap.newHashMap(1000) on JDK 19+ (so 21), or new HashMap<>((int) (1000 / 0.75f) + 1) on 8/17.

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

A HashMap has 16 buckets. Which expression picks the bucket for a spread hash h?

The index is (n - 1) & hash, which equals hash % n when n is a power of two. See lesson 0030.

A TreeSet uses a comparator that compares employees by salary only. You add Lan (3000) and Minh (3000). What is the size?

Sorted sets decide duplicates with compare, never equals. Add a unique tie-breaker. See lesson 0031.

What does Arrays.asList(arr).set(0, "X") do?

Arrays.asList is a fixed-size list backed by the array: set writes through, add throws. See lesson 0032.

In a default (insertion-order) LinkedHashMap you put("a", 1), put("b", 2), then put("a", 10). What is the order?

Re-inserting an existing key does not change its place in insertion order. See lesson 0033.

When does OpenJDK turn a HashMap bucket into a red-black tree?

TREEIFY_THRESHOLD = 8 and MIN_TREEIFY_CAPACITY = 64; a smaller table resizes instead. See lesson 0030.

What is the bug in list.sort((a, b) -> a - b) for a List<Integer>?

MIN_VALUE - 1 becomes a large positive number. Use Integer.compare or Comparator.comparingInt. See lesson 0031.

You return Collections.unmodifiableList(items), then your class adds to items. What does the caller see?

An unmodifiable view blocks the caller's writes but reads through to the source. Use List.copyOf for a snapshot. See lesson 0032.

What backs a HashSet?

The Javadoc says it is backed by a hash table, actually a HashMap instance. See lesson 0033.

A HashMap with 16 buckets resizes to 32. An entry was at index 1. Where can it be now?

One extra hash bit decides: stay at i or move to i + old n. The example showed apple going 1 → 17. See lesson 0030.

What does List.of("a", null) do?

List.of and List.copyOf disallow null elements; even contains(null) throws. See lesson 0032.

You want an LRU cache with LinkedHashMap. Which two things do you need?

Access order moves read entries to the end; removeEldestEntry is called after put inserts. See lesson 0033.

20,000 keys all return hashCode() == 42. What made lookups much faster in lesson 0030's run?

With all hashes equal, only compareTo can break ties inside the tree bin (about 3,658 ms vs 69 ms in one run). See lesson 0030.

The final test: say it in 60 seconds

Recall 1. An interviewer asks: "Walk me through a put in a HashMap, including resize and treeification." Start a timer. Answer out loud, then click.

Tick only the points you really said:

Example answer

"A HashMap is an array of buckets, 16 by default with a load factor of 0.75. On put, it takes the key's hashCode and XORs the high 16 bits into the low bits, because only the low bits pick the bucket. The index is (n minus 1) AND hash, which is a cheap modulo since n is a power of two. In the bucket it compares the hash, then equals: if the key exists it replaces the value, otherwise it appends a node. When size goes past capacity times 0.75, the table doubles, and every entry either stays at its index or moves by the old size. If one bucket reaches 8 nodes and the table has at least 64 buckets, OpenJDK turns it into a red-black tree, so the worst case is O(log n) instead of linear. And if I know the size up front, I presize with HashMap.newHashMap so it never resizes."

Recall 2. "Comparable versus Comparator, and what does 'consistent with equals' mean?"

Tick only the points you really said:

Example answer

"Comparable is the natural ordering that a class defines for itself, like String or LocalDate. A Comparator is an ordering from outside, so I can have several, by price, by date, reversed. An ordering is consistent with equals when compare returns zero exactly when equals is true. It's strongly recommended because TreeSet and TreeMap use compare, not equals, to decide duplicates: BigDecimal 4.0 and 4.00 are not equal but compare as zero, so a TreeSet keeps only one. In practice I build comparators with Comparator.comparing and thenComparing and always end with a unique field as tie-breaker. And I never write a minus b, because it overflows; I use Integer.compare or comparingInt."

Recall 3. "How do you return a collection that callers cannot change? And how would you build an LRU cache?"

Tick only the points you really said:

Example answer

"To return internal state safely I return List.copyOf, which is a real unmodifiable copy and rejects nulls. On Java 8 I copy into a new ArrayList and wrap it with Collections.unmodifiableList. Wrapping without copying is only a view: the caller can't write, but sees my later changes. Arrays.asList is different again: fixed-size, but set writes into the array. And all of these are shallow, so the elements should be immutable too, like records or Strings. For an LRU cache I extend LinkedHashMap with accessOrder true, so each get moves the entry to the end, and override removeEldestEntry to return size greater than capacity. One caveat: in access order even get changes the structure, so with several threads I need a lock, or in production I'd use a library like Caffeine."
