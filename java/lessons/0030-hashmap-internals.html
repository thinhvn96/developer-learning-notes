Inside HashMap: buckets, resize and trees

How 98262 becomes mailbox 7, what happens at the 13th entry, and why one long bucket turns into a tree.

Today's win: walk an interviewer through put in a JDK 8+ HashMap: hash spreading, bucket index, resize by doubling, and when a bucket turns into a tree.
bit
One binary digit, 0 or 1. An int in Java has 32 of them.
bin
Another word for bucket, used in the OpenJDK source. One slot of the HashMap's array.
capacity
The number of buckets, written n. In a HashMap it is always a power of two: 16, 32, 64, …
load factor
How full the map may get before it grows. The default 0.75 means "grow when entries pass 75% of the buckets".
resize
Building a new array twice as big and moving every entry into it.
red-black tree
A sorted tree that keeps itself balanced, so finding one item among k takes about log k steps instead of k.
&, ^, >>>
Bit operators: AND keeps a bit only where both have 1; XOR gives 1 where the bits differ; >>> 16 slides all bits 16 places to the right.

Before you start

Say out loud: "A new HashMap has 16 buckets. I keep calling put with new keys. When does it grow, and what happens to the entries already inside?" Guess a number. You will check it in section 4.

1. The mailbox wall, with real numbers

Lesson 0001 showed a wall of 16 mailboxes. Here are the real rules behind it. A HashMap is an array of buckets ("bins"). The default capacity is 16, and the source says it "MUST be a power of two". The default load factor is 0.75.HashMap.java

When the number of entries exceeds capacity × load factor (16 × 0.75 = 12 for the defaults), the map is "rehashed ... so that the hash table has approximately twice the number of buckets".HashMap javadoc

A small detail from the OpenJDK source: new HashMap<>() does not create the array yet. The first put calls resize(), which creates the 16 buckets.HashMap.java

2. From hash code to mailbox number

Think of a postcode. The sorting office for a small town only reads the last digit to pick a shelf. If the town grows to 100 shelves, it reads the last two digits. HashMap does the same with bits: with 16 buckets it reads the last 4 bits of the hash; with 32 buckets, the last 5.

It happens in two steps:

  1. Spread the hash. (h = key.hashCode()) ^ (h >>> 16): it "spreads (XORs) higher bits of hash to lower", because only the low bits pick the bucket.HashMap.java Without this, two keys that differ only in their high bits would always collide. A null key hashes to 0, which is why HashMap allows one null key.
  2. Pick the bucket. index = (n - 1) & hash. With n a power of two this equals hash % n, but cheaper.HashMap.java n - 1 = 15 is 1111 in binary, so & 15 keeps exactly the last 4 bits.

Here is the key "cat" from lesson 0001, bit by bit:

You can check the bucket math with the runnable example. It copies HashMap's spread and mask:

$ java java/examples/collections/HashMapInternals.java
=== bucket index = (n - 1) & spread(hashCode), table size n = 16
apple   hashCode=   93029210  index= 1
banana  hashCode=-1396355227  index= 0
cherry  hashCode=-1361513063  index= 1
Aa      hashCode=       2112  index= 0
BB      hashCode=       2112  index= 0
('Aa' and 'BB' have the same String hashCode: a real collision)

Notice: apple and cherry have different hash codes but land in the same bucket 1, because their last 4 bits match. Aa and BB have the same hash code, so they always share a bucket.

3. put(key, value), step by step

map.put("cat", 1);
Step 1  spread:  hash = 98262 ^ (98262 >>> 16)        → 98263
Step 2  index:   (16 - 1) & 98263                     → 7
Step 3  walk bucket 7: for each node, same hash? then == or equals()?
          found    → replace the value, return the old one
          not found → append a new node at the end of the chain
Step 4  ++size > threshold (12)?                      → if yes, resize()

Step 3 is what lesson 0001 drew: compare the hash first, then == or equals. Found: replace the value. Not found: append a node. In the source, putVal checks the size only after adding a new key; replacing a value never triggers a resize.HashMap.java

4. When the wall is full: resize to 32

The 13th new key makes size 13, which is more than 12. So the map builds a wall of 32 mailboxes and moves every letter. Does Java recompute every hash code? No. On resize, "the elements from each bin must either stay at same index, or move with a power of two offset".HashMap.java No full rehash of hash codes: one extra bit decides.

Back to the postcode: the office now reads one more digit. Letters whose new digit is 0 stay on their shelf; letters whose new digit is 1 move to "old shelf + 16". In the source, that test is literally (e.hash & oldCap) == 0.HashMap.java

The example prints the same thing:

=== after resize to n = 32 an entry stays at i or moves to i + 16
apple   n=16 ->  1   n=32 -> 17
banana  n=16 ->  0   n=32 ->  0
cherry  n=16 ->  1   n=32 ->  1

So the answer to the pre-test: a default map resizes when the 13th key goes in (16 → 32), and again after the 24th (32 × 0.75 = 24, so at the 25th key, 32 → 64). Each entry stays at i or moves to i + old n.

5. When one mailbox overflows: tree bins (JDK 8+)

Imagine a prank: someone writes the same postcode on thousands of letters. They all go to one mailbox, and finding yours means reading them one by one. A long bucket makes lookups degrade toward linear.

Since JDK 8 a bin is converted to a red-black tree of TreeNodes when it reaches TREEIFY_THRESHOLD = 8 nodes (the source: bins are converted "when adding an element to a bin with at least this many nodes"), but only if the table has at least MIN_TREEIFY_CAPACITY = 64 buckets; otherwise it resizes instead. A tree bin turns back into a list when a resize splits it down to UNTREEIFY_THRESHOLD = 6 nodes or fewer.HashMap.java These numbers are OpenJDK implementation details, not Javadoc promises.

This gives "worst-case O(log n)" per bucket. With random hash codes, bins follow a Poisson distribution with a mean of about 0.5, so trees are rare in healthy maps.HashMap.java

How does a tree sort keys that all have the same hash?

The tree orders keys by hash and, "when keys are Comparable", by comparison to "help break ties".HashMap javadoc If the keys are not Comparable, the tree cannot tell them apart and often has to search both sides. The example puts 20,000 keys that all return hashCode() == 42, then looks each one up:

=== 20000 keys that ALL share hashCode 42, then 20000 lookups
not Comparable :  3529 ms
Comparable     :    88 ms

Timings vary by machine and run (an earlier run measured 3658 ms vs 69 ms). The gap of about 40× is what matters.

The trap: a bad hashCode

A bad hashCode is "a sure way to slow down performance of any hash table".HashMap javadoc Implementing Comparable limits the damage; a good hash avoids it. The fix: build hashCode() from all the fields used in equals(), with Objects.hash(...) or a record.

6. Sizing the map up front

If you know the size, create the map big enough: "If the initial capacity is greater than the maximum number of entries divided by the load factor, no rehash operations will ever occur."HashMap javadoc

// expect 1,000 entries, never resize
// JDK 19+, so JDK 21:
Map<String, Order> a = HashMap.newHashMap(1000);
// JDK 8 / 17:
Map<String, Order> b = new HashMap<>((int) (1000 / 0.75f) + 1);
// trap: 1024 buckets × 0.75 = 768, still resizes
Map<String, Order> c = new HashMap<>(1000);   // wrong

HashMap.newHashMap(numMappings) (JDK 19+) does the division for you.HashMap.java The third line is a common mistake: the number you pass is a capacity, not an entry count. The source rounds it up to a power of two (tableSizeFor), so 1000 becomes 1024 buckets and the map resizes after 768 entries.

Do not oversize either: iteration costs capacity plus size.HashMap javadoc A map with a million empty buckets is slow to loop over.

JDK 8 vs 17 vs 21

  • JDK 8: tree bins and the current hash() spreading arrived. Everything in this lesson applies.
  • JDK 17: same internals.
  • JDK 21: same internals, plus HashMap.newHashMap(n) (added in 19).

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

How does a HashMap with capacity n compute the bucket index?

putVal uses tab[(n - 1) & hash]. Because n is a power of two, this keeps the low bits, like hash % n but cheaper.

Why does HashMap XOR the hash code with h >>> 16 first?

The mask reads only the last few bits. Spreading lets the high bits influence the bucket, so keys that differ only in high bits do not all collide.

A new HashMap<>() receives new keys one by one. Which put triggers the first resize?

The threshold is capacity × load factor = 12. After the 13th new key, ++size > threshold is true, so the table doubles to 32.

During a resize from 16 to 32, where does an entry at index i go?

The new mask reads one more bit. If that bit is 0 the entry stays; if it is 1 it moves by the old capacity. "cat": 7 → 23.

When does a bin become a red-black tree in OpenJDK?

TREEIFY_THRESHOLD is 8 and MIN_TREEIFY_CAPACITY is 64. Below 64 buckets the map resizes instead.

20,000 keys all return hashCode() == 42. What makes lookups much faster?

The tree uses compareTo to break ties between equal hashes: 3529 ms dropped to 88 ms in our run. A good hashCode avoids the problem entirely.

You expect 1,000 entries and write new HashMap<>(1000). What is the bug?

The argument is a capacity, rounded up to a power of two. 1024 × 0.75 = 768. Use HashMap.newHashMap(1000) on JDK 19+.

Tick only the points you really said:

Example answer

"First Java calls hashCode() on the key and spreads it by XORing the high 16 bits into the low ones, because only the low bits pick the bucket. The index is (n - 1) & hash, and that works because the table size is always a power of two, 16 by default. Then it walks that bucket: compare hashes, then equals. If the key exists, it replaces the value; otherwise it appends a node. After adding a new key, if the size passes capacity times the load factor, 12 for a default map, the table doubles. Each entry then either stays at the same index or moves by the old capacity, so there's no real rehashing. Since Java 8, if one bucket reaches 8 nodes and the table has at least 64 buckets, that bucket becomes a red-black tree, so the worst case is O(log n) instead of O(n). If I know the size up front, I use HashMap.newHashMap to avoid resizes."
