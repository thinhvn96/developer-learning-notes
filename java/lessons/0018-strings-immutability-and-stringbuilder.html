Strings: immutability, the pool and StringBuilder

Java (JDK 8, 17, 21) · Lesson 0018 · step 1 of 27 · Foundation · ~10 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap

Today's win: explain why == on strings is a trap and when to use StringBuilder.

Immutable

"Strings are constant; their values cannot be changed after they are created." Because they are immutable they can be shared safely between references.[1] Methods such as concat return a new string.

Literals and the pool

String literals are String instances, and intern() returns a canonical representation so equal contents can share one object.[1] Identical literals therefore refer to the same object, but new String("abc") creates another.

java java/examples/StringDemo.java
a == b          : true      # same literal
a == c          : false     # new String(...)
a.equals(c)     : true
a == c.intern() : true

Rule: compare contents with equals, never ==.

Concatenation

How + is compiled is left to the compiler: it may use StringBuffer, StringBuilder or StringConcatFactory depending on the JDK version.[1] In a loop, build with an explicit StringBuilder instead of repeated +=, since each += creates a new string (derived from immutability; measure before optimizing).

Source: StringDemo.java.

Retrieval practice

Answer from memory. One attempt each.

1. Are Java strings mutable?

Strings are constant; methods return new strings.[1]

2. Two identical literals compared with ==. Result?

Literals with the same contents refer to the same instance (demo: a == b true).[1]

3. What does intern() return?

It returns a canonical representation of the string.[1]

4. Best way to compare string contents?

equals compares the exact character sequence.[1]
