Why a Java string never changes

Immutability, the string pool, the == trap, and when to reach for StringBuilder.

Java (JDK 8, 17, 21) · Lesson 0018 · step 1 of 46 · Foundation · ~20 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? Strings are in every line of backend code: IDs, JSON, SQL, log messages. Interviewers love "Why is String immutable?" and "What is the difference between == and equals()?" because the wrong answer causes real bugs that only show up sometimes.
Today's win: explain why == on strings is a trap, what the string pool is, and when to use StringBuilder, in about 60 seconds.
object
A thing your program creates in memory, for example one String with the text "abc".
reference
A variable that points to an object, like an address written on a card. Two variables can point to the same object.
immutable
Cannot be changed after it is created. To get a different value, you make a new object.
literal
A value written directly in the code, like "abc" between double quotes.
string pool
A private list of shared strings kept by the String class, so equal literals can use one object.
==
On objects, it asks "do both variables point to the same object?". It does not look at the text.
equals()
A method that asks "do these two strings contain the same characters?".

Before you start

Say out loud: "String a = "abc"; String c = new String("abc"); What does a == c print, and why?" Guess first, even if you are not sure. You will check your guess in section 3.

1. The picture: a printed label

Think of a printed label on a box. You cannot rub out the letters. If you want a different text, you print a new label and stick it on. The old label still exists until someone throws it away.

A Java String works the same way. The documentation says: "Strings are constant; their values cannot be changed after they are created."String javadoc Methods that look like they change a string, such as concat, toUpperCase or replace, really return a new string.

String s = "x";
String t = s.concat("y");
Step 1  s points to the object "x"
Step 2  concat builds a NEW object "xy" and returns it
Step 3  t points to "xy"; s still points to "x"
System.out.println(s + ", " + t);   // x, xy

The runnable example prints exactly this:

$ java java/examples/StringDemo.java
...
s after concat  : x, t = xy

Trap: calling a method and ignoring the result

String name = "anna";
name.toUpperCase();              // result thrown away
System.out.println(name);        // still "anna"

name = name.toUpperCase();       // fix: keep the new string

Because strings never change, the result must be stored in a variable. Forgetting this is a classic beginner bug.

2. Why immutable is a good idea

The documentation gives the main reason in one sentence: "Because String objects are immutable they can be shared."String javadoc If nobody can change an object, many variables (and many threads) can point to it without any risk.

  • Safe sharing. You can pass a string to any method. That method cannot change your copy behind your back.
  • Safe map keys. In lesson 0001 you saw that a key that changes gets lost in a HashMap. A string key cannot change, so it cannot get lost.
  • A shared pool is possible. Because sharing is safe, Java can keep one copy of each literal. That is the next section.

3. Where strings live: the string pool

Imagine an office with one shared dictionary on a shelf. Everybody who needs it walks to the same shelf. Nobody buys a second copy, because nobody is allowed to write in it.

The String class keeps such a shelf. Its documentation for intern() says: "A pool of strings, initially empty, is maintained privately by the class String." and "All literal strings and string-valued constant expressions are interned."String javadoc The language specification says the same thing from the other side: "a string literal always refers to the same instance of class String".JLS §3.10.5

Now run the example and follow it line by line:

String a = "abc";
String b = "abc";               // same literal
String c = new String("abc");   // explicitly a new object

$ java java/examples/StringDemo.java
a == b          : true
a == c          : false
a.equals(c)     : true
a == c.intern() : true
  1. a == b is true. Both are the literal "abc", so both point to the one pooled object.
  2. a == c is false. new always creates a new object, so c points somewhere else. The text is the same; the object is not.
  3. a.equals(c) is true. equals compares the characters, not the address.
  4. a == c.intern() is true. intern() looks in the pool, finds an equal string, and returns the pooled one. The documentation: for any two strings, "s.intern() == t.intern() is true if and only if s.equals(t) is true".String javadoc

Strings built at run time are new objects

The specification also says that strings joined from constants "are computed at compile time and then treated as if they were literals", but "Strings computed by concatenation at run time are newly created and therefore distinct."JLS §3.10.5 Its own example:

String hello = "Hello", lo = "lo";
hello == ("Hel" + "lo")   // true: two constants, joined by javac
hello == ("Hel" + lo)     // false: lo is a variable → new object

This is why == on strings is so dangerous: it sometimes works (in a small test with literals) and then fails in production, where the string came from a request, a file or a database.

4. The rule: compare text with equals

Compare string contents with equals(). Never with ==.

equals is defined as: "The result is true if and only if the argument is not null and is a String object that represents the same sequence of characters as this object."String javadoc

Trap: the user input check

// answer comes from an HTTP request: built at run time
String answer = request.getParameter("confirm");

if (answer == "yes") { ... }        // bug: almost never true
if (answer.equals("yes")) { ... }   // NPE if answer is null
if ("yes".equals(answer)) { ... }   // best: null gives false

The last line puts the literal first. Since the argument may be null and equals simply returns false for null, you avoid a NullPointerException.

Should you call intern() everywhere so == works? No. It is a lookup in a shared pool, it does not fix code that forgets to call it, and equals is clear and correct. Know what intern() does; do not use it to fix comparisons.

5. Building strings: + versus StringBuilder

Back to the printed labels. If you add one letter at a time, and every time you print a whole new label, you throw away many labels. Better: use a whiteboard, write all the letters, and print once at the end. StringBuilder is that whiteboard.

Its documentation calls it "A mutable sequence of characters" and recommends it over the older StringBuffer "as it will be faster under most implementations". The price: "Instances of StringBuilder are not safe for use by multiple threads."StringBuilder javadoc That is fine, because you normally build a string inside one method, on one thread.

Follow the loop from the example:

StringBuilder sb = new StringBuilder();
for (int i = 0; i < 5; i++) sb.append(i).append(',');
Step 1  new StringBuilder(): empty buffer, room for 16 characters
Step 2  each append writes into the same buffer (no new String)
Step 3  printing sb calls toString(): one String is created at the end

$ java java/examples/StringDemo.java
...
StringBuilder   : 0,1,2,3,4,

The "room for 16" comes from the constructor's documentation: "an initial capacity of 16 characters".StringBuilder javadoc If you append more, the builder grows by itself.

So is + bad? JDK 8 versus 9+

No. For one expression like "id=" + id + ", name=" + name, just use +; it is readable. How + is compiled is the compiler's choice: "the javac compiler may implement the operator with StringBuffer, StringBuilder, or java.lang.invoke.StringConcatFactory depending on the JDK version."String javadoc So the bytecode for + on JDK 8 differs from JDK 17 and 21, but your source code stays the same.

The problem is += inside a loop. Each round makes a new string and copies all the old characters into it, so the work grows with every round (this follows from immutability). In a loop, use one explicit StringBuilder. As always: measure before you optimize small cases.

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

What happens to s after String s = "x"; s.concat("y");?

Strings are constant. concat returns a new string; if you ignore the result, nothing changes.

What does "abc" == "abc" print for two identical literals?

"A string literal always refers to the same instance of class String" (JLS §3.10.5). The demo prints a == b : true.

String a = "abc"; String c = new String("abc"); What is a == c?

== compares addresses. new creates a separate object, so the addresses differ even though the text is equal.

What is the bug in if (status == "ACTIVE") when status was read from the database?

Strings computed at run time are new objects, so == is false. Use "ACTIVE".equals(status).

What does intern() return?

It returns "a canonical representation": the pooled string equal to this one, adding it to the pool first if needed.

You build a 10 000-line report in a for loop. Which is best?

Each += creates a new string and copies the old text. A StringBuilder fills one buffer; it is the documented choice for single-threaded building.

The final test: say it in 60 seconds

An interviewer asks: "Why is String immutable in Java, and what is the difference between == and equals()?" Start a timer. Answer out loud, in full sentences. Then click the button.

Tick only the points you really said:

Example answer

"A String in Java is immutable: once it's created, its characters never change, and methods like concat or toUpperCase return a new string. The big benefit is that strings can be shared safely, between threads and as HashMap keys. It also lets Java keep a string pool: every literal with the same text points to one shared object, and intern() gives you that pooled copy. That's exactly why == is a trap. == compares references, so two literals look equal, but a string from new or from a request is a different object and == is false. To compare text I always use equals, usually "yes".equals(input) so null is safe. And when I build a string in a loop I use a StringBuilder, because each += would create a new string and copy everything again."
