When to write ? extends and when ? super

Wildcards make generic methods flexible; type erasure explains what is left of generics at run time.

Java (JDK 8, 17, 21) · Lesson 0021 · step 4 of 46 · Advanced · ~25 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? In lesson 0020 you learned that List<Integer> is not a List<Number>. So how do you write one method that sums any list of numbers? Senior interviews ask exactly this, then "What is PECS?" and "Do generics exist at run time?"
Today's win: choose ? extends or ? super by asking whether a parameter is a producer ("in") or a consumer ("out"), and explain type erasure and its consequences.
wildcard
A question mark in a generic type, List<?>: "a list of some type I don't know exactly".
? extends T
Upper bounded wildcard: "some type that is T or a subtype of T". Example: List<? extends Number>.
? super T
Lower bounded wildcard: "some type that is T or a supertype of T". Example: List<? super Integer>.
producer / "in"
A parameter your method only reads from. It gives data to your code.
consumer / "out"
A parameter your method only writes into. It receives data from your code.
type erasure
The compiler removes the type arguments after checking them, so the running program does not see them.
reifiable
A type whose full information is still available at run time. String is; List<String> is not.

Before you start

Say out loud: "I need a method copy(src, dest) that copies Integers from one list into another. Which wildcard goes on src, and which on dest?" Guess before you read.

1. Reading: ? extends

A fruit taster tastes fruit from any box you hand over. An apple box is fine, a banana box is fine. The taster only takes fruit out, so any box of "some kind of fruit" works.

A method that only reads numbers is the taster. With List<Number> it would refuse a List<Integer> (invariance). With ? extends Number it accepts both:

static double sum(List<? extends Number> in) {   // reads Numbers
    double s = 0;
    for (Number n : in) s += n.doubleValue();
    return s;
}
Step 1  sum(ints), ints is a List<Integer>: Integer is a Number → OK
Step 2  each element is read as a Number → doubleValue() works
Step 3  1 + 2 + 3 → 6.0
$ java java/examples/GenericsDemo.java
sum of ints    : 6.0
...

Trap: you cannot add to it

Why not in.add(1)? The compiler only knows "a list of some subtype of Number". It could be a List<Double>, and then an Integer would be the banana in the apple box. So JDK 21's javac refuses: error: incompatible types: int cannot be converted to CAP#1 (CAP#1 is the compiler's name for "the unknown type").

The tutorial adds a detail interviewers like: such a list "can be informally thought of as read-only, but that is not a strict guarantee". You can still add null, call clear, or remove through an iterator.Tutorial: wildcard guidelines

2. Writing: ? super

Now an apple picker who only puts apples in. Which boxes can you give the picker? An "apples" box, a "fruit" box, or an "anything" box. All of them accept apples. A "bananas only" box would not.

static void fill(List<? super Integer> out) {    // writes Integers
    for (int i = 1; i <= 3; i++) out.add(i);
}
Step 1  fill(nums), a List<Number>: Number is a supertype → OK
Step 2  fill(objs) with List<Object>: Object is a supertype too → OK
Step 3  each add(i) is safe: every such list can hold an Integer
$ java java/examples/GenericsDemo.java
...
filled Number  : [1, 2, 3]
filled Object  : [1, 2, 3]
...

The other side of the trade: when you read from a List<? super Integer>, the compiler only knows the element is "some supertype of Integer", so you get back an Object.

3. The rule: "in" and "out" (PECS)

The Java tutorial states the rule with "in" and "out" variables:Tutorial: wildcard guidelines

  • An "in" variable (it provides data to your code) uses an upper bounded wildcard: ? extends.
  • An "out" variable (it receives data) uses a lower bounded wildcard: ? super.
  • If the "in" variable is used only through Object methods: unbounded ?.
  • If it is both "in" and "out": no wildcard.

Interviewers call it PECS: Producer Extends, Consumer Super. Same rule, other words.

The JDK itself uses this rule. Here is the real signature of Collections.copy:Collections javadoc

public static <T> void copy(List<? super T> dest, List<? extends T> src)

src is read (producer, extends), dest is written (consumer, super). That is the answer to the "Before you start" question.

Two more guidelines

  • No wildcards in return types. The tutorial: "Using a wildcard as a return type should be avoided because it forces programmers using the code to deal with wildcards."Tutorial: wildcard guidelines
  • List<?> is not List<Object>. "You can insert an Object, or any subtype of Object, into a List<Object>. But you can only insert null into a List<?>."Tutorial: unbounded wildcards Use List<?> for methods like "print any list" or "count elements".

4. Type erasure: the labels come off

Back to the storeroom of lesson 0020. The inspector at the door checks every label carefully. But once a box is inside, the labels are peeled off to save space. Inside the warehouse, every box looks the same.

That is type erasure. After checking your code, the compiler:Tutorial: type erasure

  1. replaces type parameters with their bounds, or with Object if they have none,
  2. inserts casts where needed to keep type safety,
  3. generates bridge methods to keep polymorphism working in subclasses of generic types.

The tutorial sums it up: "no new classes are created for parameterized types; consequently, generics incur no runtime overhead."Tutorial: type erasure

The example proves it:

List<String> strings = new ArrayList<>();
strings.getClass() == ints.getClass()

$ java java/examples/GenericsDemo.java
...
same runtime class: true

Consequences you must know

Because the type argument is gone at run time, parameterized types are not reifiable.Tutorial: type erasure The tutorial's list of restrictions includes:Tutorial: restrictions on generics

  • "Cannot Use Casts or instanceof with Parameterized Types". obj instanceof List<String> does not compile; JDK 21's javac says Object cannot be safely cast to List<String>. Check instanceof List<?> instead.
  • "Cannot Create Arrays of Parameterized Types". No new List<String>[10].
  • "Cannot Create Instances of Type Parameters". No new T() inside a generic class.

JDK 8 vs 17 vs 21: the rules of this lesson are the same on all three. What changed is around them, for example var and records, which you will meet later.

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

A method only reads Numbers from a list. Which parameter type?

An "in" variable (producer) uses an upper bounded wildcard, so it also accepts List<Integer> and List<Double>.

A method only adds Integers to a list. Which parameter type?

An "out" variable (consumer) uses a lower bounded wildcard, so List<Number> and List<Object> work too.

Why does in.add(1) fail when in is List<? extends Number>?

The compiler only knows "some subtype of Number", so it cannot prove an Integer fits. (You can still add null or call clear.)

What is the real signature of Collections.copy?

The source is read (extends), the destination is written (super): PECS in the JDK itself.

What does new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass() print?

Type erasure creates no new classes for parameterized types; the demo prints same runtime class: true.

Why is obj instanceof List<String> rejected when obj is an Object?

List<String> is not reifiable: at run time there is only List. Use instanceof List<?>.

Which method signature follows the tutorial's guidelines?

Inputs are read, so ? extends T; the return type has no wildcard, so callers get a plain List<T>.

The final test: say it in 60 seconds

An interviewer asks: "Explain ? extends versus ? super, and what type erasure is." Start a timer. Answer out loud, in full sentences. Then click the button.

Tick only the points you really said:

Example answer

"Because generics are invariant, a List<Number> parameter won't accept a List<Integer>, so we use wildcards. I ask one question: does my method read from this parameter or write into it? If it reads, it's a producer, and I use ? extends T: for example sum(List<? extends Number>) accepts integers and doubles, but I can't add to it. If it writes, it's a consumer, and I use ? super T: fill(List<? super Integer>) accepts a list of Integer, Number or Object. That's PECS, producer extends, consumer super, and Collections.copy is the classic example. I don't put wildcards in return types. Type erasure means the compiler checks the type arguments, then erases them to their bounds or Object and inserts casts. So at run time a List<String> and a List<Integer> are the same class, and I can't do instanceof List<String>, create a generic array, or call new T()."
