Why count++ loses updates, and how to fix it

One line of Java, three steps for the CPU. Atomics and locks glue them back together.

Java (JDK 8, 17, 21) · Lesson 0024 · step 31 of 46 · Advanced · ~25 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? Counters, balances, stock levels, rate limits: real services update shared numbers from many threads all the time. Interviewers ask "Is volatile int count; count++ thread-safe?" right after the happens-before question. This lesson shows why the answer is no, and how to choose between an atomic and a lock.
Today's win: show that volatile count++ loses updates and fix it with an atomic or a lock.
atomic
"All or nothing, in one go": no other thread can see the operation half done or squeeze in between its steps.
read-modify-write
An operation in three steps: read the old value, compute a new one, write it back. count++ is one.
lost update
Two threads both write a result, and one result overwrites the other, so one change disappears.
compare-and-set (CAS)
"Set the value to 6, but only if it is still 5." It succeeds or fails as one atomic step.
lock
An object that only one thread can hold at a time. Other threads that want it wait.
reentrant
A thread that already holds the lock can take it again without blocking itself.
contention
Many threads trying to use the same lock or variable at the same moment.

Before you start

Say out loud: "Four threads each run count++ 200,000 times on a volatile int. What is the final value?" Pick a number, and say why. The real result is in section 2.

1. One line, three steps

Imagine a shared tally sheet on a wall. To add one, a person (1) reads the number, (2) adds one in their head, (3) erases and writes the new number. If two people do this at the same time, both may read 5, both think "6", and both write 6. Two people counted, but the sheet only went up by one.

That is exactly count++. The Oracle tutorial splits c++ into three steps: "Retrieve the current value of c", "Increment the retrieved value by 1", "Store the incremented value back in c".Java tutorial: thread interference Another thread can run between any two of them.

Now you can see why volatile does not help. Lesson 0005 said volatile gives visibility and ordering,JLS 17 not atomic read-modify-write. In the picture every read is fresh: both threads really saw 5. Visibility was never the problem. The problem is the gap between steps 1 and 5.

2. See it happen

The example AtomicDemo.java starts four threads. Each one does 200,000 increments on three counters: a volatile int, an AtomicInteger, and an int guarded by a ReentrantLock.

volatileCount++;                    // read-modify-write: NOT atomic
atomicCount.incrementAndGet();      // atomic
lock.lock();
try { lockedCount++; } finally { lock.unlock(); }   // one thread at a time
$ java java/examples/AtomicDemo.java
expected       : 800000
volatile int   : 797349  (lost updates: 2651)
AtomicInteger  : 800000
ReentrantLock  : 800000

The volatile number changes on every run (an earlier run lost 1642 updates). That is normal for a race: the result depends on how the threads happen to interleave. Sometimes it may even come out right, which is why tests rarely catch this bug.

3. Fix 1: atomics and compare-and-set

Back to the tally sheet. A smarter rule: "Read the number. Work out the new one. Before you write, check the sheet still shows what you read. If yes, write. If someone changed it, start over." The check-and-write is one single action, and nobody can squeeze in. That rule is compare-and-set.

AtomicInteger is "An int value that may be updated atomically", used "in applications such as atomically incremented counters".AtomicInteger javadoc Its compareAndSet(expected, newValue) "Atomically sets the value to newValue if the current value == expectedValue".AtomicInteger javadoc

Trace the bad interleaving from section 1 again, now with CAS:

Step 1  A reads 5            B reads 5
Step 2  A: CAS(5, 6) → true  count is 6
Step 3  B: CAS(5, 6) → false  (count is 6, not 5)
Step 4  B reads again → 6, CAS(6, 7) → true   count is 7 ✓

You rarely write that loop yourself. The atomic package is "a small toolkit of classes that support lock-free thread-safe programming on single variables", with low-level compareAndSet and higher-level methods like getAndUpdate.atomic package Their reads and writes publish values like a volatile field: get() has "memory effects as specified by VarHandle.getVolatile".AtomicInteger javadoc

AtomicInteger count = new AtomicInteger();
count.incrementAndGet();               // ++count, atomically
count.updateAndGet(x -> x * 2);        // any function, atomically
count.compareAndSet(10, 0);            // reset only if it is still 10

Trap: the function you pass to updateAndGet "should be side-effect-free, since it may be re-applied when attempted updates fail due to contention among threads".AtomicInteger javadoc Don't send an email or log a payment inside it: it may run twice.

Many threads, one counter: LongAdder

With very heavy contention, many CAS attempts fail and retry. For counters there are LongAdder and friends. LongAdder is "usually preferable to AtomicLong when multiple threads update a common sum that is used for purposes such as collecting statistics"; under high contention its throughput is "significantly higher, at the expense of higher space consumption".LongAdder javadoc You will meet it again in lesson 0025.

4. Fix 2: a lock

Think of a shop's single bathroom key. Whoever holds the key goes in; everyone else waits in line. When you come out, you hand back the key. A lock works the same way: the code between lock() and unlock() runs in one thread at a time, so the three steps of count++ can no longer be split.

Java has two kinds. The built-in one is synchronized. The library one is ReentrantLock: "A reentrant mutual exclusion Lock with the same basic behavior and semantics as the implicit monitor lock accessed using synchronized methods and statements, but with extended capabilities."ReentrantLock javadoc

// built-in lock
synchronized (this) { count++; }

// ReentrantLock: the documented idiom
lock.lock();
try { count++; } finally { lock.unlock(); }

Line by line:

  1. lock.lock() waits until no other thread holds the lock, then takes it. Put it right before try.
  2. The try block is the protected work.
  3. unlock() goes first in finally, so the lock is released even if the work throws an exception. The Javadoc recommends to "always immediately follow a call to lock with a try block".ReentrantLock javadoc

A lock also creates the happens-before edge from lesson 0005: an unlock happens-before the next successful lock of the same lock.java.util.concurrent: memory consistency So the next thread sees the updated count.

What "reentrant" means

If a thread already holds the lock and calls lock() again (for example, one locked method calls another), it does not block itself: "If the current thread already holds the lock then the hold count is incremented by one and the method returns immediately."ReentrantLock javadoc It must call unlock() the same number of times.

What ReentrantLock adds over synchronized

  • tryLock(): take the lock only if it is free right now; otherwise return false immediately. tryLock(time, unit) waits at most that long. Useful against deadlock (lesson 0026).
  • lockInterruptibly(): a waiting thread can be interrupted instead of waiting forever.
  • Fairness: with new ReentrantLock(true), "under contention, locks favor granting access to the longest-waiting thread"; otherwise there is no particular order.ReentrantLock javadoc
  • Conditions: newCondition() gives wait/notify-style queues.

5. Which one should you use?

SituationUseWhy
One counter or one value, simple updateAtomicInteger / AtomicLongLock-free, short, no unlock to forget
A statistics counter hit by many threadsLongAdderHigher throughput under contention
Several variables that must change togethersynchronized or a lockAn atomic protects one variable only
Need a timeout, interruptible wait or fairnessReentrantLocksynchronized has none of these

Common mistakes

  • Check-then-act on an atomic: if (a.get() == 0) a.set(1); is two separate atomic steps, so another thread can act in between. Use a.compareAndSet(0, 1).
  • Two atomics, one rule: keeping min and max in two AtomicIntegers does not make "min ≤ max" safe. Use one lock for both.
  • unlock() not in finally: one exception and the lock is held forever; every other thread waits.
  • Different locks: two threads that lock different objects do not exclude each other at all.

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

Four threads run count++ on a volatile int. What can go wrong?

count++ is read-modify-write. volatile makes each read fresh but does not stop another thread from writing between the read and the write.

Why did the lost update in the diagram happen, even though both reads were fresh?

The problem is atomicity, not visibility: the three steps were split, and B's write replaced A's.

The value is 6. Thread B calls compareAndSet(5, 6). What happens?

CAS only writes if the current value equals the expected one. It failed, so B must read again and retry.

Where should unlock() go when you use a ReentrantLock?

The documented idiom: lock() right before try, unlock() in finally, so an exception cannot leave the lock held.

Which method tries to take the lock without blocking?

tryLock() takes the lock only if no other thread holds it at that moment; otherwise it returns false at once.

You must update balance and history together so they always agree. Best tool?

Atomics protect a single variable. A rule that spans two variables needs one lock (or synchronized) around both.

Many threads increment one statistics counter, and it is slow. What does the Javadoc suggest?

Under high contention LongAdder's expected throughput is significantly higher, at the cost of more space.

An interviewer asks: "Is volatile int count; count++ thread-safe? How would you fix it?" Start a timer. Answer out loud, in full sentences. Then click the button.

Tick only the points you really said:

Example answer

"No. count++ looks like one statement but it's a read, an add and a write. Two threads can both read 5 and both write 6, so one increment is lost. volatile doesn't help, because it only guarantees visibility and ordering, not that the three steps run as one. I'd fix it with an AtomicInteger and incrementAndGet: it uses compare-and-set, so if another thread changed the value in between, the CAS fails and it retries, with no lock. If I need to update several fields together, I use synchronized or a ReentrantLock, with lock before try and unlock in finally; ReentrantLock also gives me tryLock with a timeout and fairness. For a very hot statistics counter I'd use LongAdder, which scales better under contention at the cost of some memory."
