Atomics and ReentrantLock: fixing lost updates

Java (JDK 8, 17, 21) · Lesson 0024 · step 14 of 27 · Advanced · ~10 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap

Today's win: show that volatile count++ loses updates and fix it with an atomic or a lock.

The bug

Lesson 5 said volatile gives visibility and ordering,[3] not atomic read-modify-write. Four threads doing 200,000 increments each:

java java/examples/AtomicDemo.java
expected       : 800000
volatile int   : 798358  (lost updates: 1642)   # varies run to run
AtomicInteger  : 800000
ReentrantLock  : 800000

Atomics

The atomic package is "a small toolkit of classes that support lock-free thread-safe programming on single variables", with compareAndSet and higher-level methods like getAndUpdate; operations have volatile access semantics. For heavy contention on counters there are LongAdder and friends.[1]

ReentrantLock

A reentrant mutual-exclusion lock with the same basic semantics as synchronized but extended: fairness option, tryLock, lockInterruptibly, conditions. Idiom: lock() right before try, unlock() first in finally.[2]

lock.lock();
try { count++; } finally { lock.unlock(); }

Source: AtomicDemo.java.

Retrieval practice

Answer from memory. One attempt each.

1. What does volatile int count++ risk?

count++ is read-modify-write, not atomic; the demo lost updates.

2. Which class gives lock-free atomic increments?

Atomic classes support lock-free thread-safe updates on single variables.[1]

3. Where should unlock() go?

The documented idiom puts unlock as the first statement in finally.[2]

4. Which method tries the lock without blocking?

tryLock is a non-blocking attempt to acquire.[2]
