Virtual thread: mở rộng quy mô, không phải tốc độ

JDK 21 chạy mười nghìn task đang chờ trên vài thread thật như thế nào, và hai quy tắc để nó chạy đúng.

Java (JDK 8, 17, 21) · Bài 0006 · bước 44/46 · Advanced · ~25 phút · Trang chủ · Lộ trình Java (JDK 8, 17, 21) · Lộ trình tổng · English

Vì sao có bài này? Một backend service điển hình dành phần lớn thời gian để chờ: chờ database, chờ một HTTP service khác, chờ queue. Virtual thread, chính thức từ JDK 21, thay đổi số lượt chờ mà một server xử lý được. Giờ đây nó là một trong những câu hỏi Java senior phổ biến nhất: "Virtual thread là gì, khi nào nó giúp ích, và cái gì có thể sai?"
Thành quả hôm nay: giải thích virtual thread là gì, khi nào nó có ích, và hai quy tắc: không pool chúng, và dùng Semaphore để giới hạn mức đồng thời.
thread
Một luồng công việc chạy bên trong chương trình. Nhiều thread có thể chạy cùng lúc, mỗi thread có các bước riêng.
OS thread
Thread do hệ điều hành quản lý. Nó tốn kém: hệ điều hành cấp cho mỗi thread vùng nhớ riêng, nên bạn chỉ có được vài nghìn cái.
platform thread
Thread Java kiểu cổ điển. Mỗi cái là "một lớp bọc mỏng quanh một OS thread".
virtual thread
Thread Java nhẹ, chỉ mượn một OS thread trong lúc nó thật sự đang chạy code.
carrier thread
Platform thread mà virtual thread đang chạy trên đó.
blocking I/O
Lời gọi phải chờ thế giới bên ngoài: query database, gọi HTTP, đọc file, Thread.sleep.
throughput
Số task hoàn thành mỗi giây (thông lượng). Còn latency là thời gian một task mất.

Trước khi bắt đầu

Hãy nói thành tiếng: "Server của mình có pool 200 thread. Mỗi request gọi một database trả lời sau 1 giây. Tối đa server xử lý được bao nhiêu request mỗi giây?" Giữ con số đó; bạn sẽ kiểm tra lại ở mục 3.

1. Cách cũ: mỗi bàn một người phục vụ

Hãy tưởng tượng một nhà hàng mà mỗi người phục vụ nhận order, đi vào bếp rồi đứng đó cho tới khi món ăn xong. Có 200 người phục vụ thì phục vụ được 200 bàn cùng lúc. Bàn thứ 201 phải chờ ở cửa, dù hầu hết người phục vụ chỉ đang đứng không.

Đó là một server Java cổ điển. Mỗi request nhận một platform thread, và theo tài liệu, "platform thread được hiện thực như một lớp bọc mỏng quanh một OS thread".core libraries guide OS thread tốn kém, nên ta giữ một pool cố định (bài 0023):

// JDK 8 / 17 style: a fixed pool of 200 platform threads
// (try-with-resources on an executor needs JDK 19+;
//  on 8 and 17 call shutdown() instead)
try (var pool = Executors.newFixedThreadPool(200)) {
    for (int i = 0; i < 10_000; i++) {
        pool.submit(() -> {
            Thread.sleep(Duration.ofSeconds(1));   // holds its OS thread
            return null;
        });
    }
}

Trong lúc chờ database, thread vẫn giữ OS thread của nó và chẳng làm gì. Chỉ 200 task chạy cùng lúc, nên 10.000 task một giây cần khoảng 10.000 / 200 × 1 s = 50 giây. Đó là đáp án cho phần "Trước khi bắt đầu": tối đa 200 request mỗi giây.

2. Cách mới: người phục vụ không đứng chờ

Giờ người phục vụ nhận order, đưa cho bếp, rồi đi phục vụ bàn khác. Khi món xong, bất kỳ ai đang rảnh sẽ mang ra. Vài người phục vụ có thể lo hàng trăm bàn, vì không ai đứng yên.

Đó là virtual thread. "Giống platform thread, virtual thread cũng là một instance của java.lang.Thread. Tuy nhiên, virtual thread không gắn với một OS thread cụ thể nào." Khi code trong virtual thread gọi một thao tác blocking I/O, runtime tạm dừng nó và giải phóng OS thread cho các virtual thread khác.core libraries guide

JEP 444 đặt tên cho từng phần. JDK chạy một virtual thread "bằng cách mount virtual thread lên một platform thread", và "platform thread mà scheduler giao cho virtual thread được gọi là carrier của virtual thread đó". Khi virtual thread bị block, nó "có thể unmount khỏi carrier".JEP 444

Ai quyết định virtual thread nào chạy trên carrier nào? Một scheduler: "scheduler của virtual thread trong JDK là một ForkJoinPool work-stealing hoạt động ở chế độ FIFO." Mức song song của nó, tức số carrier, "mặc định bằng số processor khả dụng".JEP 444 Trên máy 8 core bạn có khoảng 8 carrier, dù tạo bao nhiêu virtual thread đi nữa.

3. Mười nghìn lần sleep trong một giây

Đây là ví dụ của khoá học. So với code dùng pool ở mục 1: chỉ đổi một dòng.

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 10_000; i++) {
        executor.submit(() -> {
            Thread.sleep(Duration.ofSeconds(1)); // blocks: v-thread unmounts
            return null;
        });
    }
} // close() waits for all tasks
$ java java/examples/VirtualThreadsDemo.java
10,000 one-second tasks finished in 1065 ms

Mười nghìn lần sleep một giây xong trong khoảng một giây. Với pool cố định 200 platform thread, cùng công việc sẽ mất khoảng 50 giây (10.000 / 200 × 1 s); hãy thử trong bài tập. Theo dõi một task:

Step 1  submit() creates a new virtual thread v1 for the task
Step 2  the scheduler mounts v1 on a free carrier; v1 starts running
Step 3  v1 calls Thread.sleep(1 s): it unmounts, the carrier is free again
Step 4  the carrier runs v2, v3, ... which also sleep and unmount
Step 5  after 1 s, v1 is ready: it mounts on any free carrier and returns
        all 10,000 wait at the same time, so the whole job takes ~1 s

Bạn cũng có thể tạo virtual thread trực tiếp. JEP 444: "Thread.Builder, Thread.ofVirtual() và Thread.ofPlatform() là các API mới để tạo virtual thread và platform thread", và "Thread.startVirtualThread(Runnable) là cách tiện lợi để tạo rồi start một virtual thread".JEP 444 Ngoài ra, "virtual thread luôn là daemon thread", nên tự chúng không giữ JVM sống.JEP 444

4. Mở rộng quy mô, không phải tốc độ

"Virtual thread không phải là thread nhanh hơn; chúng không chạy code nhanh hơn platform thread. Chúng tồn tại để mang lại khả năng mở rộng (throughput cao hơn), không phải tốc độ (latency thấp hơn)."core libraries guide Chúng hợp với server kiểu thread-per-request có nhiều blocking I/O; cứ viết code blocking đơn giản.

Quay lại nhà hàng: người phục vụ khéo léo không làm bếp nấu nhanh hơn. Một món vẫn mất mười phút. Cái thay đổi là số bàn bạn phục vụ cùng lúc. JEP 444 nói một cách chính thức: "khả năng mở rộng của ứng dụng server tuân theo Little's Law".JEP 444 Nói đơn giản, số request mỗi giây ≈ số request đang xử lý ÷ thời gian mỗi request. Với thời gian chờ 1 giây, 200 thread cho 200 request/giây; 10.000 virtual thread cho khoảng 10.000 request/giây.

Bẫy: công việc nặng CPU

Nếu mỗi task tính toán 1 giây (hash, resize ảnh) thay vì chờ, nó không bao giờ block, nên không bao giờ unmount. Bạn vẫn chỉ có số carrier bằng số core CPU, và công việc mất đúng bằng thời gian khi dùng pool platform thread. Virtual thread giúp cho việc chờ, không giúp cho việc tính.

5. Hai quy tắc: đừng pool, giới hạn bằng Semaphore

Quy tắc 1: "Đừng bao giờ pool virtual thread." Mỗi task một virtual thread: Executors.newVirtualThreadPerTaskExecutor().core libraries guide Tài liệu giải thích lý do: "Pool được thiết kế để chia sẻ tài nguyên khan hiếm, mà virtual thread thì không khan hiếm, nên đừng bao giờ pool chúng!"core libraries guide Tạo một cái rất rẻ; JEP 444 đưa ra một chương trình tạo 10.000 cái và nói tới việc "tạo 1.000.000 virtual thread chạy đồng thời".JEP 444

Quy tắc 2: giới hạn mức đồng thời bằng Semaphore, không bằng pool.core libraries guide Code cũ hay dùng pool 10 thread đồng thời để bảo vệ một service chậm khỏi nhận quá 10 lời gọi cùng lúc. Bỏ pool đi thì bạn vẫn cần giới hạn đó. Semaphore giống một bát có 10 vé: lấy một vé trước khi gọi, trả lại sau khi xong. Ví dụ trong tài liệu:core libraries guide

Semaphore sem = new Semaphore(10);
...
Result foo() {
    sem.acquire();      // wait for a ticket (an 11th caller waits here)
    try {
        return callLimitedService();
    } finally {
        sem.release();  // always give the ticket back
    }
}

Thêm một lưu ý từ JEP 444: vì bạn có thể có hàng triệu virtual thread, "chỉ dùng thread local sau khi cân nhắc kỹ".JEP 444 Một object lớn cache trong ThreadLocal trước đây tồn tại 200 bản; giờ có thể là mỗi task một bản.

6. Điểm vướng: pinning

Đôi khi virtual thread không thể unmount trong lúc chờ. Khi đó nó bị pin (ghim) vào carrier, ví dụ trong lời gọi native, điều này làm giảm khả năng mở rộng nhưng không ảnh hưởng tính đúng đắn.core libraries guide Trên JDK 21, tài liệu liệt kê hai trường hợp: "virtual thread chạy code bên trong một block hoặc method synchronized" và "virtual thread chạy một method native hoặc một foreign function".core libraries guide

Trong nhà hàng: một người phục vụ đang cầm chìa khoá duy nhất của hầm rượu trong lúc chờ ở bếp thì không thể giao chìa khoá cho ai, nên phải đứng đó. Người phục vụ đó bị pin.

Bạn có thể nhìn thấy nó. "System property jdk.tracePinnedThreads in ra stack trace khi một thread bị block trong lúc đang bị pin."JEP 444 Mình đã chạy một virtual thread sleep bên trong synchronized (lock) trên JDK 21:

$ java -Djdk.tracePinnedThreads=short Pin.java
VirtualThread[#20]/runnable@ForkJoinPool-1-worker-1 reason:MONITOR
    Pin.lambda$main$0(Pin.java:6) <== monitors:1
virtual? true, daemon? true

Cách đọc: virtual thread #20, đang chạy trên carrier ForkJoinPool-1-worker-1, bị block trong lúc giữ một monitor (lock của synchronized) ở dòng 6. Dòng cuối xác nhận nó là virtual và là daemon.

Cách sửa trên JDK 21: với các block synchronized chạy thường xuyên và bao quanh I/O lâu, hãy dùng ReentrantLock (bài 0024).core libraries guide

// Before: pins the carrier thread during frequentIO()
synchronized(lockObj) {
    frequentIO();
}

// After
lock.lock();
try {
    frequentIO();
} finally {
    lock.unlock();
}

Sau 21: JEP 491, có trong JDK 24, cho phép virtual thread unmount bên trong synchronized, điều này "sẽ loại bỏ gần như mọi trường hợp virtual thread bị pin vào platform thread". Lời gọi native vẫn có thể pin.JEP 491 Khoá học này nhắm tới 21, nên lời khuyên dùng ReentrantLock vẫn áp dụng cho bạn.

JDK 8, 17 và 21

Virtual thread chính thức ở JDK 21 (JEP 444). JDK 8 và 17 chỉ có platform thread, nên bạn phải chọn kích thước pool (bài 0023) hoặc chuyển sang bất đồng bộ với CompletableFuture (bài 0010). Trên 21 bạn có thể viết lại code blocking bình thường mà vẫn mở rộng được.

Luyện tập

Trả lời theo trí nhớ, đừng cuộn lên. Thứ tự đáp án thay đổi mỗi lần bạn mở trang.

Lợi ích chính của virtual thread là gì?

Chúng mang lại khả năng mở rộng (throughput), không phải tốc độ. Một task vẫn mất thời gian như cũ; chỉ là chạy được nhiều task cùng lúc hơn.

Nên quản lý virtual thread thế nào?

Mỗi task là một virtual thread; đừng bao giờ pool chúng. Chúng rẻ, còn pool sinh ra để chia sẻ tài nguyên khan hiếm.

Service của bạn chỉ được gọi API đối tác tối đa 10 lời gọi cùng lúc. Với virtual thread, bạn đảm bảo điều đó thế nào?

Tài liệu khuyên dùng Semaphore để giới hạn mức đồng thời, không dùng pool.

Loại công việc nào được lợi ít nhất từ virtual thread?

Công việc nặng CPU không block, nên unmount chẳng mang lại gì; virtual thread không chạy code nhanh hơn.

Trên JDK 21, một virtual thread gọi HTTP API chậm bên trong block synchronized. Chuyện gì xảy ra?

Ở JDK 21, code bên trong synchronized pin virtual thread. Kết quả vẫn đúng, nhưng carrier không phục vụ được thread khác. Hãy dùng ReentrantLock cho I/O lâu ở chỗ đó.

Pool 200 platform thread chạy 10.000 task, mỗi task sleep 1 giây. Mất khoảng bao lâu?

200 task một lúc, mỗi task 1 giây: 10.000 / 200 × 1 s = 50 s. Với virtual thread thì mất khoảng 1 s.

Bài kiểm tra cuối: nói trong 60 giây

Người phỏng vấn hỏi: "Virtual thread là gì, và khi nào bạn dùng nó?" Bấm giờ. Trả lời thành tiếng, nói thành câu đầy đủ. Sau đó bấm nút.

Chỉ tick những ý bạn thật sự đã nói:

Câu trả lời mẫu

"Virtual thread là một java.lang.Thread bình thường, nhưng không bị gắn với một OS thread. JDK mount nó lên một carrier thread lấy từ một ForkJoinPool nhỏ, và khi nó block vì I/O, ví dụ gọi database, nó unmount để carrier chạy virtual thread khác. Nhờ vậy em có thể dùng mỗi request một thread, kể cả hàng chục nghìn, và viết code blocking đơn giản. Nó là về throughput chứ không phải tốc độ: một request không nhanh hơn, và việc nặng CPU không được lợi gì. Có hai quy tắc: em không bao giờ pool chúng, em dùng newVirtualThreadPerTaskExecutor, và nếu cần giới hạn số lời gọi tới một downstream service thì em dùng Semaphore chứ không dùng pool nhỏ. Cạm bẫy chính trên JDK 21 là pinning: trong synchronized hoặc code native thì virtual thread không unmount được, nên với I/O lâu và thường xuyên nằm dưới lock em chuyển sang ReentrantLock, và tìm những chỗ đó bằng -Djdk.tracePinnedThreads."

Tiếp theo là gì

Người phỏng vấn senior sẽ hỏi sâu hơn: "Bạn có chuyển một Spring service sang virtual thread không? Còn connection pool thì sao? Code dùng nhiều ThreadLocal sẽ ra sao?" Gợi ý: database pool vẫn chỉ có, chẳng hạn, 20 connection, nên 10.000 virtual thread sẽ xếp hàng chờ chúng; virtual thread dời điểm nghẽn đi chỗ khác chứ không xoá nó. Ôn lại cách chọn kích thước pool ở bài 0023 và lock ở bài 0024. Tiếp theo: JDK 21 thay đổi garbage collection thế nào với generational ZGC.
