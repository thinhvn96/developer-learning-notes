Chuyện gì xảy ra khi code Java gặp lỗi

Exception checked và unchecked, và cách try-with-resources tự đóng tài nguyên giúp bạn.

Java (JDK 8, 17, 21) · Bài 0019 · bước 2/46 · Foundation · ~20 phút · Trang chủ · Lộ trình Java (JDK 8, 17, 21) · Lộ trình tổng · English

Vì sao có bài này? Backend nào cũng đọc file, gọi database và nói chuyện với service khác, và tất cả đều có thể hỏng. Interviewer hỏi "Checked và unchecked exception khác nhau thế nào?" và "try-with-resources hoạt động ra sao?" để xem bạn có viết được code hỏng một cách gọn gàng và không bao giờ rò rỉ connection hay không.
Thành quả hôm nay: nói được exception nào phải catch hoặc khai báo, và dùng try-with-resources trong khi giải thích được thứ tự đóng và suppressed exception.
exception
Một object mô tả sự cố. Java "ném" (throw) nó để dừng luồng chạy bình thường của code.
throw / catch
throw khởi phát sự cố; khối catch là nơi xử lý nó.
call stack
Danh sách các method đang chạy lúc này: main gọi a, a gọi b, cứ thế.
checked
Exception mà compiler bắt buộc bạn xử lý: phải catch nó hoặc ghi throws trên method.
unchecked
Exception mà compiler không bắt bạn xử lý: RuntimeException, Error và các lớp con của chúng.
interface
Danh sách các method mà một class hứa sẽ có. Class "implement" interface bằng cách viết các method đó.
resource
Tài nguyên: thứ bạn phải đóng khi dùng xong, như file, socket hay connection tới database.

Trước khi bắt đầu

Nói thành tiếng: "Nếu code của mình mở hai file bằng try-with-resources, chúng được đóng theo thứ tự nào? Và nếu phần thân ném lỗi mà close() cũng ném lỗi, mình sẽ thấy exception nào?" Đoán ngay bây giờ. Phần 5 có output thật.

1. Hình dung: chuông báo cháy chạy lên từng tầng

Hãy tưởng tượng một tòa nhà. Tầng trệt là main. Nó nhờ tầng 1 làm việc, tầng 1 nhờ tầng 2, cứ thế. Bỗng tầng 3 bốc cháy. Chuông báo động truyền lên, từng tầng một, cho tới khi có người biết phải làm gì nhấc máy. Nếu không ai nhấc, cả tòa nhà phải sơ tán.

Đó chính là exception. Tutorial định nghĩa nó là "một sự kiện, xảy ra trong lúc chương trình chạy, làm gián đoạn luồng lệnh bình thường của chương trình." Runtime tìm dọc call stack một handler phù hợp; nếu không có, chương trình kết thúc.Tutorial: what is an exception

void main() {
    try { service(); } catch (IOException e) { log(e); }
}
void service() throws IOException { repository(); }
void repository() throws IOException {
    throw new IOException("disk");
}
Bước 1  repository() ném lỗi: code bình thường của nó dừng ngay
Bước 2  repository không có catch → exception đi lên service()
Bước 3  service không có catch → nó đi lên main()
Bước 4  main có catch phù hợp → log(e) chạy, chương trình chạy tiếp

2. Cây gia phả

Exception nào cũng là object, và tất cả đều đi ra từ một class. "Class Throwable là lớp cha của mọi error và exception trong ngôn ngữ Java."Throwable javadoc Bên dưới nó có hai nhánh, và một nhánh lại tách đôi:

Java Language Specification nêu quy tắc chính xác: "Các unchecked exception class là các run-time exception class và các error class." Mọi thứ khác là checked.JLS §11.1.1

  • Error: sự cố nghiêm trọng của chính JVM, như hết bộ nhớ. JLS gọi chúng là các exception "mà các chương trình thông thường không được kỳ vọng sẽ phục hồi."JLS §11.1.1 Bình thường bạn không catch chúng.
  • RuntimeException: thường là bug trong code, như dùng null hoặc ép kiểu sai.
  • Các Exception còn lại (checked): sự cố bên ngoài code của bạn mà bên gọi có thể xử lý, như thiếu file.

3. Checked exception: catch hoặc khai báo

Với exception checked, compiler đòi một trong hai: bạn catch nó, hoặc khai báo nó bằng throws để bên gọi phải lo. Tutorial gọi đây là "catch or specify". Runtime exception và error là unchecked: không cần catch hay khai báo.Tutorial: unchecked exceptions

static void mayFail() throws IOException {   // "I may throw this"
    throw new IOException("checked");
}

public static void main(String[] a) {
    mayFail();          // does not compile
}

javac của JDK 21 từ chối đoạn này với thông báo rất rõ:

A.java:4: error: unreported exception IOException; must be caught or declared to be thrown

Chương trình ví dụ cho thấy cả hai loại. Phép ép kiểu hỏng với ClassCastException unchecked, và không ai phải khai báo nó. Cái checked chỉ compile được vì nó được catch:

$ java java/examples/ExceptionsDemo.java
...
--- unchecked exceptions need no catch or declaration
ClassCastException
caught checked: checked

Exception của bạn nên là loại nào?

Hướng dẫn của tutorial: "Nếu có thể kỳ vọng hợp lý rằng client sẽ phục hồi được từ một exception, hãy làm nó checked. Nếu client không làm được gì để phục hồi, hãy làm nó unchecked."Tutorial: unchecked exceptions

Bẫy và cách sửa

  • Dùng RuntimeException chỉ để khỏi phải viết throws. Tutorial nói đừng làm vậy.Tutorial: unchecked exceptions
  • Làm mất lỗi gốc khi bọc lại. Nếu bạn đổi một checked exception thành exception của riêng mình, hãy truyền lỗi gốc làm cause: throw new OrderException("save failed", e);. Java giữ lại "chuỗi" các cause, nên stack trace vẫn chỉ ra sự cố thật.Throwable javadoc
  • Khối catch rỗng. Nó che giấu sự cố; chương trình chạy tiếp với dữ liệu sai. Ít nhất hãy log lại, hoặc để nó đi lên.

4. Đóng tài nguyên: finally, rồi đến try-with-resources

Hãy nghĩ tới một cuốn sách mượn thư viện. Dù chuyện gì xảy ra trong lúc đọc, bạn vẫn phải trả. Kể cả khi bạn ngủ quên, kể cả khi chuông báo cháy reo. File hay connection tới database cũng thế: bạn phải đóng nó, nếu không server sẽ dần dần cạn kiệt.

Công cụ cũ là finally: "Khối finally luôn luôn chạy khi khối try kết thúc."Tutorial: finally Nhưng cùng trang đó viết thêm: "Hãy dùng câu lệnh try-with-resources thay cho khối finally khi đóng file hoặc thu hồi tài nguyên."

Một resource là "một object phải được đóng sau khi chương trình dùng xong nó", và bất cứ thứ gì implement interface AutoCloseable đều được.Tutorial: try-with-resources Bạn khai báo nó trong ngoặc sau try, và Java gọi close() giúp bạn:

try (Res first = new Res("first", false);
     Res second = new Res("second", false)) {
    System.out.println("body");
}   // no finally needed: both are closed here

Các quy tắc trong tutorial:Tutorial: try-with-resources

  1. Thứ tự ngược. "các method close của resource được gọi theo thứ tự ngược với lúc chúng được tạo." Giống chồng đĩa: cái đặt lên sau cùng được lấy ra đầu tiên.
  2. Đóng trước đã. "mọi khối catch hoặc finally đều chạy sau khi các resource đã khai báo được đóng."
  3. Exception của phần thân thắng. Nếu phần thân ném lỗi và close() cũng ném, các exception từ close bị suppressed (nén lại), và bạn đọc được chúng bằng getSuppressed().

5. Chạy thử và đọc output

Ví dụ có một class resource nhỏ tên Res, in ra mỗi khi mở và đóng. Resource thứ hai được cố tình làm hỏng trong close().

$ java java/examples/ExceptionsDemo.java
--- close order is the reverse of opening
open  first
open  second
body
close second
close first
--- an exception from close() is suppressed when the body already threw
open  r
close r
caught: body failed
suppressed: close failed: r
...

Lần theo khối thứ hai:

try (Res r = new Res("r", true)) {
    throw new IllegalStateException("body failed");
} catch (Exception e) { ... }
Bước 1  mở r
Bước 2  phần thân ném "body failed"
Bước 3  Java vẫn gọi r.close(): in ra "close r",
        rồi close() ném "close failed: r"
Bước 4  "close failed" được gắn vào "body failed" dạng suppressed
Bước 5  giờ catch mới chạy, với e = "body failed"
Bước 6  e.getSuppressed() trả về exception của close

Vì sao thiết kế này tốt? Exception của phần thân thường là nguyên nhân thật. Với kiểu cũ finally { r.close(); }, một close() hỏng sẽ ném exception mới và exception gốc bị mất. Method getSuppressed() trả về các exception "đã bị nén lại, thường là bởi câu lệnh try-with-resources, để chuyển giao exception này".Throwable javadoc

JDK 8 so với 9+

Trên JDK 8, mọi resource phải được khai báo bên trong ngoặc (try (Res r = ...)).JLS 8 §14.20.3 Từ JDK 9 bạn còn có thể ghi tên một biến có sẵn, miễn nó là final hoặc "effectively final" (không bao giờ bị gán lại):JLS 21 §14.20.3

Res r = new Res("r", false);
try (r) {               // JDK 9+, r must be effectively final
    ...
}

Liên hệ với Spring: checked exception mặc định không rollback @Transactional, điều này làm nhiều người bất ngờ. Xem bài Spring về @Transactional.

Luyện tập

Trả lời theo trí nhớ, đừng cuộn lên. Thứ tự đáp án thay đổi mỗi lần bạn mở trang.

Những exception nào bạn bắt buộc phải catch hoặc khai báo bằng throws?

Catch-or-specify chỉ áp dụng cho checked exception. Runtime exception và error là unchecked.

Một method gọi mayFail(), vốn khai báo throws IOException, mà không có try và không có throws. Chuyện gì xảy ra?

IOException là checked, nên javac báo "must be caught or declared to be thrown".

try-with-resources mở first, rồi second. Chúng được đóng theo thứ tự nào?

Các method close chạy theo thứ tự ngược với lúc tạo; demo in close second trước close first.

Phần thân ném "body failed" và close() ném "close failed". catch nhận được gì?

Exception của phần thân được truyền đi; exception của close bị nén lại và lấy được qua getSuppressed().

Một class phải implement interface nào để dùng được trong try-with-resources?

Bất kỳ object nào implement AutoCloseable đều có thể làm resource.

Bug trong catch (SQLException e) { throw new RuntimeException("save failed"); } là gì?

Thiếu e làm cause, stack trace không còn chỉ ra lỗi SQL thật. Hãy viết new RuntimeException("save failed", e).

Bài kiểm tra cuối: nói trong 60 giây

Interviewer hỏi: "Checked và unchecked exception khác nhau thế nào, và try-with-resources hoạt động ra sao?" Bấm giờ. Trả lời thành tiếng, nói thành câu đầy đủ. Rồi bấm nút.

Chỉ tick những ý bạn thật sự đã nói:

Câu trả lời mẫu

"Trong Java mọi exception đều kế thừa Throwable. Bên dưới có Error, cho mấy sự cố nghiêm trọng của JVM như hết bộ nhớ, và Exception. RuntimeException và Error, cùng các lớp con, là unchecked; còn lại là checked. Với checked exception như IOException, compiler bắt em hoặc catch, hoặc khai báo bằng throws. Nguyên tắc thường dùng: nếu bên gọi có thể phục hồi hợp lý thì làm checked, còn nếu là bug lập trình thì unchecked. Khi bọc exception lại em luôn truyền lỗi gốc làm cause. Để đóng file hay connection thì em dùng try-with-resources: cái gì implement AutoCloseable đều được đóng tự động, theo thứ tự ngược với lúc mở, và trước khi khối catch chạy. Nếu phần thân ném lỗi mà close cũng ném, em nhận exception của phần thân, còn exception của close được gắn vào dạng suppressed, nên không mất gì cả."
