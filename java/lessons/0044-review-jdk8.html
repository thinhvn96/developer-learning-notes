1. How the six lessons connect

These lessons are not six separate tools. Lambdas are the glue: streams, collectors and CompletableFuture all take lambdas as their steps. Default methods are how the JDK could add stream() to existing collection interfaces. java.time stands a little apart: it is about picking the right value type, not about passing behaviour.

2. Mixed quiz

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

List.of(1, 2, 3).stream().peek(System.out::println).map(x -> x * 2); What is printed?

No terminal operation, so the lazy pipeline never runs. See lesson 0004.

Collectors.toMap(Emp::salary, Emp::name) meets two employees with salary 4800. What happens?

Duplicate keys throw unless you pass a merge function as the third argument. See lesson 0022.

Which threads run CompletableFuture.supplyAsync(task) when no executor is given?

Async methods without an Executor use the common pool (unless its parallelism is below two). See lesson 0010.

A lambda reads the local variable total; later in the same method total = 0; runs. Result?

Captured locals must be final or effectively final. See lesson 0008.

Which type should hold "when this payment was received", stored and sent between services?

An event timestamp is a point on the timeline: Instant, in UTC. LocalDateTime has no zone. See lesson 0011.

Robot extends Base implements Walker; Base.move() returns "base", Walker has a default move() returning "walk". Output?

Class wins: a method from the class or superclass beats an interface default. See lesson 0009.

The fallback for an empty Optional needs a slow remote call. Which line?

orElse evaluates its argument even when a value is present; orElseGet calls the supplier only when empty. See lesson 0004.

A future failed with IllegalStateException. What does get() throw?

get() throws the checked ExecutionException; join() the unchecked CompletionException. See lesson 0010.

You split users by u -> u.isActive() and must always get both a true and a false entry. Which collector?

partitioningBy's map always contains both false and true keys. See lesson 0022.

At 18:00 the evening before a one-hour DST gap, you add Period.ofDays(1) to a ZonedDateTime. Local time?

A Period adds a conceptual day and keeps the wall-clock time; a Duration of one day would give 19:00. See lesson 0011.

class Duck implements Walker, Swimmer {}, both with a default move(). What happens?

Two inherited defaults with the same signature must be resolved by overriding, e.g. with Walker.super.move(). See lesson 0009.

Which method turns a failed CompletableFuture into a fallback value?

exceptionally(fn) runs only on exceptional completion and its result replaces the error; thenApply is skipped. See lesson 0010.

3. Mixed task: find three bugs

This method builds a daily report. It compiles in the author's head, but not in reality, and it has two more problems. Find three bugs, each from a different lesson. Write your answer to the teacher before you open the solution.

Report buildReport(List<Order> orders) {
  int paid = 0;
  orders.stream().filter(Order::isPaid).forEach(o -> paid++);           // (A)

  Map<String, Order> lastByCustomer = orders.stream()
      .collect(Collectors.toMap(Order::customerId, o -> o));              // (B)

  LocalDateTime generatedAt = LocalDateTime.now();                       // (C)
  return new Report(paid, lastByCustomer, generatedAt);
}
Show the solution
  1. (A) Lesson 0008. paid++ inside a lambda changes a captured local, so paid is not effectively final: compile error. Also a side effect (lesson 0004). Fix: long paid = orders.stream().filter(Order::isPaid).count();
  2. (B) Lesson 0022. A customer usually has several orders, so toMap sees duplicate keys and throws IllegalStateException. Fix: add a merge function, e.g. (a, b) -> b to keep the later one (or groupingBy to keep all).
  3. (C) Lesson 0011. A report timestamp is a moment, but LocalDateTime has no zone, so it cannot represent an instant. Fix: Instant generatedAt = Instant.now(); and convert to a zone only for display.

4. The final test: say it in 60 seconds (three times)

Recall 1. An interviewer shows orders.stream().filter(o -> o.total() > 100).collect(groupingBy(Order::customerId, counting())) and asks: "Walk me through what happens when this runs." Start a timer, answer out loud, then click.

Tick only the points you really said:

Example answer

"The lambda in filter becomes a Predicate<Order>, because filter expects that functional interface, and Order::customerId is a method reference used as a Function. Building the pipeline does nothing yet: filter is a lazy intermediate operation. When collect, the terminal operation, runs, it pulls orders through one at a time. Orders over 100 reach the collector. groupingBy puts each one into a bin by customer ID, and the downstream counting() turns each bin into a count, so I get a map from customer to number of big orders. The docs don't promise which map type I get, so if I need ordering I'd pass a map factory. And after collect the stream is consumed; I can't reuse it."

Recall 2. "How do you store and compute dates and times in a backend?" Start a timer, answer out loud, then click.

Tick only the points you really said:

Example answer

"I use java.time. Every type is immutable, so plusDays gives me a new object and I must keep the result. For things that happened at a moment, like a payment, I use Instant, which is a point on the UTC timeline, and that is what I store and send. For a date with no zone, like a birthday, I use LocalDate. If the time belongs to a place, like a meeting at 9 in Tokyo, I keep a ZonedDateTime with the zone ID, and I convert instants to the user's zone only for display. For amounts of time I keep Duration and Period apart: a Duration of one day is always 24 hours, while a Period of one day keeps the wall-clock time, which matters on DST days."

Recall 3. "You must call a user service and an order service and combine the results. How, and what can go wrong?" Start a timer, answer out loud, then click.

Tick only the points you really said:

Example answer

"I'd start both calls with supplyAsync first, so they run at the same time; if I called join after each one, they would run one after the other. Then I combine them with thenCombine, which runs my lambda when both are done. These are blocking HTTP calls, so I pass my own executor instead of using the shared common pool, or on Java 21 virtual threads. Things that can go wrong: a call fails, so I add exceptionally or handle for a fallback; a call hangs, so I add orTimeout. When I finally wait, join wraps errors in an unchecked CompletionException and get in a checked ExecutionException. And cancelling the future doesn't stop the running call, so the timeout on the HTTP client itself still matters."
