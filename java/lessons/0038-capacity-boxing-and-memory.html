Capacity, boxing and the memory cost of collections

Why a list of a million numbers can weigh 19 MB instead of 4, and two boxing bugs that compile without a warning.

Java (JDK 8, 17, 21) · Lesson 0038 · step 20 of 46 · Senior · ~22 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? A service that caches ten million IDs, a batch job that runs out of heap, a test that passes with 100 but fails with 1000: these are capacity and boxing problems. Senior interviews ask "How does ArrayList grow?" and "Why is Integer == Integer dangerous?" to see whether you think about what your code costs.
Today's win: estimate the memory and resize cost of common collections, explain ArrayList growth, and avoid the Integer == and remove(int) traps.
capacity
How many slots the array inside a collection has. The size is how many slots are actually used.
amortized O(1)
Most operations are cheap, a rare one is expensive, and on average each costs a constant amount.
primitive
A plain value like int or long: just the number, no object around it.
boxing
Wrapping a primitive in an object, int → Integer, because collections can only hold objects. Unboxing is the reverse.
reference
The address of an object. A List<Integer> stores references, and each one points to a separate Integer object.
overload
Two methods with the same name but different parameter types, like remove(int) and remove(Object). The compiler chooses one.

Before you start

Guess: how many megabytes does an ArrayList<Integer> with one million numbers need, compared with an int[] of one million? Write down both numbers. Section 3 has a real (rough) measurement.

1. How ArrayList grows

Picture a family buying a dining table. When a fifth guest comes, they cannot "extend" the table; they buy a bigger one and move every plate across. Buying a table only one seat larger each time would mean moving plates at every visit, so they buy one about half again as big.

An ArrayList works the same way: inside it is a plain array that cannot grow. When it is full, Java creates a bigger array and copies everything. The Javadoc deliberately says little: "The details of the growth policy are not specified beyond the fact that adding an element has constant amortized time cost."ArrayList javadoc The OpenJDK 21 source is concrete: an empty new ArrayList<>() shares an empty array and allocates DEFAULT_CAPACITY = 10 on the first add; after that the preferred growth is oldCapacity >> 1, i.e. about 1.5×.OpenJDK source

The example prints the capacities that this source rule produces (it computes them with the same formula, starting at 10):

$ java -Xmx1g java/examples/collections/CapacityAndBoxing.java
ArrayList capacities: [10, 15, 22, 33, 49, 73, 109, 163, 244, 366, 549, 823] ...

Each step copies the array, which is why it is "amortized" O(1): growing by a factor means the total copying stays proportional to the number of elements. If you know the size: new ArrayList<>(n) or ensureCapacity, which "may reduce the amount of incremental reallocation"; trimToSize releases the slack.ArrayList javadoc

2. Presizing a HashMap

A HashMap doubles its bucket array when it passes 75% full and moves every entry (lesson 0030). Putting 2,000,000 entries into a default map triggers many of those resizes. HashMap.newHashMap(n) (JDK 19+, so on 21) sizes it once for n entries:HashMap javadoc

HashMap default      : 172 ms     (2,000,000 puts, one rough run)
HashMap.newHashMap(n):  94 ms

Treat these as a single rough run on one laptop, not a benchmark: your numbers will differ, and a proper measurement needs a tool like JMH. The direction is the lesson: no resizes, less work. On JDK 8 and 17 write new HashMap<>((int) (n / 0.75f) + 1).

3. Boxing: the hidden cost

Think of eggs. An int[] is an egg carton: the eggs sit right in the slots. A List<Integer> is a carton of addresses, and each egg is in its own little box somewhere else in the warehouse. You pay for the carton, the boxes, and the walk.

Rough heap growth for 1,000,000 ints, one run on JDK 21 (measured with Runtime, so treat it as an order of magnitude; your numbers will vary):

int[]               ~  4 MB
ArrayList<Integer>  ~ 19 MB
LinkedList<Integer> ~ 38 MB
HashSet<Integer>    ~ 54 MB

That 4× to 13× is why hot paths and big in-memory datasets use primitive arrays, IntStream, or primitive-collection libraries, and why LinkedList's node per element hurts (lesson 0002). A HashSet is the heaviest: each element is a HashMap entry node plus the boxed key, plus the bucket array.

4. Two boxing bugs interviewers love

Integer a = 127, b = 127, c = 128, d = 128;
System.out.println(a == b);       // compares references!
System.out.println(c == d);
System.out.println(c.equals(d));

List<Integer> nums = new ArrayList<>(List.of(10, 20, 30));
nums.remove(1);                   // which remove?
nums.remove(Integer.valueOf(10));
Integer 127 == 127: true   128 == 128: false   128 equals: true
remove(1) then remove(Integer.valueOf(10)): [30]

Bug 1: == on boxed numbers

== on two objects asks "same object?", not "same number?". Small values happen to be shared: the JLS only guarantees identical boxes for constant values in -128..127; "For other values, the rule disallows any assumptions about the identity of the boxed values".JLS 5.1.7 Integer.valueOf says the same from the library side: it "will always cache values in the range -128 to 127, inclusive, and may cache other values outside of this range".Integer javadoc

This is why the bug hides in tests: IDs 1 to 100 compare fine, then production reaches 128. The fix: compare boxed values with equals (or Objects.equals when either may be null), never ==.

Bug 2: remove(1) on a List<Integer>

List has two remove methods: remove(int index) and remove(Object o). For remove(1) the compiler picks the one that needs no boxing, so it removes index 1 (the value 20), not the value 1.

Step 1  [10, 20, 30].remove(1)                 → removes index 1 → [10, 30]
Step 2  [10, 30].remove(Integer.valueOf(10))   → removes value 10 → [30]

The fix: to remove a value, write remove(Integer.valueOf(x)).

JDK 8 vs 17 vs 21: the boxing rules are the same in all three. HashMap.newHashMap needs JDK 19+. Since JDK 9 the new Integer(int) constructor is deprecated, and it is marked for removal; use Integer.valueOf.Integer javadoc

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

In OpenJDK, what capacity does new ArrayList<>() get on the first add?

DEFAULT_CAPACITY = 10, allocated on the first add; before that the list shares an empty array.

An OpenJDK ArrayList is full. By how much does it prefer to grow?

grow() uses oldCapacity >> 1 as the preferred growth: 10 → 15 → 22. The Javadoc itself only promises amortized constant time.

Integer a = 128, b = 128; What can you say about a == b?

Identity is guaranteed only for -128..127. Above that, == compares two references that may or may not be the same; use equals.

List<Integer> nums = [10, 20, 30]. After nums.remove(1), what is the list?

Overload resolution picks remove(int index), so index 1 (the value 20) is removed. Use remove(Integer.valueOf(x)) for a value.

Why does an ArrayList<Integer> use several times more memory than an int[]?

Collections hold objects, so every int is boxed into its own Integer, plus the reference to it. The run showed about 4 MB vs 19 MB.

You will put 2,000,000 entries into a HashMap on JDK 21. What is the simplest way to avoid resizes?

newHashMap(n) sizes the table for n mappings, accounting for the 0.75 load factor. The constructor argument is a capacity, so 2,000,000 would still resize past 75%.

Example answer

"The first suspect is boxing. Collections can only hold objects, so a List of Integer stores a reference per element plus a separate Integer object. In a rough measurement, a million ints are about 4 MB in an int array, about 19 in an ArrayList, 38 in a LinkedList and over 50 in a HashSet. So on hot paths I'd switch to primitive arrays, IntStream, or a primitive-collection library. Second, growth: ArrayList copies its array when full, in OpenJDK by about one and a half times, and HashMap doubles at 75% load, so I presize: new ArrayList with n, or HashMap.newHashMap on Java 19 and later. Boxing also brings bugs: double equals on Integers is only reliable between minus 128 and 127, so I use equals, and on a List of Integer, remove(1) removes index 1, not the value 1."
