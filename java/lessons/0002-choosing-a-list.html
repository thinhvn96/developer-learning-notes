ArrayList, LinkedList or ArrayDeque?

Three ways to keep things in a row, and why one of them is almost always the answer.

Java (JDK 8, 17, 21) · Lesson 0002 · step 7 of 46 · Foundation · ~20 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? "ArrayList or LinkedList?" is one of the most common Java interview questions, and many people answer with folklore ("LinkedList is faster for inserts"). This lesson gives you the answer the documentation actually supports, and a picture to explain it.
Today's win: explain how ArrayList and LinkedList store elements, pick the right one (and ArrayDeque for queues and stacks) using the documented costs, and avoid three common bugs.
list
An ordered sequence of elements. Each element has a position called an index, starting at 0.
array
A fixed-size block of slots side by side in memory. Java can jump straight to slot i.
node
A small object that holds one element plus links (references) to the previous and next node.
capacity
How many slots the hidden array of an ArrayList has. It is always at least the list's size.
queue / stack
A queue is first in, first out (like a line at the bank). A stack is last in, first out (like a pile of plates).
deque
"Double-ended queue", pronounced "deck": you can add and remove at both ends.
amortized O(1)
Usually constant time; once in a while slower, but on average still constant per operation.

Before you start

Say out loud: "Why would list.get(500_000) be slow on one kind of list and fast on another?" Guess, even if you are unsure. You will check your guess in section 1.

1. The picture: a row of lockers vs a treasure hunt

ArrayList is a row of numbered lockers. To open locker 3 you walk straight to it; you don't open lockers 0, 1 and 2 first. Inside, ArrayList is "backed by an array" whose capacity "grows automatically".ArrayList javadoc

LinkedList is a treasure hunt. Each clue (a node) tells you where the next clue is. To reach clue 3 you must follow clues 0, 1 and 2. The Javadoc says it plainly: "Operations that index into the list will traverse the list from the beginning or the end, whichever is closer to the specified index."LinkedList javadoc

So for get(i): ArrayList is constant time, LinkedList is a walk that grows with the list. That answers the "Before you start" question.

2. What each operation costs (the documented facts)

The ArrayList Javadoc lists the costs directly: "The size, isEmpty, get, set, iterator, and listIterator operations run in constant time. The add operation runs in amortized constant time ... All of the other operations run in linear time (roughly speaking). The constant factor is low compared to that for the LinkedList implementation."ArrayList javadoc

Look at the middle row. LinkedList's "fast insert" only happens once you are already standing on the node. To insert at index 500,000 it must first walk there. That is why "LinkedList is faster for inserts" is folklore, not a rule.

Why "amortized" for add?

The hidden array has spare slots. Most add calls just fill the next empty slot. When the array is full, ArrayList creates a bigger array and copies everything over, which is one slow call. The documentation only promises that "adding an element has constant amortized time cost".ArrayList javadoc In the OpenJDK source the array grows by about 1.5× each time, so copies get rarer as the list grows (details in lesson 0038).

List<String> names = new ArrayList<>();
names.add("a");   // fills slot 0 (first add creates the array)
names.add("b");   // fills slot 1, cheap
...               // full? bigger array + copy: one slow call
names.add("z");   // cheap again

3. Queues and stacks: use ArrayDeque

For "take from one end, add at the other" you don't need indexes at all. ArrayDeque is an array used as a ring: a head and a tail position move around it, so adding or removing at either end never shifts other elements. The Javadoc: it is "likely to be faster than Stack when used as a stack, and faster than LinkedList when used as a queue."ArrayDeque javadoc

Deque<String> queue = new ArrayDeque<>();     // FIFO: line at the bank
queue.offer("job1"); queue.offer("job2");
queue.poll();                                  // "job1"

Deque<String> stack = new ArrayDeque<>();     // LIFO: pile of plates
stack.push("a"); stack.push("b");
stack.pop();                                   // "b"

The old Stack class (from JDK 1.0) still exists, but the Javadoc points you to Deque instead. Prefer ArrayDeque on JDK 8, 17 and 21 alike.

4. Three bugs, one run

$ java java/examples/ListPitfalls.java
ArrayDeque rejects null: NullPointerException
for-each + list.remove: ConcurrentModificationException
removeIf result: [1, 3]
  1. ArrayDeque refuses null. "Null elements are prohibited."ArrayDeque javadoc poll() returns null to mean "empty", so a stored null would be ambiguous.
  2. Removing inside a for-each loop throws ConcurrentModificationException, even with one thread. The iterator notices the list changed behind its back (ArrayList's iterators are "fail-fast").ArrayList javadoc Lesson 0029 explains how.
  3. The fix: list.removeIf(x -> x % 2 == 0) (JDK 8+) or the iterator's own remove().

And one more fact for interviews: none of the three classes is synchronized. If several threads change the same list, you must protect it yourself (for example Collections.synchronizedList), or use a concurrent collection (lesson 0039).ArrayList javadoc

5. The decision in one line

Need a list? ArrayList. Need a queue or a stack? ArrayDeque. LinkedList only with a specific, measured reason.

A specific reason could be: you already hold a ListIterator in the middle of a long list and insert or remove many elements right there. Even then, measure first.

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

Why is get(i) fast on an ArrayList but slow on a LinkedList?

An array slot's position can be computed directly. LinkedList "will traverse the list from the beginning or the end".

You insert one element at index 500,000 of a LinkedList with 1,000,000 elements. What is slow?

Linking is cheap, but LinkedList must first walk to the position. ArrayList would shift elements instead; both are linear.

Which class should you use for a FIFO queue of jobs?

ArrayDeque is documented as likely faster than LinkedList as a queue and than Stack as a stack. Removing index 0 of an ArrayList shifts every element.

What does new ArrayDeque<String>().offer(null) do?

"Null elements are prohibited" in ArrayDeque, because null is what poll() returns for "empty".

Why is ArrayList's add called "amortized" constant time?

When the hidden array is full, one add creates a bigger array and copies. On average each add is still constant.

Two threads add to the same plain ArrayList. What do the docs say?

None of ArrayList, LinkedList or ArrayDeque is synchronized. Lesson 0039 shows updates silently lost.

The final test: say it in 60 seconds

An interviewer asks: "ArrayList or LinkedList? When would you use each?" Start a timer, answer out loud, then click.

Tick only the points you really said:

Example answer

"By default I use ArrayList. It's backed by an array, so get and set by index are constant time, and adding at the end is amortized constant: it occasionally copies into a bigger array. LinkedList is a chain of nodes, so getting by index means walking the list. People say LinkedList is better for inserts, but inserting in the middle still means walking to that position, so both are linear, and ArrayList's constant factor is lower. If I need a queue or a stack I use ArrayDeque, which the docs say is faster than LinkedList as a queue and faster than Stack. And none of these is thread-safe, so for shared access I'd synchronize or use a concurrent collection."
