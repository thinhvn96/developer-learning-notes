Which part was null? Helpful NullPointerExceptions

Since JDK 14 the error message points at the exact link of the chain that was missing.

Java (JDK 8, 17, 21) · Lesson 0027 · step 41 of 46 · Core · ~15 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? NullPointerException (NPE) is the most common Java error in production logs. On JDK 8 the log tells you only the line. On JDK 17 and 21 it tells you which expression was null, if you know how to read it. Interviewers like asking "How do you debug an NPE?"; this is the modern first step.
Today's win: read a helpful NPE message and name the null part, explain why it sometimes says <local1>, and say in which JDK it appeared and became the default.
null
A special value meaning "this variable points to no object".
NullPointerException (NPE)
The error Java throws when you use a null as if it were an object, for example call a method on it.
exception message
The text inside an exception. You read it with e.getMessage(); it is printed after the exception name in a log.
stack trace
The list of method calls that led to the error, with file names and line numbers.
JVM
The Java Virtual Machine: the program that runs your compiled bytecode. It detects the null and throws the NPE.
debug information
Extra data that javac can store in the .class file, such as line numbers and local variable names.
JVM flag
An option you give to java on the command line, like -XX:+SomeOption.

Before you start

Look at this line and say out loud: "If it throws an NPE, which variables could be null?" Count them.

System.out.println(order.customer.address.city.toUpperCase());

1. The JDK 8 message: "something on line 7"

Imagine directions to a friend's flat: "go to the building, then the 3rd floor, then flat B, then knock". You arrive and cannot continue. A bad helper says: "Your directions failed somewhere." A good helper says: "You could not find flat B, because the 3rd floor does not exist."

A JDK 8 NPE is the bad helper. Here is the code above, run with the detail messages switched off, which gives the same output as an old JDK:

$ java -XX:-ShowCodeDetailsInExceptionMessages -cp g Order
Exception in thread "main" java.lang.NullPointerException
	at Order.main(Order.java:7)

Line 7 has four possible nulls: order, customer, address and city. JEP 358 says it directly: "The filename and line number do not pinpoint exactly which variable was null."JEP 358 On JDK 8 you add log lines or open a debugger to find out.

2. The JDK 14+ message: the exact link

JEP 358 (Java 14) aims to "improve the usability of NullPointerExceptions generated by the JVM by describing precisely which variable was null."JEP 358 Same program on JDK 21, no flags:

$ java -cp g Order
Exception in thread "main" java.lang.NullPointerException: Cannot read field "city" because "order.customer.address" is null
	at Order.main(Order.java:7)

Read it step by step

Step 1  "order" was evaluated: not null
Step 2  ".customer" was read: not null
Step 3  ".address" was read: it is null
Step 4  the JVM tries to read ".city" from null → NPE
Message = "Cannot read field "city"" (step 4) + "because "order.customer.address" is null" (step 3)

The JEP gives the same shape of example: Cannot read field "c" because "a.b" is null.JEP 358 So the answer to "Before you start" is: four things could be null, and the message tells you which one was.

The first half changes with the operation. A few real messages from JDK 21:

// calling a method on a null that a method returned
Cannot invoke "Npe2$User.getName()" because the return value of "Npe2.find(int)" is null
// a chain of method calls
Cannot invoke "String.toUpperCase()" because the return value of "Npe2$User.getName()" is null
// unboxing a null Integer into an int
Cannot invoke "java.lang.Integer.intValue()" because "<local1>" is null

The last one is a classic trap: int x = map.get(key); throws an NPE when the key is missing, because Java calls intValue() on the null for you.

3. Why does it say <local1>?

Run the course example:

$ java java/examples/NpeDemo.java
Cannot read field "city" because "<local1>.address" is null
Cannot invoke "String.trim()" because "<local2>[0]" is null

The messages appear without any flag on JDK 21. But the local variable names show as <local1> and <local2>. Why? The names of local variables are only in the .class file if javac stored them as debug information. Without them, JEP 358 says the message uses <locali> (a slot number) instead; names appear when "debug information is included in the class file (via javac -g)".JEP 358 The source launcher compiles without that debug info. With javac -g the same messages read:

$ javac -g -d out java/examples/NpeDemo.java && java -cp out NpeDemo
Cannot read field "city" because "u.address" is null
Cannot invoke "String.trim()" because "names[0]" is null

I ran both. Field names and method names are always available; only local variable names need -g. Plain javac is not enough: "By default, only line number and source file information is generated", and -g "Generates all debugging information, including local variables."javac docs

4. Which JDK, which flag, which NPEs

  1. JDK 8 to 13: no detail message. You get the exception name and the stack trace only.
  2. JDK 14: the feature exists but is off by default. You turn it on with -XX:+ShowCodeDetailsInExceptionMessages; the JEP states the intent to enable it by default later.JEP 358
  3. JDK 15 and later (so 17 and 21): on by default. The JDK 15 change says "the Helpful NullPointerExceptions of JEP 358 are printed per default."JDK-8233014 You can turn it off with -XX:-ShowCodeDetailsInExceptionMessages, which is how I produced the "old" output in section 1.

Two details that interviewers like:

  • "Only NPEs that are created and thrown directly by the JVM will include the null-detail message."JEP 358 If your code does throw new NullPointerException(), getMessage() returns null. I ran it: it printed null.
  • The message is "computed on demand", only when getMessage() is called, because many NPEs are caught and thrown away.JEP 358

Trap: logging only half the exception

Some code logs "error: " + e.getMessage(). On JDK 8 that printed error: null for an NPE, so teams learned to ignore it. On JDK 17 and 21 the message is the most useful part. The fix: log the exception object itself (for example log.error("failed", e)), so you keep both the message and the stack trace.

What does a helpful NullPointerException message add?

JEP 358 describes "precisely which variable was null", plus what the JVM was trying to do.

The message is Cannot read field "city" because "order.customer.address" is null. What was null?

The "because" part names the null expression. order and customer were fine; reading city from the null address failed.

Why does a message say "<local1>.address" instead of "u.address"?

Local names are only in the class file when compiled with javac -g. Without them the JVM shows the slot number.

Which statement about JDK versions is correct?

JEP 358 delivered it in JDK 14 behind -XX:+ShowCodeDetailsInExceptionMessages; JDK 15 turned it on by default.

Your code runs throw new NullPointerException();. What does getMessage() return on JDK 21?

Only NPEs created and thrown directly by the JVM get the helpful message.

int count = map.get("x"); throws an NPE. Why?

The missing key gives null; turning a null Integer into an int calls intValue() on null. The message says so.

Tick only the points you really said:

Example answer

"First I read the exception message, not just the stack trace. Since JDK 14, and on by default since JDK 15, the JVM writes helpful NPE messages, like Cannot read field "city" because "order.customer.address" is null. The first part is what it tried to do, the 'because' part is the expression that was null, so I know it's the address and not the order or the customer. On JDK 8 I only had the line number, which is ambiguous for a chain. If the message shows <local1> instead of a name, the class was compiled without local variable debug info; javac -g fixes that. Note that only NPEs thrown by the JVM get this message, not ones the code creates itself. Then I look at why it was null: missing data, a method that returns null, or unboxing a null Integer, and fix it at the source."
