java.time: which clock do you need?

A birthday, a meeting in Tokyo and a log timestamp need three different classes. Here is how to pick.

Java (JDK 8, 17, 21) · Lesson 0011 · step 27 of 46 · Core · ~25 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? Time bugs are some of the most expensive bugs in backend work: a job that runs twice on the day clocks change, an order stamped with the server's zone instead of UTC. Interviewers ask "How do you store a timestamp?" and "What is the difference between Duration and Period?"
Today's win: pick the right java.time class for four needs (birth date, meeting time, event timestamp, elapsed time), and explain why a "day" is not always 24 hours.
time zone
A region's rules for its clocks, with an ID like Asia/Tokyo. The rules include summer time changes.
offset
How far a clock is from UTC at a given moment, like +09:00. A zone's offset can change during the year.
UTC
The world's reference clock. Timestamps written with a Z at the end are in UTC.
epoch
The starting point Java counts machine time from: 1970-01-01T00:00:00Z.
DST
Daylight saving time: some zones move clocks forward one hour in spring and back in autumn.
immutable
Cannot be changed after it is created. "Changing" methods return a new object instead.
ISO-8601
The standard text format for dates and times, like 2026-01-01T09:00 or PT3H30M.

Before you start

Say out loud: "A user in Tokyo books a call for 9 am on 1 January. Which Java type would you store, and why?" Then read on.

1. The picture: one world clock, many wall clocks

Imagine a single clock in space that every computer on Earth can see. It just counts seconds. That is machine time: one point on one global line. In Java it is Instant.

Now imagine the clocks on the walls of offices in London and Tokyo. At the same moment they show different numbers. That is human time: year, month, day, hour as people read them. The tutorial describes the two ways: human time "such as year, month, day, hour, minute and second", and machine time, which "measures time continuously along a timeline from an origin, called the epoch, in nanosecond resolution".Date-Time tutorial

This is the key idea of the whole lesson. LocalDateTime "cannot represent an instant on the time-line without additional information such as an offset or time-zone".LocalDateTime javadoc Instant is "An instantaneous point on the time-line", counted from the epoch 1970-01-01T00:00:00Z.Instant javadoc

The tutorial's guidance: human time uses the Local classes, machine time uses Instant, and zone-aware needs use ZonedDateTime or OffsetDateTime.Date-Time tutorial Its example for LocalDate is a birth date, "because most people observe their birthday on the same day" wherever they are. For a time-stamp, "you will most likely want to use an Instant".Date-Time tutorial The Instant Javadoc agrees: it "might be used to record event time-stamps in the application".Instant javadoc

Back to the pre-test: a call booked "9 am in Tokyo" is a ZonedDateTime with zone Asia/Tokyo. A plain LocalDateTime would lose the city.

3. Follow the example step by step

LocalDate birthday = LocalDate.of(1990, 5, 17);
LocalDate next = birthday.plusDays(30);
Step 1  plusDays builds a NEW LocalDate 1990-06-16
Step 2  birthday is untouched: still 1990-05-17

Instant start = Instant.parse("2026-01-01T00:00:00Z");
Instant end   = start.plusSeconds(3 * 3600 + 30 * 60);
Duration.between(start, end);                 // counts seconds → PT3H30M
Period.between(birthday, LocalDate.of(2026, 5, 20));  // counts calendar fields → P36Y3D

start.atZone(ZoneId.of("Asia/Tokyo"));
Step 3  same instant, shown on Tokyo's wall clock → 09:00+09:00
$ java java/examples/jdk8/JavaTime.java
1990-05-17 -> 1990-06-16 (original unchanged)
Duration: PT3H30M
Period:   P36Y3D
Same instant in Tokyo: 2026-01-01T09:00+09:00[Asia/Tokyo]

Read the output in ISO-8601: PT3H30M is "a period of time, 3 hours 30 minutes"; P36Y3D is "36 years and 3 days". The first line shows that plusDays returns a new object. The class docs confirm it: LocalDateTime, ZonedDateTime and Instant each say "This class is immutable and thread-safe".LocalDateTime javadocZonedDateTime javadocInstant javadoc Source: JavaTime.java.

Common mistake: ignoring the return value

LocalDate d = LocalDate.of(2026, 1, 1);
d.plusDays(1);                 // result thrown away; d is still 2026-01-01
d = d.plusDays(1);             // fix: keep the new object

4. Duration vs Period: is a day 24 hours?

Think of two ways to say "see you in one day". A stopwatch person means "in exactly 24 hours". A calendar person means "same time tomorrow". Usually that is the same thing. On the night clocks jump forward, it is not.

The Period Javadoc: "A Duration will add an exact number of seconds, thus a duration of one day is always exactly 24 hours. By contrast, a Period will add a conceptual day, trying to maintain the local time."Period javadoc In the same way, ZonedDateTime.plusDays "operates on the local time-line", while plusHours "operates on the instant time-line, such that adding one hour will always be a duration of one hour later".ZonedDateTime javadoc

You can check this with a few lines (2026-03-29 is the spring change in Europe/Paris):

ZonedDateTime evening = ZonedDateTime.of(2026, 3, 28, 18, 0, 0, 0, ZoneId.of("Europe/Paris"));
System.out.println("start          : " + evening);
System.out.println("plus Period 1d : " + evening.plus(Period.ofDays(1)));
System.out.println("plus Duration 1d: " + evening.plus(Duration.ofDays(1)));
start          : 2026-03-28T18:00+01:00[Europe/Paris]
plus Period 1d : 2026-03-29T18:00+02:00[Europe/Paris]
plus Duration 1d: 2026-03-29T19:00+02:00[Europe/Paris]

Which one is right? It depends on the business rule. "Remind me at 18:00 every day" wants Period (or plusDays). "Expire the session after 24 hours" wants Duration.

Senior rule: store and transmit timestamps as Instant (UTC), convert to a zone only for display, and keep Duration and Period distinct: a "month" is not a fixed number of seconds.

JDK 8 vs 17 vs 21

The java.time package arrived in JDK 8 and is the same API on 17 and 21. The example compiles with javac --release 8, so everything in this lesson works on all three versions.

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

What is the best type for the time an order was created, stored in the database?

Instant is a point on the global timeline; the Javadoc says it "might be used to record event time-stamps". LocalDateTime has no zone, so it is not a moment.

What is the best type for a user's birthday?

The tutorial's example for a birth date is LocalDate: people celebrate on the same date wherever they are.

Why can't a LocalDateTime alone tell you the exact moment something happened?

It "cannot represent an instant on the time-line without additional information such as an offset or time-zone".

Which type measures an amount of time in years, months and days?

Period is date-based (P36Y3D); Duration is seconds and nanoseconds (PT3H30M).

At 18:00 the evening before a one-hour DST gap, you add Duration.ofDays(1) to a ZonedDateTime. What local time do you get?

A Duration adds exactly 24 hours. One wall-clock hour was skipped, so the clock shows 19:00. A Period of one day would give 18:00.

What is the bug? LocalDate due = start; due.plusDays(7); return due;

java.time types are immutable. Write due = due.plusDays(7).

Example answer

"I use the java.time API from JDK 8. Its types are immutable and thread-safe, so methods like plusDays return a new object. For anything that happened at a moment, like an order being created, I use Instant, which is a point on the UTC timeline, and I store and send that. I convert it to a ZonedDateTime in the user's zone only for display. For human dates with no zone, like a birthday, I use LocalDate. If a time only makes sense in a city, like a meeting at 9 in Tokyo, I keep a ZonedDateTime with the zone ID. For amounts of time I separate Duration, which is exact seconds, from Period, which is calendar days and months. They differ across daylight saving changes: one day as a Duration is always 24 hours, but a Period keeps the same wall-clock time."
