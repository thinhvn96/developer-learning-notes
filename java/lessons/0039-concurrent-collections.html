Concurrent collections: synchronized, copy-on-write, blocking queues

Four threads, one ArrayList, 40,000 adds, and about 27,000 of them vanish without a single error. Here is what to use instead.

Java (JDK 8, 17, 21) · Lesson 0039 · step 21 of 46 · Senior · ~25 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? Every backend service shares data between threads: request handlers, listeners, worker pools. Picking the wrong collection gives bugs that only appear under load. "Which thread-safe collection would you use here, and why?" is a standard senior question, and the answer is never "just synchronize everything".
Today's win: choose between a synchronized wrapper, CopyOnWriteArrayList, ConcurrentHashMap, ConcurrentSkipListMap and a BlockingQueue, and use each safely.
thread
One path of execution inside your program. Several threads run at the same time and can touch the same objects.
thread-safe
Still correct when many threads use it at once, without extra locking by the caller.
lock
A "one at a time" rule: while one thread holds it, other threads that want it must wait. synchronized is Java's built-in lock.
contention
Many threads wanting the same lock at the same time, so they spend time waiting.
snapshot
A frozen copy of the data at one moment; later changes do not appear in it.
producer / consumer
One side creates work items, the other side processes them. A queue between them is the hand-off point.
backpressure
Slowing down the producer when the consumer cannot keep up, instead of letting work pile up until memory runs out.

Before you start

Predict: four threads each call list.add(i) 10,000 times on one shared ArrayList. What is list.size() at the end? Pick one: exactly 40,000; less than 40,000; more than 40,000; it always throws. Say why.

1. Why plain collections break

Imagine two cashiers sharing one paper notebook of sales. Both look at the notebook: "the next empty line is 5". Both write on line 5. One sale overwrites the other, and nobody notices.

That is what happens inside ArrayList.add. Simplified, it reads the current size, writes the element at that index, then stores size + 1. Two threads can read the same size at the same moment:

$ java java/examples/collections/ConcurrentCollections.java
ArrayList, 4 threads x 10,000 adds   : size=12481
synchronizedList, same work          : size=40000
CopyOnWriteArrayList iterate+add     : saw 2, list now [a, b, a2, b2]
offer on full queue                  : true true false
producer/consumer sum 1..100         : 5050
ConcurrentSkipListMap first/last key : 2 / 996  ceilingKey(500)=500

Over 27,000 adds vanished with no exception in this run; the number changes every run (an earlier run gave 13,243), and on some runs the example also reports an exception. Unsynchronized collections do not fail loudly. The ArrayList Javadoc warns: "Note that this implementation is not synchronized."ArrayList javadoc

The synchronized wrapper and its iteration trap

A synchronized wrapper is like a single key to a shared room: every method (add, get, size) takes the key, does its job and gives it back. That fixed the run: size=40000. But a loop is many calls in a row, and between them another thread can grab the key and change the list. So for iteration you must hold the key yourself:

List<String> list = Collections.synchronizedList(new ArrayList<>());
synchronized (list) {                 // required for iteration
    for (String s : list) process(s);
}

Without the block the loop can throw ConcurrentModificationException (lesson 0029). With it, every other thread waits for the whole loop: that is the price of one lock.

ConcurrentSkipListMap: the sorted one

For a shared sorted map (lesson 0034), four threads put random prices into a ConcurrentSkipListMap, and firstKey, lastKey and ceilingKey still work: 2 / 996 ceilingKey(500)=500 in this run (the keys are random, so yours will differ).

3. CopyOnWriteArrayList: snapshots

Think of a restaurant menu board. Changing the menu means printing a whole new board and swapping it in. Customers already reading the old board keep reading it, undisturbed. Reprinting is expensive, but menus change rarely and are read all day.

The Javadoc: "A thread-safe variant of ArrayList in which all mutative operations (add, set, and so on) are implemented by making a fresh copy of the underlying array. This is ordinarily too costly, but may be more efficient than alternatives when traversal operations vastly outnumber mutations".CopyOnWriteArrayList javadoc

Iterators use the array "at the point that the iterator was created", so they never throw ConcurrentModificationException and "will not reflect additions, removals, or changes" made after; iterator.remove() is unsupported.CopyOnWriteArrayList javadoc

List<String> listeners = new CopyOnWriteArrayList<>(List.of("a", "b"));
for (String l : listeners) { listeners.add(l + "2"); seen++; }
Step 1  The loop starts on snapshot [a, b]
Step 2  add("a2") makes a new array [a, b, a2]; the loop still reads [a, b]
Step 3  add("b2") makes another new array [a, b, a2, b2]
Step 4  The loop ends after 2 elements → saw 2, list now [a, b, a2, b2]

With a plain ArrayList that same loop would throw ConcurrentModificationException, or never end. Typical uses: event listener lists, routing tables, feature flags. Trap: a list that is written often (a log, a queue of tasks) turns every add into a full copy.

4. BlockingQueue: the producer-consumer hand-off

Picture a sushi conveyor belt with room for only a few plates. The chef (producer) puts plates on; if the belt is full, the chef waits. The customer (consumer) takes plates off; if the belt is empty, the customer waits. Nobody needs to shout "ready?": the belt does the coordination.

Four ways to react when it cannot proceed

ThrowsSpecial valueBlocksTimes outBlockingQueue javadoc
Insertaddofferputoffer(e, t, unit)
Removeremovepolltakepoll(t, unit)
BlockingQueue<Integer> q = new ArrayBlockingQueue<>(2);
q.offer(1); q.offer(2); q.offer(3);   // true true false: no room for 3

// consumer thread
for (int x; (x = q.take()) != -1; ) sum += x;
// producer thread
for (int i = 1; i <= 100; i++) q.put(i);
q.put(-1);                            // poison pill: "no more items"

Why a poison pill? "A BlockingQueue does not intrinsically support any kind of 'close' or 'shutdown' operation"; "a common tactic is for producers to insert special end-of-stream or poison objects".BlockingQueue javadoc

Implementations: ArrayBlockingQueue (bounded array), LinkedBlockingQueue (optionally bounded), PriorityBlockingQueue, DelayQueue, SynchronousQueue (no capacity, direct hand-off), LinkedTransferQueue.BlockingQueue javadoc Nulls are rejected because null signals "poll failed".BlockingQueue javadoc Like other concurrent collections, putting an element in happens-before taking it out in another thread (lesson 0005).BlockingQueue javadoc This is exactly the queue inside a ThreadPoolExecutor (lesson 0023).

Trap: the bulk methods addAll, containsAll, retainAll and removeAll "are not necessarily performed atomically", so addAll(c) can fail after adding only some elements.BlockingQueue javadoc

JDK 8 vs 17 vs 21: all these classes are available and behave the same on 8, 17 and 21. On JDK 21 a consumer blocked in take() can be a virtual thread (lesson 0006), where blocking is cheap.

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

Four threads each add 10,000 items to one plain ArrayList. What is the most likely result?

Updates are lost silently when two threads write the same slot. The run showed size=12481.

What do you need to iterate a Collections.synchronizedList safely?

Each method is locked, but a loop is many calls. You must manually synchronize on the returned list when traversing it.

When does CopyOnWriteArrayList fit best?

Every write copies the array. That only pays off when traversal operations vastly outnumber mutations, like listener lists.

A loop over a CopyOnWriteArrayList of [a, b] adds one item per element. What happens?

The iterator reads the snapshot taken when it was created; additions go to a new array.

Which BlockingQueue method waits until there is space?

put blocks; offer returns false; add throws. The run showed offer returning false on a full ArrayBlockingQueue(2).

Why does a BlockingQueue reject null elements?

poll returns null when nothing is available, so null cannot also be a real element.

You need a sorted map with range queries, shared by many threads. Which one?

ConcurrentSkipListMap is a concurrent NavigableMap with expected log(n) operations. ConcurrentHashMap has no order.

The final test: say it in 60 seconds

An interviewer asks: "Which thread-safe collections does Java offer, and how do you choose?" Start a timer. Answer out loud, in full sentences. Then click the button.

Tick only the points you really said:

Example answer

"First, why it matters: a plain ArrayList shared by four threads lost most of 40,000 adds in my test, without any exception. The simplest fix is Collections.synchronizedList or synchronizedMap: one lock around every method, fine for low contention, but I have to hold the lock myself while iterating. For lists that are read all the time and written rarely, like listeners, I use CopyOnWriteArrayList: each write copies the array, and iterators work on a snapshot, so they never throw. For shared maps I use ConcurrentHashMap with its atomic methods, and ConcurrentSkipListMap if I need it sorted. Between producers and consumers I use a BlockingQueue, ideally bounded like ArrayBlockingQueue, so put blocks when it's full and gives backpressure. It doesn't accept nulls, and to stop consumers I send a poison pill."
