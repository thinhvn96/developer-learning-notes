Map power methods: merge, compute and their traps

Replace "get, check for null, put" with one call, and learn the three ways it can surprise you.

Java (JDK 8, 17, 21) · Lesson 0037 · step 19 of 46 · Advanced · ~20 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? Counting words, grouping orders by customer, building a cache: half of all map code is "if the key is missing, create something; otherwise update it". Java 8 added methods that do this in one call. Reviewers and interviewers expect you to use them, and to know where they bite: null results, eager arguments and recursion.
Today's win: replace get-check-put code with merge, computeIfAbsent and friends, and avoid their three null and recursion traps.
default method
A method with a body inside an interface. Java 8 used them to add new methods to Map without breaking every class that implements it.
lambda
A small unnamed function you pass as a value, like k -> new ArrayList<>(). Lesson 0008 covers them.
method reference
A short way to write a lambda that calls one existing method: Integer::sum means (a, b) -> Integer.sum(a, b).
mapping function
The function you give to computeIfAbsent: it receives the key and returns the new value.
remapping function
The function you give to merge or compute: it receives the old value and returns the new one.
multimap
A map where one key holds many values, usually Map<K, List<V>>.
eager / lazy
Eager: computed right away, even if not needed. Lazy: computed only when it is actually needed.

Trace: counting words with merge

merge(key, value, function) reads like this: "If the specified key is not already associated with a value or is associated with null, associates it with the given non-null value."Map javadoc Otherwise it calls your function with the old value and the new one.

for (String w : List.of("kafka", "java", "kafka", "sql", "java", "kafka"))
    counts.merge(w, 1, Integer::sum);
Step 1  "kafka": absent → store 1
Step 2  "java":  absent → store 1
Step 3  "kafka": old 1 → sum(1, 1) → store 2
...     "sql" → 1, "java" → 2, "kafka" → 3
$ java java/examples/collections/MapPowerMethods.java
merge count         : {java=2, kafka=3, sql=1}
computeIfAbsent list: {j=[java, java], k=[kafka, kafka, kafka], s=[sql]}
getOrDefault        : 0
objects built (putIfAbsent + computeIfAbsent on existing key): 1
null result removes : {}
getOrDefault on null value: null
recursive computeIfAbsent: ConcurrentModificationException
groupingBy+counting : {java=2, kafka=3, sql=1}

The last line shows the stream alternative from lesson 0004: Collectors.groupingBy(w -> w, TreeMap::new, Collectors.counting()) gives the same counts. Use merge when you update a map that already exists; use groupingBy when you build a new map from a stream.

2. Concurrency: where these methods matter most

On a plain HashMap these methods are just shorter code. The Javadoc is explicit: "The default implementation makes no guarantees about synchronization or atomicity properties of this method. Any implementation providing atomicity guarantees must override this method and document its concurrency properties."Map javadoc

ConcurrentHashMap does override them and makes them atomic, which is why they matter even more there (lesson 0025). With two threads, get then put can lose an update: both read 2, both write 3. merge on a ConcurrentHashMap does the read and the write as one step.

3. The traps

objects built (putIfAbsent + computeIfAbsent on existing key): 1
null result removes : {}
getOrDefault on null value: null
recursive computeIfAbsent: ConcurrentModificationException

Trap 1: putIfAbsent is eager

Java evaluates method arguments before the call. So m.putIfAbsent("x", new ArrayList<>()) builds a new list even when "x" already exists, and throws it away. computeIfAbsent takes a function, and only calls it when the key is missing.

For a cheap value like 0 this does not matter. For a database call or a big object, it does.

Trap 2: null means "no mapping"

If the mapping function returns null "no mapping is recorded"; if a remapping function returns null "the mapping is removed".Map javadoc In the example, computeIfAbsent("pear", k -> null) adds nothing, and decreasing apple's stock to 0 with v - 1 == 0 ? null : v - 1 removes apple: the map prints {}. That is handy on purpose, and a surprise by accident.

And getOrDefault returns "the value to which the specified key is mapped, or defaultValue if this map contains no mapping for the key".Map javadoc A key mapped to null has a mapping, so you get the stored null, not your default. The run printed getOrDefault on null value: null.

Trap 3: do not modify the map inside the function

"The mapping function should not modify this map during computation."Map javadoc HashMap "will, on a best-effort basis, throw a ConcurrentModificationException" when it detects this.HashMap javadoc The classic victim is memoized recursion:

static int fib(int n, Map<Integer, Integer> memo) {
    if (n < 2) return n;
    return memo.computeIfAbsent(n, k -> fib(k - 1, memo) + fib(k - 2, memo));
}
Step 1  computeIfAbsent(30) starts; HashMap is in the middle of an insert
Step 2  the function calls fib(29) → computeIfAbsent(29) → puts into the same map
Step 3  back in step 1, HashMap sees the map changed under it → ConcurrentModificationException

The fix: use a plain get and put there: compute the value first, then store it.

Integer cached = memo.get(n);
if (cached != null) return cached;
int value = fib(n - 1, memo) + fib(n - 2, memo);
memo.put(n, value);
return value;

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

Which call counts words in a Map<String, Integer> in one line?

merge stores 1 the first time and combines old + 1 after that. put(w, get(w) + 1) throws NullPointerException the first time.

The function passed to computeIfAbsent returns null. What happens?

If the mapping function returns null, no mapping is recorded, and computeIfAbsent returns null.

The key "x" already exists. Which call still builds its argument object?

putIfAbsent takes a value, and Java evaluates arguments before the call. computeIfAbsent takes a function and only runs it when needed. (List.of() is built too, but it is a shared empty list, not a new object you asked for.)

The map holds "k" → null. What does getOrDefault("k", "default") return?

The key has a mapping (to null), so the default is not used. The example printed null.

A memoized fib calls itself inside computeIfAbsent on a HashMap. What is the bug?

The mapping function should not modify the map. HashMap detects it on a best-effort basis and throws ConcurrentModificationException.

On a plain HashMap, is merge atomic when two threads call it?

Only implementations that override and document it, like ConcurrentHashMap, give atomicity. A plain HashMap is not thread-safe at all.

An interviewer shows you get-check-put code and asks: "How would you write this in modern Java, and what should you be careful about?" Start a timer. Answer out loud, in full sentences. Then click the button.

Tick only the points you really said:

Example answer

"Since Java 8, Map has default methods for exactly this. For counting I write merge with the key, 1 and Integer::sum, which stores 1 the first time and adds after that. For a multimap I write computeIfAbsent with a function that creates the list, and call add on the result. There are a few traps. putIfAbsent takes a value, so the value is built even if the key exists, while computeIfAbsent only calls the function when needed. If my function returns null, nothing is stored, or with merge and compute the entry is removed. getOrDefault returns a stored null instead of my default. And the function must not modify the same map, so a recursive memoized fib inside computeIfAbsent can throw ConcurrentModificationException on a HashMap. Finally, these methods are only atomic on ConcurrentHashMap, not on a plain HashMap."
