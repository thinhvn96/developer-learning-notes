Why a List<Integer> is not a List<Number>

What generics give you, how to read <T>, and the one rule that surprises everybody.

Java (JDK 8, 17, 21) · Lesson 0020 · step 3 of 46 · Core · ~20 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? You write List<Order> and Map<String, User> every day. Interviewers ask "What are generics for?" and then the trick question "Integer is a Number, so is List<Integer> a List<Number>?". Most people say yes. This lesson shows why the answer is no.
Today's win: name the three benefits of generics and explain, with a short story, why List<Integer> is not a List<Number>.
class
A blueprint for objects. ArrayList is a class; each new ArrayList<>() is one object.
generic type
A class or interface with a "blank" for a type, written in angle brackets: List<E>, Box<T>.
type parameter
The name of the blank, like T or E. You fill it when you use the class.
type argument
The real type you put in the blank: in List<String> it is String.
subtype
A more specific type that can be used where the general one is expected. Integer is a subtype of Number.
cast
Telling the compiler "trust me, this object is really a String": (String) obj. Wrong casts fail at run time.
compile time / run time
Compile time is when javac checks your code. Run time is when the program actually runs.

Before you start

Say out loud: "Integer extends Number. Can I pass a List<Integer> to a method that takes a List<Number>? Why or why not?" Commit to yes or no before you read on.

1. The picture: labelled boxes

Imagine a storeroom full of boxes with no labels. You put shoes in one. Later a colleague opens it, expects books, and drops it on the floor in surprise. Now imagine every box has a label: "Shoes only". The person at the door checks the label and refuses to put books in it. Nobody gets a surprise later.

Generics are those labels, and the compiler is the person at the door. Look at old code without generics:

List list = new ArrayList();      // no label: holds any Object
list.add("hello");
list.add(42);                     // allowed, nobody checks
String s = (String) list.get(1);  // ClassCastException at run time

And with a label:

List<String> list = new ArrayList<>();
list.add("hello");
list.add(42);                     // compile error: 42 is not a String
String s = list.get(0);           // no cast needed

The tutorial lists exactly three benefits: stronger type checks at compile time, elimination of casts, and the ability to write generic algorithms that work on collections of different types.Tutorial: why use generics The big idea: a bug that used to appear in production (a ClassCastException) now appears in your editor.

2. Reading and writing <T>

Here is a tiny generic class from the tutorial's style. T is a blank; whoever creates a Box decides what goes in it.

class Box<T> {
    private T item;
    void set(T item) { this.item = item; }
    T get()          { return item; }
}

Box<Integer> b = new Box<>();
b.set(7);
int n = b.get();
Step 1  Box<Integer>: the compiler reads every T as Integer
Step 2  b.set(7) is checked: 7 is an Integer → OK
Step 3  b.get() is known to return Integer → no cast needed
Step 4  b.set("seven") would be a compile error

Names. "By convention, type parameter names are single, uppercase letters": E for Element (used all over the collections), K for Key, V for Value, T for Type, N for Number.Tutorial: generic types So Map<K, V> reads "a map from keys to values".

The diamond <>. "In Java SE 7 and later", you may leave the brackets empty on the right side when the compiler can infer the type: new Box<>().Tutorial: generic types So this works the same on JDK 8, 17 and 21.

Trap: primitives cannot fill the blank

List<int> nums;        // compile error
List<Integer> nums;    // fix: use the wrapper class

The tutorial's list of restrictions starts with "Cannot Instantiate Generic Types with Primitive Types".Tutorial: restrictions on generics Java converts between int and Integer for you when you add and get.

3. The surprising rule: no family relationship

Back to the storeroom. You have a box labelled "Apples only". A colleague asks for "a fruit box". An apple is a fruit, so you hand over the apple box. Your colleague, holding a "fruit box", puts a banana in it. That is allowed for a fruit box! Now your apple box contains a banana, and the next person who takes out "an apple" gets a banana.

Java prevents this story at the door. The tutorial says: "Although Integer is a subtype of Number, List<Integer> is not a subtype of List<Number> and, in fact, these two types are not related."Tutorial: generics and subtyping If it were allowed, you could add a Double through the List<Number> reference into what is really a List<Integer>, breaking type safety.Tutorial: generics and subtyping

Try it. The example has this line commented out because it does not compile:

List<Integer> ints = new ArrayList<>(List.of(1, 2, 3));
// List<Number> nums = ints;   // compile error

If you remove the //, JDK 21's javac says:

error: incompatible types: List<Integer> cannot be converted to List<Number>

Interviewers call this rule invariance: a generic type does not follow the family tree of its type argument. Integer → Number is a relationship; List<Integer> → List<Number> is not.

Reading is fine, though: a method that only reads numbers should accept a list of integers. That is what wildcards (? extends Number) give you, in lesson 0021.

4. Arrays made the other choice

Arrays are older than generics, and they do follow the family tree: an Integer[] can be used as a Number[]. The JLS says such a variable "can hold a reference to an instance of any array type B[], provided B can be assigned to A", and warns: "This may result in a run-time exception on a later assignment".JLS §10.2 That exception is ArrayStoreException.JLS §10.5

Number[] arr = new Integer[3];   // compiles
arr[0] = 3.14;                   // ArrayStoreException at run time

A good way to say it in an interview: invariance lets generics catch the "banana in the apple box" bug at compile time, where it is cheap to fix, instead of at run time, where it becomes a production incident.

Is List<Integer> a subtype of List<Number>?

Generic types are invariant: "List<Integer> is not a subtype of List<Number>" (Java Tutorials).

Why does Java refuse List<Number> nums = ints;?

Allowing it would break type safety: the "banana in the apple box" story.

Which is one of the three benefits of generics in the tutorial?

The three: stronger compile-time checks, no casts, and generic algorithms.

What does this print or do? Number[] a = new Integer[1]; a[0] = 1.5;

Arrays are covariant, so the assignment compiles; the store is checked at run time and fails (JLS §10.5).

What is wrong with List<int> scores = new ArrayList<>();?

"Cannot Instantiate Generic Types with Primitive Types" is the first restriction in the tutorial.

With List<String> list, why can you write String s = list.get(0); without a cast?

The type argument tells the compiler what get returns, so the cast is no longer needed.

Example answer

"Generics let a class like List take a type parameter, so I write List<String> and the compiler knows what's inside. That gives three benefits: type errors are caught at compile time, I don't need casts, and I can write algorithms that work for many types. Now, is a List<Integer> a List<Number>? No, even though Integer is a Number. The two list types are unrelated; generics are invariant. If Java allowed it, I could take my list of integers, look at it as a list of numbers, and add a Double. Then code that reads integers would crash. Arrays actually allow this, and they fail at run time with ArrayStoreException; generics chose to fail at compile time instead. If I just want to read numbers from any such list, I use a wildcard: List<? extends Number>."
