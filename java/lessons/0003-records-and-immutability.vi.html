Record: một dòng thay cho bốn mươi dòng

record viết sẵn những gì cho bạn, và một chữ, nông (shallow), vẫn có thể làm bạn dính bug.

Java (JDK 8, 17, 21) · Bài 0003 · bước 39/46 · Core · ~20 phút · Trang chủ · Lộ trình Java (JDK 8, 17, 21) · Lộ trình tổng · English

Vì sao có bài này? Các service Java hiện đại dùng record cho DTO, event, key của map và kết quả query. Interviewer hỏi "Record là gì? Nó có immutable không?" Câu trả lời mong đợi là "có, nhưng chỉ ở mức nông", và bạn nên chỉ ra được cách sửa.
Thành quả hôm nay: kể ra record sinh ra những gì, giải thích vì sao record chứa một ArrayList thì chưa thật sự immutable, và sửa nó bằng compact constructor cùng List.copyOf.
field
Biến thuộc về một object, như x bên trong một Point.
final
Với field: chỉ được gán một lần, trong constructor. Với class: không ai kế thừa (subclass) được nó.
immutable (bất biến)
Không thay đổi được sau khi tạo. String là immutable; ArrayList thì không.
reference (tham chiếu)
Field kiểu object không chứa chính object đó, mà chỉ chứa một mũi tên trỏ tới nó trong bộ nhớ.
constructor
Method đặc biệt chạy khi bạn viết new Point(1, 2). Nó gán giá trị cho các field.
accessor
Method trả về giá trị của một field. Code JDK 8 gọi nó là getter: getX().
record component
Một trong các giá trị liệt kê ở phần đầu record, như x và y trong record Point(int x, int y).

Trước khi bắt đầu

Hãy nói to: "Nếu mọi field của một class đều là final, object đó có immutable không?" Có hay không, và vì sao? Bạn sẽ kiểm tra ở mục 4.

1. Cách của JDK 8: gõ rất nhiều cho hai con số

Hãy nghĩ tới một nhãn bưu kiện. Nó chứa vài giá trị (tên, đường, thành phố) và bạn chỉ đọc chúng. Bạn không bao giờ "làm" gì với cái nhãn. Rất nhiều class trong backend giống vậy: một order event, một mức giá, một toạ độ. Chúng chỉ mang dữ liệu.

Ở JDK 8, ngay cả một nhãn chỉ có hai con số cũng cần cả đống code này:

// JDK 8: a correct immutable value class
public final class Point {
    private final int x;
    private final int y;

    public Point(int x, int y) { this.x = x; this.y = y; }

    public int getX() { return x; }
    public int getY() { return y; }

    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Point)) return false;
        Point p = (Point) o;
        return x == p.x && y == p.y;
    }
    @Override public int hashCode() { return Objects.hash(x, y); }
    @Override public String toString() { return "Point[x=" + x + ", y=" + y + "]"; }
}

// JDK 16+: the same thing
record Point(int x, int y) {}

Phiên bản JDK 8 rất dễ viết sai. Sau này thêm field z mà quên cập nhật equals hoặc hashCode là bạn dính ngay bug HashMap âm thầm ở bài 0001. Record chính thức từ JDK 16, nên bạn có nó trên 17 và 21.JEP 395

2. Record sinh ra những gì

Javadoc định nghĩa: "Record class là một vật chứa trong suốt, bất biến ở mức nông, cho một tập giá trị cố định, gọi là các record component."Record javadoc Từ phần đầu record Point(int x, int y), compiler tạo ra:

Javadoc liệt kê các "mandated member" (thành viên bắt buộc): một canonical constructor, "một field private final tương ứng với mỗi component", và "một accessor method public tương ứng với mỗi component, có tên và kiểu trả về giống hệt component đó".Record javadoc Còn equals, hashCode và toString ngầm định thì "được suy ra từ tất cả các field của component".Record javadoc

Chạy ví dụ của khoá học và theo dõi từng dòng:

$ java java/examples/RecordDemo.java
Point[x=1, y=2]             ← toString: name and every component
true                        ← equals: same class, every component equal
true                        ← hashCode: equal points, equal hash codes
LeakyTeam sees outside change: [ann, bob]
Team (copyOf) is protected:    [ann]

Điều này nối với bài 0001: record tuân thủ contract equals/hashCodeObject javadoc miễn phí, nên nó là key tốt cho HashMap, miễn là các component của nó cũng an toàn. (Hai dòng cuối dành cho mục 4.)

Để ý tên accessor: p.x(), không phải p.getX(). Code chờ tên kiểu JDK 8 getX() sẽ không tìm thấy chúng trên record.

3. Quy tắc: những gì record không làm được

Record chỉ để mang dữ liệu, nên JEP 395 đặt ra vài giới hạn cứng:JEP 395

  1. "Record class ngầm định là final, và không thể là abstract." Không ai kế thừa nó được.
  2. "Superclass của một record class luôn là java.lang.Record." Bạn không được viết extends.
  3. "Record class không được khai báo tường minh instance field". Mọi trạng thái nằm ở phần đầu record.
  4. Nhưng "record class có thể implement interface", và "có thể khai báo method, field và initializer static".

Mình đã thử các trường hợp bị cấm với javac 21:

record P(int x) { int y; }
error: field declaration must be static

System.out.println(P.class.getSuperclass() + " final=" + Modifier.isFinal(P.class.getModifiers()));
class java.lang.Record final=true

Bạn có thể tự viết accessor (ví dụ để trả về một bản copy). JEP 395 cho phép, miễn là kiểu trả về khớp chính xác.JEP 395

4. Chữ quan trọng: nông (shallow)

Hình dung một tủ kính khoá kín trong bảo tàng. Bên trong là một tấm thẻ ghi địa chỉ một ngôi nhà. Không ai sửa được tấm thẻ: nó bị khoá. Nhưng ngôi nhà ở địa chỉ đó vẫn có thể bị sơn lại. Tủ kính bảo vệ tấm thẻ, không bảo vệ ngôi nhà.

Field final chính là tấm thẻ bị khoá. Nếu field là một reference tới ArrayList, field sẽ luôn trỏ tới cùng một list, nhưng ai đang giữ list đó vẫn add thêm được. Đó là ý nghĩa của "bất biến ở mức nông".Record javadoc Vậy câu trả lời cho "Trước khi bắt đầu" là không: mọi field đều final vẫn chưa đủ khi có field trỏ tới thứ có thể thay đổi.

record LeakyTeam(String name, List<String> members) {}

List<String> shared = new ArrayList<>(List.of("ann"));
LeakyTeam leaky = new LeakyTeam("a", shared);
shared.add("bob");                         // change the list from outside
leaky.members();                           // [ann, bob]: the record changed!
Step 1  shared points to a list [ann]
Step 2  the record's members field gets a copy of the ARROW, not of the list
Step 3  shared.add("bob") changes the one list both arrows point to
Step 4  leaky.members() follows its arrow and finds [ann, bob]

Cách sửa: compact constructor với defensive copy

Record có thể có constructor compact: bạn viết tên record và phần thân, không lặp lại danh sách tham số. JEP 395 nói các tham số được khai báo sẵn cho bạn, và các field được gán tự động ở cuối.JEP 395 Đây là chỗ lý tưởng để kiểm tra dữ liệu và copy:

record Team(String name, List<String> members) {
    Team {
        if (name == null || name.isBlank()) throw new IllegalArgumentException("name");
        members = List.copyOf(members);    // replace the parameter with a copy
    }                                      // fields are assigned here, from the parameters
}
$ java java/examples/RecordDemo.java
...
LeakyTeam sees outside change: [ann, bob]
Team (copyOf) is protected:    [ann]

Vì sao dùng List.copyOf chứ không phải new ArrayList<>(members)? List.copyOf trả về một "unmodifiable List", và theo Javadoc, "nếu Collection đầu vào bị sửa sau đó, List trả về sẽ không phản ánh những thay đổi ấy".List javadoc Vì nó không sửa được, ai gọi team.members().add("x") cũng thất bại. Mình đã chạy: UnsupportedOperationException. Một bản copy ArrayList thường chặn được thay đổi từ bên ngoài, nhưng không chặn được trường hợp này.

Bẫy: null bên trong list

List.copyOf ném NullPointerException "nếu coll là null, hoặc chứa bất kỳ phần tử null nào".List javadoc Thường đó chính là điều bạn muốn với một value object (báo lỗi sớm). Nếu dữ liệu của bạn hợp lệ khi có null, hãy quyết định rõ ràng và ghi lại.

Javadoc của Record là nguồn cho những gì được sinh ra. Mẫu compact constructor là thực hành phổ biến; demo ở trên cho thấy nó chạy thật thay vì trích dẫn.

Luyện tập

Trả lời theo trí nhớ, đừng cuộn lên. Thứ tự đáp án thay đổi mỗi lần bạn mở trang.

equals() ngầm định của record dựa trên cái gì?

equals, hashCode và toString được suy ra từ mọi field của component: cùng record class và mọi component bằng nhau.

Với record Point(int x, int y), compiler tạo ra những field nào?

Javadoc quy định mỗi component có một field private final, cùng một accessor public cùng tên.

Đọc x từ Point p thế nào khi Point là record?

Accessor cùng tên với component, không có tiền tố get. Bản thân field là private.

Chuyện gì xảy ra với record P(int x) { int y; }?

Record không được khai báo instance field; mọi trạng thái nằm ở phần đầu. Trong thân chỉ cho phép field static.

Record có một component ArrayList mà caller vẫn đang giữ. Record đó có immutable không?

Field final luôn trỏ tới cùng một list, nhưng bản thân list vẫn thay đổi được từ bên ngoài.

Cách sửa tốt nhất cho component list bị rò rỉ đó là gì?

List.copyOf lưu một bản copy không sửa được, nên cả caller bên ngoài lẫn members().add() đều không đổi được nó.

Record có kế thừa class khác được không, như record P(int x) extends Base?

Record luôn kế thừa java.lang.Record và ngầm định là final. Tuy vậy nó có thể implement interface.

Interviewer hỏi: "Record trong Java là gì, và nó có immutable không?" Bấm giờ. Trả lời to, thành câu đầy đủ. Rồi bấm nút.

Câu trả lời mẫu

"Record, chính thức từ JDK 16, là class chỉ để mang dữ liệu. Em viết record Point(int x, int y) là compiler sinh ra field private final, canonical constructor, accessor x() và y(), cùng equals, hashCode, toString dựa trên mọi component. Nó thay cho khoảng bốn mươi dòng code JDK 8 và dùng làm key của map rất an toàn. Record ngầm định là final, kế thừa java.lang.Record, không được khai báo thêm instance field, nhưng implement interface thì được. Còn immutable không? Chỉ ở mức nông. Field là final, nhưng nếu một component là ArrayList thì caller vẫn sửa được list đó. Nên trong compact constructor em kiểm tra đầu vào và làm members = List.copyOf(members); vậy là record có list riêng, không sửa được."
