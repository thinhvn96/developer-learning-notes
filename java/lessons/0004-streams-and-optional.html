Streams and Optional without the traps

A stream is a conveyor belt that only starts when someone at the end pulls. Optional is a box that may be empty.

Java (JDK 8, 17, 21) · Lesson 0004 · step 25 of 46 · Core · ~25 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? Streams are everywhere in modern Java services: filtering orders, mapping DTOs, summing amounts. Interviewers love small "what does this print?" puzzles about streams, because the answer is often nothing. They also ask "How should you use Optional?"
Today's win: predict what a stream pipeline prints (or doesn't), explain why a stream can't be reused, and choose correctly between orElse and orElseGet.
stream
A one-time flow of elements that you process step by step. It is not a list; it stores nothing.
source
Where the elements come from: a list, an array, a file.
pipeline
The chain of steps: source, then zero or more middle steps, then one final step.
intermediate operation
A middle step like filter or map. It returns a new stream and only describes work.
terminal operation
The final step like toList(), count() or forEach. It produces a result and starts the work.
lazy
"Not done until needed." The work waits until someone asks for the result.
side effect
When a lambda changes something outside itself, like adding to a list or printing.
Optional
A small box that holds either one value or nothing. It makes "no result" visible in a method's return type.

Before you start

Say out loud: "What does List.of(1, 2, 3).stream().peek(System.out::println).map(x -> x * 2); print?" Commit to an answer before you read on.

1. The picture: a conveyor belt with a start button at the end

Picture a factory belt. At the start is a box of parts (the source). Along the belt are stations: one throws away bad parts (filter), one paints each part (map). At the very end stands a worker who packs the result (the terminal operation).

The strange part: the belt has no power switch at the start. Building the stations does nothing. The belt only moves when the worker at the end pulls the next part. No worker at the end, no movement at all.

The java.util.stream docs say a stream has "No storage": it "is not a data structure that stores elements; instead, it conveys elements from a source ... through a pipeline of computational operations."stream package

2. Rule one: intermediate operations are lazy

"Intermediate operations are always lazy." Traversal of the source "does not begin until the terminal operation of the pipeline is executed."stream package

List<Integer> data = List.of(1, 2, 3);

data.stream().peek(x -> System.out.println("  saw " + x)).map(x -> x * 2);
Step 1  stream()  → a belt starting at data
Step 2  peek(...) → a station is added; nothing runs
Step 3  map(...)  → a station is added; nothing runs
Step 4  the line ends. No terminal op → nothing is printed

data.stream().peek(x -> System.out.println("  saw " + x)).map(x -> x * 2).toList();
Step 1  toList() asks for an element → 1 goes through peek ("saw 1") and map (2)
Step 2  toList() asks again          → 2 goes through ("saw 2") → 4
Step 3  toList() asks again          → 3 goes through ("saw 3") → 6

Notice in Step 1 to 3 that each element travels the whole belt before the next one starts. That is why laziness pays off: for "find the first String with three consecutive vowels", the stream "need not examine all the input strings".stream package Operations like findFirst or limit are short-circuiting: they may stop early, even on an infinite stream.

peek "exists mainly to support debugging", to see elements as they flow past a point.Stream javadoc Don't put business logic in it.

3. Rule two: a stream is used once

A belt is built for one run. "After the terminal operation is performed, the stream pipeline is considered consumed, and can no longer be used"; to traverse the same data again, you go back to the source for a new stream.stream package

Stream<Integer> s = data.stream();
s.count();     // 3
s.count();     // IllegalStateException

The fix: don't store streams in fields or variables to reuse. Keep the source (the list) and call data.stream() each time, or use a Supplier<Stream<T>>.

4. Rule three: don't touch the outside world from inside

Two rules from the docs about the lambdas you pass in (the docs call them behavioral parameters):

  • Non-interference. They "should never modify the stream's data source".stream package Don't add to or remove from the list you are streaming over.
  • Avoid side effects. "Side-effects in behavioral parameters to stream operations are, in general, discouraged." The docs show forEach(results::add) as the anti-pattern and a collecting terminal operation as the fix.stream package
// Wrong: the lambda changes a list outside the stream
List<String> results = new ArrayList<>();
names.stream().filter(n -> n.length() <= 3).forEach(results::add);

// Right: let the stream build the result
List<String> results = names.stream().filter(n -> n.length() <= 3).toList();

Why does it matter? The side-effect version breaks as soon as someone adds .parallel(): several threads then call add on one ArrayList at the same time.

JDK 8 vs 17 vs 21: toList()

Stream.toList() arrived in JDK 16, so it works on 17 and 21 but not on 8. "The returned List is unmodifiable"; calling add on it throws UnsupportedOperationException.Stream javadoc On JDK 8 you write .collect(Collectors.toList()), which gives no guarantee about mutability (see lesson 0022).

5. Optional: a box that may be empty

Think of a parcel locker. When you open it, either there is a parcel inside or it is empty. You can't forget to check, because you have to open the box first. Compare with null: a method returns null, you forget to check, and you get a NullPointerException far away.

The Javadoc is clear about its purpose: "Optional is primarily intended for use as a method return type where there is a clear need to represent 'no result,' and where using null is likely to cause errors." And: "A variable whose type is Optional should never itself be null".Optional javadoc

Optional<User> findByEmail(String email);              // good: return type

String city = findByEmail(e)
    .map(User::city)                                   // empty stays empty
    .orElse("unknown");

class User { Optional<String> nickname; }              // avoid: not a field type

The trap: orElse vs orElseGet

Both give a fallback when the box is empty. The difference is when the fallback is computed. orElse(x) takes a ready value, so Java computes x before the call, even when the box is full. orElseGet(supplier) takes a recipe (a Supplier) and only runs it when the box is empty.Optional javadoc

Common Optional mistakes

  • Calling get() without checking. It throws NoSuchElementException when empty. The Javadoc says "The preferred alternative to this method is orElseThrow()", which says the same thing more honestly.Optional javadoc
  • Returning null from a method whose type is Optional. Return Optional.empty() instead; use Optional.ofNullable(x) to wrap a value that might be null.
  • Using orElse(callDatabase()). The call runs every time. Use orElseGet(() -> callDatabase()).

Version notes: the no-argument orElseThrow() is JDK 10+, and isEmpty() is JDK 11+.Optional javadoc On JDK 8 use get() after isPresent(), or orElseThrow(SomeException::new).

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

A pipeline has peek(print) and map but no terminal operation. What is printed?

Intermediate operations are lazy. Without a terminal operation, the belt never moves, so peek never runs.

You call s.count() twice on the same stream s. What happens?

The terminal operation consumes the stream. To traverse again, go back to the source: data.stream().

In data.stream().peek(print).map(x -> x * 2).toList() with data 1, 2, 3, in what order do things happen?

The terminal operation pulls one element at a time through the whole pipeline. That is what lets short-circuiting operations stop early.

What is the bug? List<String> out = new ArrayList<>(); names.stream().filter(ok).forEach(out::add);

The docs discourage side effects in behavioral parameters and show forEach(results::add) as the anti-pattern. It breaks under .parallel().

What is the intended main use of Optional?

The Javadoc: "primarily intended for use as a method return type where there is a clear need to represent 'no result'".

The fallback value needs a slow database call. Which line is best?

orElse's argument is computed even when a value is present. orElseGet only calls the supplier when the Optional is empty.

On JDK 21, var list = Stream.of(1, 2).toList(); list.add(3); What happens?

Stream.toList() (JDK 16+) returns an unmodifiable list; any mutator throws UnsupportedOperationException.

The final test: say it in 60 seconds

An interviewer asks: "How do Java streams work, and how should you use Optional?" Start a timer. Answer out loud, in full sentences. Then click the button.

Tick only the points you really said:

Example answer

"A stream pipeline has a source, like a list, then intermediate operations like filter and map, and one terminal operation like toList or count. The intermediate operations are lazy: they only describe the work, and nothing runs until the terminal operation pulls elements through, one at a time. That's why findFirst can stop early. A stream is single-use; calling a second terminal operation throws IllegalStateException, so I keep the list and call stream() again. I avoid side effects in the lambdas, for example adding to an outside list in forEach, and let a collector build the result. For Optional: I use it as a return type when 'no result' is a normal case, never as a field, and never return null instead. And I use orElseGet when the default is expensive, because orElse evaluates its argument every time."
