Streams and Optional without the traps

Today's win: predict what a stream pipeline prints (or does not), and use Optional as intended.

Four rules from the stream package docs

  • Lazy. "Intermediate operations are always lazy." Traversal "does not begin until the terminal operation of the pipeline is executed."[1]
  • Single use. "After the terminal operation is performed, the stream pipeline is considered consumed, and can no longer be used."[1]
  • Non-interference. Behavioral parameters "should never modify the stream's data source."[1]
  • Avoid side effects. "Side-effects in behavioral parameters to stream operations are, in general, discouraged." The docs show forEach(results::add) as the anti-pattern and .toList() as the fix.[1]

Optional: a return type, not a field type

"Optional is primarily intended for use as a method return type where there is a clear need to represent 'no result,' and where using null is likely to cause errors."[2] And orElseGet takes a supplier that only runs when empty, while orElse's argument is computed regardless.[2]

Retrieval practice

Answer from memory. One attempt each.

1. Pipeline has filter and map but no terminal op. Result?

Intermediate operations are lazy; nothing runs until a terminal operation.[1]

2. You call count() twice on one stream. Result?

A stream is consumed by its terminal operation; reuse throws IllegalStateException.[1]

3. Intended primary use of Optional?

The Javadoc: primarily a return type where 'no result' must be represented.[2]

4. Default value is costly to build. Which call?

orElseGet only invokes the supplier when the Optional is empty.[2]
