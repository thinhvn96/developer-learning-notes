What happens when Java code fails

Checked versus unchecked exceptions, and how try-with-resources closes things for you.

Java (JDK 8, 17, 21) · Lesson 0019 · step 2 of 46 · Foundation · ~20 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? Every backend reads files, calls databases and talks to other services, and all of these can fail. Interviewers ask "What is the difference between checked and unchecked exceptions?" and "How does try-with-resources work?" to see whether you can write code that fails cleanly and never leaks connections.
Today's win: say which exceptions you must catch or declare, and use try-with-resources while explaining its close order and suppressed exceptions.
exception
An object that describes a problem. Java "throws" it to stop the normal flow of your code.
throw / catch
throw starts the problem; a catch block is the place that handles it.
call stack
The list of methods that are running right now: main called a, which called b, and so on.
checked
An exception the compiler forces you to handle: you must catch it or write throws on your method.
unchecked
An exception the compiler does not force you to handle: RuntimeException, Error and their subclasses.
interface
A list of methods a class promises to have. A class "implements" an interface by writing those methods.
resource
Something you must close when you are done with it, like a file, a socket or a database connection.

Before you start

Say out loud: "If my code opens two files with try-with-resources, in which order are they closed? And if the body throws and close() also throws, which exception do I see?" Guess now. Section 5 shows the real output.

1. The picture: a fire alarm going up the floors

Imagine a building. The ground floor is main. It asks floor 1 to do some work, floor 1 asks floor 2, and so on. Suddenly there is a fire on floor 3. The alarm goes up, floor by floor, until somebody who knows what to do picks up the phone. If nobody does, the whole building is evacuated.

That is an exception. The tutorial defines it as "an event, which occurs during the execution of a program, that disrupts the normal flow of the program's instructions." The runtime searches the call stack for a matching handler; if none is found, the program terminates.Tutorial: what is an exception

void main() {
    try { service(); } catch (IOException e) { log(e); }
}
void service() throws IOException { repository(); }
void repository() throws IOException {
    throw new IOException("disk");
}
Step 1  repository() throws: its normal code stops at once
Step 2  repository has no catch → the exception goes up to service()
Step 3  service has no catch → it goes up to main()
Step 4  main has a matching catch → log(e) runs, program continues

2. The family tree

Every exception is an object, and all of them come from one class. "The Throwable class is the superclass of all errors and exceptions in the Java language."Throwable javadoc Below it there are two branches, and one of them splits again:

The Java Language Specification gives the exact rule: "The unchecked exception classes are the run-time exception classes and the error classes." Everything else is checked.JLS §11.1.1

  • Error: serious problems of the JVM itself, like running out of memory. The JLS calls them the exceptions "from which ordinary programs are not ordinarily expected to recover."JLS §11.1.1 You normally do not catch them.
  • RuntimeException: usually a bug in the code, like using null or a bad cast.
  • Other Exceptions (checked): problems outside your code that a caller may handle, like a missing file.

3. Checked exceptions: catch or specify

For a checked exception the compiler insists on one of two things: you catch it, or you declare it with throws so your caller must deal with it. The tutorial calls this "catch or specify". Runtime exceptions and errors are unchecked: no catch or declaration is required.Tutorial: unchecked exceptions

static void mayFail() throws IOException {   // "I may throw this"
    throw new IOException("checked");
}

public static void main(String[] a) {
    mayFail();          // does not compile
}

JDK 21's javac refuses this with a clear message:

A.java:4: error: unreported exception IOException; must be caught or declared to be thrown

The example program shows both kinds. The cast fails with an unchecked ClassCastException, and nobody had to declare it. The checked one compiles only because it is caught:

$ java java/examples/ExceptionsDemo.java
...
--- unchecked exceptions need no catch or declaration
ClassCastException
caught checked: checked

Which kind should your exception be?

The tutorial's guideline: "If a client can reasonably be expected to recover from an exception, make it a checked exception. If a client cannot do anything to recover from the exception, make it an unchecked exception."Tutorial: unchecked exceptions

Traps and fixes

  • Using RuntimeException only to avoid writing throws. The tutorial says not to do this.Tutorial: unchecked exceptions
  • Losing the original error when you wrap it. If you convert a checked exception into your own, pass the original as the cause: throw new OrderException("save failed", e);. Java keeps the "chain" of causes, so the stack trace still shows the real problem.Throwable javadoc
  • An empty catch block. It hides the failure; the program continues with bad data. At least log it, or let it go up.

4. Closing things: finally, then try-with-resources

Think of a library book. Whatever happens while you read, you must give it back. Even if you fall asleep, even if the fire alarm rings. A file or a database connection is the same: you must close it, or your server slowly runs out of them.

The old tool is finally: "The finally block always executes when the try block exits."Tutorial: finally But the same page adds: "Use a try-with-resources statement instead of a finally block when closing a file or otherwise recovering resources."

A resource is "an object that must be closed after the program is finished with it", and anything that implements the AutoCloseable interface qualifies.Tutorial: try-with-resources You declare it in brackets after try, and Java calls close() for you:

try (Res first = new Res("first", false);
     Res second = new Res("second", false)) {
    System.out.println("body");
}   // no finally needed: both are closed here

The rules from the tutorial:Tutorial: try-with-resources

  1. Reverse order. "the close methods of resources are called in the opposite order of their creation." Like stacking plates: the last one on is the first one off.
  2. Closing comes first. "any catch or finally block is run after the resources declared have been closed."
  3. The body's exception wins. If the body throws and close() also throws, the close exceptions are suppressed, and you can read them with getSuppressed().

5. Run it and read the output

The example has a small resource class Res that prints when it opens and closes. The second resource is made to fail in close().

$ java java/examples/ExceptionsDemo.java
--- close order is the reverse of opening
open  first
open  second
body
close second
close first
--- an exception from close() is suppressed when the body already threw
open  r
close r
caught: body failed
suppressed: close failed: r
...

Trace the second block:

try (Res r = new Res("r", true)) {
    throw new IllegalStateException("body failed");
} catch (Exception e) { ... }
Step 1  open r
Step 2  the body throws "body failed"
Step 3  Java still calls r.close(): "close r" is printed,
        then close() throws "close failed: r"
Step 4  "close failed" is attached to "body failed" as suppressed
Step 5  only now does catch run, with e = "body failed"
Step 6  e.getSuppressed() returns the close exception

Why is this design good? The body's exception is usually the real cause. With an old finally { r.close(); }, a failing close() would throw a new exception and the original one would be lost. The getSuppressed() method returns the exceptions "that were suppressed, typically by the try-with-resources statement, in order to deliver this exception".Throwable javadoc

JDK 8 versus 9+

On JDK 8 every resource must be declared inside the brackets (try (Res r = ...)).JLS 8 §14.20.3 Since JDK 9 you may also name an existing variable, as long as it is final or "effectively final" (never reassigned):JLS 21 §14.20.3

Res r = new Res("r", false);
try (r) {               // JDK 9+, r must be effectively final
    ...
}

Link to Spring: checked exceptions do not roll back @Transactional by default, which surprises many people. See the Spring lesson on @Transactional.

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

Which exceptions must you catch or declare with throws?

Catch-or-specify applies only to checked exceptions. Runtime exceptions and errors are unchecked.

A method calls mayFail(), which is declared throws IOException, with no try and no throws. What happens?

IOException is checked, so javac says "must be caught or declared to be thrown".

try-with-resources opens first, then second. In which order are they closed?

Close methods run in the opposite order of creation; the demo prints close second before close first.

The body throws "body failed" and close() throws "close failed". What does the catch receive?

The body's exception is propagated; the close exception is suppressed and available through getSuppressed().

Which interface must a class implement to be used in try-with-resources?

Any object that implements AutoCloseable can be a resource.

What is the bug in catch (SQLException e) { throw new RuntimeException("save failed"); }?

Without e as the cause, the stack trace no longer shows the real SQL problem. Write new RuntimeException("save failed", e).

The final test: say it in 60 seconds

An interviewer asks: "Checked versus unchecked exceptions, and how does try-with-resources work?" Start a timer. Answer out loud, in full sentences. Then click the button.

Tick only the points you really said:

Example answer

"Every exception in Java extends Throwable. Under it there's Error, for serious JVM problems like out of memory, and Exception. RuntimeException and Error, with their subclasses, are unchecked; everything else is checked. For a checked exception, like IOException, the compiler forces me to either catch it or declare it with throws. The usual guideline: if the caller can reasonably recover, make it checked; if it's a programming bug, make it unchecked. When I wrap an exception I always pass the original as the cause. For closing files or connections I use try-with-resources: anything that implements AutoCloseable is closed automatically, in reverse order of opening, and before my catch block runs. If the body throws and close also throws, I get the body's exception, and the close exception is attached as suppressed, so nothing is lost."
