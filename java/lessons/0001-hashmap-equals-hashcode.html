How HashMap finds your value

And why equals() and hashCode() must work together.

Java (JDK 8, 17, 21) · Lesson 0001 · step 9 of 46 · Foundation · ~20 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? Interviewers very often open with "How does a HashMap work?" You use HashMap every day. This lesson helps you explain it, in simple words, and avoid the most common bug.
Today's win: explain HashMap out loud in about 60 seconds, including why overriding equals() without hashCode() silently breaks it.
key, value
A map stores pairs. You look up the value by its key, like a word and its meaning in a dictionary.
entry
One key and its value, stored together. For example "cat" → 1.
bucket
One "box" inside the HashMap. A HashMap has many buckets, and each bucket holds some of the entries.
hash code
A whole number (int) made from an object. You get it by calling hashCode(). HashMap uses it to choose a bucket.
collision
Two different keys that land in the same bucket. It is normal.
override
Writing your own version of a method that your class inherited, here equals() and hashCode() from Object.
O(1)
Read "O of one": the time stays about the same even when the map gets bigger.

1. The picture: a wall of mailboxes

Imagine a wall with 16 mailboxes, numbered 0 to 15. Each mailbox is a bucket. A new HashMap starts with 16 of them.source

When you put something, Java does not search for an empty place. It calculates the right mailbox from the key. When you get, Java does the same calculation and goes straight to the same mailbox.

This is why get() is fast. Java does not look in all 16 mailboxes; it looks in one. The documentation calls it "constant-time performance for the basic operations (get and put), assuming the hash function disperses the elements properly among the buckets".HashMap javadoc That is what interviewers mean by O(1) on average.

2. Follow one key, step by step

map.put("cat", 1);
Step 1  Java calls "cat".hashCode()          → 98262
Step 2  Java turns 98262 into a box number   → 7
Step 3  Java stores the entry "cat" → 1 in box 7

map.get("cat");
        Same steps → box 7 → found → returns 1

How does Java turn 98262 into 7? With a fast bit trick that you will learn in lesson 0030. For now remember: same key → same number → same box.

3. Two keys in the same box

There are only 16 boxes but millions of possible keys, so sometimes two different keys land in the same box. This is a collision, and it is normal.

A real example: the strings "Aa" and "BB" have the same hash code, 2112. So they go into the same box.

map.put("Aa", 1);
map.put("BB", 2);   // same box as "Aa"
map.get("BB");      // returns 2

How does Java find the right one? Inside the box the entries form a small chain. Java walks it and asks two questions for each entry:

  1. Is the hash code the same? If not, skip it. Comparing two numbers is very fast.
  2. Is the key equal? Java calls equals(). If it returns true, this is the right entry.source

So hashCode() finds the box, and equals() finds the right entry inside the box.

4. The rule: equal objects, same hash code

Because of this, Java has a rule in the documentation of Object.hashCode:Object javadoc

If two objects are equal (equals() returns true), they must have the same hash code.

The opposite is not required. Two different objects may share a hash code, like "Aa" and "BB". That is allowed; it only makes the map a little slower.

Interviewers call this the equals/hashCode contract. "Contract" just means "a rule you must follow".

What happens if you break the rule?

Here the class overrides equals() but forgets hashCode():

class Point {
  final int x, y;
  Point(int x, int y) { this.x = x; this.y = y; }

  @Override public boolean equals(Object o) {
    return o instanceof Point p && p.x == x && p.y == y;
  }
  // hashCode() is missing!
}

map.put(new Point(1, 2), "A");
map.get(new Point(1, 2));   // almost always null!

Why? Without your own hashCode(), Java uses the default one from Object, which gives each new object its own number. The two Point objects are equal but have different numbers, so Java looks in the wrong box and finds nothing. No error message: just null. Run it yourself:

$ java java/examples/LostKey.java
BadKey  lookup: null
GoodKey lookup: value

The fix: always override both methods together. Or, easier, use a record (JDK 16+, so fine on 17 and 21): it writes equals() and hashCode() for you from its fields.Record javadoc

@Override public int hashCode() { return Objects.hash(x, y); }   // JDK 8 style

record Point(int x, int y) {}                                     // JDK 17 / 21 style

5. Don't change a key after you put it in

Back to the mailboxes. You write an address on a letter and drop it in mailbox 7. Then you secretly change the address on the letter. Later you ask "where is my letter?". Java reads the new address, goes to a different mailbox, and finds nothing. The letter is still in mailbox 7, but nobody will find it.

That is what happens when you change a key's fields after put(): its hash code changes, so Java looks in the wrong box. The Map documentation warns: "Great care must be exercised if mutable objects are used as map keys."Map javadoc

The fix: use immutable keys, keys that cannot change: String, Integer, List.of(...), records with immutable fields. Exercise 0001 lets you watch this bug happen.

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

Why is map.get(key) fast?

The hash code tells Java which bucket to use. Java looks in one bucket only, not all of them.

"Aa" and "BB" have the same hash code. After map.put("Aa", 1) and map.put("BB", 2), what does map.get("BB") return?

Both keys are in the same bucket (a collision). Inside the bucket, equals() finds the right key, "BB", so you get 2.

Which sentence is the Java rule?

The rule goes in one direction only: equal → same hash code. Different objects can share a hash code ("Aa" and "BB").

Point overrides equals() but not hashCode(). After map.put(new Point(1, 2), "A"), what does map.get(new Point(1, 2)) return?

The default hashCode() gives each new object its own number, so Java looks in the wrong bucket. No error, just null.

Now Point is record Point(int x, int y) {}. Same put, same get. Result?

A record creates equals() and hashCode() from its fields. Two points with the same x and y are equal and share a hash code.

You put a key in a HashMap, then change the key's fields. Now get() cannot find it. Best way to avoid this?

Changing the key changes its hash code, so Java looks in the wrong bucket. Use immutable keys: String, records, List.of(...).

Example answer

"A HashMap stores entries in an array of buckets. When I call put, Java calls hashCode() on the key and uses that number to choose a bucket. When I call get, it does the same calculation, so it goes straight to the right bucket. That's why get and put are O(1) on average. Sometimes two keys land in the same bucket, a collision; then Java uses equals() to find the right key inside the bucket. That's why equal objects must have the same hash code: if they don't, Java looks in the wrong bucket. And keys should be immutable, because if a key changes after I put it in, the map can't find it again."
