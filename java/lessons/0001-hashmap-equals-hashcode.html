HashMap, equals and hashCode

Java (JDK 8, 17, 21) · Lesson 0001 · step 3 of 27 · Foundation · ~10 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap

Today's win: explain, in three sentences, why overriding equals without hashCode silently breaks a HashMap. This is one of the most common Senior-level opening questions.

The contract

Two rules from the Object Javadoc[1] matter here:

  • If two objects are equal according to equals, calling hashCode on each must produce the same integer.
  • Unequal objects are not required to have different hash codes, though distinct ones improve hash-table performance.

The first rule is a one-way promise: equal ⇒ same hash. It does not say same hash ⇒ equal. A collision is legal, just slower.

What HashMap does with it

A HashMap stores entries in buckets. The hash code picks the bucket; equals then picks the entry inside it. When entries exceed load factor × capacity (defaults 0.75 and 16), the table is rebuilt with about twice as many buckets[2].

So a lookup is: hash → bucket → equals. If two equal keys hash to different buckets, the second lookup goes to the wrong bucket and never runs equals. Run it yourself:

java java/examples/LostKey.java
BadKey  lookup: null
GoodKey lookup: value

Source: LostKey.java. BadKey overrides only equals, so its default identity-based hashCode differs between two instances with the same id, and the lookup misses.

Other facts to keep ready, all from the HashMap Javadoc[2]: it permits one null key and null values; it guarantees no iteration order; it is not synchronized; its iterators are fail-fast and throw ConcurrentModificationException on structural modification.

Retrieval practice

Answer from memory. One attempt each.

1. Two keys are equal by equals. What must be true of their hash codes?

Equal objects must produce the same hash code. This is the core of the contract.

2. Two keys have the same hash code. What does that tell you?

The contract is one-way. Equal hash codes only mean a collision is possible; equals decides.

3. You override only equals on a key class. What is the typical symptom?

It compiles and runs. Equal keys usually land in different buckets, so get quietly returns null. Silent failure is what makes this bug dangerous.

4. Two threads write to one plain HashMap. What does the Javadoc say?

HashMap is not synchronized; concurrent structural modification requires external synchronization (or a different class, which a later lesson covers).
