Vì sao List<Integer> không phải là List<Number>

Generic mang lại gì, cách đọc <T>, và một quy tắc khiến ai cũng bất ngờ.

Java (JDK 8, 17, 21) · Bài 0020 · bước 3/46 · Core · ~20 phút · Trang chủ · Lộ trình Java (JDK 8, 17, 21) · Lộ trình tổng · English

Vì sao có bài này? Ngày nào bạn cũng viết List<Order> và Map<String, User>. Interviewer hỏi "Generic dùng để làm gì?" rồi tung câu hỏi mẹo "Integer là Number, vậy List<Integer> có phải List<Number> không?". Phần lớn mọi người trả lời có. Bài này cho bạn thấy vì sao câu trả lời là không.
Thành quả hôm nay: nêu được ba lợi ích của generic và giải thích, bằng một câu chuyện ngắn, vì sao List<Integer> không phải là List<Number>.
class
Bản thiết kế cho các object. ArrayList là một class; mỗi lần new ArrayList<>() là một object.
generic type
Một class hoặc interface có một "chỗ trống" cho kiểu, viết trong ngoặc nhọn: List<E>, Box<T>.
type parameter
Tên của chỗ trống, như T hay E. Bạn điền vào khi dùng class.
type argument
Kiểu thật mà bạn điền vào chỗ trống: trong List<String> đó là String.
subtype
Kiểu con: một kiểu cụ thể hơn, dùng được ở nơi cần kiểu tổng quát. Integer là subtype của Number.
cast
Ép kiểu: bảo compiler "tin tôi đi, object này thật ra là String": (String) obj. Ép sai sẽ hỏng lúc chạy.
compile time / run time
Compile time là lúc javac kiểm tra code. Run time là lúc chương trình thật sự chạy.

Trước khi bắt đầu

Nói thành tiếng: "Integer kế thừa Number. Mình có truyền được List<Integer> vào một method nhận List<Number> không? Vì sao?" Chọn hẳn có hoặc không trước khi đọc tiếp.

1. Hình dung: những chiếc hộp có dán nhãn

Hãy tưởng tượng một nhà kho đầy hộp không dán nhãn. Bạn bỏ giày vào một hộp. Sau đó một đồng nghiệp mở ra, tưởng là sách, giật mình làm rơi xuống đất. Giờ hãy tưởng tượng mỗi hộp đều có nhãn: "Chỉ đựng giày". Người đứng ở cửa kiểm tra nhãn và không cho bỏ sách vào. Về sau không ai bị bất ngờ nữa.

Generic chính là những cái nhãn đó, còn compiler là người đứng ở cửa. Xem code cũ không dùng generic:

List list = new ArrayList();      // no label: holds any Object
list.add("hello");
list.add(42);                     // allowed, nobody checks
String s = (String) list.get(1);  // ClassCastException at run time

Và khi có nhãn:

List<String> list = new ArrayList<>();
list.add("hello");
list.add(42);                     // compile error: 42 is not a String
String s = list.get(0);           // no cast needed

Tutorial liệt kê đúng ba lợi ích: kiểm tra kiểu chặt hơn lúc compile, bỏ được việc ép kiểu, và viết được các thuật toán generic chạy trên collection của nhiều kiểu khác nhau.Tutorial: why use generics Ý chính: một bug trước đây chỉ lộ ra trên production (ClassCastException) giờ hiện ngay trong editor của bạn.

2. Đọc và viết <T>

Đây là một generic class nhỏ theo phong cách của tutorial. T là chỗ trống; ai tạo Box sẽ quyết định cái gì được bỏ vào.

class Box<T> {
    private T item;
    void set(T item) { this.item = item; }
    T get()          { return item; }
}

Box<Integer> b = new Box<>();
b.set(7);
int n = b.get();
Bước 1  Box<Integer>: compiler đọc mọi chữ T thành Integer
Bước 2  b.set(7) được kiểm tra: 7 là Integer → OK
Bước 3  b.get() được biết là trả về Integer → không cần cast
Bước 4  b.set("seven") sẽ là lỗi compile

Cách đặt tên. "Theo quy ước, tên type parameter là một chữ cái in hoa duy nhất": E cho Element (dùng khắp các collection), K cho Key, V cho Value, T cho Type, N cho Number.Tutorial: generic types Vậy Map<K, V> đọc là "một map từ key tới value".

Diamond <>. "Từ Java SE 7 trở đi", bạn có thể để trống ngoặc nhọn ở vế phải khi compiler suy ra được kiểu: new Box<>().Tutorial: generic types Nên cú pháp này chạy như nhau trên JDK 8, 17 và 21.

Bẫy: kiểu primitive không điền vào chỗ trống được

List<int> nums;        // compile error
List<Integer> nums;    // fix: use the wrapper class

Danh sách các giới hạn trong tutorial mở đầu bằng "Cannot Instantiate Generic Types with Primitive Types" (không thể dùng kiểu primitive cho generic type).Tutorial: restrictions on generics Java tự chuyển qua lại giữa int và Integer khi bạn add và get.

3. Quy tắc bất ngờ: không có quan hệ họ hàng

Quay lại nhà kho. Bạn có một hộp dán nhãn "Chỉ đựng táo". Một đồng nghiệp xin "một hộp trái cây". Táo là trái cây, nên bạn đưa hộp táo. Đồng nghiệp, đang cầm "hộp trái cây", bỏ một quả chuối vào. Với hộp trái cây thì việc đó hợp lệ! Giờ hộp táo của bạn có chuối, và người tiếp theo lấy ra "một quả táo" sẽ nhận được chuối.

Java chặn câu chuyện này ngay từ cửa. Tutorial viết: "Mặc dù Integer là subtype của Number, List<Integer> không phải là subtype của List<Number> và thực ra hai kiểu này không hề liên quan."Tutorial: generics and subtyping Nếu được phép, bạn có thể add một Double qua reference List<Number> vào thứ mà thật ra là List<Integer>, phá vỡ type safety.Tutorial: generics and subtyping

Thử xem. Trong ví dụ, dòng này bị comment lại vì nó không compile được:

List<Integer> ints = new ArrayList<>(List.of(1, 2, 3));
// List<Number> nums = ints;   // compile error

Nếu bạn bỏ //, javac của JDK 21 báo:

error: incompatible types: List<Integer> cannot be converted to List<Number>

Interviewer gọi quy tắc này là invariance (tính bất biến về kiểu): một generic type không đi theo cây gia phả của type argument. Integer → Number là một quan hệ; List<Integer> → List<Number> thì không.

Nhưng chỉ đọc thì không sao: một method chỉ đọc số thì nên nhận được list số nguyên. Đó là việc của wildcard (? extends Number), ở bài 0021.

4. Mảng thì chọn cách ngược lại

Mảng có trước generic, và mảng có đi theo cây gia phả: một Integer[] dùng được như Number[]. JLS nói một biến như vậy "có thể giữ reference tới một instance của bất kỳ kiểu mảng B[] nào, miễn B gán được cho A", và cảnh báo: "Điều này có thể gây ra một exception lúc chạy ở một phép gán sau đó".JLS §10.2 Exception đó là ArrayStoreException.JLS §10.5

Number[] arr = new Integer[3];   // compiles
arr[0] = 3.14;                   // ArrayStoreException at run time

Một cách nói hay trong interview: invariance giúp generic bắt bug "chuối trong hộp táo" ngay lúc compile, khi sửa còn rẻ, thay vì lúc chạy, khi nó đã thành sự cố production.

Luyện tập

Trả lời theo trí nhớ, đừng cuộn lên. Thứ tự đáp án thay đổi mỗi lần bạn mở trang.

List<Integer> có phải subtype của List<Number> không?

Generic type là invariant: "List<Integer> không phải là subtype của List<Number>" (Java Tutorials).

Vì sao Java từ chối List<Number> nums = ints;?

Cho phép thì sẽ phá vỡ type safety: chính là chuyện "chuối trong hộp táo".

Đâu là một trong ba lợi ích của generic theo tutorial?

Ba lợi ích: kiểm tra lúc compile chặt hơn, không cần cast, và thuật toán generic.

Đoạn này in ra gì hoặc làm gì? Number[] a = new Integer[1]; a[0] = 1.5;

Mảng là covariant nên phép gán compile được; việc lưu được kiểm tra lúc chạy và hỏng (JLS §10.5).

List<int> scores = new ArrayList<>(); sai ở đâu?

"Cannot Instantiate Generic Types with Primitive Types" là giới hạn đầu tiên trong tutorial.

Với List<String> list, vì sao bạn viết được String s = list.get(0); mà không cần cast?

Type argument cho compiler biết get trả về gì, nên không cần cast nữa.

Bài kiểm tra cuối: nói trong 60 giây

Interviewer hỏi: "Generic dùng để làm gì, và List<Integer> có phải là List<Number> không?" Bấm giờ. Trả lời thành tiếng, nói thành câu đầy đủ. Rồi bấm nút.

Chỉ tick những ý bạn thật sự đã nói:

Câu trả lời mẫu

"Generic cho phép một class như List nhận type parameter, nên em viết List<String> và compiler biết bên trong chứa gì. Có ba lợi ích: lỗi kiểu bị bắt lúc compile, không cần cast, và viết được thuật toán dùng cho nhiều kiểu. Còn List<Integer> có phải List<Number> không? Không, dù Integer là Number. Hai kiểu list này không liên quan gì nhau; generic là invariant. Nếu Java cho phép, em có thể lấy list số nguyên, nhìn nó như list Number, rồi add một Double vào. Lúc đó code nào đọc Integer ra sẽ crash. Mảng thì thật ra cho phép chuyện này, và hỏng lúc chạy với ArrayStoreException; generic thì chọn báo lỗi ngay lúc compile. Nếu em chỉ cần đọc số từ list kiểu đó, em dùng wildcard: List<? extends Number>."
