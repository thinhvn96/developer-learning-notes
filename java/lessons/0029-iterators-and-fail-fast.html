Why removing items in a loop crashes

Iterators, fail-fast checks and ConcurrentModificationException, with no threads involved.

Java (JDK 8, 17, 21) · Lesson 0029 · step 8 of 46 · Foundation · ~20 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? "Remove the inactive users from this list" is an everyday task, and the first version most people write crashes. Interviewers love the follow-up: "Can you get a ConcurrentModificationException with only one thread?" After this lesson you can say yes, explain why, and show three correct ways.
Today's win: explain why a single thread can get ConcurrentModificationException, and remove elements while looping the three correct ways.
collection
An object that holds a group of other objects, like a List, a Set or the keys of a Map.
iterator
A small helper object that walks through a collection one element at a time. It has hasNext() ("is there another one?") and next() ("give me the next one").
for-each loop
The short loop for (String n : names). Behind the scenes Java creates an iterator and calls hasNext() and next() for you.
structural change
A change to the shape of a collection: adding or removing elements. Replacing one value with another is not structural.
modCount
A counter inside ArrayList and HashMap that goes up by one on every structural change. Think of it as a version number.
fail-fast
An iterator that stops with an exception as soon as it notices the collection changed under it, instead of continuing with wrong data.
exception
An error object that Java "throws" to stop normal work. If nobody catches it, the program stops and prints it.

Before you start

Predict, out loud: this list is [ann, bob, cid, dan]. What happens when you run for (String n : names) if (n.startsWith("b")) names.remove(n);? Does it print, crash, or skip something? Commit to an answer; you will check it in section 2.

1. The picture: a teacher reading the attendance list

A teacher reads names from an attendance sheet, moving a finger down one line at a time. At the top of the sheet there is a small version number. Every time the office adds or crosses out a name, they increase it.

The careful teacher notes the version number before starting. Before reading each next name, she checks it again. If the number changed, someone edited the sheet while she was reading, and her finger may now point at the wrong line. So she stops and says "the list changed!" instead of reading wrong names.

That is exactly a fail-fast iterator:

  • The sheet is the ArrayList.
  • The version number is its modCount field. In ArrayList (via AbstractList), every structural change increments it.
  • The finger is the iterator. It remembers the number as expectedModCount and checks it on each next(): if (modCount != expectedModCount) throw new ConcurrentModificationException();ArrayList.java

The name misleads: it is not about threads

"Concurrent" sounds like "two threads". But the Javadoc says: "this exception does not always indicate that an object has been concurrently modified by a different thread ... if a thread modifies a collection directly while it is iterating over the collection with a fail-fast iterator, the iterator will throw this exception."CME javadoc One thread is enough.

2. Trace the crash, step by step

A for-each loop is just an iterator. The Java Language Specification defines for (T x : collection) as a loop that calls iterator(), then hasNext() and next().JLS 14.14.2 So list.remove(x) inside it bumps modCount behind the iterator's back.

List<String> names = new ArrayList<>(List.of("ann", "bob", "cid", "dan"));
for (String n : names) if (n.startsWith("b")) names.remove(n);

Step 1  iterator created            expectedModCount = 0, cursor = 0
Step 2  next() → "ann"              check 0 == 0 ✓, cursor = 1
Step 3  next() → "bob"              check 0 == 0 ✓, cursor = 2
Step 4  names.remove("bob")         modCount = 1, size = 3
Step 5  hasNext(): cursor 2 != size 3 → true
Step 6  next(): check 1 == 0 ✗          → ConcurrentModificationException

In the OpenJDK source, hasNext() is simply return cursor != size; and next() runs the check first.ArrayList.java Keep that in mind: it explains the trap in the next section.

Here is the real output of the runnable example. Line 1 is the crash you just traced:

$ java java/examples/collections/IteratorsAndFailFast.java
1. for-each + list.remove        -> ConcurrentModificationException
2. remove 2nd-to-last in for-each -> no exception, list=[ann, cid]  (loop silently skipped 'cid')
3. Iterator.remove()              -> [ann, cid, dan]
4. removeIf (JDK 8)               -> [ann, cid, dan]
5. ListIterator set + add         -> [ANN, ann!, BOB, bob!]
6. entry.setValue while iterating -> {a=10, b=20}
7. map.put new key while iterating -> ConcurrentModificationException

3. The trap: sometimes it does not crash

Look at line 2. Same mistake, but the list is [ann, bob, cid] and you remove bob, the second-to-last element. No exception. But cid was never visited.

List<String> tricky = new ArrayList<>(List.of("ann", "bob", "cid"));
for (String n : tricky) if (n.equals("bob")) tricky.remove(n);

Step 1  next() → "ann"                cursor = 1
Step 2  next() → "bob"                cursor = 2
Step 3  tricky.remove("bob")          size = 2, modCount = 1
Step 4  hasNext(): cursor 2 != size 2 → false
        → loop ends, no check ever runs

This is the interview trap: removing the second-to-last element shrinks the size so hasNext() returns false before the check runs. No exception, and the last element was never visited. A bug that does not crash.

That is why the Javadoc calls fail-fast "best-effort": "it would be wrong to write a program that depended on this exception for its correctness".CME javadoc The exception is a bug detector, not a guarantee.

4. The correct ways

Back to the teacher: if she crosses out a name herself, she knows about it and updates her note. Only edits made by someone else confuse her. In Java, "she" is the iterator.

Way 1: Iterator.remove()

for (Iterator<String> it = a.iterator(); it.hasNext(); )
  if (it.next().startsWith("b")) it.remove();   // [ann, cid, dan]

This is the only removal the iterator knows about. In the source, Itr.remove() removes the element, moves the cursor back and sets expectedModCount = modCount, so the next check passes.ArrayList.java HashMap's views are fail-fast "in any way except through the iterator's own remove method".HashMap javadoc

Way 2: removeIf (JDK 8+)

b.removeIf(n -> n.startsWith("b"));             // [ann, cid, dan]

One call, no iterator in your code. n -> n.startsWith("b") is a lambda: a tiny function that answers "remove this one?". On ArrayList it compacts in one pass instead of shifting the array after every removal. This is the version to write in an interview.

Way 3: ListIterator to change while walking

for (ListIterator<String> it = c.listIterator(); it.hasNext(); ) {
  String n = it.next();
  it.set(n.toUpperCase());   // replace the current element
  it.add(n + "!");           // insert after it
}                            // [ANN, ann!, BOB, bob!]

A ListIterator can also set and add while walking a list.

Maps: values yes, keys no

  • Changing a value (entry.setValue) is not structural, so it is allowed (line 6 of the output).
  • Adding or removing keys is structural, so map.put(newKey, ...) inside a key loop throws (line 7).

Two more options: collect the items into a new list and change the original after the loop, or use a concurrent collection if other threads modify it (lesson 0039).

JDK 8 vs 17 vs 21

The fail-fast rules are the same in all three. The difference is style: removeIf exists since JDK 8, so on any modern codebase it is the default answer.

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

Can a program with only one thread get a ConcurrentModificationException?

Modifying a collection directly while iterating it with a fail-fast iterator throws it, even in one thread.

What does the fail-fast iterator compare on every next()?

Every structural change bumps modCount. The iterator remembered the old value; if they differ, it throws.

The list is [ann, bob, cid]. A for-each loop calls list.remove("bob"). What happens?

After the remove, size is 2 and the cursor is 2, so hasNext() is false and the check never runs. A silent bug.

Is fail-fast detection guaranteed?

The Javadoc says it would be wrong to write a program that depends on this exception for its correctness.

Which removal is safe inside an explicit iterator loop?

The iterator's own remove updates expectedModCount, so the next check still passes.

You loop over map.entrySet() and call entry.setValue(v * 10). What happens?

Only adding or removing keys changes the structure. Line 6 of the run prints {a=10, b=20}.

The final test: say it in 60 seconds

An interviewer asks: "What is a ConcurrentModificationException, and how do you remove items from a list while looping?" Start a timer. Answer out loud, in full sentences. Then click the button.

Tick only the points you really said:

Example answer

"Despite the name, it's usually not about threads. If I call list.remove inside a for-each loop, I get it in a single thread, because for-each uses an iterator. The list keeps a modCount that goes up on every add or remove, and the iterator remembers the value it started with. On each next() it compares them and throws if they differ. It's best-effort only: if I remove the second-to-last element, the size shrinks, hasNext() returns false, and the last element is silently skipped. So the right way is removeIf, or Iterator.remove(), or a ListIterator if I also need to replace or insert. Changing a map value with setValue is fine, because it's not a structural change."
