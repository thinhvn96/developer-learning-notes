Which collections remember order, and an LRU cache in ten lines

HashSet is secretly a HashMap, and LinkedHashMap can become a cache.

Java (JDK 8, 17, 21) · Lesson 0033 · step 14 of 46 · Core · ~22 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? "Why does my set print in a strange order?" is a common surprise, and "Implement an LRU cache" is a classic interview task. Java gives you the cache almost for free, if you know one constructor flag and one method to override.
Today's win: explain how HashSet is built, choose between HashSet, LinkedHashSet and TreeSet by ordering need, and build an LRU cache in ten lines.
Set
A collection with no duplicates. Adding something that is already there does nothing.
iteration order
The order in which a loop (or println) visits the elements.
doubly linked list
A chain where each item points to the one before it and the one after it, so you can unlink an item quickly.
cache
A small, fast store of recent results, so you don't recompute or refetch them. It has a size limit.
LRU
"Least recently used": when the cache is full, throw away the item that nobody has touched for the longest time.
eviction
Removing an item from a cache to make room for a new one.
extends, override
class A extends B makes A a child class of B; A can then override (replace) some of B's methods.

Before you start

Predict: a cache holds at most 3 items. You put a, b, c, then get(a), then put(d). Which key gets thrown out? Say it out loud with the reason. Section 3 traces it.

1. HashSet is a HashMap in disguise

Imagine a hotel guest list kept in the hotel's key-card system: each guest name is a card key, and the "value" on every card is the same blank sticker. You only care whether the name is there. That is HashSet.

"This class implements the Set interface, backed by a hash table (actually a HashMap instance)."HashSet javadoc Each element is a key whose value is a shared dummy object. In the OpenJDK source it is literally:HashSet.java

static final Object PRESENT = new Object();

public boolean add(E e) {
    return map.put(e, PRESENT)==null;   // true if the key was new
}

So everything from HashMap internals applies: constant-time add/contains "assuming the hash function disperses the elements properly", one null allowed, and "no guarantees as to the iteration order ... in particular, it does not guarantee that the order will remain constant over time".HashSet javadoc The order you see is just the bucket order from lesson 0030, and a resize can change it.

2. Linked variants keep insertion order

Now picture the same hotel, plus a paper guest book at the reception: every new guest signs at the bottom. The key-card system still finds a guest fast; the guest book remembers who came first.

LinkedHashMap adds a doubly linked list through the entries. Its encounter order is "normally the order in which keys were inserted"; re-inserting a key with put does not move it.LinkedHashMap javadoc In the source each entry gets two extra fields, before and after, and the map keeps head (oldest) and tail (newest).LinkedHashMap.java LinkedHashSet is the same idea for sets.

$ java java/examples/collections/LruCache.java
insertion order (re-put 'a' keeps its place): {c=3, a=10, b=2}
HashSet: [java, kafka, redis, docker, sql]   LinkedHashSet: [kafka, java, docker, sql, redis]

Both sets got kafka, java, docker, sql, redis in that order. The HashSet prints bucket order; the LinkedHashSet prints the order you added them.

A bonus: iteration costs time proportional to size, while a plain HashMap's iteration is proportional to capacity.LinkedHashMap javadoc

3. Access order and the LRU cache

Change the guest book rule: every time a guest uses the bar, they cross out their line and sign again at the bottom. Now the top line is always the guest who has been quiet the longest. When the hotel is full, that is who you ask to leave. That is an LRU cache.

A special constructor LinkedHashMap(initialCapacity, loadFactor, accessOrder) orders entries from least to most recently accessed: "This kind of map is well-suited to building LRU caches."LinkedHashMap javadoc get, put, getOrDefault, the compute* methods and merge count as access.LinkedHashMap javadoc Then override removeEldestEntry, which "is invoked by put and putAll after inserting a new entry".LinkedHashMap javadoc

class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;
    LruCache(int capacity) {
        super(16, 0.75f, true);       // accessOrder = true
        this.capacity = capacity;
    }
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;      // true = drop the eldest
    }
}

Line by line: extends LinkedHashMap reuses the whole map. super(16, 0.75f, true) calls the parent constructor with access order switched on. removeEldestEntry is asked after every insert; returning true removes the head of the chain, the least recently used entry.

Trace it with capacity 3

                          chain: eldest → newest
Step 1  put a, b, c       [a, b, c]           size 3, nothing to evict
Step 2  get(a)            [b, c, a]           a moves to the end
Step 3  put d             [b, c, a, d]        size 4 > 3 → evict b
                          [c, a, d]
Step 4  put e             [c, a, d, e]        size 4 > 3 → evict c
                          [a, d, e]

The real run agrees:

LRU after get(a), put(d): [c, a, d]     // b was least recently used
LRU after put(e):         [a, d, e]

Two senior-level caveats

  • Threads. In access-order mode "merely querying the map with get is a structural modification", so even reads need a lock when threads share it; wrap with Collections.synchronizedMap or use a cache library (Caffeine) in production.LinkedHashMap javadoc This also means a get inside a loop over the map is a structural change (lesson 0029).
  • JDK 21. A LinkedHashMap is a SequencedMap, so putFirst/putLast and reversed() also exist (lesson 0016). On JDK 8 and 17 they do not.

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

What is inside a HashSet?

HashSet is "backed by a hash table (actually a HashMap instance)". Each element is a key; the value is the shared PRESENT object.

You add five words to a HashSet and print it. Which statement is true?

HashSet gives "no guarantees as to the iteration order", not even that it stays constant. Use LinkedHashSet for insertion order.

In a normal (insertion-order) LinkedHashMap, you put("a", 10) when a is already there. Where is a now?

Insertion order "is not affected if a key is re-inserted". The run printed {c=3, a=10, b=2}.

Which constructor argument turns a LinkedHashMap into access order?

The three-argument constructor LinkedHashMap(int, float, boolean accessOrder).

An LRU cache of size 3 gets put a, b, c, then get(a), then put(d). Which key is evicted?

get(a) moved a to the end, so the chain is [b, c, a]. b is the head: least recently used.

When does LinkedHashMap call removeEldestEntry?

It "is invoked by put and putAll after inserting a new entry". Returning true removes the eldest entry.

Two threads share your access-order LruCache but only call get. Why is that still unsafe?

In access-order mode "merely querying the map with get is a structural modification". Use a lock or a cache library such as Caffeine.

The final test: say it in 60 seconds

An interviewer asks: "How would you implement an LRU cache in Java?" Start a timer. Answer out loud, in full sentences. Then click the button.

Tick only the points you really said:

Example answer

"In Java I'd extend LinkedHashMap. It's a HashMap plus a doubly linked list through the entries. Normally the list keeps insertion order, but if I call the constructor with accessOrder set to true, every get or put moves that entry to the end, so the head is always the least recently used one. Then I override removeEldestEntry to return size() > capacity; the map calls it after each insert and removes the head when I return true. Lookups stay O(1) on average. The catch is concurrency: in access order even get modifies the list, so if threads share it I'd need a lock, and in production I'd rather use a library like Caffeine. If they want it from scratch, it's the same idea: a HashMap from key to node, plus my own doubly linked list."
