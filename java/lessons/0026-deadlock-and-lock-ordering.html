When two threads wait for each other forever: deadlock

How it happens, how to find it in a running JVM, and the one rule that prevents it.

Java (JDK 8, 17, 21) · Lesson 0026 · step 34 of 46 · Advanced · ~22 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? A deadlocked service does not crash and does not log an error: it just stops answering, and CPU stays low. Knowing how to spot and prevent one is a classic Senior question: "What is a deadlock? How would you find one in production? How do you avoid it?"
Today's win: explain how a lock-ordering deadlock arises, detect it with ThreadMXBean, and prevent it.
lock / monitor
Something only one thread can hold at a time. Every Java object has a built-in one, the monitor, used by synchronized.
blocked
A thread that is waiting to get a lock and cannot do anything else until it gets it.
deadlock
Threads that each hold a lock and wait for a lock another one of them holds, in a circle, so none can ever continue.
lock ordering
A rule that every thread takes several locks in the same fixed order, for example always A before B.
thread dump
A text snapshot of every thread in a running JVM: what it is doing, which locks it holds and which it waits for.
jstack
A JDK command-line tool that prints a thread dump of a running Java process.

Before you start

Say out loud: "Thread 1 locks A, then B. Thread 2 locks B, then A. Can this freeze? Under which timing?" Try to describe the exact moment it gets stuck. Section 2 traces it.

1. The picture: two people, two keys

Two colleagues need two things to do their job: the meeting room key and the projector. Anna takes the room key and goes to get the projector. Ben already took the projector and goes to get the room key. Anna waits for Ben's projector. Ben waits for Anna's key. Nobody gives anything back, because nobody has finished. They wait forever.

The Oracle tutorial's definition: "Deadlock describes a situation where two or more threads are blocked forever, waiting for each other."Java tutorial: deadlock Its example: two friends bow to each other and each must stay bowed until the other bows back, with both methods synchronized.Java tutorial: deadlock

2. Reproduce it

The example DeadlockDemo.java starts two threads with opposite lock orders. The key part:

synchronized (first) {               // T1: first = A    T2: first = B
    bothHoldFirst.countDown();       // "I have my first lock"
    bothHoldFirst.await();           // wait until the other one has its first lock too
    synchronized (second) {          // T1: second = B   T2: second = A
        System.out.println(name + " got both locks");
    }
}

The CountDownLatch just forces the bad timing every time, so the demo is reliable. Trace:

Step 1  T1 locks A                 T2 locks B
Step 2  both pass the latch: each knows the other holds its first lock
Step 3  T1 asks for B → B is held by T2 → T1 blocks
Step 4  T2 asks for A → A is held by T1 → T2 blocks
Step 5  neither block ever ends: "got both locks" is never printed

In real code there is no latch; the bad timing just happens now and then, under load. That is why deadlocks show up in production and not in tests.

$ java java/examples/DeadlockDemo.java
--- opposite lock order (A then B, B then A)
deadlocked threads detected: 2
--- same lock order everywhere (A then B)
T5 got both locks
T6 got both locks

The two stuck threads are daemon threads, so the program can still exit at the end. A normal (non-daemon) deadlocked thread would keep the JVM running forever.

3. Detect it

From inside the program: ThreadMXBean

The demo calls ManagementFactory.getThreadMXBean().findDeadlockedThreads(), which returns the stuck threads. The Javadoc: it "Finds cycles of platform threads that are in deadlock waiting to acquire object monitors or ownable synchronizers" (that is, synchronized and locks like ReentrantLock). It returns the thread IDs, or "null otherwise", so check for null.ThreadMXBean javadoc It "is designed for troubleshooting use, but not for synchronization control. It might be an expensive operation." In JDK 21, "Cycles that include virtual threads are not found by this method."

From outside: a thread dump

In production you usually take a thread dump with jstack <pid>; it reports deadlocks too. Here is the real end of a dump from a small program with the same A/B, B/A pattern (addresses shortened):

$ jstack 13046
...
Found one Java-level deadlock:
=============================
"T1":
  waiting to lock monitor 0x...1920 (object 0x...e8e8, a java.lang.Object),
  which is held by "T2"

"T2":
  waiting to lock monitor 0x...0f60 (object 0x...e8d8, a java.lang.Object),
  which is held by "T1"
...
Found 1 deadlock.

Read it as the diagram: T1 waits for something held by T2, and T2 waits for something held by T1. The dump also shows the exact source lines, so you know which code to fix.

4. Prevent it

Rule 1: one global lock order

If every thread takes A before B, the circle cannot close: whoever gets A first will also get B; the other thread simply waits for A, then continues. The demo's second part (T5, T6) does exactly this and both threads finish.

A classic case is a money transfer, transfer(from, to). One thread transfers from X to Y while another transfers from Y to X: opposite orders. The fix is to order by something stable, like the account ID:

Account first  = a.id() < b.id() ? a : b;   // always the smaller ID first
Account second = a.id() < b.id() ? b : a;
synchronized (first) {
    synchronized (second) {
        // move the money
    }
}

The same advice appears for databases: PostgreSQL's docs say the best defense is to "acquire locks on multiple objects in a consistent order across all applications", and it detects deadlocks and aborts one transaction, so applications should be prepared to retry.PostgreSQL: explicit locking See PostgreSQL locking.

Rule 2: don't wait forever

With a ReentrantLock (from the previous lessons), tryLock(timeout, unit) "Acquires the lock if it is not held by another thread within the given waiting time".ReentrantLock javadoc If it returns false, release what you hold, wait a little, and try again. A synchronized block cannot do this: it waits forever.

Rule 3: hold fewer locks, for less time

Other prevention tools: holding fewer locks, and not calling foreign code while holding a lock (a callback, a listener, a remote call), because you cannot know which locks that code takes. This is general practice, not from the tutorial.

T1 runs synchronized(A){ synchronized(B){…} }. T2 runs synchronized(B){ synchronized(A){…} }. What can happen?

It deadlocks only with bad timing: T1 holds A and T2 holds B at the same moment. That is why it is rare in tests and appears under load.

What is the most reliable way to prevent a lock-ordering deadlock?

With one global order, a thread that waits holds nothing the other needs, so a cycle cannot form.

Which API can find deadlocked threads from inside the JVM?

findDeadlockedThreads() finds cycles of platform threads waiting on monitors or ownable synchronizers, and returns null if there are none.

Example answer

"A deadlock is when two or more threads are blocked forever, each waiting for a lock another one holds. The classic case is lock ordering: one thread takes A then B, another takes B then A; if each grabs its first lock at the same time, they wait for each other forever. It depends on timing, so it often only shows up under production load. To detect it, I take a thread dump with jstack; the JVM prints 'Found one Java-level deadlock' with the threads and the source lines. From code, ThreadMXBean.findDeadlockedThreads does the same check. To prevent it, I make every code path take locks in one global order, for example by account ID in a transfer. Where that's hard, I use ReentrantLock.tryLock with a timeout and back off, hold as few locks as possible, and never call unknown code while holding a lock. Databases have the same problem; PostgreSQL aborts one transaction, so the application should retry."
