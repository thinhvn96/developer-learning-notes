Deadlock and lock ordering

Java (JDK 8, 17, 21) · Lesson 0026 · step 17 of 27 · Advanced · ~10 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap

Today's win: explain how a lock-ordering deadlock arises, detect it with ThreadMXBean, and prevent it.

Definition

"Deadlock describes a situation where two or more threads are blocked forever, waiting for each other."[1] The tutorial's example: two friends bow to each other and each must stay bowed until the other bows back, with both methods synchronized.[1]

Reproduce, detect, fix

java java/examples/DeadlockDemo.java
--- opposite lock order (A then B, B then A)
deadlocked threads detected: 2
--- same lock order everywhere (A then B)
T5 got both locks
T6 got both locks

ManagementFactory.getThreadMXBean().findDeadlockedThreads() returns the stuck threads; a thread dump (jstack) reports them too. The fix in the demo is a consistent lock order.

The same advice appears for databases: PostgreSQL's docs say the best defense is to "acquire locks on multiple objects in a consistent order across all applications", and it detects deadlocks and aborts one transaction, so applications should be prepared to retry.[2] Source: DeadlockDemo.java; see PostgreSQL locking.

Other prevention tools: tryLock with a timeout (from the previous lesson), holding fewer locks, and not calling foreign code while holding a lock (general practice, not from the tutorial).

Retrieval practice

Answer from memory. One attempt each.

1. Definition of deadlock?

Two or more threads blocked forever waiting for each other.[1]

2. Most reliable prevention?

Acquire locks in the same order everywhere.[2]

3. Which API detects deadlocked threads?

findDeadlockedThreads on ThreadMXBean (shown in the demo).

4. Database reports a deadlock. What should code do?

PostgreSQL aborts one transaction; handle by retrying.[2]
