var and text blocks: less typing, same types

Two small JDK 10 and JDK 15 features you will see in every modern Java codebase.

Java (JDK 8, 17, 21) · Lesson 0012 · step 37 of 46 · Core · ~20 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? When a team moves from JDK 8 to 17 or 21, var and text blocks appear in code reviews on day one. Interviewers like to ask "Does var make Java dynamically typed?" The answer is no, and this lesson shows you why.
Today's win: rewrite a JDK 8 local variable and a JDK 8 multi-line JSON string with var and a text block, and name four places where var is not allowed.
local variable
A variable declared inside a method. It lives only while that method runs.
initializer
The value after the = sign when you declare a variable: in int n = 5; the initializer is 5.
type inference
The compiler works out a type by itself, by looking at the code around it, so you don't have to write it.
static typing
Every variable has one fixed type, checked when you compile. Java has always worked this way.
compiler (javac)
The program that turns your .java file into bytecode before it runs. Many mistakes are caught here.
escape sequence
A backslash code inside a string, like \n (new line) or \" (a quote character).
string literal
Text written directly in code between quotes, like "hello".

Before you start

Say out loud: "After var x = "hi";, can I write x = 42; on the next line?" Commit to yes or no and give a reason. You will check your answer in section 2.

1. var: let the compiler copy the type for you

Think of a form at the bank. One box says "Name", and the next box says "Name again, for the receipt". Writing the same thing twice is boring, and it adds nothing. The clerk could copy it for you.

JDK 8 code is often like that form. The type is written on the left, and the same type is written again on the right:

// JDK 8: the type appears twice
ArrayList<String> names = new ArrayList<String>();
Map<String, List<Order>> byCustomer = new HashMap<String, List<Order>>();

// JDK 10+: the compiler copies the type from the right side
var names = new ArrayList<String>();
var byCustomer = new HashMap<String, List<Order>>();

JEP 286, delivered in JDK 10, was written to "extend type inference to declarations of local variables with initializers".JEP 286 In plain words: if a local variable has an initializer, you may write var and the compiler fills in the type. JDK 17 and 21 include it, because each release keeps everything from the releases before it.

2. Follow the compiler, step by step

var names = new ArrayList<String>();
Step 1  javac reads the right side: new ArrayList<String>()
Step 2  its type is ArrayList<String>
Step 3  javac gives names that type, for ever: ArrayList<String> names

names.add("ann");   // fine
names.add(42);      // compile error: 42 is not a String
names = "hello";    // compile error: a String is not an ArrayList

So the answer to "Before you start" is no. After var x = "hi"; the variable x is a String, and x = 42; does not compile. JEP 286's own example is var list = new ArrayList<String>();, which "infers ArrayList<String>".JEP 286 Java stays statically typed; var only saves typing.

Notice the type is ArrayList<String>, not List<String>. The compiler copies the exact type on the right.

Where var is not allowed

var works for local variables with an initializer and for the index of a for loop. It does not work for method parameters, constructor parameters, return types, fields or catch parameters, and not for a variable without an initializer.JEP 286 The JEP also says that an initializer of the null type is an error, and that an array initializer or a lambda will "trigger an error", because there is no type on the right to copy.JEP 286 I ran all four through javac 21:

var x = null;
  error: cannot infer type for local variable x
    (variable initializer is 'null')
var y;
    (cannot use 'var' on variable without initializer)
var a = {1, 2};
    (array initializer needs an explicit target-type)
var f = () -> 1;
    (lambda expression needs an explicit target-type)

A fun detail: "The identifier var is not a keyword; instead it is a reserved type name."JEP 286 That is why old code with a variable called var still compiles. In JDK 11 you may also write var on lambda parameters, mainly so you can put annotations on them: (@Nonnull var x, @Nullable var y) -> x.process(y).JEP 323

Trap: var with the diamond <>

var list = new ArrayList<>();   // ArrayList<Object>, not what you wanted
list.add(1);
list.add("a");                   // compiles: anything goes in

The diamond <> normally takes its type from the left side. With var the left side is empty, so the compiler has nothing to copy. The OpenJDK style guide marks this exact case "DANGEROUS: infers as PriorityQueue<Object>".LVTI style guide The same guide warns about number literals: with var, 17 becomes an int, even if you meant a long.LVTI style guide

The fix: with var, always write the type argument on the right (new ArrayList<String>()), and use var only when the right side makes the type obvious to a reader.

3. Text blocks: paste the text as it looks

Imagine copying a poem by hand, but every line break must be written as the word "NEWLINE" and every quote mark as "QUOTE". You would make mistakes, and nobody could read the result. That is a JSON string in JDK 8:

// JDK 8: escapes and + everywhere
String json = "{\n" +
              "  \"name\": \"orders\",\n" +
              "  \"port\": 8080\n" +
              "}\n";

// JDK 15+: a text block
var json = """
        {
          "name": "orders",
          "port": 8080
        }
        """;

JEP 378 defines it: "A text block is a multi-line string literal that avoids the need for most escape sequences, automatically formats the string in a predictable way, and gives the developer control over the format when desired."JEP 378 It became final in JDK 15, after previews in JDK 13 and 14.JEP 378

The rules you need:

  1. It opens with """ followed by a line break. Text on the same line as the opening """ is not allowed.JEP 378
  2. Double quotes inside need no escaping.
  3. The indentation that all lines share is stripped, and trailing spaces at the end of each line are removed.JEP 378
  4. The result is a normal String: the JEP calls it "a constant expression of type String, just like a string literal".JEP 378

4. How the compiler cleans a text block

JEP 378 processes the content in three steps.JEP 378 Follow them on the example above:

Step 1  Line breaks become \n, whatever your editor used (Windows \r\n too).
Step 2  Find the smallest indentation of the non-blank lines and of the
        closing """ line: 8 spaces. Remove 8 spaces from every line.
        Remove trailing spaces at the end of each line.
Step 3  Turn escape sequences like \n, \t, \s into real characters.
Result  "{\n  \"name\": \"orders\",\n  \"port\": 8080\n}\n"

The opening """ has no effect on the indentation, "but the position of the closing """ characters does have an effect if placed on its own line".JEP 378 Move it left and you keep some indentation. I ran both versions:

String t1 = """
        <p>
          hi
        </p>
        """;               // closing """ in line with <p>

String t2 = """
        <p>
          hi
        </p>
    """;                   // closing """ 4 columns further left

t1 prints:
<p>
  hi
</p>
t2 prints:
    <p>
      hi
    </p>

Also: when the closing """ is on its own line, the string ends with a \n. Put it right after the last word if you don't want that final newline.JEP 378

Two new escapes and one new method

Two escapes arrived with the feature. \<line-terminator> (a backslash at the very end of a line) "explicitly suppresses the insertion of a newline character", and \s "simply translates to a single space".JEP 378 \s is useful because trailing spaces are otherwise removed. The JEP also added String::formatted(Object... args) to fill in values:JEP 378

String sql = """
    SELECT id, name \
    FROM users""";                       // "SELECT id, name FROM users" on one line
String hi = """
    Hello, %s!""".formatted("Ann");       // "Hello, Ann!"

Run the real example

The course example uses var, a text block and a switch expression (next lesson). It compiles with --release 17:

$ java java/examples/jdk17/Jdk17Features.java
{
  "name": "orders",
  "port": 8080
}
weekend, weekday, invalid: 9
3.14 4.00 6.00

The first four lines come from the text block: the 16 spaces of source indentation are gone, and only the 2 spaces you meant are left.

JDK 8 to 17 migration note: neither feature exists on JDK 8. Code using them compiles only at --release 10+ (var) or --release 15+ (text blocks). If your library must still run on JDK 8, you cannot use them there.

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

After var x = "hi";, what happens with x = 42;?

The compiler fixes the type of x to String from its initializer. Java stays statically typed; var only saves typing.

Where is var allowed?

var is for local variables with initializers and for-loop indexes. Not for parameters, fields, return types or catch parameters.

What is the bug in var ids = new ArrayList<>(); ids.add("x"); when you meant a list of Long?

With var there is no left side for the diamond to copy from, so it falls back to Object. Write new ArrayList<Long>().

Which line is a valid start of a text block?

The opening """ must be followed by a line break; the content starts on the next line.

You move the closing """ of a text block four columns to the left. What changes?

The closing delimiter on its own line takes part in finding the shared indentation. Further left means less is stripped.

In which release did text blocks become a final (non-preview) feature?

Text blocks were previews in 13 and 14 and final in 15. var came earlier, in JDK 10.

The final test: say it in 60 seconds

An interviewer asks: "What is var in Java, and does it make Java dynamically typed? Also, what are text blocks?" Start a timer. Answer out loud, in full sentences. Then click the button.

Tick only the points you really said:

Example answer

"var came in JDK 10. It's local-variable type inference: I write var and the compiler takes the type from the right side. It does not make Java dynamic. If I write var names = new ArrayList<String>(), names is an ArrayList<String> for ever, and assigning a number to it doesn't compile. It only works for local variables with an initializer and loop indexes, not for fields, parameters or return types, and not with null or a lambda, because there's no type to copy. One trap: var with the diamond gives ArrayList<Object>. I use it when the type is obvious from the right side. Text blocks are final since JDK 15: a multi-line string between triple quotes. I don't need \n or \", the compiler strips the common indentation, and the closing quotes decide how much. It's great for JSON, SQL and test data."
