happens-before
The rule that guarantees one thread sees another thread's write (lesson 0005).
lost update
Two threads read the same value and one write overwrites the other (lesson 0024).
check-then-act
Two safe calls with a gap between them where another thread can act (lesson 0025).
core / queue / max
The order in which a thread pool grows: core threads, then the queue, then extra threads (lesson 0023).
deadlock
Threads blocked forever, waiting for each other's locks in a circle (lesson 0026).
generations
Young and old parts of the heap, because most objects die young (lesson 0007).

1. The whole section on one page

Every lesson in this section answered one problem with one main tool. If you can rebuild this table from memory, you have the skeleton of every answer.

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

Four threads each run count++ 200,000 times on a volatile int. What do you expect?

count++ is read, add, write; volatile doesn't make it atomic, so updates are lost. See lesson 0024.

No heap flags, a machine with 16 GB of RAM. Roughly how large can the heap grow?

The default maximum heap is 1/4 of physical memory. See lesson 0007.

A pool has core 4, max 8 and a bounded queue with free space. All 4 core threads are busy. A task arrives. What happens?

The order is core → queue → max → reject. Extra threads start only when the queue is full. See lesson 0023.

Which of these creates a happens-before edge between two threads?

start() happens-before the started thread's actions. Sleeping or locking different objects gives no ordering. See lesson 0005.

A thread dump says: T1 "waiting to lock … which is held by T2", and T2 "waiting to lock … which is held by T1". What is it?

Each holds what the other wants: a cycle. Fix with one global lock order. See lesson 0026.

What does new ConcurrentHashMap<String, Integer>().put("a", null) do?

ConcurrentHashMap allows no null keys and no null values. See lesson 0025.

In Pause Young … 38M->3M(64M) 2.0ms, what does 3M mean?

Before → after (total heap), then pause time. 3M survived. See lesson 0007.

An AtomicInteger holds 7. A thread calls compareAndSet(6, 7). Result?

CAS writes only if the current value equals the expected one (6). It is 7, so nothing changes and the caller must retry. See lesson 0024.

Main writes config = load() (plain field), then ready = true (volatile). A worker sees ready == true. Is config guaranteed visible to it?

Happens-before is transitive: write config → write ready → read ready → read config. See lesson 0005.

Core 4, max 50, unbounded LinkedBlockingQueue. Under a huge load, how many threads run?

An unbounded queue never fills, so max has no effect. This is also the trap of newFixedThreadPool. See lesson 0023.

Two threads each run map.put(k, map.get(k) + 1) on a ConcurrentHashMap. Which fix is correct?

Each call is safe, but the get-then-put gap is not. merge does both atomically. See lesson 0025.

transfer(a, b) locks a then b. Two threads call transfer(x, y) and transfer(y, x). Best fix?

Opposite orders make a cycle possible. A stable global order (by ID) prevents it. See lesson 0026.

Why is a young-generation collection usually short?

Most objects die young; a minor GC pays for survivors, not for garbage. See lesson 0007.

2. Mixed task: find the bugs

Read this class slowly. It has at least three bugs, each from a different lesson. Write them down (line and lesson) before you open the answers.

class TrafficStats {
    private boolean running = true;                                   // line 2
    private final Map<String, Integer> hits = new ConcurrentHashMap<>();
    private final ExecutorService pool = Executors.newFixedThreadPool(8); // line 4

    void record(String page) {
        Integer old = hits.get(page);                                 // line 7
        hits.put(page, old == null ? 1 : old + 1);                    // line 8
    }

    void reporterLoop() {               // runs in its own thread
        while (running) { report(); }                                 // line 12
    }
    void stop() { running = false; }    // called from another thread

    void merge(Account a, Account b) {
        synchronized (a) {                                            // line 17
            synchronized (b) { a.add(b.drain()); }
        }
    }
}
Show the answers
  1. Line 2 and 12 (lesson 0005): running is a plain field written by one thread and read in a loop by another. There is no happens-before edge, so the reporter may never stop. Fix: private volatile boolean running.
  2. Lines 7 and 8 (lesson 0025): get-then-put on a ConcurrentHashMap is check-then-act; two threads can lose a hit. Fix: hits.merge(page, 1, Integer::sum).
  3. Line 17 (lesson 0026): the lock order depends on the argument order. merge(x, y) and merge(y, x) at the same time can deadlock. Fix: lock the account with the smaller ID first.
  4. Bonus, line 4 (lesson 0023): newFixedThreadPool uses an unbounded queue; under load tasks pile up until memory runs out. Fix: a ThreadPoolExecutor with a bounded queue and an explicit rejection policy. If it does fill the heap, the GC log from lesson 0007 shows the "after" value growing.

The final test: say it in 60 seconds

Three questions. Do them one at a time, each with its own timer.

Question 1: "Is volatile int count; count++ thread-safe? What does volatile actually guarantee?" Start a timer. Answer out loud, in full sentences. Then click the button.

Tick only the points you really said:

Example answer

"No, it isn't. volatile gives visibility and ordering: a write to a volatile field happens-before every later read of it, so readers see the newest value and everything written before it. But count++ is three steps, read, add one, write, and volatile doesn't glue them together, so two threads can read the same value and one increment is lost. I'd use an AtomicInteger, which does compare-and-set and retries if another thread got there first, or a lock if several fields must change together, with unlock in a finally block. For a very hot statistics counter, LongAdder scales better."

Question 2: "Under load, our service stops responding. Walk me through what you check." Start a timer. Answer out loud, in full sentences. Then click the button.

Tick only the points you really said:

Example answer

"First I take a thread dump with jstack, a few seconds apart. If the JVM prints 'Found one Java-level deadlock', I look at which locks each thread holds and fix the order so every path takes them in the same global order, or use tryLock with a timeout. If there's no deadlock, I check what the request threads are doing: if they're all waiting, I look at the thread pools, whether the queue is growing or tasks are being rejected; a newFixedThreadPool has an unbounded queue, so I'd switch to a bounded queue with an explicit rejection policy. In parallel I read the GC log: if pauses are long or full GCs repeat and the after-value keeps growing, live data is piling up, which is a leak or an unbounded cache, and I check that the heap size was set on purpose."

Question 3: "HashMap vs ConcurrentHashMap, and how does a thread pool decide what to do with a new task?" Start a timer. Answer out loud, in full sentences. Then click the button.

Tick only the points you really said:

Example answer

"HashMap isn't synchronized, so concurrent writes need external locking. ConcurrentHashMap makes every single call thread-safe, gets don't lock, it doesn't allow nulls, and its iterators are weakly consistent, so they never throw ConcurrentModificationException. But a get followed by a put can still lose updates, so I use merge or computeIfAbsent, which run atomically. Those maps are usually updated from a thread pool. When I submit a task, the pool starts a new thread if it has fewer than core threads; otherwise it queues the task; only when the queue is full does it add threads up to max; after that the task is rejected, and the default AbortPolicy throws. With an unbounded queue the max size never matters, which is why I prefer a bounded queue."
