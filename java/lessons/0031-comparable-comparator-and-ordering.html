How Java puts things in order

Comparable, Comparator, and why a TreeSet can silently lose an element.

Java (JDK 8, 17, 21) · Lesson 0031 · step 12 of 46 · Core · ~22 minutes · Home · Java (JDK 8, 17, 21) ladder · Roadmap · Tiếng Việt

Why this lesson? Sorting orders by price, showing employees by department, keeping a leaderboard in a TreeMap: ordering is everywhere. Interviewers ask "Comparable or Comparator?" and then the trap: "Why did my TreeSet lose an employee?" After this lesson you can answer both and write comparators that cannot overflow.
Today's win: write correct Comparators with Comparator.comparing chains, and explain why a TreeSet can silently lose elements.
compare result
Comparing a with b returns an int: negative means "a comes first", zero means "same place", positive means "b comes first".
Comparable<T>
An interface a class implements to give itself one built-in order, with the method compareTo. <T> is the type being compared.
natural ordering
That built-in order: numbers small to big, strings alphabetically, dates oldest first.
Comparator<T>
A separate object with a compare(a, b) method. You can make as many as you like: by price, by name, reversed.
method reference
A short way to write a lambda: Employee::salary means "take an employee, return its salary".
TreeSet, TreeMap
A set and a map that keep their elements sorted all the time, using compare results.
stable sort
A sort that keeps elements that compare as equal in their original order.

Before you start

Predict: you put four employees into a TreeSet that is sorted only by salary. Two of them, Lan and Minh, both earn 3000. How many employees does the set hold afterwards? Say the number and why. Section 3 shows the real run.

1. The picture: lining people up

A school photo: the photographer lines children up by height. Height is the children's own property, and everyone agrees on it: that is a natural ordering. But the teacher may want a different line, alphabetical for roll call or by birthday for a party. The teacher brings her own rule from outside: that is a comparator.

  • Comparable<T>: the class's natural ordering, one compareTo inside the class (String, Integer, LocalDate).Comparable javadoc
  • Comparator<T>: an ordering from outside, as many as you like (by price, by date, reversed).Comparator javadoc
record Money(long cents) implements Comparable<Money> {
  public int compareTo(Money o) { return Long.compare(cents, o.cents); }
}
// natural order, written once inside the class

Comparator<Employee> byName = Comparator.comparing(Employee::name);
// an outside rule; you can have many

Only the sign of the result matters: Long.compare(5, 9) returns a negative number, so 5 comes first. Do not rely on it being exactly -1.

The rules every compareTo must follow

The contract: sgn(x.compareTo(y)) == -sgn(y.compareTo(x)) (if x is before y, then y is after x), transitivity (if x < y and y < z, then x < z), and compareTo(null) throws NullPointerException.Comparable javadoc Sorting algorithms trust these rules. Break them and sorts can give strange orders.

2. Consistent with equals

An ordering is consistent with equals when compareTo == 0 exactly when equals is true. It is "strongly recommended (though not required)" because sorted sets and maps "behave 'strangely'" otherwise: they use compareTo, not equals, to decide duplicates.Comparable javadoc

TreeMap states the same: "two keys that are deemed equal by this method are, from the standpoint of the sorted map, equal."TreeMap javadoc Compare this with lesson 0001: a HashSet asks hashCode and equals; a TreeSet never calls equals at all.

The JDK's own example is BigDecimal 4.0 vs 4.00.Comparable javadoc They are the same number, but written with a different number of decimals, so equals says no and compareTo says "same":

$ java java/examples/collections/OrderingAndComparators.java
4.0 equals 4.00?     false   compareTo == 0? true
HashSet size: 2   TreeSet size: 1
TreeSet by salary only keeps 3 of 4: [Hoa, Lan, An]
  ...

Same two objects: the HashSet keeps both, the TreeSet keeps one.

3. The trap: a TreeSet that loses people

The third line of the output is the production bug. Here is the code:

Set<Employee> bySalary =
    new TreeSet<>(Comparator.comparingInt(Employee::salary));
bySalary.addAll(List.of(lan3000, minh3000, hoa2500, an4000));

Step 1  add Lan  (3000)  tree is empty         → root
Step 2  add Minh (3000)  compare(Minh, Lan) = 0 → "already there"
Step 3  add Hoa  (2500)  compare(Hoa, Lan) < 0  → goes left
Step 4  add An   (4000)  compare(An, Lan)  > 0  → goes right
                                         size 3, Minh is gone

No exception, no warning: add just returns false. The fix: always end a comparator with a unique tie-breaker, for example .thenComparing(Employee::name) or an id.

4. Building comparators (JDK 8+)

Think of a sports league table: sort by points; if equal, by goal difference; if still equal, by name. Each rule only matters when all the earlier rules tie. Java's comparator chain works exactly like that:

staff.sort(Comparator.comparing(Employee::dept)
        .thenComparing(Employee::salary, Comparator.reverseOrder())
        .thenComparing(Employee::name));
  Employee[dept=eng, name=An, salary=4000]
  Employee[dept=eng, name=Lan, salary=3000]
  Employee[dept=eng, name=Minh, salary=3000]
  Employee[dept=ops, name=Hoa, salary=2500]

Line by line: comparing(Employee::dept) sorts by department, A to Z. thenComparing(Employee::salary, Comparator.reverseOrder()) breaks ties by salary, highest first. thenComparing(Employee::name) breaks the last ties by name.

Stability

Object sorts (List.sort, Arrays.sort(Object[])) are "guaranteed to be stable: equal elements will not be reordered", using TimSort; primitive arrays use Dual-Pivot Quicksort.Arrays javadoc Stability is what makes sorting by one key, then another, predictable: if you sort by name and then by department, people inside one department stay in name order.

JDK 8 vs 17 vs 21

Comparator.comparing, thenComparing, reverseOrder and nullsFirst are JDK 8+, so they work everywhere. On JDK 17 and 21 you will often compare records, as in the example, because records give you the accessor methods (Employee::salary) for free.

5. Two classic bugs

Bug 1: comparing by subtraction

Comparator<Integer> broken = (a, b) -> a - b;   // looks fine, is not

Step 1  a = Integer.MIN_VALUE = -2147483648, b = 1
Step 2  a - b = -2147483649, which does not fit in an int
Step 3  the int wraps around                    → +2147483647
Step 4  positive means "a comes after b"       → claims MIN_VALUE > 1
broken compare(MIN_VALUE, 1) = 2147483647  (positive: claims MIN_VALUE > 1)
Integer.compare(MIN_VALUE, 1) = -1

(a, b) -> a - b overflows; use Integer.compare or Comparator.comparingInt.Comparator javadoc

Bug 2: nulls in the list

naturalOrder with null -> NullPointerException
nullsFirst -> [null, a, b]

The natural order cannot compare null. For nullable fields wrap with Comparator.nullsFirst/nullsLast.Comparator javadoc

Practice

Answer from memory, don't scroll up. The options are in a different order every time you open the page.

What does a TreeSet use to decide that two elements are duplicates?

Sorted sets and maps perform all comparisons with compareTo or compare. equals is never called.

You add new BigDecimal("4.0") and new BigDecimal("4.00") to a HashSet and to a TreeSet. What are the sizes?

equals is false (different scale), so the HashSet keeps both. compareTo is 0, so the TreeSet keeps one.

A TreeSet sorted only by salary gets Lan (3000), Minh (3000), Hoa (2500) and An (4000). What is its size?

Minh compares as 0 with Lan, so the tree treats Minh as a duplicate. Add a unique tie-breaker such as the name.

What is wrong with the comparator (a, b) -> a - b?

MIN_VALUE - 1 wraps to 2147483647, a positive number. Use Integer.compare or Comparator.comparingInt.

Is List.sort on objects stable?

Object sorts are guaranteed stable (TimSort). Primitive arrays use Dual-Pivot Quicksort, where stability does not matter.

In comparing(Employee::dept).thenComparing(Employee::name), when is the name compared?

A chain stops at the first non-zero result. The next rule only breaks ties left by the earlier ones.

A list contains null. How do you sort it in natural order without an exception?

naturalOrder throws NullPointerException on null. nullsFirst puts nulls first and compares the rest normally: [null, a, b].

The final test: say it in 60 seconds

An interviewer asks: "What's the difference between Comparable and Comparator, and how can a TreeSet lose elements?" Start a timer. Answer out loud, in full sentences. Then click the button.

Tick only the points you really said:

Example answer

"Comparable is the natural order a class defines for itself, with one compareTo method, like strings alphabetically. A Comparator is an ordering from outside, and I can have as many as I want, by price, by date, reversed. Both return negative, zero or positive. The trap is that TreeSet and TreeMap decide duplicates with the comparator, not with equals. So if I sort employees only by salary, two people with the same salary compare as zero and the second one is silently dropped. The fix is to chain with thenComparing and end with something unique, like an id. I also never write a - b, because it can overflow; I use Integer.compare or comparingInt. And object sorts in Java are stable, which makes multi-key sorting predictable."
