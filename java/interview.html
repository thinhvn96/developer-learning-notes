Java (JDK 8, 17, 21): interview questions and answers

Questions you should be able to answer aloud for a Senior Java interview. Each answer starts with a short version, then the detail, with citations to the specification or official docs. Anything beyond the sources I read is flagged in the follow-up.

Try answering out loud first, then open the answer. Superscript links go to the source that backs the claim.

1.Explain the equals/hashCode contract. What breaks if you override only equals?

Short answer: equal objects must have equal hash codes; the reverse is not required. Overriding only equals makes hash-based collections silently lose entries.

The Object Javadoc states that if two objects are equal by equals, calling hashCode on each must give the same integer, while unequal objects are not required to have different hash codes (distinct ones just help performance). equals must also be reflexive, symmetric, transitive, consistent, and return false for null.[1]

A HashMap uses the hash code to choose a bucket and then equals inside it. If two equal keys hash differently, the second lookup goes to the wrong bucket and equals never runs, so get returns null. It compiles and runs, which is what makes it dangerous. I demonstrated it in LostKey.java: the broken key printed null, the correct key printed value.

Likely follow-up: Why are mutable keys dangerous even with a correct hashCode? (If the fields used in hashCode change after insertion, the entry is in the wrong bucket. The Map Javadoc warns great care must be exercised with mutable keys.)

Learn it: HashMap, equals and hashCode

2.How does HashMap work, and what do you say about thread safety?

Short answer: an array of buckets addressed by hash; default capacity 16 and load factor 0.75; it doubles when it fills past load factor times capacity; it is not thread-safe.

From the Javadoc: the default load factor is 0.75 and default initial capacity 16. When the number of entries exceeds load factor times capacity, the table is rehashed to about twice as many buckets. It permits one null key and null values, makes no ordering guarantee, and "is not synchronized": concurrent structural modification needs external synchronization. Iterators are fail-fast and throw ConcurrentModificationException on structural modification outside the iterator. When keys are Comparable the class may use comparison order to help break ties.[2]

For concurrent use I would name ConcurrentHashMap and explain the trade-off rather than wrapping HashMap in Collections.synchronizedMap (the atomics/concurrent-collections lesson is still planned in this course; say so honestly if you have not studied it).

Likely follow-up: What happens to iteration order when the map resizes? (No guarantee: the docs say order may not remain constant over time.)

Learn it: HashMap, equals and hashCode · HashMap internals

3.ArrayList vs LinkedList vs ArrayDeque: which do you choose?

Short answer: default to ArrayList; use ArrayDeque for stacks and queues; LinkedList needs a specific justification.

ArrayList: size, isEmpty, get, set and iterator run in constant time, add is amortized constant, the rest linear, and its constant factor is low compared to LinkedList.[3] LinkedList index operations traverse from the nearer end, so get(i) is a walk.[4] ArrayDeque "is likely to be faster than Stack when used as a stack, and faster than LinkedList when used as a queue"; nulls are prohibited.[5] None is synchronized.

Likely follow-up: Delete elements while iterating an ArrayList? (Use removeIf or the iterator's remove; a for-each with list.remove throws ConcurrentModificationException, as ListPitfalls.java shows.)

Learn it: Choosing a list

4.What did Java 8 add that changed how you write code?

Short answer: lambdas and method references, default methods, streams, Optional, java.time, and CompletableFuture.

  • Lambdas: treat functionality as a method argument; used with functional interfaces (one abstract method), with standard ones in java.util.function.[6]
  • Default methods: add methods to interfaces without breaking existing implementers.[7]
  • Streams: lazy pipelines with a terminal operation; single use.[8]
  • Optional: a return type for "no result".[9]
  • java.time: LocalDate, Instant, Duration, ZonedDateTime and friends.[10]
  • CompletableFuture: composable async computations.[11]
Likely follow-up: Pick one and go deep. (Have a 60-second answer ready for each; the follow-ups are in the questions below.)

Learn it: Java ladder

5.What is the rule for local variables captured by a lambda?

Short answer: they must be final or effectively final.

"A lambda expression can only access local variables and parameters of the enclosing block that are final or effectively final." Effectively final means never reassigned after initialization; assigning to it inside the lambda or afterwards is a compile error. Lambdas are lexically scoped: they add no new scope level and inherit no names from a supertype.[6] The reason is that a lambda may run later or on another thread, and captured locals are copied, so allowing mutation would give confusing, racy semantics (that rationale is standard reasoning, not a quote from the tutorial).

Likely follow-up: How do you count inside forEach then? (Use a reduction, an AtomicInteger, or restructure; do not mutate an outer local.)

Learn it: Lambdas

6.Streams: what are the traps? And Optional's orElse vs orElseGet?

Streams: intermediate operations are lazy and nothing runs until a terminal operation; a consumed stream cannot be reused (it throws IllegalStateException); behavioral parameters should not modify the source and should avoid side effects, with the docs showing toList() instead of forEach(results::add).[8]

Optional: "primarily intended for use as a method return type"; a variable of type Optional should never itself be null. orElse(x) evaluates x even when a value is present; orElseGet(supplier) calls the supplier only when empty, so use it when the default is expensive.[9]

Likely follow-up: Should Optional be a field or parameter? (The Javadoc's intent is return types.)

Learn it: Streams and Optional

7.Two interfaces provide the same default method. What happens?

Short answer: the class must override the method and choose, or it does not compile.

Rules: a concrete class method wins over an interface default; a more specific interface can inherit, redeclare (abstract) or redefine the default.[7] For two unrelated defaults with the same signature, the compiler rejects the class ("types W and S are incompatible" in my test) until you override and pick with Walker.super.move().

Likely follow-up: Default methods vs abstract classes? (Interfaces have no instance state and a class can implement many; default methods exist to evolve interfaces.)

Learn it: Default methods

8.CompletableFuture: which threads run it, and how do errors surface?

Short answer: async methods without an executor use ForkJoinPool.commonPool(); join() throws CompletionException, get() throws ExecutionException.

The Javadoc: a CompletableFuture may be explicitly completed and supports dependent actions; async methods without an explicit Executor use the common pool; exceptionally recovers, handle sees result and exception; cancellation is exceptional completion; among competing complete/cancel calls only one wins.[11] Practical consequence: do not run blocking I/O in the common pool; supply your own executor (or, on JDK 21, virtual threads).

Likely follow-up: Compare CompletableFuture with virtual threads. (Virtual threads let you write simple blocking code per task; CompletableFuture composes async stages.[12])

Learn it: CompletableFuture

9.Which java.time type would you use for a birthday, a meeting, a timestamp and an elapsed time?

Short answer: LocalDate, ZonedDateTime, Instant, Duration.

The tutorial: human time uses the Local classes, machine time uses Instant (nanosecond resolution from the epoch), zone-aware needs use ZonedDateTime or OffsetDateTime; Duration measures seconds and nanoseconds while Period measures years, months and days.[10] Store and exchange Instants, convert to a zone for display.

Likely follow-up: Why not java.util.Date? (Beyond this course's scope of sources; describe the design issues you know and check the Javadoc before an interview.)

Learn it: java.time

10.What language features arrived between Java 8 and 17?

Short answer: var (10), switch expressions (14), text blocks (15), pattern matching for instanceof (16), records (16), sealed classes (17).

  • var: local variable type inference for locals with initializers; not for fields, parameters or return types.[13]
  • Switch expressions: arrow labels, no fall-through, yield, must be exhaustive.[14]
  • Text blocks: multi-line literals opened with """, indentation stripped.[15]
  • instanceof patterns: if (o instanceof String s) with flow-scoped binding.[16]
  • Records: shallowly immutable, transparent carriers with generated equals, hashCode, toString.[17]
  • Sealed classes: permits; subclasses are final, sealed or non-sealed.[18]

Java 17 is an LTS release (8, 11, 17, 21 and 25 are).[19]

Likely follow-up: Which of these would you use in a real codebase first, and why? (Records for DTOs, with a defensive copy for collections.)

Learn it: Java ladder

11.Are records immutable? What do they generate?

Short answer: shallowly immutable only.

"A record class is a shallowly immutable, transparent carrier for a fixed set of values." It has a canonical constructor, a private final field and a public accessor per component; equals, hashCode and toString derive from all components.[17] A record holding an ArrayList is only as immutable as that list; use a compact constructor with List.copyOf. Demonstrated in RecordDemo.java.

Likely follow-up: Can a record extend a class? (Records cannot extend other classes; check the Java Language Specification before asserting details beyond what the Javadoc says.)

Learn it: Records

12.Why sealed classes? How do they relate to switch?

Short answer: to model a closed set of subtypes, which lets the compiler check switches for exhaustiveness.

JEP 409's goals: let the author control which code implements a type, be more declarative than access modifiers, and support exhaustive pattern analysis. Each permitted subclass is exactly one of final, sealed, non-sealed.[18] In JDK 21, a pattern switch over a sealed type must be exhaustive, and coverage is checked from the permitted subtypes, sometimes removing the need for default.[20]

Likely follow-up: Sealed vs enum? (Enum: closed set of instances of one type. Sealed: closed set of types with different data.)

Learn it: Sealed classes

13.What changed from Java 17 to 21 that you would actually use?

Short answer: pattern matching for switch, record patterns, sequenced collections, virtual threads, generational ZGC.

  • Pattern switch (final in 21): type patterns, when guards, case null, exhaustiveness for sealed types, dominance checks.[20]
  • Record patterns: deconstruct records, nestable.[21]
  • Sequenced collections: SequencedCollection, SequencedSet, SequencedMap with getFirst, getLast, reversed and more.[22]
  • Virtual threads: for scale (throughput), not speed.[12]
  • Generational ZGC: -XX:+UseZGC -XX:+ZGenerational, sub-millisecond pause goal.[23]

I verified that a pattern-switch example compiles with --release 21 and fails with --release 17.

Likely follow-up: Show a pattern switch over a sealed hierarchy. (See Jdk21Features.java.)

Learn it: Pattern matching for switch

14.What are virtual threads, and what are the rules for using them?

Short answer: lightweight Threads not tied to an OS thread; they give scale, not speed; do not pool them.

A virtual thread runs on an OS thread but is suspended on blocking I/O so the OS thread serves others. "Virtual threads are not faster threads ... They exist to provide scale (higher throughput), not speed (lower latency)." Use one per task via Executors.newVirtualThreadPerTaskExecutor(), never pool them, and limit concurrency with a Semaphore. They can be pinned to their carrier (for example in native calls), which hurts scalability but not correctness.[12] My demo ran 10,000 one-second sleeps in about one second.

Likely follow-up: When would virtual threads not help? (CPU-bound work: they do not run code faster.)

Learn it: Virtual threads

15.Explain the Java Memory Model: what is happens-before, and what does volatile give you?

Short answer: happens-before is the ordering guarantee that makes one thread's writes visible to another; volatile gives visibility and ordering for that variable, not atomic compound actions.

JLS 17: two conflicting accesses not ordered by happens-before are a data race. Edges include: monitor unlock before every later lock of that monitor; a volatile write before every later read of that field; Thread.start() before the started thread's actions; a thread's actions before another thread returns from join() on it. If a program is correctly synchronized, all executions appear sequentially consistent. Non-volatile long and double writes can be split into two 32-bit writes.[24] The concurrent package adds edges for concurrent collections, Executor submission, Future.get(), locks and latches.[25] volatile does not make count++ atomic (that needs atomics or a lock).

Likely follow-up: Why can a loop on a non-volatile flag hang? (No happens-before edge means the write is not guaranteed to become visible.)

Learn it: Visibility and happens-before

16.How does the JVM choose a GC and heap size, and what do you do in a container?

Short answer: G1 on server-class machines, otherwise Serial; initial heap 1/64 and max heap 1/4 of physical memory.

Server-class means two or more processors and at least 1792 MB of physical memory.[26] -XX:MaxRAMPercentage defaults to 25 percent; on Linux the JVM detects container limits by default (-Xlog:os+container=trace shows what it saw).[27] In my Docker run, a 256 MB limit gave a heap of about 121 MB, consistent with the documented 50 percent default for small heaps. For a service I would set MaxRAMPercentage deliberately (for example 70) to leave room for non-heap memory, enable GC logging and measure. On JDK 21, generational ZGC is available for very low pause targets.[23] The GC's job is allocating memory and reclaiming what is no longer in use.[28]

Likely follow-up: Your pod is OOM-killed but heap looks fine. Why? (Non-heap memory: metaspace, thread stacks, buffers; heap plus that exceeded the limit.)

Learn it: Heap and GC

17.Which Java version would you run in production, and why?

Short answer: an LTS release: 17, 21 or 25 today, depending on library and support constraints.

Oracle lists 8, 11, 17, 21 and 25 as LTS releases, with a two-year cadence going forward and the next LTS planned as 29 in September 2027. Java 25 updates are planned under the No-Fee Terms until September 2028.[19] A migration path from 8: move to 17 (get records, sealed classes, text blocks, switch expressions, var), then to 21 (pattern switch, virtual threads, sequenced collections). I would justify with support windows and measured GC/startup, not fashion.

Likely follow-up: What breaks when migrating from 8 to 17? (Beyond the sources gathered in this course; prepare your own list from the release notes of each version.)

Learn it: Java ladder

18.Why are Strings immutable, and what is the difference between == and equals on them?

Short answer: the Javadoc says strings are constant, so they can be shared safely; == compares references, equals compares contents.

"Strings are constant; their values cannot be changed after they are created", which is why references can share them. Literals refer to interned instances, and intern() returns a canonical representation. In StringDemo.java: two identical literals were ==, but new String("abc") was not, while equals was true for both. How + is compiled is up to the compiler (StringBuilder, StringBuffer or StringConcatFactory); in loops use a StringBuilder.[29]

Likely follow-up: Why is String a good HashMap key? (Immutable, so its hashCode cannot change after insertion; see the mutable-key exercise.)

Learn it: Strings

19.Checked versus unchecked exceptions: which do you use and why? What is try-with-resources?

Short answer: checked when the caller can reasonably recover, unchecked otherwise; try-with-resources closes AutoCloseable resources automatically.

Checked exceptions are subject to catch-or-specify; RuntimeException and Error are not. The tutorial's guideline: make it checked if a client can reasonably recover, unchecked if not; do not use RuntimeException just to avoid declaring.[30] Try-with-resources closes resources in the opposite order of creation; if the body throws and close() also throws, the body's exception propagates and the other is suppressed (getSuppressed()); catch/finally run after the resources are closed.[31] Spring link: checked exceptions do not roll back @Transactional by default.

Likely follow-up: Where is the suppressed exception lost if you use try/finally instead? (The finally's exception can replace the original; try-with-resources keeps the original and attaches the rest.)

Learn it: Exceptions

20.Explain generic invariance, wildcards (extends/super) and type erasure.

Short answer: List<Integer> is not a List<Number>; use ? extends for producers and ? super for consumers; type arguments are erased at runtime.

"Although Integer is a subtype of Number, List<Integer> is not a subtype of List<Number>": otherwise you could add a Double to a list of Integers.[32] The tutorial's rules: an "in" variable uses an upper bounded wildcard (extends), an "out" variable a lower bounded one (super), unbounded when only Object methods are used, none when it is both; avoid wildcards in return types.[33] The compiler erases type parameters to their bounds or Object, inserts casts and generates bridge methods, so parameterized types are not reifiable: no instanceof List<String> and no arrays of parameterized types.[34]

Likely follow-up: Why can't you write new T()? (Erasure removes T at runtime; state it as a consequence of erasure.)

Learn it: Wildcards and erasure

21.Write a stream that groups employees by department and sums salaries. What happens with toMap and duplicate keys?

Short answer: Collectors.groupingBy(Emp::dept, Collectors.summingInt(Emp::salary)); toMap throws IllegalStateException on duplicate keys unless you provide a merge function.

groupingBy classifies into a Map with an optional downstream collector; partitioningBy always yields both true and false keys; joining concatenates; toList/toSet promise nothing about type or mutability (use toCollection for control); toUnmodifiableList etc. arrived in Java 10.[35] My run: grouping gave {ops=9600, dev=9400}, duplicate keys threw IllegalStateException, and a merge function combined them.

Likely follow-up: How would this differ in SQL? (GROUP BY with SUM; see the PostgreSQL aggregates lesson.)

Learn it: Collectors

22.How does a ThreadPoolExecutor decide between running, queueing and rejecting a task?

Short answer: below core size it starts a thread; at or above core it queues; if the queue is full and below max it starts another thread; otherwise it rejects.

The Javadoc rules plus queue types (direct handoff, unbounded queue where max has no effect, bounded queue) and rejection policies (AbortPolicy default, CallerRunsPolicy slows submission, discard policies rarely acceptable).[36] In PoolDemo.java (core 2, max 4, queue 2) tasks 1-2 took core threads, 3-4 were queued, 5-6 created extra threads and task 7 was rejected. On JDK 21 consider virtual threads instead of pools for blocking I/O.

Likely follow-up: Why is an unbounded queue risky? (Unbounded work growth if tasks arrive faster than they finish; the Javadoc lists it.)

Learn it: Thread pools

23.volatile int count++ from several threads gives wrong totals. Why, and how do you fix it?

Short answer: count++ is read-modify-write, not atomic; use an atomic or a lock.

volatile gives visibility and ordering but not atomic compound actions. The atomic package offers lock-free thread-safe operations on single variables (compareAndSet, getAndUpdate) with volatile semantics, and LongAdder for contended counters.[37] ReentrantLock offers synchronized-like semantics plus fairness, tryLock and interruptible locking; unlock in finally.[38] In AtomicDemo.java, 4 threads x 200,000 increments: the volatile int lost about 1,600 updates, while AtomicInteger and the lock produced 800,000.

Likely follow-up: When do you prefer a lock to an atomic? (When several variables must change together.)

Learn it: Atomics and locks

24.HashMap versus ConcurrentHashMap: differences, null rules, and the right way to update a counter?

Short answer: ConcurrentHashMap has lock-free reads, weakly consistent iterators, forbids nulls, and offers atomic compound methods like merge.

Retrievals do not lock, updates have high expected concurrency, iterators do not throw ConcurrentModificationException, null keys/values throw NPE; putIfAbsent, compute* and merge are atomic and their functions must be short and not modify the map; size() is only reliable without concurrent updates.[39] HashMap is unsynchronized with fail-fast iterators.[2] My run: merge("hits", 1, Integer::sum) from 4 threads gave exactly 400,000. A "check then put" is still a race.

Likely follow-up: Why does ConcurrentHashMap forbid nulls? (Ambiguity of get returning null; a reasoning point, the Javadoc simply states the rule.)

Learn it: ConcurrentHashMap

25.What is a deadlock, how do you detect it, and how do you prevent it?

Short answer: threads blocked forever waiting on each other; detect with a thread dump or ThreadMXBean; prevent with a consistent lock order.

The tutorial's definition and bowing-friends example (both methods synchronized).[40] DeadlockDemo.java reproduced it with opposite lock orders, findDeadlockedThreads() reported 2 threads, and the same lock order removed the problem. Other tools: tryLock with a timeout,[38] fewer locks held, no foreign calls while holding a lock (the last two are general practice).

Likely follow-up: How does PostgreSQL handle the same problem? (Detects and aborts one transaction; retry.)

Learn it: Deadlock

26.What is a helpful NullPointerException?

Short answer: the JVM message names the null expression, for example Cannot invoke "String.trim()" because "names[0]" is null.

JEP 358 (Java 14): "describing precisely which variable was null"; off by default in JDK 14 behind -XX:+ShowCodeDetailsInExceptionMessages.[41] On JDK 21 my run printed the messages with no flag; local variable names appear only if compiled with -g (otherwise <local1>).

Likely follow-up: Should you still validate arguments? (Yes: fail early with clear messages via Objects.requireNonNull; helpful NPEs are for debugging.)

Learn it: Helpful NPEs

27.Why can a single-threaded loop throw ConcurrentModificationException, and how do you remove while iterating?

Short answer: fail-fast iterators compare the collection's modCount with the value they captured; removing through the collection instead of the iterator trips the check. Use Iterator.remove or removeIf.

The Javadoc says the exception "does not always indicate that an object has been concurrently modified by a different thread" and is thrown "on a best-effort basis", so it must only be used to detect bugs.[42] In my run, removing the second-to-last element of an ArrayList inside for-each threw nothing and silently skipped the last element.

Likely follow-up: Why is entry.setValue() allowed while iterating a HashMap? (It is not a structural modification.)

Learn it: Iterators and fail-fast

28.What changed inside HashMap in Java 8, and when does a bucket become a tree?

Short answer: long bins are converted to red-black trees: at 8 nodes, if the table has at least 64 buckets, otherwise it resizes; back to a list below 6. Worst case per bucket goes from O(n) to O(log n).

The hash is spread with h ^ (h >>> 16), the index is (n - 1) & hash, and on resize an entry stays at i or moves to i + oldCapacity.[43] With 20,000 keys sharing one hashCode, my run took 3,658 ms for non-Comparable keys and 69 ms for Comparable ones.

Likely follow-up: How do you presize a map for 1M entries? (JDK 21: HashMap.newHashMap(1_000_000); JDK 8/17: capacity of expected / 0.75 + 1.)

Learn it: HashMap internals

29.Comparable vs Comparator, and what does "consistent with equals" mean?

Short answer: Comparable is the class's natural order; Comparator is an external order. Consistent with equals means compareTo == 0 exactly when equals is true; otherwise sorted sets and maps treat different objects as duplicates.

The Javadoc's example is BigDecimal 4.0 vs 4.00: equal by compareTo, not by equals, so a TreeSet keeps one and a HashSet keeps two.[44] A TreeSet with a salary-only comparator kept 3 of 4 employees in my run. Build comparators with Comparator.comparing(...).thenComparing(...) and end with a unique key; never write a - b.

Likely follow-up: Is List.sort stable? (Yes for objects: TimSort, guaranteed stable.)

Learn it: Comparable and Comparator

30.Unmodifiable vs immutable: Arrays.asList, Collections.unmodifiableList, List.of?

Short answer: Arrays.asList is fixed-size but writes through to the array; unmodifiableList is a read-only view that still shows source changes; List.of/copyOf are independent unmodifiable copies that reject nulls. None makes the elements immutable.

List.of and List.copyOf: "Elements cannot be added, removed, or replaced", "They disallow null elements", and mutable elements can still change.[45] JDK 9 added List.of, JDK 10 copyOf, so on JDK 8 use Collections.unmodifiableList(new ArrayList<>(src)).

Likely follow-up: Why does List.of("a").contains(null) throw? (These lists disallow nulls, and contains(null) throws NullPointerException.)

Learn it: Unmodifiable vs immutable

31.Implement an LRU cache in Java.

Short answer: extend LinkedHashMap with accessOrder = true and override removeEldestEntry to return size() > capacity.

The access-order constructor is documented as "well-suited to building LRU caches", and removeEldestEntry "is invoked by put and putAll after inserting a new entry". In access-order mode even get is a structural modification, so shared use needs synchronization.[46]

Likely follow-up: Without LinkedHashMap? (HashMap of key to node plus a doubly linked list; O(1) get and put.)

Learn it: LinkedHashMap and LRU

32.When would you use a TreeMap instead of a HashMap?

Short answer: when you need sorted iteration, range views or nearest-key lookups (floor, ceiling, subMap); cost is guaranteed log(n) instead of expected O(1).

TreeMap is "A Red-Black tree based NavigableMap" with "guaranteed log(n) time cost" for get/put/remove; floorKey returns the greatest key ≤ k and subMap is a live [from, to) view.[47] Typical uses: price or tax tiers, time-series windows, leaderboards.

Likely follow-up: Thread-safe sorted map? (ConcurrentSkipListMap.)

Learn it: TreeMap and NavigableMap

33.How does PriorityQueue work, and how do you find the top K of N items?

Short answer: a binary heap: head is the smallest, offer/poll are O(log n), iteration is not sorted. For the K largest keep a min-heap of size K: O(n log k).

"The Iterator ... [is] not guaranteed to traverse the elements of the priority queue in any particular order"; contains and remove(Object) are linear; peek is constant.[48]

Likely follow-up: Max-heap? (new PriorityQueue<>(Comparator.reverseOrder()).)

Learn it: PriorityQueue and top-K

34.What are EnumMap, IdentityHashMap and WeakHashMap for?

Short answer: EnumMap/EnumSet: compact array/bit-vector structures for enum keys; IdentityHashMap: == instead of equals, for object-graph work like deep copy; WeakHashMap: entries vanish when the key is no longer referenced.

IdentityHashMap "is not a general-purpose Map implementation" and "intentionally violates Map's general contract".[49] WeakHashMap values are strongly held, so a value referring to its key keeps it alive.[56]

Likely follow-up: Is WeakHashMap a good cache? (No: no size or time bound, GC-timed; use an LRU or a cache library.)

Learn it: Special-purpose maps

35.merge, computeIfAbsent, putIfAbsent: when do you use each, and what are the traps?

Short answer: merge to combine values (counting), computeIfAbsent to create lazily (multimaps, memo), putIfAbsent only when the value is cheap. Returning null removes or skips a mapping; never modify the map inside the function.

"If the mapping function returns null, no mapping is recorded"; "The mapping function should not modify this map during computation".[50] HashMap throws ConcurrentModificationException when it detects that, which is what happened to my recursive memoized fib.

Likely follow-up: Which of these are atomic? (On ConcurrentHashMap all of them; on HashMap none are thread-safe.)

Learn it: Map power methods

36.How does ArrayList grow, and what does boxing cost in collections?

Short answer: starts with a shared empty array, allocates 10 on the first add, then grows by about 1.5× with an array copy (amortized O(1)). Boxed elements cost several times a primitive array.

In OpenJDK 21 grow() uses oldCapacity >> 1 as preferred growth.[51] Integer identity is only guaranteed for -128..127, so compare with equals.[52] In my rough measurement 1M ints took ~4 MB as int[], ~19 MB in ArrayList<Integer>, ~38 MB in LinkedList.

Likely follow-up: list.remove(1) on a List<Integer>? (Removes index 1; use remove(Integer.valueOf(1)) for the value.)

Learn it: Capacity, boxing and memory

37.Which thread-safe collection would you pick, and why?

Short answer: ConcurrentHashMap for shared maps, ConcurrentSkipListMap for sorted ones, CopyOnWriteArrayList when reads vastly outnumber writes, a bounded BlockingQueue for producer-consumer; synchronized wrappers only for low contention, with manual locking during iteration.

BlockingQueue has four forms per operation (add/offer/put/offer with timeout) and is "designed to be used primarily for producer-consumer queues".[53] CopyOnWriteArrayList copies the array on every write and gives snapshot iterators.[54] synchronizedList requires synchronized (list) around iteration.[55] In my run a plain ArrayList shared by 4 threads lost 26,757 of 40,000 adds without any exception.

Likely follow-up: Why must a ThreadPoolExecutor queue usually be bounded? (Backpressure: an unbounded queue hides overload until memory runs out.)
